## Harrison Chase 的核心观点

Harrison Chase 发表了一篇 X Article《How Coding Agents Are Reshaping Engineering, Product and Design》，核心论述：

1. **代码写作不再是瓶颈** — Coding Agent 让任何人都能写代码、构建产品。但"能写"不等于"写得好" — 架构是否合理、是否解决了正确的问题、是否好用，这些仍然需要人来判断。

2. **EPD 瓶颈从"实现"转向"评审"** — Engineering、Product、Design 三个角色的核心工作变成了 review：确保架构优良、解决用户痛点、设计可用。

3. **传统 PRD 流程已死** — "PRD → Mock → Code" 的线性流程被打破。新方式是先出原型再配文档。Chase 提出：未来的 PRD 可能就是结构化的、版本化的 prompt。

4. **Prompt 即意图传达** — 用于创建功能的 prompt 本身就可以作为沟通意图的方式。

## YC (@lyc_zh) 的延伸

YC 在引用 Chase 文章的基础上进一步提炼：

- **沟通成本成为最大瓶颈** — 实现成本降低后，跨界人才比以前更值钱，因为协调与沟通才是真正的成本。
- **通才 > 三人团队** — 一个懂全局的通才，比传统的工程师+PM+设计师三人小队更快。
- **系统思维是关键技能** — 不是会写代码，而是能看清系统全局、做出正确判断。
- **职业路径两极分化**：Builder（产品直觉 + AI 编码 + 设计感）或 Reviewer（系统思维 + 快速评审能力）。

## 附录：自我思考

### 最后一公里是代码质量

我们团队已经在实践这种工作流。最大的感受是：**代码不是瓶颈，但最后一公里的交付很难，难在代码质量。** AI 能快速生成 80% 的代码，但边界条件、架构一致性、可维护性、安全性 — 这些仍然需要经验和判断力。

转型不容易。技术是有门槛的。

### AI 不是初级工程师，是不守规矩的顶尖工程师

一个重要的认知纠偏：AI 的代码能力本身是顶尖的 — 算法、设计模式、API 用法、架构设计都能达到很高水平。它不是"能力不够"，而是**没有上下文纪律**。它不知道团队约定、项目历史债务、线上实际状况，也不会主动遵守那些没有明确写下来的隐性规则。

所以 review 的性质完全不同：

- 带初级工程师：你在**教**他怎么做
- 带 AI：你在**约束**一个能力很强但不守规矩的角色

这也解释了为什么约束体系（CLAUDE.md、context system）如此重要 — 不是在降低难度，而是在**把隐性规则显性化**，让一个顶尖但没有组织记忆的角色能融入团队。Review 的价值变成了：检查它有没有在这个特定项目的特定上下文里做对。

### 工作组模型

实际运作模式类似工作组：AI 高速产出，资深工程师 review 把关。约束体系越完善，review 的重心就越从"纠正方向"转向"抓细节"，效率越高，但对 reviewer 的专业深度要求也越高。
