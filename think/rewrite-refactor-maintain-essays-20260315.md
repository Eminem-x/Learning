# 重写、重构与维护：四篇经典文章合集

> 来源：Web 搜索整理
> 收录时间：2026-03-15 CST
>
> 背景：记忆中有一篇关于程序员重写/重构/维护的思考文章，其中举了某公司因大量测试导致上线延误、市场丧失的例子。以下四篇是最接近的候选。

---

## 1. Things You Should Never Do, Part I — Joel Spolsky (2000)

> 原文：https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/

### 核心论点

从头重写软件是一家公司能犯的最严重的战略错误。现有代码看起来丑陋，但它包含了多年积累的 bug 修复和真实世界的测试成果，这些无法快速复制。

### 关键案例

- **Netscape 6.0**：决定从头重写浏览器，导致近 3 年没有发布新版本。期间 IE 吃掉了市场份额，Netscape 从此一蹶不振。
- **Borland**：犯了两次同样的错误。先是试图把 Arago 转成 dBase for Windows（最终被 Microsoft Access 打败），后又从头重写 Quattro Pro，上线时功能远少于 Excel。
- **Microsoft Word "Pyramid" 项目**：微软差点也犯同样的错，启动了 Word 的重写项目 Pyramid，所幸保留了原始代码库，避免了灾难。

### 核心观点

1. **读代码比写代码难**——程序员因此总是低估现有系统
2. **隐藏的复杂度**：那些冗长的函数里藏着多年真实使用中发现的边界情况修复
3. 架构问题、性能问题、代码美感问题都可以渐进式解决，无需完全重写
4. 重写意味着**把 2-3 年拱手让给竞争对手**
5. 从头开始并不保证你会做得更好

## 2. Rewrite, Refactor, or Reinvent? — Herb Caudill (2019)

> 原文：https://herbcaudill.com/words/20190219-rewrite-refactor-reinvent

### 核心论点

Joel Spolsky 的"永远不要重写"统治了软件行业思维几十年，但这个二元选择过于简化。正确的做法取决于具体场景，而且重写和重构并不是唯一的选项——你可以**构建自己的竞争者**。

### 六个案例

#### ① Netscape（反面教材）
放弃 Navigator 4.0，通过 Mozilla 开发开源继任者。砍掉了未发布的 5.0，从头开发 6.0，花了三年，产出了一个又慢又多 bug 的软件。IE 趁机抢占市场，Netscape 变得无关紧要，最终被 AOL 清算，知识产权流入微软。

#### ② Basecamp（成功样本）
盈利 7 年后，DHH 意识到"金手铐"阻碍了创新——不是技术债务，而是现有客户抗拒变化。解决方案：从头构建 Basecamp 2，同时承诺无限期维护 Basecamp Classic。2015 年又重复了一次推出 Basecamp 3。多个版本共存，去除了强制迁移的压力。

#### ③ Visual Studio 和 VS Code（平行产品）
微软没有试图改造重型 IDE Visual Studio，而是用 Electron + TypeScript 从头打造了 VS Code，瞄准 Node.js/JavaScript 开发者。两个产品共存，VS Code 的开源社区带来了近万个扩展。

#### ④ Gmail 和 Inbox（失败实验）
Google 用 Inbox 作为 Gmail 的替代 UI，共享后端。但共享基础设施限制了创新空间。Inbox 关闭后用户失去了邮件暂停等功能，部分创新被移植回 Gmail，但关闭过程伤害了用户信任。

#### ⑤ FogBugz 和 Trello（转型路线）
Joel Spolsky 的 bug 追踪器 FogBugz 被自身成功困住——盈利但停滞，面临 Jira 竞争。Fog Creek 没有重写 FogBugz，而是创造了 Trello，解决不同层次的问题。Trello 最终以 4.25 亿美元卖给了 Atlassian。FogBugz 则被单独出售。

#### ⑥ FreshBooks（卧底重写）
面对多年积累的"创始人代码"，FreshBooks CEO 秘密注册了一个竞争对手公司 BillSpring。以假身份运营了 18 个月，用精益 UX + 敏捷方法开发新平台。证明可行后才揭示这是 FreshBooks 的下一代产品。

### 作者框架

不要在"改进现有"和"从头开始"之间做二选一，而是问：

- **"我的 Trello 对 FogBugz 是什么？"**
- **"我的 VS Code 对 Visual Studio 是什么？"**

核心原则：
1. 永远不要强制关闭旧版本
2. 新产品不背负向后兼容的包袱，能吸引有动力的开发者
3. 从成熟代码库学习，但不做一比一复刻
4. 多产品共存，服务不同客户需求

## 3. Rebuild vs. Refactor vs. "Leave It Alone" — Ulad Shauchenka

> 原文：https://www.uladshauchenka.com/p/rebuild-vs-refactor-vs-leave-it-alone

### 核心论点

拒绝"重写 vs 不动"的假二元。Joel Spolsky 说重写是最糟糕的战略错误，但放任遗留系统又会积累安全和运维风险。最优路径在两者之间，可以借助 Gartner 的 "7 Rs" 框架：封装、迁移主机、换平台、重构、重新架构、重建、替换。

### 决策框架（七维评分卡）

| 维度 | 关键指标 |
|------|---------|
| 安全态势 | ~70% 严重安全漏洞源于 C/C++ 内存安全问题 |
| 技术债拖累 | McKinsey：CIO 估计 10-20% 产品预算用于债务修复 |
| 交付效能 | DORA 指标（部署频率、前置时间、变更失败率、恢复时间） |
| 延迟成本 vs 工期 | WSJF 加权最短作业优先 |
| 人才风险 | COBOL 仍支撑 43% 银行系统和 95% ATM 交易 |
| 合规隔离 | 分离受监管组件（PCI-DSS, HIPAA） |
| 客户影响 | 量化延迟、崩溃、兼容性问题的用户可见痛点 |

### 案例一览

**不该重写的反面教材：**
- **Netscape (1998-2000)**：暂停功能开发做重写，IE 趁机占领市场
- **Digg v4 (2010)**：大改版砍掉功能、引入不稳定性，美国流量一个月暴跌 26-30%
- **Southwest Airlines (2022)**：过时的机组调度软件导致近 17,000 航班取消，10 亿+美元损失，1.4 亿美元联邦罚款
- **Equifax (2017)**：未修补的 Apache Struts 漏洞导致大规模数据泄露，负债超 13 亿美元

**渐进式现代化成功案例：**
- **Shopify**：Rails 模块化单体 + Packwerk 工具强制边界
- **Etsy**：维护良好的单体架构实现每天 50+ 次部署
- **Amazon**：Bezos 的 API 强制令创建了内部服务边界，最终孕育了 AWS
- **eBay**：多年演进到 Java，支撑每天数十亿页面访问

**成功的定向重建：**
- **Slack (2019)**：桌面端重建，启动速度快 33%，内存减少 50%
- **Snapchat Android (2019)**：性能快 20%，体积小 25%，扭转了用户增长停滞
- **Firefox Quantum (2017)**：用 Rust 重写热路径，速度 ~2 倍，内存少 ~30%
- **Microsoft Edge (2018)**：转向 Chromium 内核
- **Facebook (2012)**：Zuckerberg 承认"在 HTML5 上押注太多，烧掉了两年"，转向原生
- **PayPal (2013-2014)**：Node.js 重建，构建时间减半，代码量少 33%，响应时间降 35%

### 核心结论

- **该重写**：安全需要换语言、架构性能瓶颈、人才风险生死攸关时
- **该渐进改造**：组件可隔离、可逐步替换时（Shopify/Etsy/Amazon 模式）
- **该维持**：系统稳定、合规、易于 API 封装时（但必须持续监控和打补丁）
- **用数据说话**：用 DORA 指标、WSJF 分析和性能数据驱动决策

## 4. How Microsoft Does QA — Gergely Orosz / The Pragmatic Engineer

> 原文：https://newsletter.pragmaticengineer.com/p/how-microsoft-does-quality-assurance

### 核心论点

微软的 QA 模式从"大量专职测试人员"演变为"工程师自己负责质量"。旧模式虽然保证了覆盖率，但拖慢了交付速度，新模式则提升了速度和责任感。

### 演变历史

**旧模式（~2014 年之前）：**
- 微软在 1990 年代开创了 **SDET（Software Development Engineer in Test）** 角色
- 标准配比是 **2:1 开发:测试**
- 每个子系统（界面、网络、驱动等）都有专门的测试团队，每天开会讨论 bug

**旧模式的问题：**
- **"我们 vs 他们"** 的对立关系：开发者把测试视为别人的事
- **单元测试被推卸**：开发者把基础测试也甩给 SDET
- **工单乒乓**：功能在开发和测试之间来回弹
- **认知偏见**：很多开发者认为 SDET 的工作"不如真正的工程"

**2014 年转型：**
- Bing 等 Web 团队率先发现合并开发和测试角色能显著提速
- 微软正式**取消 SDET 角色**，要求 SDET 转为标准软件工程师
- 测试金字塔转变：从脆弱的端到端测试为主，转为单元/集成测试为主

**转型成果：**
- 消除了交接延迟，代码变更到质量验证的时间缩短
- 工程师对自己的代码质量负责
- 一位微软领导者说："我们开始在质量、敏捷性和工程师满意度上收获回报。"

### 核心教训

**关注点分离不等于价值分离。** 专职测试角色可能无意中让开发者降低了对质量的重视；而由工程师自己编写所有测试的集成责任制，能对齐激励、加速交付。

## 附录：自我思考

这四篇文章覆盖了"重写/重构/维护"这个经典议题的不同维度：

| 文章 | 核心立场 | 最佳启发 |
|------|---------|---------|
| Joel Spolsky (2000) | 永远不要从头重写 | 旧代码里藏着多年 bug 修复的隐性知识 |
| Herb Caudill (2019) | 不是二选一，可以"构建自己的竞争者" | Basecamp/VS Code/Trello 的平行产品策略 |
| Ulad Shauchenka | 用数据驱动的七维评分卡决策 | DORA 指标 + WSJF 量化延迟成本 |
| Pragmatic Engineer | 微软测试文化演变：从 2:1 配比到工程师自负其责 | 大量测试人员≠高质量，反而可能拖慢交付 |

**关于"大量测试导致上线延误"的线索：**

第四篇（Pragmatic Engineer）最接近这个描述。微软在 2014 年之前的 2:1 开发/测试比模式下，虽然有了严密的测试覆盖，但开发和测试之间的反复交接、职责推诿显著拖慢了产品交付。尤其是 Web 团队发现合并角色后速度大幅提升，说明旧模式确实在组织层面造成了交付延误。

但如果记忆中的文章更强调的是"因为写了太多测试而错过市场窗口"，那可能是另一篇尚未找到的文章。建议回忆更多细节后继续搜索。
