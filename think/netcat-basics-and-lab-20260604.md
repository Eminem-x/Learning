## 一、netcat 是什么

`netcat`（命令名 `nc`）被称为「网络界的瑞士军刀」，本质是一句话：

> **在命令行里读写 TCP/UDP 连接。**

名字 = `net` + `cat`。`cat`（conCATenate）是把**文件**内容读出来 / 倒进去的基础命令；`netcat` 把同样的动作搬到**网络连接**上。

| | 操作对象 | 干的事 |
|---|---|---|
| `cat` | 文件 | 读出来 / 倒进去 |
| `netcat` (`nc`) | TCP/UDP 连接 | 读出来 / 倒进去 |

正因为它把网络连接变成「像文件一样可读写」的东西，才能自然地配合 `<` `>` `|` 等 shell 工具。

### 两种基本身份

| 身份 | 命令形态 | 作用 |
|---|---|---|
| **客户端** | `nc 主机 端口` | 主动连别人 |
| **服务端** | `nc -l 端口` | 自己监听，等别人连 |

## 二、常用参数

| 参数 | 含义 | 备注 |
|---|---|---|
| `-l` | listen，进入服务端监听模式 | |
| `-v` | verbose，打印连接细节 | 排查必加，可叠 `-vv` |
| `-z` | zero-I/O，只探测不传数据 | **扫端口**专用 |
| `-u` | 用 UDP（默认 TCP） | UDP 探测不可靠 |
| `-w 秒` | 连上后的**读写**超时 | |
| `-G 秒` | TCP **握手**超时（仅 macOS BSD 版） | |
| `-k` | 服务端处理完一个连接后**保持监听** | |
| `-p` | 指定本地源端口 | |

> ⚠️ **平台差异**：macOS 自带的是 BSD netcat，Linux 多为 GNU/OpenBSD 版，参数不完全一样。
> - `-G`（握手超时）**只有 macOS** 有；Linux 用 `-w` 控制超时。
> - `-e`（连上后执行程序、反弹 shell）很多 Linux 发行版默认**禁用或不编译**。
> - 在 Mac 与 OPNsense / Linux 之间切换命令时要留意。

## 三、最常见的用法

下面命令均已在本机（macOS BSD nc）实测通过，附真实输出。

### 1. 测端口通不通（最高频）

```bash
nc -vz 192.168.1.10 22       # 单个端口
nc -vz 192.168.1.10 20-25    # 扫一段范围
```

三种结果含义**完全不同**，是排障的关键信号：

| 结果 | 含义 |
|---|---|
| `succeeded!`（退出码 0） | 端口开着、有程序 listen、防火墙放行 |
| `Connection refused` | 机器活着，但该端口**没人监听** |
| `Connection timed out` | 通常是**防火墙在丢包**（机器不回应） |

实测（本机 9999 端口无人监听）：

```
nc: connectx to 127.0.0.1 port 9999 (tcp) failed: Connection refused
```

### 2. 临时传文件（不用装任何软件）

接收方先监听：

```bash
nc -l 9000 > received.txt
```

发送方连过去并把文件灌进去：

```bash
nc 接收方IP 9000 < send.txt
```

原理：一端的标准输入 → 网络 → 另一端的标准输出。

### 3. 当个临时聊天 / 双向调试通道

```bash
# 终端 A
nc -l 9000
# 终端 B
nc 对方IP 9000
```

两端互相打字、回车即送达，用来验证双向链路是否通。

### 4. 手动跟服务「对话」（理解文本协议的利器）

```bash
printf 'GET / HTTP/1.0\r\nHost: example.com\r\n\r\n' | nc -G 5 example.com 80
```

实测真实回包（节选）：

```
HTTP/1.1 200 OK
Date: Thu, 04 Jun 2026 06:38:40 GMT
Content-Type: text/html
Connection: close
Server: cloudflare
```

亲手发字节、亲眼看回包，比读文档更能理解 HTTP / SMTP / Redis 这类文本协议。

### 5. UDP 探测（注意不可靠）

```bash
nc -u -vz 8.8.8.8 53
```

UDP 无连接，没回应可能是**开着**也可能是**丢包**，结果别太当真，需要时改用 `nmap -sU`。

## 三·进阶：脚本与自动化里的 nc

前面 5 条是「手动敲、肉眼看」。下面 3 条是把 nc 编进**脚本 / 自动化**的关键，做 homelab / 运维迟早天天用。命令均已实测。

### 6. 用退出码判断端口（脚本的基石）

肉眼看 `succeeded` 不能写进脚本，**退出码**才能：通了为 `0`，不通为非 `0`。

```bash
if nc -z -G 2 192.168.1.10 22; then
  echo "SSH 端口开着"
else
  echo "连不上"
fi
```

实测：

```
nc -z -G 2 127.0.0.1 9999; echo $?
→ 1          # 端口没人监听，退出码非 0
```

这条是从「工具」升级到「自动化零件」的分水岭——监控脚本、健康检查全靠它。

### 7. 等端口就绪再继续（wait-for-it 模式）

起服务 / 跑容器时极常见：数据库还没起好，应用就连过去报错。于是循环探测直到端口通：

```bash
until nc -z -G 1 localhost 5432; do
  echo "等数据库启动..."; sleep 1
done
echo "数据库好了，继续"
```

实测（探一个已通的端口，循环立即跳出）：

```
Connection to example.com port 80 succeeded!
→ 端口已就绪，循环退出
```

用 Docker / 编排服务时，这个模式几乎天天出现。

### 8. Banner grabbing（看对面是什么服务 / 版本）

连上端口后，很多服务会主动报「名片」。

```bash
# SSH：连上即回版本号
printf '' | nc -w 3 -G 5 192.168.1.10 22
# 典型输出（示例）：SSH-2.0-OpenSSH_9.6
```

```bash
# HTTP：用 HEAD 请求看 Server 头
printf 'HEAD / HTTP/1.0\r\n\r\n' | nc -G 5 example.com 80 | grep -i server
```

实测 HTTP banner：

```
Server: cloudflare
```

> 说明：SSH banner 那条因本机环境没有可达的 SSH 服务，未在此次实测中抓到真实回显，故标为「典型输出示例」；HTTP banner 的 `Server: cloudflare` 为实测结果。
> 排查「这端口到底是什么服务在占」时，banner grabbing 能让你立刻知道对面跑的是什么、什么版本。

## 四、动手 Lab

分三关，**从单机可独立完成，逐步升级到结合你的 OPNsense + Mac homelab**。每一步都有「预期结果」，可自行验证。

### 关卡 0：单机自测（无需第二台机器）

目的：先在一台 Mac 上把「监听 + 收发」跑通，建立直觉。

开两个终端窗口。

**终端 A（服务端，监听 9000）：**
```bash
nc -l 9000
```

**终端 B（客户端，连 localhost）：**
```bash
nc 127.0.0.1 9000
```

在任一终端打字回车 → 另一终端立刻出现同样的字。

✅ **预期**：双向实时收发。按 `Ctrl+C` 退出。

> 验证过的等价单行测试（用脚本一次性跑完）：
> ```bash
> echo "lab-test-payload-12345" | nc -l 9999 > /tmp/nc_recv.txt &
> sleep 1
> echo "from-client-hello" | nc -w 2 127.0.0.1 9999
> sleep 1; cat /tmp/nc_recv.txt
> ```
> 实测：客户端收到 `lab-test-payload-12345`，服务端文件里是 `from-client-hello`。

### 关卡 1：两台机器传文件

目的：跨机验证三层连通 + 实用文件传输。

设：Mac 是接收方，IP 假设 `192.168.1.50`；另一台机器（或 OPNsense 后的设备）是发送方。

**Mac（接收）：**
```bash
nc -l 9000 > got.bin
```

**另一台（发送）：**
```bash
nc 192.168.1.50 9000 < 要传的文件
```

文件传完后发送端连接自动关闭，Mac 端 `nc` 也随之退出。

✅ **预期**：`got.bin` 与源文件一致。可用 `shasum 文件` 两边比对校验：
```bash
shasum got.bin        # 两边 hash 相同即传输无误
```

❌ **若失败**：八成是 Mac 的防火墙（系统设置 → 网络 → 防火墙）或 OPNsense 规则挡了 9000 端口。这正好引出关卡 2。

### 关卡 2：用 nc 验证 OPNsense 防火墙规则（结合你的 homelab）

目的：把 nc 当成「探针」，验证你写的防火墙规则到底放行还是拦截。

**步骤：**

1. 在 Mac 上起一个监听端口，模拟一个「服务」：
   ```bash
   nc -k -l 8080      # -k 让它处理完一个连接后继续监听
   ```

2. 从 OPNsense **另一个网段**（如 VLAN / 来宾网）的设备探测这个端口：
   ```bash
   nc -vz Mac的IP 8080
   ```

3. 对照结果调试规则：

   | nc 结果 | 说明 | 下一步 |
   |---|---|---|
   | `succeeded!` | 规则放行、路由可达 | 规则按预期工作 ✅ |
   | `refused` | 包到了 Mac，但 8080 没监听 | 检查第 1 步的 `nc -l` 是否在跑 |
   | `timed out` | 包被防火墙丢了 | 检查 OPNsense 该网段的 pass/block 规则 |

4. 故意在 OPNsense 上加一条 block 规则挡掉 8080，再跑一次 `nc -vz` —— 结果应从 `succeeded` 变成 `timed out`。**这一步让你亲眼看到规则生效，而不是猜。**

✅ **预期**：你能通过 nc 的三种结果，反推出包在「路由 / 防火墙 / 服务」哪一层出了问题。

## 五、定位与局限

nc 的哲学是「小而专」：只搬数据，**不加密、不解析协议、不做认证**。

| 需求 | 该用的工具 |
|---|---|
| 加密通道 | `openssl s_client` |
| 强大的转发 / 中继 / 双向代理 | `socat`（nc 的加强版） |
| 功能化端口扫描 / 服务识别 | `nmap` |

但因为它简单、几乎所有系统自带，**排查网络问题的第一反应往往就是掏出 nc**。

## 附录：自我思考

1. **nc 的真正价值是「分层切割问题」**。它只能验证到 TCP（第四层），但恰恰因此，它能把「连不上」这个模糊问题一刀切成两半：nc 通 → 问题在应用 / 认证层；nc 不通 → 问题在网络 / 防火墙层。前一轮测腾讯云 PG 时（`succeeded` 但能否登录是另一回事）就是这个思路的体现。对一个网络学习者，养成「先用 nc 定位在哪一层」的反射，比记住一堆参数更重要。

2. **`refused` vs `timed out` 是最该刻进肌肉记忆的区分**。前者证明对端主机活着、协议栈在工作，只是没人接这个端口；后者多半是防火墙在「黑洞」式丢包。把这两个信号搞混，排障方向就会完全跑偏。

3. **Lab 设计刻意做成「可证伪」**。关卡 2 里「故意加 block 规则、看结果从 succeeded 变 timed out」这一步，是整个 lab 的灵魂——它不是让你确认「能通」，而是让你制造一次「不通」并解释它。能主动复现失败、并预测失败的表现，才算真懂了防火墙规则，而不是碰巧配对了。

4. **平台差异是隐形的坑**。`-G` 在 Mac 有、Linux 没有这类细节，会在你「Mac 上好好的、SSH 到 Linux 就报错」时浪费时间。结合 homelab 多平台的现实，早点知道「nc 有好几个实现」能省掉一类莫名其妙的报错。
