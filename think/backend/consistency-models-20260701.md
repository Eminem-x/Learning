## 一、四档一致性，从强到弱的阶梯

一致性模型描述的是：**在有多个副本的系统里，"读到的数据能有多新、多可靠"的保证等级**。它是 PACELC 里 `E`（正常运行时）那一侧的细化 —— 说"选了一致性(EC)"还不够，还得说清一致到什么程度。

```
线性一致性  ─── 最强，认"真实时间"：写完返回后，全世界立刻读到最新
   │
顺序一致性  ─── 全局有序，但不认真实时间：大家看到同一个顺序，可能整体慢一拍
   │
因果一致性  ─── 只保证"有因果关系的"有序：回复不会跑到原消息前面
   │
最终一致性  ─── 最弱，只保证"最后会收敛"，中间过程随意
```

**越往上，一致性越强、代价（延迟/可用性）越大；越往下，越快越可用、但越可能读到旧值。**

## 二、逐档拆解 + 常用组件对照

### 1. 线性一致性（Linearizability / 强一致）

**要求**：每个操作看起来在某个瞬间原子生效，且**尊重真实时间顺序** —— 你写完返回后，全世界任何人立刻都能读到最新值。

| 组件 | 说明 |
|------|------|
| **etcd** | Raft 实现，默认线性一致读写；K8s 元数据就靠它 |
| **ZooKeeper（写）** | 写是线性一致的；但**读默认只是顺序一致**，可能读到旧值，要强读得调 `sync()` |
| **Consul**（consistent 模式） | 同样基于 Raft |
| **Google Spanner / TiDB** | 更强，叫"外部一致性"，本质是线性一致 + 全局时间戳（TrueTime/TSO） |

> 典型用途：分布式锁、选主、配置中心、元数据 —— 一丁点旧数据都不能容忍的场景。

### 2. 顺序一致性（Sequential Consistency）

**要求**：所有操作能排成**一个全局顺序**，且每个客户端自己的操作保持程序顺序 —— 但**不要求这个顺序符合真实时间**。即：大家看到的顺序一致，但可能整体"慢一拍"。

| 组件 | 说明 |
|------|------|
| **ZooKeeper（读）** | 单客户端看到的更新单调有序，但可能落后于真实最新状态 |
| **CPU / 内存模型** | 这个概念更多来自多核内存一致性；分布式里纯"顺序一致"的产品较少单独打广告 |

> 和线性一致只差一个词：**线性一致认真实时间，顺序一致不认**。所以顺序一致允许"所有人一起看到一个稍旧但彼此一致的世界"。

### 3. 因果一致性（Causal Consistency）

**要求**：**有因果关系**（happens-before）的操作，所有人看到的顺序一致；**并发无因果**的操作，不同人可以看到不同顺序。经典例子：评论必须在被评论的帖子之后出现，但两条无关帖子谁先谁后无所谓。

| 组件 | 说明 |
|------|------|
| **MongoDB**（causal consistency sessions） | 3.6+ 提供因果一致会话，保证"读自己写""单调读"等 |
| **Azure Cosmos DB**（Session 级别） | 五档一致性里的 Session ≈ 因果一致，是其默认档 |
| **COPS / Bayou** | 学术界因果一致的经典实现 |

> 典型用途：社交动态、评论、聊天消息 —— 要保证"回复不会跑到原消息前面"，但不必全局强一致。

### 4. 最终一致性（Eventual Consistency）

**要求**：最弱。只承诺"**只要没有新写入，副本们最终会收敛到一致**"，中间过程可以乱、可以读到旧值，连"读到自己刚写的"都不保证。

| 组件 | 说明 |
|------|------|
| **Cassandra / DynamoDB** | PA/EL 的代表，默认最终一致（可调 quorum 换强一致） |
| **Redis 主从（异步复制）** | 从库异步追，读从库可能旧 |
| **Amazon S3**（历史上） | 曾是经典最终一致例子（现已改为强读写一致） |
| **DNS** | 教科书级例子：改了解析记录，全球慢慢生效 |
| **CouchDB / Riak** | 为高可用天生走最终一致 |

> 典型用途：点赞数、浏览量、CDN、DNS、推荐 —— 数据旧几秒没人在意，但要极致的可用与低延迟。
>
> ⚠️ 但"最终一致"实战里从不裸用，会叠加一组客户端保证（读己之写、单调读等）。详见 **第四节：最终一致性的五种客户端变体**。

## 三、案例精解：MySQL 主从同步是哪一档？

结论：**默认配置（异步复制）下就是最终一致性。** 但它是一个"可调档位"，从最终一致一路能调到接近强一致。

### 三档一致性

**① 异步复制（默认）→ 最终一致**

```
   Client ──写──► 主库 ──立刻返回成功──► Client
                   │
                   └─(异步、慢慢地)─► 从库 apply
```

主库提交后**不等从库**就返回，从库通过 binlog 慢慢追。所以：

- 主从之间有**复制延迟（replication lag）**，读从库可能读到旧值 → **最终一致**。
- 极端情况：主库刚提交完就宕机、binlog 还没传给从库 → **数据直接丢**（连最终一致都没兜住）。

**② 半同步复制（semi-sync）→ 更持久，但仍不是读强一致** ⚠️

规则：**主库要等至少一个从库"收到"binlog（写进 relay log）才返回**。

关键坑：它等的是从库**"收到"**，不是从库**"应用完（apply）"**。所以：

- ✅ 提升了**持久性**（数据至少在一个从库落盘，主库挂了不丢）。
- ❌ **没提升读一致性** —— 从库收到了但还没回放，你去读它照样是旧的。

> 半同步解决的是"**丢不丢数据**"，不是"**读不读得到最新**"。想读到最新，要么读主库，要么用 MGR。

**③ 组复制 MGR（MySQL 8.0）→ 可配到近似强一致**

基于类 Paxos 协议，提供 `group_replication_consistency` 参数（EVENTUAL / BEFORE / AFTER / BEFORE_AND_AFTER）。配到 `AFTER` / `BEFORE_AND_AFTER` 时，读能保证看到之前已提交的写 → **接近线性一致**。

### 一个重要澄清：主库自己一直是强一致的

别把"主从最终一致"误读成"MySQL 是弱一致数据库"：

- **单看主库**：标准 ACID、单机强一致，所有读写都走主库时就是线性一致，压根没有一致性问题。
- **"最终一致"只发生在"读从库"这件事上** —— 是你为了读写分离、分摊读压力，主动引入从库副本，才把一致性从强降到了最终。

这正好呼应 [[cap-theorem-deep-dive-20260630]] 里 6.3 那条：**"MySQL 读写分离 = 牺牲 C 换 A"** —— 从库这个副本一出现，一致性问题才上桌。

### 汇总表

| MySQL 配置 | 一致性档位 | 对应 PACELC |
|-----------|-----------|-------------|
| 异步复制（默认） | 最终一致 | 偏 EL（读从库快但可能旧） |
| 半同步复制 | 最终一致（但更持久） | 主要改善持久性，不是读一致 |
| MGR + AFTER | 近似线性一致 | 偏 EC（读一致但要等，慢） |
| 只读主库 | 线性一致 | 单点强一致，无副本问题 |

> 一句话：**MySQL 主从默认是最终一致，但"最终一致"是它的默认档不是本质；本质是主库强一致，一旦你为了扩展读而去读异步从库，才滑到了最终一致。** 想往回调，半同步管持久、MGR 管读一致。

## 四、深入：最终一致性的五种客户端变体（Vogels）

> 论文出处：Werner Vogels（Amazon CTO），**《Eventually Consistent》**，ACM Queue, Vol. 6, No. 6, 2008（后收录于 Communications of the ACM, Vol. 52, No. 1, 2009, pp. 40–44）。原文：https://queue.acm.org/detail.cfm?id=1466448 ——这是 Dynamo 思想的同源文，也是"最终一致性有几种"这个问题在业界的**标准出处**。

"最终一致性"只承诺"最终会收敛"，体验太差（刚写完自己都读不到）。所以实战里从不裸用，而是在其之上叠加一组**客户端级保证（client-side variations）**。Vogels 在原文中列了 **5 种**：

| # | 变体 | 保证什么 | 翻车场景 |
|---|------|---------|---------|
| 1 | **因果一致性 Causal** | 有因果关系的写，所有人看到的顺序一致 | 回复先到、原帖没到 → 孤儿回复 |
| 2 | **读己之写 Read-Your-Writes** | 自己写的，自己一定读得到（因果的特例） | 改了头像，刷新还是旧的 |
| 3 | **会话一致性 Session** | 在**一个会话内**保证"读己之写"，换会话不保证 | 换设备登录，看不到上个设备的改动 |
| 4 | **单调读 Monotonic Read** | 读到新值后，不会再读回旧值 | 刷新列表：10 条 → 下拉 → 变 8 条（时间倒流）|
| 5 | **单调写 Monotonic Write** | 同一进程的多次写，按发出顺序生效 | 先设密码 A 再设 B，最终存的是 A |

**关键洞察（原文强调）**：这五种**不是五选一，而是可叠加勾选**。常见组合如"单调读 + 读己之写"。且它们有强弱包含关系——**因果一致 ≈ 读己之写 + 单调读 + 单调写 + 写跟随读 的总和**，因果是其中最强的一档。这正呼应 [[logical-clocks-and-causality-20260701]]：因果一致靠逻辑时钟追踪 happens-before 实现。

### 与另一套分类的对照：Bayou 四大"会话保证"

学术/工程界还有一套来自 **Bayou 系统**的"四大会话保证"：读己之写、单调读、单调写、**写跟随读（Writes-Follow-Reads）**。它和 Vogels 五种的差异只是**切法不同**：

- Vogels 版多了 **因果、会话** 两项，少了 **写跟随读**。
- 二者交集里，**读己之写 / 单调读 / 因果** 这三个是业界**真正天天挂嘴边**的高频词；单调写、写跟随读概念重要但常被"因果一致"一词整体覆盖，会话一致则更多作为**产品档位名**出现（Cosmos DB、MongoDB 的 `session` 级别）。

> 选型记忆优先级：**读己之写 > 单调读 > 因果一致** 是硬通货；要成套列举时引 **Vogels 五种**（有现成清单、出处权威）；落到具体 bug / 功能设计时，大家只说那几个具体名字。

## 五、串回 CAP / PACELC

这四档一致性正好挂在 PACELC 的 **E（正常运行时）那一侧**上：

- **EC（正常时选一致）** → 通常做到**线性一致**（etcd、Spanner）
- **EL（正常时选低延迟）** → 只做到**因果 / 最终一致**（Cassandra、Cosmos 默认档）

所以 [[cap-theorem-deep-dive-20260630]] 第七节那句"正常运行时一致性 = 无分区 ∧ EC"，可以进一步细化：

> **EC 只是说"正常时选了一致"，但一致到什么程度（线性？顺序？因果？），得看这个系统声称的一致性模型。** 一致性不是"有/无"的开关，而是一整条从线性到最终的连续光谱。

## 附录：自我思考

### "强一致"是个偷懒的词

工程里张口就说"强一致 / 弱一致"，其实太粗。真正落地时，"强"到底是线性还是顺序、"弱"到底是因果还是最终，行为差别巨大：因果一致能保证"读自己写"，最终一致连这个都不保证。把这四档记清楚，才不会在设计时用一个模糊的"强一致"骗过自己。

### 判断一个系统属于哪一档的实操问法

不用背定义，按三个递进的问题问自己：

1. **写完立刻读另一个副本，一定是最新的吗？** → 是，线性一致。
2. **不一定最新，但所有人看到的顺序至少一致吗？** → 是，顺序一致。
3. **顺序也不保证，但至少"有因果关系的事件"顺序对吗？** → 是，因果一致；否则就是最终一致。

### 与 MySQL 案例的最大启发

MySQL 这个例子最妙的地方：**同一个数据库产品，能横跨"最终一致"到"线性一致"整条光谱，只取决于你怎么配、读哪里。** 这说明一致性档位不是"数据库的固有属性"，而是"你的部署方式 + 读写路径"共同决定的。选型时别只问"这个库强一致吗"，要问"我这条读写路径最终落在哪一档"。
