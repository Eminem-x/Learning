## 一、Raft 到底要解决什么问题

一句话：**让一群机器，在有些机器会宕机的情况下，依然对"一系列操作的顺序"达成完全一致。**

### 为什么需要它

回忆 [[cap-theorem-deep-dive-20260630]]：当你选择 **CP（一致性优先）**，就需要保证多个副本的数据完全一致。但多台机器怎么保证一致？

最朴素的想法是"所有写操作让每台机器都执行一遍"。但问题来了：

- 如果两个客户端同时写，机器们收到的顺序可能不同 → 数据就乱了。
- 如果某台机器在执行到一半时宕机 → 它的数据和别人就不一致了。

**Raft 的解法：选出一个"老大"(Leader)，所有写操作只经过老大，由老大决定顺序、再复制给小弟。** 这样顺序就唯一确定了。

```
   客户端写请求
        │
        ▼
   ┌─────────┐         ┌─────────┐
   │ Leader  │ ──复制──►│Follower │
   │ (老大)   │ ──复制──►│Follower │
   └─────────┘         └─────────┘
   唯一接受写的人        被动接收数据
```

Raft 把这个大问题拆成两个子问题：
1. **怎么选出老大？**（Leader Election，选主）
2. **老大怎么把数据可靠地同步给小弟？**（Log Replication，日志复制）

## 二、三种角色

每个节点在任意时刻，都处于以下三种状态之一：

```
        ┌──────────────┐
        │   Follower   │  跟随者：默认状态，被动接收心跳和数据
        └──────┬───────┘
               │ 长时间没收到老大的心跳，怀疑老大挂了
               ▼
        ┌──────────────┐
        │  Candidate   │  候选人：选举期间的临时状态，正在拉票
        └──────┬───────┘
               │ 拿到超过半数的票
               ▼
        ┌──────────────┐
        │    Leader    │  领导者：唯一的老大，处理所有写请求
        └──────────────┘
```

正常运行时，集群里**只有 1 个 Leader，其余都是 Follower**。Candidate 只在"换届选举"那一小段时间出现。

## 三、核心概念：任期（Term）

Raft 把时间切成一段一段的"任期"，每个任期一个编号，单调递增。

```
任期1          任期2       任期3              任期4
├──选举──┬─────┼──选举─┬───┼──选举失败──┼──选举──┬────────►
         └正常运行      └正常运行                    └正常运行
   Leader=A           Leader=B    (没人过半,重选)   Leader=C
```

- 每个任期最多有一个 Leader（也可能没有，比如选举失败）。
- Term 就像"届数"——"第 3 届领导"。
- **Term 是 Raft 判断信息新旧的关键依据**：谁的 Term 大，谁的信息就新，小 Term 的要服从大 Term。这能解决"老 Leader 复活后造成混乱"的问题。

## 四、选主流程（Leader Election）图解

### 触发条件

每个 Follower 都有一个**随机的"选举超时计时器"**（比如 150~300ms 之间随机）。只要在这段时间内收到 Leader 的心跳，就重置计时器。如果超时还没收到心跳 → 认为 Leader 挂了，发起选举。

### 流程分步图

**步骤 0：正常状态**，Leader 定期发心跳

```
   [Leader A] ──心跳──► [Follower B]  (计时器不断重置)
              ──心跳──► [Follower C]
```

**步骤 1：Leader A 宕机**，B、C 收不到心跳了

```
   [Leader A] ✗ 挂了
              
   [Follower B] 计时器在走... 没收到心跳
   [Follower C] 计时器在走... 没收到心跳
```

**步骤 2：谁先超时，谁先变 Candidate 发起选举**

假设 B 的随机计时器先到期：

```
   [Candidate B]  Term+1，先投自己一票
        │
        ├──"投我！"──► [Follower C]
        └──"投我！"──► [已挂的 A]（收不到，无所谓）
```

**步骤 3：C 收到拉票，如果自己这一票还没投出去，就投给 B**

```
   [Follower C] ──"好，投你一票"──► [Candidate B]
```

**步骤 4：B 拿到 2 票（自己 + C），3 个节点里 2 票过半 → 当选！**

```
   [Leader B]  开始向大家发心跳，新任期开始
        ├──心跳──► [Follower C]
        └──心跳──► (A 若复活会以 Follower 身份回归)
```

### 关键设计：为什么计时器要"随机"？

如果所有 Follower 的超时时间一样，Leader 一挂，大家会**同时**变成 Candidate 同时拉票，结果谁也凑不齐过半数（票被分散了），选举失败，只能重来——可能无限循环（这正是 FLP 定理预言的僵局）。

**随机化**让某个节点大概率"先一步"超时、抢先拉票，从而快速决出胜负。这就是工程上用随机绕过 FLP 的经典手法。

### "过半数"为什么能防止两个 Leader（脑裂）？

假设 5 个节点，当选需要 ≥3 票。两个 Candidate 不可能同时各拿到 3 票（总共才 5 票，3+3=6>5 矛盾）。所以**同一任期内最多一个 Leader**。

## 五、日志复制（Log Replication）图解

选出 Leader 后，就开始干正事：处理写请求。

### 什么是"日志"

每个节点都维护一个**日志数组**，每个条目是一条操作命令（比如 `set x=5`），带 Term 和索引：

```
索引:    1        2        3        4
      ┌──────┬────────┬────────┬────────┐
日志: │x=1   │ y=2    │ x=5    │ z=9    │
      │(T1)  │ (T1)   │ (T2)   │ (T2)   │
      └──────┴────────┴────────┴────────┘
```

所有节点按相同顺序执行相同日志 → 最终状态必然一致。这叫**状态机复制**。

### 复制流程分步图

**步骤 1：客户端发写请求给 Leader**

```
   客户端 ──"set x=5"──► [Leader]
```

**步骤 2：Leader 先把这条记到自己日志（标记为"未提交"）**

```
   [Leader] 日志: [...已有..., (x=5)未提交]
```

**步骤 3：Leader 把这条复制给所有 Follower**

```
   [Leader] ──"追加 x=5"──► [Follower 1]
            ──"追加 x=5"──► [Follower 2]
```

**步骤 4：Follower 写入自己日志，回复"收到了(ACK)"**

```
   [Follower 1] ──ACK──► [Leader]
   [Follower 2] ──ACK──► [Leader]
```

**步骤 5：Leader 收到「过半数」ACK（含自己），标记为"已提交"，执行并回复客户端**

```
   含 Leader 自己共 3 票，过半！
   [Leader] 标记 x=5 为"已提交(committed)"
            执行 set x=5
            ──"成功"──► 客户端
```

**步骤 6：Leader 在后续心跳中告诉 Follower"这条可以提交了"**

```
   [Leader] ──心跳(已提交到索引N)──► [Follower] 也执行 set x=5
```

### 关键点

- **"过半数确认"才算提交**，不需要等所有节点（容忍少数节点慢或宕机）。
- 这正是 [[distributed-systems-core-theories-20260630]] 里讲的 **Quorum 多数派思想**。
- 5 个节点的集群，能容忍 2 个宕机（剩 3 个仍过半）。容忍故障数 = `(N-1)/2`。

## 六、安全性：Raft 如何防止数据错乱

Raft 有几条铁律保证即使发生宕机、网络抖动也不会出错：

### 1. 选举限制：只有"日志足够新"的节点才能当 Leader

拉票时，Candidate 要带上自己最后一条日志的信息。Follower 只会投票给"日志和自己一样新或更新"的 Candidate。

> 这保证了：**新 Leader 一定包含所有已提交的日志**，不会出现"选了个数据落后的当老大，导致已提交数据丢失"。

### 2. 日志匹配特性

如果两个节点的日志在某个索引上 Term 相同，那么这个索引之前的所有日志都完全相同。Leader 通过"回溯比对"强制 Follower 的日志和自己对齐。

### 3. 老 Leader 复活的处理

假设老 Leader A 因网络分区被孤立，集群选了新 Leader B（Term 更大）。当 A 网络恢复：

```
   [A] 自以为还是 Leader (Term=2)
   [A] ──心跳(Term=2)──► [B]
   [B] "你 Term 太小了！现在是 Term=3，我才是 Leader"
   [A] 一看对方 Term 更大 → 自觉退位变 Follower
```

**Term 大的说了算**，老 Leader 自动退位，不会脑裂。

## 七、脑裂场景演练（最经典的考点）

假设 5 节点集群 `[A B C | D E]`，网络从中间裂开成两块：

```
   分区1: [A B C]  (3个节点)        分区2: [D E]  (2个节点)
        │                                 │
   能凑齐过半数(3≥3)                  凑不齐过半数(2<3)
        │                                 │
   选出新 Leader，正常工作            无法选出 Leader，只能拒绝写请求
   (CP 中的 C：少数派宁可不可用)
```

**结果**：
- 多数派 `[A B C]` 继续提供服务（仍强一致）。
- 少数派 `[D E]` 因为无法达成过半数，**主动拒绝写入**（牺牲可用性保一致性）。

这完美呼应了 [[cap-theorem-deep-dive-20260630]]：Raft 是 **CP 系统**，分区时少数派宁可不可用，也绝不返回可能错误的数据。**这就是为什么 etcd、ZooKeeper 部署都推荐奇数台（3/5/7）**——便于明确"过半数"，且能最大化容错。

## 九、Raft vs Paxos：关系与该学到什么程度

常见困惑：**"Paxos 还要学吗？还是只学 Raft 就够了？"** 实用主义答案：**Raft 学透，Paxos 理解到"基本 Paxos 的核心思想"这一层就够了，不必啃 Multi-Paxos 的完整实现；但"完全不学 Paxos"也不对。**

### 两者的关系：Raft 是 Paxos 的"可教学化重写"

Raft 不是 Paxos 的替代品，而是**同一个问题（分布式共识）的"人类友好版"**。

- **Paxos（1998, Lamport）**：最早证明"分布式共识可行"，但以**极难懂**著称，连 Lamport 自己都补写了《Paxos Made Simple》。
- **Raft（2014）**：设计初衷就写在论文标题里 —— *In Search of an Understandable Consensus Algorithm*。它把 Paxos 拆成选主、日志复制、安全性三块，好懂好实现（正是本篇附录说的"更懂人"）。

```
   要解决的问题：分布式共识(Consensus)
        ├── Paxos    → 理论奠基，难懂，工业界多用其变体
        └── Raft     → 同一问题的"人类友好版"，现代系统首选
```

> 一句话：**Raft ≈ 一种结构化、加了 Leader 约束的 Multi-Paxos。** 学会 Raft，已经掌握了 Paxos 想解决的 90%。

### 分层学习建议：哪层要学、哪层选学

| 层次 | 要不要学 | 理由 |
|------|---------|------|
| **基本 Paxos 的核心思想**（两阶段 prepare/accept、多数派 quorum 相交） | ✅ **要**，理解级 | 所有共识算法的理论底座；Raft 的设计（为什么要多数派、为什么 Term 递增）本质都在复现它 |
| **Multi-Paxos 的完整工程实现** | ⚠️ 选学 | 极绕，Raft 就是来替代"必须掌握它"的；除非造共识库或做研究，否则不必啃 |
| **Paxos 变体**（ZAB、Raft、EPaxos） | 按需 | 用到哪个学哪个 |

### 为什么"基本 Paxos"仍值得花两小时

1. **面试**：基础架构岗常问 Paxos，或"Paxos 与 Raft 的区别"。
2. **读得懂重要系统**：很多顶级系统是 **Paxos 系**而非 Raft 系 ——
   - Google **Chubby / Spanner** → Paxos
   - **ZooKeeper** → ZAB（Paxos 家族）
   - **Cassandra 轻量级事务(LWT)** → 基本 Paxos
   - MySQL **MGR** → 类 Paxos（见 [[consistency-models-20260701]]）
3. **理解 Raft 的"为什么"**：Raft 为何强制单 Leader、日志为何不允许空洞 —— 都是在**规避基本 Paxos 的复杂性**；懂 Paxos 才知道它在躲什么坑，而不是死记规则。

### 推荐路径

```
1. Raft 学透（本篇）                        ← 你的"工作母机"
        │
2. 花 1~2 小时理解「基本 Paxos」核心：
   - 为什么多数派(quorum)两两必然相交 → 共识不冲突的根
   - prepare / accept 两阶段在干什么
   - 不必能手写，能讲清"凭什么保证一致"即可
        │
3. Multi-Paxos / EPaxos / ZAB → 用到再深入
```

> 判断基准：目标是"做后端、用好 etcd/Consul/TiDB、应付多数面试" → **Raft 学透 + 基本 Paxos 理解思想**足够。只有要**自己实现共识、读 Paxos 系源码、做分布式研究**时，才需真正啃 Multi-Paxos。而"多数派两两相交"这个核心，正是本篇附录「过半数思想的优雅」讲的那个数学直觉 —— Paxos 和 Raft 共享同一个根。

## 十、本专题要记住的三句话

1. **Raft = 选个老大(Leader) + 老大带着大家按同一顺序记日志**，从而让多副本强一致。
2. **一切以"过半数"为准**：选举要过半票当选，写入要过半 ACK 才提交；这让系统能容忍少数节点故障，又能防脑裂。
3. **随机超时**绕过 FLP 僵局，**Term 编号**让老 Leader 自动退位——这两个小设计是 Raft 优雅的关键。

## 附录：自我思考

### Raft 的伟大不在"更强"，而在"更懂人"

Raft 和 Paxos 解决的是同一个问题，理论能力也相当。但 Paxos 出了名地难懂，多年来无数工程师啃不动、实现不对。Raft 的作者明确把"**可理解性(understandability)**"当成第一设计目标——把一个浑然一体的难题，硬拆成"选主"和"日志复制"两个能分开理解的部分。

这给我的启发超出技术本身：**一个能被广泛正确使用的方案，胜过一个理论更优但没人能用对的方案。** 工程世界里，"可理解、可落地"本身就是一种核心竞争力。

### "过半数"思想的优雅

最初我不理解为什么是"过半数"而不是"全体同意"或"任意一个"。想通后觉得极妙：
- 要"全体同意" → 一台宕机就全瘫，太脆弱。
- "任意一个" → 无法保证一致，太松散。
- "过半数" → 恰好卡在中间：任意两个多数派集合**必然有交集**，这个交集节点就像"信息的接力棒"，保证了新旧决策之间的连续性，既容错又一致。

很多分布式机制（Quorum、ZAB、甚至区块链的 51%）底层都是这同一个数学直觉。**抓住"过半数交集"这一个点，能串起一大片知识。**

### 下一步可以深挖的方向

- **日志压缩与快照（Snapshot）**：日志无限增长怎么办？Raft 如何做快照来回收空间。
- **成员变更（Membership Change）**：集群要加/减节点时，如何安全地"换人"而不破坏过半数规则（联合共识 Joint Consensus）。
- **读请求优化**：读也要走一遍日志复制吗？了解 ReadIndex、Lease Read 等优化手段。
- 这些是从"懂 Raft"到"能用好 Raft"的进阶台阶。
