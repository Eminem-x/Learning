## 一、先分清两条正交的主线：复制 vs 分片

这是理解分布式存储最重要的一张思维图。数据规模变大时，你面对**两个完全不同、互相正交的问题**：

| | 复制（Replication） | 分片（Partitioning / Sharding） |
|--|--------------------|-------------------------------|
| 解决的问题 | **可用性 + 读扩展**：一台挂了还有别的 | **容量 + 写扩展**：一台放不下这么多数据 |
| 做法 | 同一份数据存**多个副本** | 把数据**切成多块**，各存一部分 |
| 你已学的 | Raft、主从、Quorum NWR | ← **本篇要补的空白** |
| 一句话 | "同一份数据，多台备份" | "不同的数据，分到不同机器" |

> **关键认知：你前面所有文档（CAP/Raft/一致性）讲的都是"复制"这条线 —— 同一份数据怎么在多副本间保持一致。但"分片"是另一条完全独立的线 —— 数据太大放不下，怎么切开。** 真实系统两者同时用：先分片，每个分片再各自复制。

```
   实际生产架构 = 分片 × 复制
   ┌──────分片1──────┐  ┌──────分片2──────┐  ┌──────分片3──────┐
   │ 主   从   从     │  │ 主   从   从     │  │ 主   从   从     │
   └────(Raft组)─────┘  └────(Raft组)─────┘  └────(Raft组)─────┘
     负责 key A~H         负责 key I~P         负责 key Q~Z
```

## 二、为什么要分片

单台机器的容量、内存、磁盘、CPU、网卡都有上限。当数据量或写入量超过一台机器能扛的极限，**纵向扩展（加配置）撞墙**，只能**横向扩展（加机器）** —— 而横向扩展存储的前提，就是把数据切开分到不同机器。

分片带来的收益：容量随机器数线性增长、写入压力分摊、故障影响面缩小（一个分片挂了不影响其他）。

## 三、分片策略：按范围 vs 按哈希

### 1. 范围分片（Range Partitioning）

按 key 的**区间**切：`A~H` 一台、`I~P` 一台、`Q~Z` 一台。

- ✅ **范围查询高效**：`scan 用户名 B 到 E` 落在同一台。
- ❌ **容易热点**：如果 key 是时间戳，最新写入永远打在最后一个分片 → 写热点。
- 用户：HBase、TiKV、MongoDB（range 模式）。

### 2. 哈希分片（Hash Partitioning）

对 key 算哈希，用哈希值决定去哪台：`hash(key) % N`。

- ✅ **数据分布均匀**，天然打散热点。
- ❌ **丢失范围查询能力**：相邻 key 被打散到不同机器。
- 用户：Cassandra、DynamoDB、Redis Cluster。

---

## 四、朴素哈希的致命伤：`hash(key) % N`

哈希分片最直觉的做法是 `节点编号 = hash(key) % N`（N = 机器数）。平时没问题，但**一旦增减机器，N 变了，几乎所有 key 的归属都变了**：

```
   原本 N=3:  hash(key)=100 → 100%3 = 1 号机
   加一台 N=4: hash(key)=100 → 100%4 = 0 号机   ← 变了！

   结果：扩容/缩容时，绝大部分数据要"搬家"
   → 缓存全部失效、海量数据迁移、系统雪崩
```

对缓存集群这是灾难：加一台机器本想减压，结果缓存命中率瞬间归零，压力全压到数据库。**这就是一致性哈希要解决的问题。**

---

## 五、一致性哈希（Consistent Hashing）

核心思想：**把哈希空间首尾相接成一个环（0 ~ 2³²-1），节点和 key 都映射到环上；key 顺时针找到的第一个节点，就是它的归属。**

```
              0 / 2³²
                │
        节点C ──┼── 节点A
          \     │     /
           \    │    /
   ─────────环 (hash ring)─────────
           /    │    \
          /     │     \
        节点B ──┴──
   key 落在环上某点，顺时针遇到的第一个节点即归属
```

### 为什么增减节点只影响一小段

```
   加入节点D（插在 A 和 B 之间）：
   只有"原本属于 B、但现在落在 D~B 这一段"的 key 需要迁移到 D
   其他所有 key 的归属完全不变！
```

- 增减一个节点，**平均只影响 `1/N` 的数据**，而不是全部 → 解决了朴素哈希的搬家灾难。

### 虚拟节点（Virtual Nodes）：解决数据倾斜

朴素一致性哈希有个问题：节点在环上分布不均，会导致某些节点负载远高于其他（数据倾斜）；且节点少时更明显。

**解法**：每个物理节点在环上放**多个"虚拟节点"**（比如每台机器对应 150 个环上的点）。

```
   物理节点A → A#1, A#2, ... A#150  散布在环各处
   物理节点B → B#1, B#2, ... B#150
   → 环上分布更均匀，负载更平衡；某节点挂了，它的负载被均摊给所有其他节点，而非全压给邻居
```

> 虚拟节点是一致性哈希**真正能用于生产**的关键。Cassandra、Dynamo 都靠它做负载均衡。

### 变体：固定 slot（哈希槽）

Redis Cluster 用了一个更简单的变体：预先划定 **16384 个固定槽（slot）**，`slot = CRC16(key) % 16384`，再把槽分配给节点。增减节点时只搬**槽**，槽到 key 的映射永不变。本质是"一致性哈希"思想的工程简化版。

## 六、路由：客户端怎么知道 key 在哪台？

分片后多了一个问题：请求进来，怎么找到负责这个 key 的节点？三种主流方案：

| 方案 | 做法 | 代表 |
|------|------|------|
| **客户端路由** | 客户端自己持有分片表，直接连对应节点 | Redis Cluster（MOVED 重定向）、Cassandra |
| **代理层路由** | 中间加一层 Proxy，由它转发 | Codis、Twemproxy、Vitess |
| **协调者/元数据服务** | 有个中心记录分片分布，客户端先问它 | HBase（靠 ZooKeeper/Meta 表）、MongoDB（mongos + config server） |

## 七、真实组件里的分片

| 组件 | 分片方式 | 备注 |
|------|---------|------|
| **Redis Cluster** | 16384 哈希槽 | 客户端 MOVED/ASK 重定向 |
| **Cassandra / DynamoDB** | 一致性哈希 + 虚拟节点 | 按 partition key 哈希 |
| **MongoDB** | 支持 range 和 hash | mongos 路由，config server 存元数据 |
| **HBase / TiKV** | range 分片（Region/Region） | 自动分裂与迁移，热点需设计 rowkey |
| **Kafka** | topic 按 partition 切 | 生产者按 key 哈希选 partition，保证同 key 有序 |
| **分库分表（ShardingSphere 等）** | 按分片键 hash/range | 传统 MySQL 横向扩展的落地 |

## 八、分片带来的新麻烦（选型时要预判）

分片不是免费的，它引入几个新问题：

1. **跨分片查询/事务**：数据被切开后，`JOIN`、聚合、跨分片事务变得昂贵 —— 这正好接回 [[distributed-systems-core-theories-20260630]] 的**分布式事务**（2PC/Saga）。
2. **热点（Hotspot / 数据倾斜）**：某个 key 特别热（大 V、爆款商品），单分片扛不住 → 需要二次拆分或加缓存。
3. **再平衡（Rebalancing）**：扩缩容时数据迁移，要做到不停服、不影响正确性。
4. **分片键选择**：选错分片键（比如选了低基数字段）会导致分布不均或跨分片查询频繁 —— 这是分库分表最关键、最难改的决策。

## 附录：自我思考

### 补上"分片"这条线，分布式的图才完整

学分布式时，我一直在"复制/一致性"的圈子里打转（CAP、Raft、Quorum），直到意识到那**只是一条主线**。真实的大规模系统是"**分片 × 复制**"的二维网格：横向切成分片解决容量，每个分片再纵向复制解决可用。缺了分片这一维，我对"为什么 Cassandra 既要 partition key 又要 replication factor"这种设计始终是懵的。**两条线合起来，分布式存储的骨架才立起来。**

### 一致性哈希是"最小惊讶"的典范

`hash % N` 的问题本质是：一个本该"局部"的变更（加一台机器）引发了"全局"的后果（所有 key 重映射）。一致性哈希的全部优雅，就在于把这个爆炸性的全局影响**收敛成 1/N 的局部影响**。这种"让变更的影响范围最小化"的思想，在系统设计里到处都是（增量更新、局部失效、蓝绿部署）—— 一致性哈希只是它在数据分布上最漂亮的一个化身。

### 分片键选择是"一次性决策"

代码可以重构，但分片键一旦定了、数据按它铺开了，再改就是伤筋动骨的全量迁移。这让我对"选分片键"这件事的敬畏上了一个台阶：它不是实现细节，而是和"选主键""定表结构"同级的、需要在设计阶段就想清楚未来查询模式的架构决策。
