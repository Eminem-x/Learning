## 一、根本困境：分布式系统里没有"全局的现在"

单机上判断两件事谁先谁后很简单：看时间戳，或看它们在同一个 CPU 上的执行顺序。但分布式系统里这条路断了：

**每台机器有自己的物理时钟，而这些时钟不可能完全一致。**

- 石英晶振有误差，机器间时钟会**漂移(clock drift)**，一天差几十毫秒是常态。
- NTP 校时本身有网络延迟，且会让时钟**回拨（往回跳）** —— 你可能看到"后发生的事件时间戳反而更小"。
- 结论：**你不能用两台机器的 wall-clock 时间戳来判断事件先后。** 时间戳小的那个，未必真的先发生。

```
   机器A: 事件P 发生，打时间戳 10:00:00.500
   机器B: 事件Q 发生，打时间戳 10:00:00.480   ← 时间戳更小
   但 B 的时钟慢了 50ms，实际上 Q 比 P 晚发生！
```

所以分布式系统需要一套**不依赖物理时钟、只靠消息传递就能推断顺序**的机制 —— 这就是**逻辑时钟**。

## 二、地基概念：Happens-Before（发生在...之前）

Lamport 1978 年定义了一个偏序关系 `→`（读作"happens-before"），它是**唯一能被可靠断言的因果顺序**。规则只有三条：

1. **同一进程内**：a 在 b 之前执行 → `a → b`
2. **消息传递**：发送消息的 send 事件 → 接收该消息的 recv 事件（`send → recv`）
3. **传递性**：`a → b` 且 `b → c` → `a → c`

```
   进程P:  a ──► b ──────► send(m)
                              │  m
                              ▼
   进程Q:              recv(m) ──► c

   可断言: a→b, b→send, send→recv, recv→c  (以及传递组合)
```

### 关键：并发（Concurrent）

如果两个事件**互相都推不出 happens-before**（既没有 `a→b` 也没有 `b→a`），它们就是**并发的**，记作 `a ∥ b`。

> **并发 ≠ 同时发生**，而是"**因果上无关，谁先谁后无所谓、也无法确定**"。这正是 [[consistency-models-20260701]] 里因果一致性的核心：有因果关系的必须有序，并发的可以乱。

## 三、Lamport 逻辑时钟（标量时钟）

用一个整数计数器给每个事件打"逻辑时间戳"，规则：

1. 进程每发生一个事件，本地计数器 `+1`。
2. 发消息时，把当前计数器值附在消息里。
3. 收消息时，本地计数器 = `max(本地, 消息里的值) + 1`。

```
   P: 1 ──► 2 ──► 3(send,带3)
                       │
                       ▼
   Q: 1 ──► 2 ──► recv: max(2,3)+1=4 ──► 5
```

### 它能做什么、不能做什么

- ✅ **保证**：如果 `a → b`，那么 `C(a) < C(b)`（因果先后 → 时间戳更小）。
- ❌ **反过来不成立**：`C(a) < C(b)` **推不出** `a → b`！时间戳小的，可能只是并发事件，不一定有因果关系。

```
   L 时钟的单向性：
   a → b   ⟹   C(a) < C(b)      ✅ 有因果 → 戳更小
   C(a)<C(b) ⟹  a→b ？          ❌ 戳更小 ≠ 有因果（可能并发）
```

**用途**：给全体事件排出一个**全序**（打破平局用进程 ID），够用于"需要一个确定顺序但不关心因果方向"的场景（如某些互斥算法）。**局限**：无法区分"真有因果"还是"只是并发"。

## 四、向量时钟（Vector Clock）—— 能识别因果与并发

要解决 Lamport 时钟"分不清因果和并发"的缺陷，就升级成**向量**：每个进程维护一个数组，记录"我所知道的每个进程各自进展到第几步"。

规则（N 个进程，每个持有长度 N 的向量 `V`）：

1. 进程 i 发生事件：`V[i] += 1`。
2. 发消息：附带整个向量 `V`。
3. 收消息：对每一位取 max（`V[k] = max(V[k], 收到的[k])`），再 `V[i] += 1`。

### 怎么比较两个向量时钟

- `Va < Vb`（Va happens-before Vb）：当 Va 每一位都 `≤` Vb，且**至少有一位严格小于**。
- `Va > Vb`：反之。
- **既不 < 也不 >** → **并发** `Va ∥ Vb`！

```
   P: [1,0] ─► [2,0] ─► send[2,0]
                            │
                            ▼
   Q: [0,1] ─► recv:[max]→[2,2]

   比较 [2,0] 和 [0,1]:  2>0 但 0<1 → 谁也不包含谁 → 并发 ∥
   比较 [2,0] 和 [2,2]:  每位都≤且有严格小 → [2,0] → [2,2] 有因果
```

> **这就是向量时钟的杀手锏：它能明确告诉你两个事件是"有因果先后"还是"并发冲突"** —— 而并发冲突正是最终一致系统需要检测并解决的东西。

## 五、落到真实组件

| 组件 / 机制 | 用了什么 | 用来干嘛 |
|------------|---------|---------|
| **Amazon Dynamo / Riak** | **向量时钟** | 检测并发写冲突，冲突时把多个版本交给应用/客户端去合并（siblings） |
| **Cassandra** | **物理时间戳 + LWT** | 默认 Last-Write-Wins（靠 wall-clock 时间戳定胜负，有丢更新风险） |
| **Git** | **DAG（有向无环图）** | commit 的 parent 指针本质就是因果关系，merge 处理并发分支 |
| **CRDT** | 向量时钟 / 版本向量 | 无需协调地合并并发更新（下一步可深挖） |
| **Google Spanner** | **TrueTime** | 用原子钟 + GPS 把时钟误差**有界化**，从而能给全球事务排真序 |

### 现代扩展：把物理时钟"救"回来

逻辑时钟丢掉了物理时间信息（你无法从逻辑戳知道"大概几点"）。工程上有两种把物理时间找回来的办法：

- **TrueTime（Spanner）**：不假装时钟精确，而是给出一个**误差区间** `[earliest, latest]`；提交时**故意等待**这个区间过去（commit-wait），从而保证全球事务的真实时间序。代价是每次提交多等几毫秒。
- **HLC（Hybrid Logical Clock）**：混合逻辑时钟，把物理时间戳和逻辑计数器打包进一个值 —— 既接近真实时间（便于人读、便于 TTL），又保留 happens-before 保证。CockroachDB、MongoDB 都用它。

```
   物理时钟不可靠（漂移/回拨）
            │  所以需要
   Happens-Before（唯一可靠的因果序）
            │  用什么表达？
     ┌──────┴───────┐
  Lamport 标量时钟    向量时钟
  (能排全序,          (能区分 因果 vs 并发,

   支撑上层的【因果一致性】(见 consistency-models)

```

- 它是 [[consistency-models-20260701]] 里**因果一致性**的底层实现工具。
- 它是 [[distributed-systems-core-theories-20260630]] 附录明确 flag 的"待延伸方向"，现在补齐。
- 它回答了一个 CAP/PACELC 没回答的问题：**选了 AP、允许并发写之后，你怎么知道两个写"冲突了"？** —— 答案就是向量时钟。

## 附录：自我思考

### 最反直觉、也最解放的一课：放弃"全局时间"

初学时总想给分布式事件找一个"真实的绝对顺序"。逻辑时钟告诉我：**这个绝对顺序根本不存在，也不需要。** 你真正需要的只是"有因果关系的事件保持顺序"，而并发事件本就没有客观先后。一旦接受"世界是偏序而非全序"，很多分布式设计（因果一致、CRDT、Git 分支）突然就自洽了。

### Lamport 时钟单向性的深意

`a→b ⟹ C(a)<C(b)`，但反过来不行 —— 这个"单向箭头"我一开始觉得是缺陷，后来才明白它精确地划出了逻辑时钟能力的边界：**标量时钟能"保序"，但不能"判因果"。** 想判因果，信息量就不够，必须升级到向量。这是一个"能力和信息量成正比"的漂亮例子：你想区分多少种关系，就得付出多少维度的存储。

### 下一步

- **CRDT（无冲突复制数据类型）**：向量时钟能"检测"冲突，CRDT 则让冲突"自动、正确地合并"，是最终一致性最优雅的落地。
- **一致性哈希与分片**：另一条正交主线，见 [[data-partitioning-and-sharding-20260701]]。
