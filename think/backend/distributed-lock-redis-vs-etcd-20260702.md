## 一、SETNX 单实例锁

用 `SETNX`（set if not exist）插入键值对：Key 已存在返回 False，否则插入成功返回 True。

- 类比**数据库唯一索引**：保证同一个 Key 只存在一份，用"这个 Key 是否存在"表示"是否处于锁定状态"。
- 配 `EXPIRE` 设过期时间，避免持锁进程崩溃后**死锁**。

### ⚠️ 坑 1：SETNX + EXPIRE 两条命令不原子

```
SETNX lock 1      # ← 如果客户端在这两条之间崩溃
EXPIRE lock 30    # ← 这条没执行，锁永不过期 → 死锁
```

**正解：用一条原子命令** `SET key value NX EX seconds`，同时完成"加锁 + 设过期"。

### ⚠️ 坑 2（致命）：单点 / 主从切换会丢锁

SETNX 锁的真正短板不在加锁逻辑，而在**它押注于单个 Redis**。主从架构下的经典事故：

```
1. 客户端 A 在【主库】SET NX 加锁成功
2. 主库还没把锁同步给从库就宕机（Redis 主从是【异步复制】）
3. 从库被提升为新主 —— 新主上根本没有这把锁
4. 客户端 B 加锁成功 —— A、B 同时持锁 ❌ 互斥被破坏
```

根因就是 [[consistency-models-20260701]] 讲的**主从异步复制 = 最终一致**：主库返回成功时，锁可能还没到从库，故障切换后锁"蒸发"。

## 二、RedLock 多实例锁

Redis 作者 Antirez 提出：**不靠复制，靠"多数派"**，专治 SETNX 的单点丢锁。

### 算法

用 **N 个相互独立**的 Redis 实例（通常 5 个），加锁时：

1. 依次向 N 个实例请求加锁（各自 `SET NX EX`）；某个实例不可用就**尽快跳下一个**。
2. 记录**总耗时**，仅当同时满足才算成功：
   - 拿到锁的实例数 **≥ N/2+1**（5 个里至少 3 个）；
   - **总耗时 < 锁的过期时间**（否则锁可能已在某些实例过期，无意义）。
3. 锁的真实有效期 = 设定过期时间 − 加锁耗时。
4. 加锁失败时，**去每一个实例上都释放锁**（含没拿到的，防残留）。

即使挂掉 2 个实例，剩 3 个仍构成多数派，锁不丢——**用多数派替代主从复制，规避单点**。

## 三、SETNX 锁 vs RedLock：区别

| | SETNX 单实例锁 | RedLock 多实例锁 |
|---|---|---|
| 用几个 Redis | 1 个（或 1 主 N 从） | N 个**相互独立**实例（通常 5） |
| 加锁成功条件 | 那 1 个实例 SET NX 成功 | **N/2+1 个**实例都拿到 |
| 解决的核心问题 | 互斥 | **单点故障 / 主从切换丢锁** |
| 复杂度 | 一条命令 | 算耗时 + 多数派 + 时钟依赖 |

> 二者不是并列的两种锁，而是 **RedLock 为修补 SETNX 的高可用短板而生**。

## 四、关键误区：RedLock 的 N 实例 ≠ Redis Cluster

**RedLock 用不了 Redis Cluster，也不能靠一个 DNS 域名连过去。** 两者要解决的问题正交：

| | Redis Cluster（集群） | RedLock 的 N 实例 |
|---|---|---|
| 目的 | **分片**：不同 key 放不同节点 | **冗余**：同一把锁在 N 处各存一份 |
| 节点关系 | 一个整体，有主从/槽迁移 | **完全独立**，无复制、互不知情 |
| 怎么连 | 连一个入口，按 key 路由到某节点 | **显式挨个连 N 个地址** |

### 为什么 DNS / 单入口是错的

给集群配个 DNS 域名、往一个入口发加锁命令：

```
你以为：一条命令 → 锁存到 5 个地方
实际上：集群按 key 的 hash slot，只把锁路由到【其中 1 个】节点
```

→ 花了 5 个节点的钱，**退化成单实例锁**，多数派荡然无存。DNS/Proxy 只会转发到**一个**后端，而 RedLock 的安全性恰恰建立在"客户端亲自向 N 个独立实例分别请求、自己统计"之上。这正是**分片（Cluster）与冗余（RedLock）两条正交主线**的混淆，呼应第 6 篇 [[data-partitioning-and-sharding-20260701]]。

### 正确部署

**N 套相互独立、无复制关系的 Redis master**，客户端代码里显式配置这 N 个地址逐个请求：

```
        ┌─ Redis A (独立 master, 可自带从库做自身HA)
        ├─ Redis B (独立 master)
客户端 ──┼─ Redis C (独立 master)   ← 亲自连全部5个，逐个 SET NX，自己数
        ├─ Redis D (独立 master)
        └─ Redis E (独立 master)
        （5个之间没有主从、没有集群、没有同步）
```

- **不是**一个 6 节点集群里挑 5 个，**是** 5 套独立部署（可跨机房）。
- 每个实例内部**可**配主从做自身高可用，但 5 个实例**互相绝不复制**——一复制就又回到主从异步丢锁的老问题。
- 客户端 SDK（如 Redisson）配的是一个**地址列表**，不是一个域名。

## 五、选型结论

| 场景 | 方案 |
|------|------|
| 绝大多数业务 | **单实例 `SET key val NX EX`** 一条命令，简单可靠 |
| 想要 Redis 高可用锁 | RedLock（但见下方争议，慎用） |
| 要极致正确性（金融、绝不允许双持锁） | **etcd / ZooKeeper** |

### RedLock 的争议（重要）

《DDIA》作者 Martin Kleppmann 专门撰文批评 RedLock：在 **GC 停顿、时钟漂移、进程暂停**下，RedLock 依然可能让两个客户端同时持锁，**并不提供它宣称的安全性**。加之复杂度和成本陡增，性价比很低，多数团队不用。

### 为什么 etcd / ZooKeeper 是"要正确性"时的正解

- 基于 **Raft / ZAB 共识协议**（见 [[raft-consensus-deep-dive-20260630]]），天生强一致，锁不会因故障切换蒸发。
- 提供 **fencing token**（单调递增的版本号）：即使发生进程暂停导致的"过期持锁者"，下游存储也能靠 token 大小拒绝旧请求，从根上防双持锁——这是 Redis 锁难以提供的安全保证。

## 附录：自我思考

### 一条主线：锁的安全性 = 底层一致性模型

三种方案的强弱，本质由**底层存储的一致性模型**决定：

- SETNX 单实例锁弱，是因为它坐在**最终一致**的主从复制上；
- RedLock 想用多数派把一致性抬上去，但没有真正的共识协议兜底，时钟一漂就露馅；
- etcd/ZK 强，是因为它坐在**线性一致**的共识协议上。

所以"用什么做分布式锁"这个问题，答案不在锁本身，而在 [[consistency-models-20260701]] 那条从最终一致到线性一致的光谱——**你的锁最终能落到哪一档，取决于你把它建在哪种一致性之上。**

### 一个容易被"高级方案"迷惑的教训

RedLock 看起来"更高级、更高可用"，很多人会下意识觉得它比单实例锁"更安全"。但事实相反：它更复杂、争议更大、还不一定安全。**复杂度不等于正确性。** 简单业务老老实实用一条 `SET NX EX`，要正确性就直接上专门为协调而生的 etcd——别在中间那个又复杂又不保险的档位上纠结。
