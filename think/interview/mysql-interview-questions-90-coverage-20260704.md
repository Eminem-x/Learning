## 30 秒电梯版（盖住全文也要能背出主线）

MySQL 面试就八条主线：

1. **索引**：InnoDB 用 **B+ 树**，聚簇索引叶子存整行、二级索引叶子存主键（要**回表**）；用好靠**最左前缀 + 覆盖索引 + 索引下推**，失效靠背「函数/隐式转换/`%`前缀/`OR`/范围后失效」。
2. **事务 ACID**：原子性靠 **undo**，持久性靠 **redo**，隔离性靠**锁 + MVCC**，一致性是目的。
3. **隔离级别**：RU/RC/**RR(默认)**/Serializable；RR 靠 **MVCC(快照读) + Next-Key Lock(当前读)** 基本解决幻读。
4. **MVCC**：隐藏列(trx_id, roll_pointer) + **undo 版本链** + **ReadView**，靠「可见性算法」决定读哪个版本；RC 每次读建 ReadView，RR 事务首次读建一次。
5. **锁**：全局/表/行；行锁三形态 = **记录锁 + 间隙锁 + 临键锁**；加意向锁做表/行冲突快速判定；死锁靠 `innodb_deadlock_detect` 回滚小事务。
6. **三大日志**：**redo**(物理、循环写、崩溃恢复)、**undo**(逻辑、回滚 + MVCC)、**binlog**(逻辑、归档 + 主从)；redo 与 binlog 靠**两阶段提交**保证一致。
7. **主从复制**：主库写 binlog → 传给从库 relay log → 从库回放；binlog 三格式(statement/row/mixed)；延迟靠并行复制/半同步缓解。
8. **优化**：`EXPLAIN` 看 type/key/rows/Extra；慢查询靠 slow log + `pcap`；深分页、count、大表 DDL 各有套路。

卡在哪一条，就往对应章节回挖。

## 一、索引（考频 ★★★★★）

### Q1. InnoDB 为什么用 B+ 树而不是 B 树 / 红黑树 / Hash？

**一句话**：B+ 树矮胖（3~4 层扛千万级数据）、非叶子只存索引 → 一次 IO 载入更多 key、叶子链表天然支持范围查询与排序。

**追问链**：
- **vs B 树**：B 树非叶子也存 data，单节点能放的 key 少 → 树更高 → IO 更多；B+ 树的 data 全在叶子，非叶子纯索引更「瘦」，扇出（fan-out）更大。
- **vs 红黑树/AVL**：二叉树高度 log₂N，千万数据约 24 层 → 24 次磁盘 IO，灾难；B+ 树一个节点一个页（16KB），扇出上千，高度只 3~4。
- **vs Hash**：Hash 只能等值 `=`，不支持范围、排序、最左前缀；且有 hash 冲突。InnoDB 有**自适应哈希索引(AHI)**，是引擎自动为热点页建的，不可手动指定。
- **B+ 树一层能放多少？** 页 16KB，假设主键 bigint 8B + 页指针 6B = 14B，非叶子一页约 16384/14 ≈ 1170 个指针；叶子放整行假设 1KB，一页 16 行。3 层 = 1170×1170×16 ≈ **2000 万行**。这是必背的「口算容量」。

### Q2. 聚簇索引 vs 二级索引？回表是什么？

- **聚簇索引(clustered)**：叶子节点存**整行数据**，按主键组织。InnoDB 表本身就是一棵聚簇索引 B+ 树（表即索引）。
- **二级索引(secondary/辅助)**：叶子存**索引列 + 主键值**，不存整行。
- **回表**：走二级索引查到主键 → 再拿主键去聚簇索引查整行，这第二次查找叫回表。
- **为什么二级索引叶子存主键而不是行地址？** 行会因页分裂移动，存地址维护成本高；存主键则聚簇索引自己管理行位置。

### Q3. 主键为什么建议用自增整数、不用 UUID？

- 自增 → 顺序插入，总是追加到 B+ 树最右，**避免页分裂**、页利用率高。
- UUID/无序主键 → 随机插入到中间，频繁**页分裂 + 页移动**，写放大、碎片多。
- UUID 还长（36 字符），二级索引都带主键 → 每个二级索引都变胖。
- 8.0 建议：无自然主键就用自增 bigint 或有序 UUID（UUIDv7 / `UUID_TO_BIN(uuid, 1)` 交换时间位）。

### Q4. 覆盖索引、最左前缀、索引下推、回表——串起来讲

- **覆盖索引(covering index)**：查询字段全在索引里，`Extra: Using index`，**无需回表**。是最重要的优化手段之一。`select id,name from t where name=?`，`(name)` 索引就覆盖了（name 在索引、id 是主键天然带）。
- **最左前缀(leftmost prefix)**：联合索引 `(a,b,c)` 能命中 `a` / `a,b` / `a,b,c`，命中不了 `b` / `c` / `b,c`。`where a=1 and c=3` 只能用到 `a`。
- **范围后失效**：`where a=1 and b>2 and c=3`，`c` 用不上索引（b 是范围，其后的列在索引里无序）。
- **索引下推(ICP, Index Condition Pushdown, 5.6+)**：`Extra: Using index condition`。联合索引 `(name,age)`，`where name like '张%' and age=20`——没有 ICP 时先按 name 回表再过滤 age；有 ICP 时在**索引层就用 age 过滤**，减少回表次数。

### Q5. 索引失效有哪些场景？（必背清单）

1. **函数/表达式包裹索引列**：`where date(create_time)=...`、`where id+1=...`。
2. **隐式类型转换**：`where phone=13800000000`（phone 是 varchar），等价于对列做函数转换。字符集不一致的 join 也同理。
3. **`like '%xx'`** 前缀通配 → 失效；`like 'xx%'` 可用。
4. **`OR` 连接非索引列**：`where a=1 or b=2`，b 无索引 → 全表扫。
5. **联合索引不满足最左前缀**。
6. **`!=` / `<>` / `not in` / `is not null`**（视优化器与数据分布，不绝对）。
7. **优化器认为全表扫更快**（回表行数占比大时，主动放弃索引）——这不算「失效」而是「优化器选择」。

**验证手段**：`EXPLAIN` 看 `type` 是否退化到 `ALL`，`key` 是否为 NULL。

### Q6. 前缀索引？

对长字符串列（如 url、email）只索引前 N 个字符：`index(email(20))`。省空间但**无法用于覆盖索引和排序**，选择性要够（`count(distinct left(col,N))/count(*)` 接近 1）。

## 二、事务与隔离级别（考频 ★★★★★）

### Q7. ACID 分别靠什么实现？

| 特性 | 含义 | 实现 |
|------|------|------|
| **A** 原子性 | 要么全成要么全败 | **undo log**（回滚） |
| **C** 一致性 | 数据满足约束、业务不变量 | 是**目的**，靠 AID + 应用共同保证 |
| **I** 隔离性 | 并发事务互不干扰 | **锁 + MVCC** |
| **D** 持久性 | 提交后不丢 | **redo log**（WAL） |

### Q8. 四种隔离级别 + 各解决什么问题？

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|:--:|:--:|:--:|
| Read Uncommitted | ✗ | ✗ | ✗ |
| Read Committed | ✓ | ✗ | ✗ |
| **Repeatable Read（MySQL 默认）** | ✓ | ✓ | ✓(靠间隙锁) |
| Serializable | ✓ | ✓ | ✓ |

- **脏读**：读到别的事务**未提交**的数据。
- **不可重复读**：同一事务两次读同一行，值变了（别的事务改了并提交）——针对 **update**。
- **幻读**：同一事务两次范围查询，行数变了（别的事务 insert 了并提交）——针对 **insert**。
- **RR 如何解决幻读**：
  - **快照读**（普通 `select`）：靠 MVCC，读的是事务开始时的快照，天然不幻读。
  - **当前读**（`select ... for update`、`update`、`delete`）：靠 **Next-Key Lock（间隙锁+记录锁）** 锁住范围，阻止其他事务插入。
- ⚠️ RR 下幻读**并非 100% 解决**：快照读 + 当前读混用仍可能出现幻读（经典面试陷阱，见 Q11）。

### Q9. 为什么 MySQL 默认 RR 而不是 RC？（Oracle/PG 默认 RC）

历史原因：早期 binlog 只有 **statement 格式**，RC 下会导致主从数据不一致（快照读+当前读顺序问题），必须 RR + 间隙锁才能保证 binlog 复制一致。现在 row 格式已无此问题，很多大厂**线上反而调成 RC**（间隙锁少 → 并发高、死锁少）。

## 三、MVCC（考频 ★★★★★，最容易被追到底）

### Q10. MVCC 的实现原理？完整讲一遍

**三要素**：
1. **隐藏列**：每行有 `DB_TRX_ID`（最后修改的事务 id）、`DB_ROLL_PTR`（指向 undo log 的指针）、`DB_ROW_ID`（无主键时的隐藏行 id）。
2. **undo 版本链**：每次修改把旧值写入 undo log，`roll_pointer` 串成一条**版本链**（从新到旧）。
3. **ReadView**：快照读时生成，含四个字段：
   - `m_ids`：生成 ReadView 时**活跃（未提交）**的事务 id 列表。
   - `min_trx_id`：m_ids 最小值。
   - `max_trx_id`：下一个将分配的事务 id。
   - `creator_trx_id`：当前事务 id。

**可见性算法**（拿版本链某行的 trx_id 判断）：
- `trx_id == creator_trx_id` → 自己改的，**可见**。
- `trx_id < min_trx_id` → 生成 ReadView 前已提交，**可见**。
- `trx_id >= max_trx_id` → 生成 ReadView 后才开始的事务，**不可见**，顺 roll_pointer 找更旧版本。
- `min_trx_id <= trx_id < max_trx_id`：若在 `m_ids` 里 → 未提交，**不可见**；不在 → 已提交，**可见**。

**RC vs RR 的唯一区别**：
- **RC**：**每次快照读**都重新生成 ReadView → 能看到别的事务新提交的 → 不可重复读。
- **RR**：**事务第一次快照读**生成 ReadView，之后一直复用 → 整个事务看到同一快照 → 可重复读。

### Q11. RR 下幻读真的解决了吗？（陷阱题）

没完全解决。反例：
```sql
-- 事务A（RR）
select * from t where id=1;        -- 快照读，空（没这行）
-- 事务B：insert id=1，commit
select * from t where id=1;        -- 快照读，仍然空（MVCC）
update t set v=9 where id=1;        -- 当前读！改到了 B 插入的行
select * from t where id=1;        -- 快照读，突然出现了！幻读
```
原因：`update` 是当前读，会更新最新版本并把该行 trx_id 改成自己 → 后续快照读就可见了。**当前读和快照读混用会「戳破」快照。**

## 四、锁（考频 ★★★★★）

### Q12. InnoDB 锁的分类？

**按粒度**：
- **全局锁**：`flush tables with read lock (FTWRL)`，全库只读，用于全库逻辑备份（mysqldump `--single-transaction` 可避免）。
- **表级锁**：表锁 `lock tables`、**元数据锁 MDL**（DML 加读锁、DDL 加写锁，改表结构时被长事务阻塞的经典事故源）、**意向锁 IS/IX**。
- **行级锁**（InnoDB 特有，**加在索引上**）。

**行锁三形态**（RR 下）：
- **记录锁 Record Lock**：锁单行索引记录。
- **间隙锁 Gap Lock**：锁记录**之间的间隙**（开区间），防插入，解决幻读。间隙锁之间**不冲突**（都是防插入）。
- **临键锁 Next-Key Lock**：记录锁 + 间隙锁，左开右闭 `(x, y]`，是 RR 默认的行锁形式。

**读写属性**：
- **共享锁 S**：`select ... lock in share mode` / `for share`。
- **排他锁 X**：`select ... for update`、`update`、`delete`。

### Q13. 意向锁有什么用？

意向锁是**表级**锁，表示「表内有行被加了行锁」。目的：当某事务想加**表锁**时，不用逐行检查有没有行锁，只需看表上有没有意向锁 → **快速判断冲突**。IS/IX 之间互相兼容，它们只和表级 S/X 冲突。

### Q14. 一条 `update t set v=1 where id=10` 加什么锁？（要分情况）

- **id 是主键**：给 id=10 加**记录锁**（唯一等值，无需间隙）。
- **id 是唯一二级索引**：给二级索引记录 + 对应聚簇索引记录都加记录锁。
- **id 是普通索引**：加 Next-Key Lock（锁住命中记录及左右间隙）+ 前后间隙锁。
- **id 无索引**：**锁全表所有行**（走聚簇索引全扫，每行加锁）——线上大忌，会把并发写全堵死。
- **等值查询命中唯一记录**：Next-Key 退化为记录锁；**等值查询未命中**：退化为间隙锁。

### Q15. 死锁怎么产生、怎么排查、怎么预防？

- **产生**：两事务互相持有对方要的锁，循环等待。经典：A 锁行 1 等行 2，B 锁行 2 等行 1；或两事务**加锁顺序相反**。
- **检测**：InnoDB 默认 `innodb_deadlock_detect=ON`，检测到就**回滚 undo 量最小的事务**（报 `Deadlock found`）；另有 `innodb_lock_wait_timeout`（默认 50s）超时兜底。
- **排查**：`show engine innodb status` 看 `LATEST DETECTED DEADLOCK`；`information_schema.innodb_trx / innodb_locks / innodb_lock_waits`。
- **预防**：① 固定加锁顺序；② 事务尽量短小、及时提交；③ 降低隔离级别到 RC（减少间隙锁）；④ 热点行用队列/乐观锁；⑤ 一次性锁定所需资源。

## 五、三大日志 + Buffer Pool（考频 ★★★★★）

### Q16. redo / undo / binlog 三大日志对比

| | redo log | undo log | binlog |
|--|----------|----------|--------|
| **层** | InnoDB 引擎层 | InnoDB 引擎层 | Server 层 |
| **内容** | 物理日志（某页某位置改成什么） | 逻辑日志（反向操作） | 逻辑日志（原始 SQL / 行变更） |
| **作用** | **崩溃恢复**（持久性，WAL） | **回滚**（原子性）+ **MVCC 版本链** | **归档 + 主从复制** |
| **写法** | 循环写（固定大小，覆盖旧） | 随事务，purge 线程清理 | 追加写（不覆盖） |
| **是否可关** | 不可（引擎核心） | 不可 | 可（但主从/恢复需要） |

### Q17. WAL 是什么？为什么能提升性能？

**Write-Ahead Logging**：改数据前先写 redo log（顺序 IO），再异步刷脏页到磁盘（随机 IO）。核心是**用顺序写换随机写**：redo 追加是顺序 IO 快，脏页刷盘可以攒批、合并、后台慢慢做。崩溃后用 redo 恢复未刷盘的脏页。参见 `../infra/postgresql-wal-replication-and-amplification.md`——PG 的 WAL 是同一套思想。

### Q18. redo log 两阶段提交（2PC）——为什么需要？

一条 update 的提交流程（redo 和 binlog 要保证一致）：
1. 写 redo log，置 **prepare** 状态。
2. 写 binlog。
3. 写 redo log **commit** 状态。

**为什么要两阶段**：redo 和 binlog 是两个独立日志，若不用 2PC：
- 先写 redo 后崩溃（binlog 没写）→ 主库用 redo 恢复有这条，从库没有 → **主从不一致**。
- 先写 binlog 后崩溃（redo 没写）→ 从库有、主库没有 → 不一致。

**崩溃恢复判断规则**：
- redo 是 commit → 直接生效。
- redo 是 prepare → **看 binlog 是否完整**：binlog 完整就提交，不完整就回滚。

### Q19. Buffer Pool / 脏页 / change buffer？

- **Buffer Pool**：InnoDB 内存中缓存数据页/索引页，改数据先改内存页（**脏页**），再由 WAL + 后台线程刷盘。用改进版 **LRU**（冷热分离，midpoint insertion，防全表扫污染热数据）。
- **脏页刷盘时机**：redo 写满、内存不足淘汰脏页、系统空闲、正常关闭。
- **change buffer（写缓冲）**：对**非唯一二级索引**的写操作，若目标页不在内存，先缓存变更，等页被读入时再合并（merge），减少随机 IO。唯一索引不能用（要读页校验唯一性）。写多读少的场景收益大。

### Q20. redo log 的 `innodb_flush_log_at_trx_commit` 与 binlog 的 `sync_binlog`？

- `innodb_flush_log_at_trx_commit`：`1`(默认，每次提交刷盘，最安全) / `0`(每秒刷，崩溃丢 1s) / `2`(写 OS cache，MySQL 崩溃不丢、OS 崩溃丢)。
- `sync_binlog`：`1`(每次提交 fsync，最安全) / `0`(靠 OS) / `N`(攒 N 个)。
- **双 1 配置**（`=1` + `sync_binlog=1`）= 最高安全性，性能代价换不丢数据，金融场景标配。

## 六、主从复制与高可用（考频 ★★★★）

### Q21. 主从复制原理？

1. 主库把变更写 **binlog**。
2. 主库 **log dump 线程**把 binlog 推给从库。
3. 从库 **IO 线程**接收，写入本地 **relay log（中继日志）**。
4. 从库 **SQL 线程**（8.0 多线程）回放 relay log，应用到从库。

### Q22. binlog 三种格式？

- **statement**：记原始 SQL。省空间，但 `now()`/`uuid()`/`limit` 等非确定性函数会主从不一致。
- **row**：记每行变更前后的值。**准确、可靠**，但量大。8.0 默认。
- **mixed**：MySQL 自动判断，确定性用 statement、非确定性用 row。

### Q23. 主从延迟（复制延迟）怎么产生、怎么解决？

**成因**：从库单/少线程回放追不上主库多线程写、大事务、大表 DDL、从库配置弱、从库还要扛读请求。

**解决**：
- **并行复制**：8.0 基于 **WRITESET**（逻辑时钟，判断事务是否冲突，不冲突就并行），比 5.7 的库级并行更细。
- 拆大事务、避免大批量操作。
- 读写分离时，强一致读走主库，或读从库前判断 `seconds_behind_master` / GTID 位点。
- **半同步复制**：主库至少等一个从库 ACK 再返回，降低丢数据风险（不是解延迟，是解一致性）。

### Q24. 异步 / 半同步 / 组复制（MGR）？

- **异步**（默认）：主库写完 binlog 就返回，不等从库 → 主库宕机可能丢已提交数据。
- **半同步**：主库等**至少一个**从库写入 relay log 的 ACK 才返回 → 更安全，牺牲一点延迟。
- **组复制 MGR / InnoDB Cluster**：基于 Paxos 变体，多数派确认，支持自动故障切换，是 8.0 官方高可用方案。

## 七、存储引擎与基础（考频 ★★★）

### Q25. InnoDB vs MyISAM？

| | InnoDB | MyISAM |
|--|--------|--------|
| 事务 | 支持 | 不支持 |
| 锁 | 行锁 | 表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 有（redo） | 无 |
| 索引 | 聚簇索引（叶子存行） | 非聚簇（叶子存行地址） |
| count(*) | 需扫描 | 有计数器，O(1) |
| 适用 | 事务型（默认） | 只读/读多写少（已过时） |

### Q26. `count(*)` / `count(1)` / `count(字段)` / `count(主键)` 谁快？

- InnoDB 中 `count(*)` 官方专门优化，**不比 count(1) 慢**，优化器会选**最小的可用二级索引**扫描（比聚簇索引小、IO 少）。
- `count(字段)`：不统计该字段为 NULL 的行，且若无索引要全表扫。
- 结论：`count(*)` ≈ `count(1)` ≥ `count(主键)` > `count(普通字段)`。**优先 `count(*)`**。
- 精确实时总数很贵时：用 Redis 计数 / 单独统计表（但要处理一致性）。

### Q27. `char` vs `varchar`？`datetime` vs `timestamp`？

- **char(N)**：定长，右补空格，适合定长如手机号 MD5；**varchar(N)**：变长，存实际长度 + 1~2 字节长度头，适合长度波动大的。
- **datetime**：8 字节，范围大（1000~9999 年），不带时区，存什么读什么；**timestamp**：4 字节，1970~2038，**带时区转换**，受 `time_zone` 影响，有 2038 问题。跨时区业务偏向 datetime + 应用层统一 UTC。

### Q28. 三大范式 & 何时反范式？

- 1NF：字段原子不可分；2NF：非主键完全依赖主键（消除部分依赖）；3NF：非主键不依赖其他非主键（消除传递依赖）。
- **反范式**：为了查询性能故意冗余字段（如订单表冗余商品名），避免 join，用一致性维护成本换读性能。互联网高并发场景常见。

## 八、SQL 优化与排障（考频 ★★★★）

### Q29. `EXPLAIN` 关键字段怎么读？

- **type**（访问类型，从好到差）：`system > const > eq_ref > ref > range > index > ALL`。至少要到 `range`，`ALL` 全表扫要警惕。
- **key**：实际用的索引；**key_len**：用了索引的多少字节（判断联合索引用到第几列）。
- **rows**：预估扫描行数（越小越好）。
- **Extra**：`Using index`(覆盖索引，好)、`Using index condition`(索引下推)、`Using where`(存储引擎返回后 server 层过滤)、`Using filesort`(额外排序，要优化)、`Using temporary`(用临时表，group by/distinct 常见，要优化)。

### Q30. 慢查询怎么定位和优化？

1. **开慢查询日志**：`slow_query_log=ON`，`long_query_time=1`（超 1s 记录）。
2. 用 `mysqldumpslow` / `pt-query-digest` 聚合分析。
3. `EXPLAIN` / `EXPLAIN ANALYZE`（8.0，真实执行统计）看执行计划。
4. **优化方向**：加/改索引（覆盖、联合、避免失效）、改写 SQL（消除 filesort/临时表）、拆分大查询、避免 `select *`、`limit` 深分页优化。
5. `show profile` / `performance_schema` 看各阶段耗时。

### Q31. 深分页 `limit 1000000, 10` 为什么慢？怎么优化？

慢因：要扫描并丢弃前 100 万行（回表 100 万次）再取 10 行。

优化：
- **游标/书签法（推荐）**：`where id > 上次最大id order by id limit 10`，利用主键有序，O(1) 定位。
- **延迟关联（子查询覆盖索引）**：`select * from t join (select id from t order by id limit 1000000,10) x using(id)`，先在**二级索引上**分页拿主键（覆盖索引不回表），再回表 10 次。

### Q32. 大表加索引 / 改字段（DDL）会锁表吗？怎么做？

- 8.0 支持 **Online DDL**（`ALGORITHM=INPLACE, LOCK=NONE`），加二级索引等操作基本不阻塞 DML，但仍有短暂 MDL 锁。
- **风险**：长事务持有 MDL 读锁 → DDL 拿不到 MDL 写锁 → 后续所有 DML 全被堵（雪崩）。改表前先 `show processlist` 查长事务。
- 生产大表 DDL 用 **gh-ost / pt-online-schema-change**：建影子表 + 触发器/binlog 同步增量 + 原子 rename，全程不锁。

### Q33. 分库分表？

- **垂直拆分**：按业务拆库、按列拆表（大字段/冷字段分离）。
- **水平拆分**：按行拆，路由键 hash / range / 一致性 hash。
- **问题**：跨库 join（改成应用层聚合/冗余）、分布式事务（见能力地图第 8 格）、**全局唯一 ID**（雪花算法 Snowflake / 号段 / Redis incr）、跨分片分页排序（归并）、扩容 rehash。
- **中间件**：ShardingSphere、Vitess、MyCat。
- **原则**：能不拆就不拆，先分区表/读写分离/上缓存，单表超千万或 IO 撑不住再考虑。

### Q34. 一条 SQL 从连接到返回经历了什么？

**连接器**（鉴权、连接管理）→ **查询缓存**（8.0 已删除）→ **分析器**（词法/语法解析）→ **优化器**（选索引、定 join 顺序、生成执行计划）→ **执行器**（校验权限、调引擎接口）→ **存储引擎**（InnoDB 取数据，走 buffer pool / 磁盘）→ 返回。

## 九、其余高频小题（快问快答）

- **为什么不建议 `select *`**：多余字段网络/内存开销、破坏覆盖索引、表结构变更易出错。
- **NULL 的坑**：`= NULL` 永远为假（要用 `is null`）；`count(col)` 不计 NULL；NULL 参与运算结果为 NULL；索引可存 NULL 但影响选择性。
- **`in` vs `exists`**：小表驱动大表原则；`in` 适合子查询结果集小，`exists` 适合外表小。现代优化器差异已不大，看执行计划。
- **truncate vs delete vs drop**：delete（DML，逐行、可回滚、走事务、不释放空间）；truncate（DDL，清空、不可回滚、重置自增、快）；drop（删表结构）。
- **乐观锁 vs 悲观锁**：悲观锁 = `for update`（先锁再改）；乐观锁 = 版本号/CAS（`update ... where version=旧值`），冲突少时性能好。
- **自增主键用完了会怎样**：报主键冲突（bigint 基本用不完；int 21 亿要警惕）。无主键的隐藏 row_id 是全局 6 字节，用完会回绕覆盖数据（罕见但存在）。
- **联合索引 `(a,b)` 能否优化 `order by b`**：不能直接（需 a 有等值条件才行，`where a=1 order by b` 可以）。
- **一个事务里的自增值回滚会填补吗**：不会，自增值不回滚（保证唯一，可能有空洞）。
