## 30 秒电梯版(盖住全文也要能讲清主线)

一句话主线:**主从 / 主备 / 读写分离是同一套 binlog 复制机制的不同"用途",一致性不是宿命而是一条可花性能买的光谱。**

三个必须张口就来:
1. **主从、主备、读写分离底层是不是同一套?** 是。都是 `主库 binlog → 从库 relay log → 从库重放` 这一套,区别只在"副本平时服不服务、挂了顶不顶上"——从库对外读(读写分离)/ 备库热备容灾(主备)/ 离线喂数仓。**没有第二套机制。**
2. **"MySQL 最终一致"是铁律吗?** 不是,只对**默认的异步复制**成立。往上是**半同步**(等从库 ACK)、**组复制 MGR**(Paxos 多数派,准强一致)——花延迟/性能换一致性,是 CAP 的活例子。
3. **同样"最终一致",坑随用途变**:读写分离怕**读旧**(复制延迟→读到旧数据);主备容灾怕**丢新**(主库崩溃切换,没传过去的 binlog 丢了)。根子都是异步,暴露面不同。

## 一、核心澄清:三个词,同一套机制,不同角色

最容易混的点——以为"主备"和"读写分离"是两种技术。**不是,是同一技术的两种用途。**

```
                 binlog 复制机制(唯一的一套底层)
                 主库 binlog → 从库 relay log → 从库重放
                              │
          ┌───────────────────┼───────────────────┐
     副本拿来"扛读"        副本拿来"容灾"        副本拿来"分析"
          │                   │                   │
     读写分离              主备(HA)            离线从库
     从库【对外读】       备库【平时不服务】     喂数仓/大数据
     主写从读              主挂了切换顶上          不对外
```

| 叫法 | 强调什么 | 副本平时干嘛 | 主库挂了 |
|---|---|---|---|
| **主从(master-slave)** | 复制动作 / 从库对外读 | 分摊读流量(读写分离) | 视配置切换 |
| **主备(master-standby)** | 高可用容灾 | **热备份,通常不对外服务** | **切换顶上(failover)** |
| **读写分离** | 扩读性能 | 从库承接 `SELECT` | — |

> **直接回答"主备还是 binlog 同步吗":是,和主从同一套复制,没有第二套机制。** 差的不是"怎么同步",是"副本这个用途"。"不是读写库"说的正是:备库平时闲着容灾,不像读写分离的从库那样对外扛读。

## 二、底层机制:三个线程 + relay log

不管叫主从还是主备,同步链路都是这条(记住"1 推 2 拉 3 放"):

```
  主库                              从库
  ┌──────────────┐                ┌──────────────────────────────┐
  │ 事务提交       │                │ IO 线程 ── 收 event → relay log │
  │ 写 binlog      │  ── 网络 ──►   │              (中继日志)          │
  │ dump 线程 推送  │                │ SQL 线程 ── 读 relay log → 重放  │
  └──────────────┘                └──────────────────────────────┘
     ① dump thread                    ② IO thread   ③ SQL thread(可并行)
```

- **① 主库 dump 线程**:把 binlog event 推给从库(每个从库一个 dump 线程)。
- **② 从库 IO 线程**:接收 event,原样落到 **relay log(中继日志)**。
- **③ 从库 SQL 线程**:读 relay log,**重放**变更到从库数据。8.0 默认**并行重放**(基于 group commit 的 LOGICAL_CLOCK / WRITESET),缓解延迟。

> **⚠️ 澄清:relay log 是「名词」不是「动词」。** 它是从库上一组**实实在在的物理文件**(`<host>-relay-bin.00000x`),内容基本是主库 binlog event 在从库的本地副本;**不是**「回放」这个动作。回放/重放是 SQL 线程**读这份文件去执行**的过程。名词(文件) vs 动词(应用),别混。
>
> **为什么要这份中间文件(而不是收到就直接执行)?** 为了**解耦「收」和「用」两个速度**:IO 线程只管快速拉、落成 relay log(网络快就跑满,不被回放拖累);SQL 线程慢慢读 relay log 重放(回放慢也不阻塞接收)。这正是复制延迟的常见成因——relay log 已收到(IO 快),但 SQL 线程还没重放完(见第五节「收到≠重放」陷阱)。
>
> relay log 重放完的部分会被**自动清理**(`relay_log_purge=ON` 默认开),是个过路的中转站,不像 binlog 长期堆着。
>
> **三份日志别混**:binlog(主库 Server 层,复制源头)/ relay log(**从库** IO 线程写,待重放的 binlog 副本)/ redo log(各自本机 InnoDB,崩溃恢复,与复制无关)。

两个关键工程点(面试加分):
- **GTID(全局事务 ID,5.6+)**:每个事务一个全局唯一 ID,替代"binlog 文件名 + 位点"。切换主库、找同步点、防重放全靠它,是现代复制的标配。
- **并行复制**:早期 SQL 线程单线程重放是延迟主因;5.7 LOGICAL_CLOCK、8.0 WRITESET 让从库多线程重放,显著降延迟。

## 三、一致性光谱:异步 / 半同步 / 组复制

"MySQL 最终一致"只对**默认异步**成立。复制其实是一条可选的光谱——**嫌弱就加同步性,拿延迟换一致性**(格 8 CAP 的具体落地):

| 模式 | 主库提交时等不等从库 | 一致性 | 丢数据风险 | 典型用途 |
|---|---|---|---|---|
| **异步 async(默认)** | 不等,自己提交完就返回 | **最终一致** | 主库崩且 binlog 没传到 → **丢** | 读写分离、离线从库 |
| **半同步 semi-sync** | 等**≥N 个**从库 ACK 收到 binlog 才返回(默认 N=1) | 准强一致 | 大幅缩小丢数据窗口 | **主备容灾**首选 |
| **组复制 MGR** | 基于 Paxos 变体,**多数派**认证通过才提交 | **准强一致**(可配) | 几乎不丢已提交事务 | 金融级高可用 |

- **半同步**是插件(`rpl_semi_sync`),超时(`rpl_semi_sync_master_timeout`)会**退化回异步**保可用——所以它不是"全同步",是"尽量同步"。
- **MGR**是"虚拟同步":事务要过组认证(多数派)才能提交,冲突自动检测;但**其它节点的"应用"仍是异步的**(见第五节的"收到≠重放"陷阱)。

## 四、半同步的两种时机:AFTER_SYNC vs AFTER_COMMIT(防丢数据必考)

半同步"在哪一步等从库 ACK",直接决定会不会丢已提交数据:

| 时机 | 顺序 | 风险 |
|---|---|---|
| **AFTER_COMMIT**(老,5.5/5.6) | 主库**先在引擎提交** → 再等从库 ACK → 返回客户端 | 提交后 ACK 前,**别的会话已能读到**;若主库此刻崩,这条"已被别人读到"的事务可能在从库**丢失** → 幻读式不一致 |
| **AFTER_SYNC**(默认 5.7+,"无损复制") | 主库写 binlog → **先等从库 ACK** → 再在引擎提交 → 返回 | 客户端见到提交时**从库一定已收到**;主库崩溃**不丢已提交事务** ✅ |

> 结论:**主备容灾要防丢数据,用增强半同步 AFTER_SYNC(无损复制)。** 这也是"半同步"能当容灾方案的底气。

## 五、最关键洞察:一致性"问题"随用途而变

同样是异步"最终一致",在读写分离和主备容灾里坑长得**完全不同**——这是本篇最值钱的一点:

| 用途 | 副本干嘛 | "最终一致"具体坑成啥样 | 缓解手段 |
|---|---|---|---|
| **读写分离** | 从库**对外读** | **复制延迟 → 读到旧数据**:刚写主库立刻读从库,可能读到旧值 | 强制读主库、按 GTID 等从库追上再读、降低复制延迟(并行复制) |
| **主备容灾** | 备库**平时不服务** | **切换丢数据**:主库崩时没传到备库的 binlog 丢了 | 无损半同步(AFTER_SYNC)、双一、MGR |

> 一句话:**读写分离怕"读旧"(延迟),主备怕"丢新"(切换窗口)。** 机制一样,风险面不一样——这正是你直觉里"主备和读写库不一样"的正确来源。

**⚠️ 一个高频陷阱:半同步保证的是"从库收到(relay log)",不是"从库重放"。** 所以即便开了半同步,**从库上读仍可能读到旧数据**——因为 SQL 线程还没把 relay log 应用上去。要在从库读到自己刚写的数据(read-your-writes),得:
- 用 `WAIT_FOR_EXECUTED_GTID_SET(gtid)` 等这条事务在从库**重放完**再读;或
- MGR 配 `group_replication_consistency = AFTER / BEFORE`(8.0 的一致性级别)。

"收到"和"重放"是两件事——这一句能挡住"开了半同步为什么还读到旧数据"的追问。

## 六、缓解手段速查

| 想解决 | 手段 |
|---|---|
| 减少切换丢数据 | 增强半同步 AFTER_SYNC、`sync_binlog=1`+`trx_commit=1`(双一)、MGR |
| 减少复制延迟 | 并行复制(8.0 WRITESET)、大事务拆小、从库硬件跟上 |
| 读到自己刚写的(RYW) | 强制读主库、`WAIT_FOR_EXECUTED_GTID_SET`、MGR AFTER |
| 切换自动化/防脑裂 | GTID + MHA / Orchestrator / MGR 多数派选主 |

## 七、自测题(盖住答案,先自己讲一遍)

<details>
<summary>1. 主从、主备、读写分离是三种技术吗?底层同不同?</summary>

同一套 binlog 复制机制(主库 binlog→从库 relay log→重放),没有第二套。区别只在副本用途:读写分离=从库对外扛读;主备=备库热备容灾、平时不服务、主挂顶上;离线从库=喂数仓。
</details>

<details>
<summary>2. 复制链路的三个线程各干嘛?relay log 是什么?</summary>

主库 dump 线程推 binlog event;从库 IO 线程收 event 写 relay log(中继日志);从库 SQL 线程读 relay log 重放(8.0 默认并行)。relay log = 从库暂存主库 binlog 的中转日志。
</details>

<details>
<summary>3. "MySQL 最终一致"是铁律吗?一致性光谱有哪几档?</summary>

只对默认异步成立。光谱:异步(最终一致,可能丢)→ 半同步(等从库 ACK 收到,准强一致,主备首选)→ MGR(Paxos 多数派认证,准强一致,金融级)。花延迟/性能换一致性。
</details>

<details>
<summary>4. 半同步 AFTER_SYNC 和 AFTER_COMMIT 区别?哪个防丢数据?</summary>

AFTER_COMMIT:先引擎提交再等 ACK,提交后 ACK 前别人已能读,主库崩可能丢这条(幻读式不一致)。AFTER_SYNC(5.7+ 默认,无损复制):先等 ACK 再提交,客户端见提交时从库一定已收到,不丢已提交事务。容灾用 AFTER_SYNC。
</details>

<details>
<summary>5. 读写分离和主备,"最终一致"暴露的坑有何不同?</summary>

读写分离怕"读旧":复制延迟导致从库读到旧数据。主备怕"丢新":主库崩溃切换时没传到备库的 binlog 丢失。根子都是异步复制,风险面不同。
</details>

<details>
<summary>6. 开了半同步,为什么从库读还可能读到旧数据?</summary>

半同步保证的是从库"收到(写入 relay log)",不是"重放(SQL 线程应用)"。SQL 线程还没应用时读就是旧的。要 RYW 需 WAIT_FOR_EXECUTED_GTID_SET 等重放完,或 MGR AFTER 一致性级别。
</details>

**毕业标准**:能白板画出"一套机制三种用途"的分叉图;能脱稿讲三线程复制链路 + relay log;能说清一致性光谱三档 + 半同步两时机;能区分"读写分离怕读旧 / 主备怕丢新",并解释"收到≠重放"这个陷阱。
