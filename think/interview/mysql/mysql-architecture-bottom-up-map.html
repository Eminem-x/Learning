MySQL 自底向上架构 · 八层认知地图

一摞有依赖的层，不是一堆并列的名词 —— 认知要自底向上搭，还要分清「包含」与「并列」。

一句话把八层串起来 数据按「表空间→页」摆在磁盘，页组织成 B+树 当 索引；读写先进 Buffer Pool 内存页；改动靠 undo 存旧值、redo 保证不丢、锁 + MVCC 管并发；提交时 redo 和 Server 层的 binlog 用 2PC 对齐、binlog 喂给从库；这一切之上，优化器 决定怎么查、你用 EXPLAIN 验证。

两条对称轴（记住这两条，整张图就立起来了）

磁盘侧 vs 内存侧

第 1~3 层（表空间 / B+树 / 索引）是数据在磁盘怎么摆；第 4~5 层 Buffer Pool 是数据在内存怎么缓存。WAL、脏页、trx_commit 全建立在「先改内存页、后台刷盘」这条桥上。

盒子内 vs 盒子外

第 1~5 层全在 InnoDB 盒内（只救本机）；第 6 层 binlog 在 Server 层（跨引擎、喂从库）。2PC 就是缝合这条边界的针 —— 换成 MyISAM，盒内的 MVCC/redo/undo/行锁全没了。

三条审计红线（平铺背名词最常犯的维度错位）

①

InnoDB 是「盒子」，不是和 index/锁/MVCC 并列的「一层」

index / 锁 / MVCC / undo / redo 全在盒内，只有 binlog 在盒外。它是第 1~5 层的容器边界，不是某一横层。

②

undo 垫在 MVCC 下面 —— 别把「三大 log」捆成一块

三者层级散开：undo 是 MVCC 和回滚的地基（排 MVCC 之下）、redo 管持久性、binlog 在 Server 层（不属 ACID）。捆一块恰恰割裂了 undo→MVCC 依赖。

③

锁 与 MVCC 是并列的两套并发控制，不是上下层

锁管写写冲突 / 当前读（UPDATE、SELECT…FOR UPDATE），MVCC 管读写不阻塞 / 快照读（普通 SELECT）。RR 防幻读 = 快照读(MVCC) + next-key 锁(当前读)，两手都要。
