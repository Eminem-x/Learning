## 30 秒电梯版(盖住全文也要能讲清主线)

一句话主线:**「列在索引里(存着)」≠「列能用来定位(seek)」——这一句能解开 ICP、最左前缀、`c=3` 为什么半命中三个谜。**

```
一个索引列有两种用法,别混:
  ① 定位/seek(访问):靠 B+ 树有序结构跳位、缩小扫描范围
       └ 前提:该列在【当前上下文】必须「连续有序」
       └ 一旦前面出现范围列(b>2),它右边的列(c)就失序 → 定位到此为止
  ② 过滤/filter:逐条比对索引里存的值,不满足就跳过
       └ 前提:该列【只要存在索引里】即可,跟顺序无关
       └ 这就是 ICP(索引条件下推):在存储引擎层、回表前就地刷掉
```

三个必须张口就来:
1. **`WHERE a=1 AND b>2 AND c=3`(索引 abc)命中到哪?** 定位用到 `a=1 AND b>2`(`key_len` 只含 a、b);`c=3` 定位不了,但走 ICP 在索引上过滤,`Extra` 显示 `Using index condition`。
2. **为什么范围列后面的列定位失效?** 联合索引按 `(a,b,c)` 字典序排,`b` 一旦变成范围(跨多个 b 值),`c` 在整段里反复重来、不连续 → 树没法再用 c 往下跳。
3. **ICP 靠什么成立?** 靠"c 就在索引叶子里存着"——存着 → 能过滤免回表;但"存着"不代表"能定位"。

## 一、核心误解:「在索引里」≠「能定位」

最常卡人的一句疑问:「c 不是已经在索引节点里了吗,为什么不算命中?」——把**两种不同能力**当成了一种:

| 能力 | 干什么 | 前提条件 | 术语 / EXPLAIN |
|---|---|---|---|
| **① 定位 / seek(访问)** | 靠 B+ 树有序结构**直接跳到目标位置,缩小扫描范围** | 该列在"当前上下文里"必须**连续有序** | `ref` / `range` |
| **② 过滤 / filter** | 把条件**逐条比对索引里存的值**,不满足就跳过 | 只要该列**存在索引里**即可,跟顺序无关 | ICP → `Using index condition` |

> **c=3 用不了能力①(定位),但用得上能力②(过滤),而能力②恰恰就是 ICP。** 所以 c 不是"没用",是"没法定位,但能过滤"。你那句"key 不是在节点里了吗",问的其实就是 ICP 的前提。

## 二、联合索引长什么样,为什么范围列打断定位

联合索引 `(a,b,c)` 的叶子,按 **`(a,b,c)` 字典序**排:先比 a、a 相同再比 b、b 相同再比 c。看一份具体数据(聚焦 a=1),这就是叶子里真实的物理顺序:

```
索引叶子的排列顺序(= ORDER BY a,b,c):
   (1,1,1)
   (1,1,3)
   (1,2,2)
 ┌ (1,3,1)     ← a=1 AND b>2 从这里开始
 │ (1,3,3)  ✓c=3
 │ (1,4,3)  ✓c=3      b>2 的这一段是【连续】的一整块 ✅
 │ (1,5,1)
 └ (1,5,3)  ✓c=3
```

- **`a=1`(等值)+ `b>2`(范围)→ 能定位**:满足 `a=1 AND b>2` 的记录在叶子里是**连续的一整块**,树一跳跳到 `(1,3,1)`,往后顺扫即可。
- **`c=3` → 定位不了**:那三个 `✓c=3` 分别在 b=3、4、5,**被 c≠3 的行(1,5,1 等)隔开,不是连续的一块**。因为 c 只在"b 固定时"才有序;`b>2` 跨了多个 b 值,c 在整段里**反复重来**(每个 b 内部各自从小排到大),没有全局顺序 → 树用不了 c 再往下跳。

> **范围列(`b>2`)是最左前缀的"刹车":** 它自己能定位,但它**右边的列(c)从此丧失"连续有序"前提,只能降级成"过滤",不能再"定位"。** 这就是"联合索引最多用到第一个范围列为止"的物理原因。

**对照记牢:是范围打断了 c,不是 c 本身有问题。** 若查询是 `a=1 AND b=2 AND c=3`(**三个都等值**),b 是定值不是范围,c 在 `a=1,b=2` 内部连续有序 → 三列全能定位,`key_len` 覆盖 a+b+c,这才叫"完全命中"。

## 三、ICP 是什么(Index Condition Pushdown,索引条件下推)

MySQL **5.6** 引入的优化。拆名字:

- **Index Condition**:能在**索引记录**上就地判断的条件(条件里的列都在索引中)。
- **Pushdown**:把这个判断从 **Server 层** 下推到 **存储引擎(InnoDB)层** 去做。

**没有 ICP 时(5.6 之前)**,`c=3` 这种"定位不了但列在索引里"的条件:

```
InnoDB:用 a=1 AND b>2 定位 → 每条都【回表】捞整行 → 交给 Server
Server:再逐行判断 c=3,不满足的【白回表了】丢掉
```

痛点:`(1,3,1)`、`(1,5,1)` 这些 c≠3 的行,**c 就在索引里、一眼能刷掉,却非要先回表捞整行再丢**,回表(随机 IO)全浪费。

**有了 ICP**,`c=3` 被下推给 InnoDB,扫描索引时**就地拿叶子里存的 c 值判断**:

```
InnoDB:用 a=1 AND b>2 定位 → 扫索引时【先在索引上判断 c=3】
        c≠3 直接跳过(不回表!)→ 只有 c=3 的才回表捞整行 → 交给 Server
```

省掉了 `(1,3,1)`、`(1,5,1)` 的无效回表。

> **ICP 能成立的唯一原因,正是"c 就在索引节点里"。** 存着 → 能过滤;只是"存着"不等于"能定位"。ICP 把过滤从 Server 层挪进引擎层,少回表、少传数据,是"能力②"的工程化落地。

## 四、三层递进 + EXPLAIN 验证

同一个 `c=3`,在三种情形下待遇不同,`Extra` 一眼区分:

| 阶段 | 谁做 | c=3 怎么处理 | EXPLAIN Extra |
|---|---|---|---|
| 能力① 定位 | InnoDB 树结构 | 用不上(b>2 后失序) | —(体现在 `key_len` 只含 a、b) |
| 能力② 过滤·有 ICP | InnoDB 在索引上 | 就地刷掉,免回表 | **`Using index condition`** |
| 无 ICP(旧/关闭) | Server 回表后 | 回表后才刷,浪费回表 | `Using where` |
| 覆盖索引(不取表外列) | 无需回表 | 索引内解决 | `Using index` |

动手验证:

```sql
CREATE TABLE t (
  id INT PRIMARY KEY AUTO_INCREMENT,
  a INT NOT NULL, b INT NOT NULL, c INT NOT NULL,
  d VARCHAR(32),                       -- 不在索引里的列,故意制造回表
  KEY idx_abc (a,b,c)
);

EXPLAIN SELECT * FROM t WHERE a=1 AND b>2 AND c=3;
```

盯两个字段:

- **`key_len`**:只会是 `a+b = 4+4 = 8`(int NOT NULL 各 4 字节),**不含 c 的 4 字节** → "c 没参与定位"的铁证(`key_len` 只统计用于 seek 的前缀)。
  - 补:列可空 `+1`;`varchar(n)` utf8mb4 记 `n*4 + 2`(长度前缀)`+1`(可空)。
- **`Extra`**:出现 **`Using index condition`** → `c=3` 走了 ICP。
  - 若 `SELECT a,b,c`(不取 d)→ 变 **`Using index`**(覆盖索引,连回表都免)。
  - 关掉 ICP 再跑对比:`SET optimizer_switch='index_condition_pushdown=off';` → Extra 退回 **`Using where`**。ICP 的作用立刻具象。

## 五、动手实验:亲眼看到 abc 索引的形态

### 简单版(强烈推荐,30 秒,无需任何工具)

**联合索引 `(a,b,c)` 的叶子顺序 = `SELECT ... ORDER BY a,b,c`。** 直接用 SQL 就能"看到"索引里数据的排列:

```sql
-- 灌入第二节那份数据后:
-- 这就是 idx_abc 叶子里记录的物理顺序(带主键 id = 二级索引叶子实际存的东西)
SELECT a, b, c, id FROM t FORCE INDEX(idx_abc) ORDER BY a,b,c;
```

跑出来那张表,**每一行就是索引叶子里的一条记录**(二级索引叶子存的正是 `索引列(a,b,c) + 主键 id`)。你会亲眼看到 `c=3` 的行在 `b>2` 段里**跳着出现**——为什么定位不了,一目了然。**先做这个。**

### 硬核版(innodb_ruby,想看物理字节再做)

innodb_ruby **能** dump 二级联合索引,关键是**对着 `idx_abc` 这棵二级索引树跑,而不是主键树**。之前对 `-r PRIMARY`(聚簇索引)跑当然看不到 abc——聚簇叶子存的是整行、按 id 排。改成按索引名:

```bash
innodb_space -f <datadir>/test/t.ibd space-page-type-regions        # 每页角色
innodb_space -f <datadir>/test/t.ibd -r idx_abc index-recurse       # ★ 递归打印 idx_abc 这棵树
```

`index-recurse idx_abc` 把叶子里每条 `(a,b,c,id)` **按序打印**,和"简单版"完全一致,只是这次从**真实 `.ibd` 字节**解析。**认知增量不大**——它证明的东西简单版已让你看见,只多一层"物理文件也验过"的踏实。按性价比:**简单版必做,innodb_ruby 归到"想深挖的周末项目"**(详见 [四棵树 §8.E](./tree-structures-bplus-btree-rbtree-20260708.md) 的取舍原则)。

## 六、延伸:ICP 的边界与最左前缀全景

### 6.1 最左前缀:索引 `(a,b,c)` 能定位哪些查询

| 查询条件 | 能定位的前缀 | 说明 |
|---|---|---|
| `a=1` | a | ✅ |
| `a=1 AND b=2` | a,b | ✅ |
| `a=1 AND b=2 AND c=3` | a,b,c | ✅ 全命中 |
| `a=1 AND b>2 AND c=3` | a,b | c 走 ICP 过滤(本篇主线) |
| `a=1 AND c=3` | a | b 缺失,c 断层,只能定位 a;c 走 ICP 过滤 |
| `b=2` / `b=2 AND c=3` / `c=3` | 无 | ❌ 跳过最左列 a,整棵索引用不上定位 |
| `ORDER BY a,b,c` | — | ✅ 直接利用叶子有序,免 filesort |

一句话:**定位能力从最左列起、连续吃到"第一个非等值(范围)列"为止;断层或跳列之后的列,最多靠 ICP 过滤。**

### 6.2 ICP 的边界(面试追问点)

- **只对二级索引有意义**:聚簇索引叶子本就是整行,谈不上"回表",ICP 主要收益在避免二级索引的无效回表。
- **只能下推"列在索引里"的条件**:`d`(不在 idx_abc 里)这类条件下推不了,仍在 Server 层回表后过滤(`Using where`)。
- **下推不了的情形**:条件引用**子查询**、**存储函数/触发器**(引擎层无法执行)、部分虚拟生成列等。
- **和覆盖索引的区别**:覆盖索引是"要的列全在索引里 → 根本不回表(`Using index`)";ICP 是"仍要回表,但先在索引上把不合格的刷掉 → 减少回表次数(`Using index condition`)"。二者都利用"列在索引里",但一个免回表、一个减回表。

## 七、自测题(盖住答案,先自己讲一遍)

<details>
<summary>1. 「列在索引里」和「列能用来定位」是一回事吗?</summary>

不是。定位(seek)要求该列在当前上下文连续有序;过滤(filter)只要求该列存在索引里。范围列右边的列失去连续有序 → 不能定位,但仍能过滤(ICP)。
</details>

<details>
<summary>2. `WHERE a=1 AND b>2 AND c=3`(索引 abc)命中到哪?key_len 和 Extra 各是什么?</summary>

定位用到 a=1(ref)+ b>2(range),`key_len` 只含 a、b(int 各 4B = 8)。c=3 定位不了,走 ICP 在索引上过滤,`Extra=Using index condition`。
</details>

<details>
<summary>3. 为什么 b>2 之后 c=3 就不能定位了?</summary>

联合索引按 (a,b,c) 字典序排,c 只在 b 固定时才有序。b>2 跨多个 b 值,c 在整段里反复重来、不连续成块,B+ 树无法用 c 再往下跳。若 b=2(等值),c 在 a,b 固定内连续有序,就能定位。
</details>

<details>
<summary>4. ICP 是什么?靠什么成立?省了什么?</summary>

Index Condition Pushdown(5.6+):把"列在索引里但不能定位"的条件从 Server 层下推到 InnoDB,在扫描索引时就地用叶子存的值过滤。靠的是"该列就存在索引里"。省掉不合格行的无效回表(随机 IO)。
</details>

<details>
<summary>5. Using index condition / Using where / Using index 三者区别?</summary>

`Using index condition`=ICP,在索引上过滤后仍回表;`Using where`=Server 层(回表后或无索引)过滤;`Using index`=覆盖索引,要的列全在索引里,完全不回表。
</details>

<details>
<summary>6. 怎么不用任何工具就"看到"联合索引 (a,b,c) 的排列?</summary>

`SELECT a,b,c,id FROM t FORCE INDEX(idx_abc) ORDER BY a,b,c;`——二级索引叶子按 (a,b,c) 字典序存「索引列+主键」,ORDER BY a,b,c 的输出就是叶子物理顺序。
</details>

<details>
<summary>7. 索引 (a,b,c),查询 `b=2 AND c=3` 能用上索引定位吗?</summary>

不能。跳过了最左列 a,整棵索引无法用于定位(可能全表扫或走别的索引)。最左前缀必须从最左列 a 起、连续。
</details>

**毕业标准**:能在白板上①用一份具体数据画出 (a,b,c) 叶子的字典序,指出 c=3 在 b>2 段里"跳着出现"故不能定位;②讲清 ICP 是什么、靠"列在索引里"成立、省了无效回表;③说出 `a=1 AND b>2 AND c=3` 的 `key_len` 只含 a、b 且 `Extra=Using index condition`,并区分 `Using index condition / Using where / Using index`。

## 附录:自我思考
