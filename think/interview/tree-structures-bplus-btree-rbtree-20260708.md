## 30 秒电梯版(盖住全文也要能讲清主线)

一句话主线:**这四棵树是「有序数据动态增删查」的四代解法,主线是对抗 BST 退化 + 适配存储介质。**

```
BST 会退化成链表(O(n))
  → 加"平衡"约束 → 平衡二叉树/AVL(高度差≤1,查最快,旋转贵)
  → 放松平衡     → 红黑树(弱平衡,增删更快,内存容器首选)
  → 二叉改多叉   → B 树(为磁盘压矮树,减少 IO)
  → B 树再改良   → B+ 树(数据只在叶子 + 叶子链表,数据库索引终选)
```

三个"为什么"必须张口就来:
1. **数据库为什么不用红黑树用 B+ 树?** 二叉扇出小、树高、IO 多;B+ 多叉压矮树,叶子链表天然支持范围查/排序。
2. **B 树 vs B+ 树?** B+ 内部节点不存数据(更瘦→更矮)、叶子双向链表(范围快)、查询深度一致(稳)。
3. **为什么 AVL 少见红黑树多?** AVL 平衡太严旋转频繁;红黑树弱平衡,查改综合最优。

## 一、坐标:它们都在解决同一个问题

所有这些树解决的是同一件事:**有序数据的动态增删改查**,并保证操作稳定在 `O(log n)`,不退化成链表的 `O(n)`。

区别只在两点:**对抗退化的手段**、**面向的存储介质(内存 vs 磁盘)**。

```
                        二叉搜索树 BST
                   (左<根<右,但会退化成链表)
                              │
            ┌─────────────────┼─────────────────┐
            │                 │                 │
      严格平衡            弱平衡              多叉化
            │                 │                 │
       AVL / 平衡二叉树     红黑树           B 树 ──→ B+ 树
       (查最快,改贵)   (综合最优,内存)   (磁盘,减少 IO 次数)
```

## 二、问题的起点:BST 为什么会退化

二叉搜索树:每个节点左子树都比它小、右子树都比它大。理想情况查询 `O(log n)`。

但**按有序序列插入**会退化成一条斜链:

```
插入 1,2,3,4,5:

    1                       想要的样子:
     \                          3
      2                        / \
       \                      2   4
        3       ← 退化成      /     \
         \       链表 O(n)   1       5
          4
           \
            5
```

「平衡」的全部意义,就是**强制这棵树保持「矮胖」**,让高度锁死在 `log n`。

### 2.1 树高为什么是 log n(所有平衡树的共同根子)

直觉:**每往下一层,能容纳的节点数翻多少倍**。翻倍是指数增长,反过来求层数就是取对数——log 的本质就是「翻多少次能到 n」。

满二叉树严格推导,高度 `h`,每层 `2⁰,2¹,…,2^(h-1)`,等比求和:

$$
n = 2^0 + 2^1 + \dots + 2^{h-1} = 2^h - 1 \;\Rightarrow\; h = \log_2(n+1) \approx \log_2 n
$$

隐含前提:**每层填满**——这正是「平衡」保证的。退化成链表则每层只 1 个,`n = h`,退回 `O(n)`。

**多叉树(B/B+)**:每层翻 `m` 倍(m=扇出),`n ≈ m^h`,反解:

$$
h \approx \log_m n = \frac{\log_2 n}{\log_2 m}
$$

分母是大常数 → 底数越大树越矮。InnoDB `m≈1170`,高度只有二叉的 ~1/10,这就是「千万级 B+ 树只有 3 层」的来路(见第八节 A)。

| | 每层翻倍 | 高度 |
|---|:--:|:--:|
| 平衡二叉/红黑树 | ×2 | `log₂n`,高 |
| B/B+ 树 | ×m(几百上千) | `log_m n`,矮 |
| 退化链表 | ×1 | `n` |

### 2.2 顺带:`log n` = `log₂n` 的简写吗?

- **算具体树高时**:是。CS 约定不写底数默认底数 2(计算机处处二分)。
- **写复杂度 `O(log n)` 时**:底数无所谓。换底公式 `log_a n = log_b n / log_b a`,不同底只差**固定常数倍**,而大 O 天生吞常数 → `O(log₂n)=O(log_m n)=O(log n)`。
- **反差点**:B+ 树和红黑树复杂度都是 `O(log n)`,**理论上一样快**。但 B+ 树的真本事恰恰藏在被大 O 忽略的那个常数里——底数 2→1170,层数实际少 10 倍,而每层 = 一次磁盘 IO。**大 O 相同 ≠ 实际一样快**,数据库选 B+ 树选的就是这个被公式藏起来的常数。

## 三、平衡二叉树 / AVL 树

**定义**:一棵 BST,额外要求**任意节点的左右子树高度差 ≤ 1**(这个差叫**平衡因子**,取值 -1/0/1)。

维持手段:插入/删除后若某节点平衡因子变成 ±2,通过**旋转**修复。四种情形:LL / RR / LR / RL。

```
LL 型失衡(左孩子的左子树太高)→ 右旋:

        30(bf=+2)                    20
        /                           /  \
      20            ── 右旋 ──→    10    30
      /
    10

旋转后高度差恢复 ≤1,树重新矮胖。
```

- **优点**:平衡最严 → 树最矮 → **查询最快**。
- **缺点**:约束太死 → 增删可能一路旋转到根 → **写入维护贵**。
- **定位**:理论价值大,工程里纯 AVL 反而少见(被红黑树抢了饭碗)。

> 强迫症级别的平衡:查最快,改最累。

## 四、红黑树(Red-Black Tree)

**定义**:一棵"弱平衡"BST,节点染红/黑,靠 5 条规则约束:

1. 节点非红即黑;
2. 根是黑;
3. **红节点的孩子必须是黑**(不能有两个连续红节点);
4. 从任一节点到其所有叶子(NIL)的路径,**黑节点数相同**(黑高相等);
5. 叶子 NIL 视为黑。

这几条合起来保证:**最长路径 ≤ 2 × 最短路径**。不追求「高度差≤1」的严格平衡,只保证「烂不到哪去」,高度仍是 `O(log n)`,但常数比 AVL 大。

```
  示意(●黑 ○红):

            13●
           /    \
        8○       17○
       /  \     /   \
     1●   11●  15●   25●
       \            /   \
       6○         22○   27○

规则4:从根到每个 NIL 叶子,一路上的黑节点个数都相等 → 黑高一致。
规则3:任何红节点(○)的孩子都是黑(●)→ 红节点不相邻。
两条合起来:最长路径(红黑交替)最多是最短路径(全黑)的2倍。
```

- **和 AVL 的核心权衡**:平衡更松 → 增删**旋转更少**(插入最多 2 次旋转,删除最多 3 次;AVL 可能旋到根)。用**查询略慢**换**增删更快**。
- **哪里在用**:C++ `std::map/set`、Java `TreeMap/TreeSet`、Linux 内核(CFS 调度、内存管理 vma)……几乎所有**内存有序容器**。

> 工程界的实用主义平衡树:查改都不极端,综合最优,所以内存里遍地是它。

### 4.1 发明史:和 B 树竟是同一个人

| 时间 | 人物 | 贡献 |
|---|---|---|
| **1970** | **Rudolf Bayer** & Ed McCreight | 发明 **B 树**(见第五节) |
| **1972** | **Rudolf Bayer** | 发明红黑树原型,叫「**对称二叉 B 树**」 |
| **1978** | **Guibas & Sedgewick** | 引入红/黑染色,提出「双色平衡树框架」,红黑树定名 |

戏剧性的地方:**红黑树和第五节的 B 树出自同一个人(Bayer)之手**——这不是巧合,是同一思想的两种投影(见 4.2)。

至于为什么叫「红黑」?Sedgewick 后来在演讲里承认:当年施乐(Xerox)实验室那台**彩色打印机**,红和黑打出来最好看,就这么定了。纯审美,无深意。

### 4.2 钥匙:红黑树 ≡ 2-3-4 树(4 阶 B 树)的二叉表示

红黑树那 5 条规则不是硬凑的,背后有个严格等价关系:

> **红黑树 ≡ 2-3-4 树的二叉伪装。**「黑高相等」就是 B 树「所有叶子同层」的完美平衡。

**2-3-4 树**就是每节点装 1~3 个 key(2/3/4 个孩子)的 B 树,天生完美平衡。红黑树把它的「胖节点」拆成二叉:

```
 2-3-4 树的一个 3-key 节点            红黑树等价表示
 (完美平衡,天然合法)                (黑当骨架,红当挂件)

    [ a | b | c ]         ≡              b●
    /   |   |   \                       /  \
   ..  ..  ..  ..                     a○    c○
                                     / \    / \
                                    .. .. .. ..

  红节点(○)= 被"塞进"父节点的额外 key;黑节点(●)= B 树节点的骨架。
```

5 条规则逐条对应 B 树的天然性质:

| 红黑树规则 | 对应 2-3-4 树 |
|---|---|
| 红节点不相邻(规则3) | 一个 B 树节点最多 3 key,拆开红节点连不成串 |
| **黑高处处相等(规则4)** | ⭐ 就是 B 树「所有叶子同层」的完美平衡 |
| 根是黑 | B 树根就是个正常节点 |

红节点是「不算高度的免费挂件」,所以红黑树的**黑高 = 它对应的 2-3-4 树的真实高度**,天然平衡。规则不是拍脑袋加的约束,是「维持 B 树等价性」的必要条件。理解了这个,5 条规则不用背——它们只在说一句话:「我等价于一棵完美平衡的 2-3-4 树」。

### 4.3 严格证明:高度 ≤ 2·log₂(n+1)

「弱平衡也能保证 O(log n)」可以证出来,三步:

1. **定义黑高 `bh(x)`**:节点 x 到叶子路径上的黑节点数。
2. **引理**:以 x 为根的子树至少有 `2^bh(x) − 1` 个内部节点。
   归纳:两个孩子黑高至少 `bh(x)−1`,各至少 `2^(bh(x)−1)−1` 个,加 x 自己 → `n_x ≥ 2(2^(bh(x)−1)−1)+1 = 2^bh(x) − 1`。
3. **由规则3(红不相邻)**,根到叶子黑节点至少占一半:`bh(root) ≥ h/2`。

代入:`n ≥ 2^bh(root) − 1 ≥ 2^(h/2) − 1`,反解得:

$$
h \le 2\log_2(n+1)
$$

**结论**:红黑树高度最多是理想满树(`log₂n`)的 2 倍。这就是「弱平衡」的精确含义——不追求最矮,但保证「烂不过 2 倍」,高度锁死在 `O(log n)`。

```
Rudolf Bayer
   ├─ 1970  B 树 ────────────► 第五节:横着胖(一节点多 key,面向磁盘)
   └─ 1972  红黑树原型 ──────► 第四节:竖着拆(胖节点拆成红黑二叉,面向内存)
        同一个东西的两种形态。
```

## 五、B 树(B-Tree):从二叉到多叉

前面全是**二叉**。B 树的突破:**多叉**——一个节点存很多 key、带很多孩子。

**定义(m 阶 B 树)**:

- 每个节点最多 `m` 个孩子、`m-1` 个 key;
- 除根外每个节点至少 `⌈m/2⌉` 个孩子(保证"半满");
- 节点内 key 有序,key 之间的空隙指向孩子;
- **所有叶子在同一层**(完美平衡,靠分裂/合并维持)。

```
  一棵 5 阶 B 树(节点内可存多个 key):

                    [ 17 | 35 ]
                   /     |     \
          [7|12]     [20|29]     [40|46|52]
          / | \       / | \        / | | \
        叶  叶 叶    叶  叶 叶     叶 叶 叶 叶

  每个节点塞多个 key → 一个节点就能"分很多岔" → 树被压得很矮。
```

**为什么要多叉——理解一切的钥匙**:

B 树为**磁盘**而生。磁盘特点是**一次读一整块(4~16KB)很便宜,但 IO 次数极贵**(机械盘一次寻道 ~10ms,是内存访问的十万倍)。

- 二叉树:`n` 个数据高度 `log₂n`,要 `log₂n` 次 IO。百万数据 ≈ 20 次 IO。
- B 树:一个节点塞满整个磁盘块(几百个 key),**扇出(fan-out)大 → 树极矮**。百万数据只要 2~3 层,2~3 次 IO。

> 磁盘数据结构第一性原理:**用「一次读一大块」换「更少的 IO 次数」,把树压矮。**

B 树每个节点**同时存 key 和数据(或数据指针)**,查询可能在非叶子节点就命中。

## 六、B+ 树(B+ Tree):数据库/文件系统的终选

B 树的改良版。MySQL InnoDB、PostgreSQL、大多数文件系统的索引都用它。三个关键改动:

| 改动 | B 树 | B+ 树 |
|------|------|-------|
| **数据存哪** | 每个节点都存数据 | **只有叶子存数据**,内部节点只存 key 当"路标" |
| **叶子结构** | 叶子间无联系 | **所有叶子用双向链表串起来** |
| **key 冗余** | key 不重复 | 内部节点 key 是叶子的**副本**(冗余) |

```
  B+ 树结构(★=数据在叶子;内部节点只是"路标索引"):

                       [ 17 | 35 ]              ← 内部节点:只有 key,不存数据
                      /     |     \
              [7|12]      [23|29]     [40|52]    ← 内部节点:路标
             /  |  \      /  |  \     /  |  \
            ▼   ▼   ▼    ▼   ▼   ▼   ▼   ▼   ▼
   ┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐
   │5★  ││10★ ││15★ ││20★ ││26★ ││33★ ││38★ ││45★ ││60★ │   ← 叶子:存全部数据
   └─┬──┘└─┬──┘└─┬──┘└─┬──┘└─┬──┘└─┬──┘└─┬──┘└─┬──┘└─┬──┘
     │←───►│←───►│←───►│←───►│←───►│←───►│←───►│←───►│         ← 双向链表串联所有叶子
     └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

  ↑ 注意:17、35、23 这些 key 在内部节点是"副本",真正数据在叶子。
```

三点改动正好命中数据库核心需求:

1. **内部节点更瘦 → 扇出更大 → 树更矮 → IO 更少**。
   内部节点不存数据,同样大小的磁盘块能塞更多 key,扇出比 B 树还大。

2. **范围查询极快(数据库杀手锏)**。
   `WHERE age BETWEEN 20 AND 30`、`ORDER BY`、分页——定位到起点叶子后,**顺着叶子链表往后扫**即可。B 树做范围查询要中序遍历,来回跳节点,IO 乱序且多。

   ```
   查 20~40:先定位到叶子[20]，然后顺链表扫 →
       [20★] ─► [26★] ─► [33★] ─► [38★]  ✓ 一路顺扫,不回树
   ```

3. **查询性能稳定**。
   B 树可能第 2 层命中、也可能到叶子,**路径长度不一**;B+ 树数据全在叶子,**每次都走到叶子**,深度一致,性能可预测。

> B+ 树 = 内部节点当「稀疏索引路标」+ 叶子当「有序数据链表」。等值查、范围查、排序、分页全照顾,为关系型数据库量身定做。

### 6.1 易错点:内部节点的 key 是「路标」,不是「上限」

常见误解:看到根是 `[17|35]`,以为「整棵树的值都该 ≤ 35」。**错**。看上面的图,根是 `[17|35]`,但子节点里却有 `[40|52]`、叶子里有 60——为什么?

实际规则:**`n` 个 key 把范围切成 `n+1` 段,每个孩子负责一段。**

```
        [ 17 | 35 ]
       /     |     \
     <17   17~35   ≥35     ← 3 个孩子各管一段;最右段没有上限!
      │      │       │
   [7|12] [23|29] [40|52]
```

- 孩子1 管 `<17`,孩子2 管 `17≤x<35`,孩子3(`[40|52]`)管 **`≥35`** → 所以它当然能有 40、52、60。
- **最右孩子敞口朝上,没有封顶**。35 只说「≥35 往这边拐」,没说「最大是 35」。
- **整棵树的最大值(60)住在最右下角的叶子里,根本不在根上。**

查 60 的路径:根 `60≥35` 走最右 → `[40|52]` `60≥52` 走最右 → 叶子 `[60★]`。52 是子层的分界点(把 ≥35 这段再切成 `<40 / 40~52 / ≥52`)。

> 一句话:**内部节点 key 是「往哪拐」的路标,不是「最大值」的封顶。** 每层拿本层 key 把区间再切细,最右分支永远敞口。这正是它被叫「稀疏索引 / 路标」的原因——只指路,不存边界,更不存数据。

## 八、动手验证(别只看文字)

### A. 千万级数据 B+ 树为什么只有 3 层——手算一遍

假设 InnoDB 页大小 16KB:

- **内部节点**:一条记录 = 主键(bigint 8B)+ 页指针(6B)= 14B。一页放 `16KB / 14B ≈ 1170` 个路标。
- **叶子节点**:假设一行数据 1KB,一页放 `16KB / 1KB = 16` 行。

层数与容量:

| 层数 | 容量 |
|:--:|:--|
| 2 层(1 内部 + 叶子) | `1170 × 16 ≈ 1.8 万` |
| 3 层(2 内部 + 叶子) | `1170 × 1170 × 16 ≈ 2000 万` |

→ **千万级数据 B+ 树只有 3 层**;根节点常驻内存,实际查一行只需 **2 次磁盘 IO**。这是面试经典结论,自己能推出来就吃透了。

### B. 用 MySQL 看 B+ 树的行为

```sql
-- 建表,主键即聚簇索引 B+ 树的 key
CREATE TABLE t (id INT PRIMARY KEY, name VARCHAR(32), KEY idx_name(name));

-- 范围查询走 B+ 树叶子链表扫描,type=range
EXPLAIN SELECT * FROM t WHERE id BETWEEN 100 AND 200;

-- ORDER BY 主键无需额外排序(叶子本就有序),Extra 不出现 Using filesort
EXPLAIN SELECT * FROM t ORDER BY id LIMIT 10;
```

练手方向:定义 `order`(阶),叶子节点带 `next *node` 指针,实现 `insert`(满则分裂、向上传播)、`search`、`rangeScan`(定位起点叶子后顺 `next` 扫)。写完 `rangeScan` 那一刻,就真正理解叶子链表的价值了。

## 九、自测题(盖住答案,先自己讲一遍)

<details>
<summary>1. 为什么数据库索引用 B+ 树,不用红黑树/AVL?</summary>

红黑树/AVL 是二叉,扇出小、树高,`n` 大时层数多。磁盘场景每层一次 IO,IO 是瓶颈。B+ 树多叉压矮树 → IO 次数少;叶子双向链表天然支持范围查询和排序。
</details>

<details>
<summary>2. B 树和 B+ 树到底差在哪?为什么选 B+?</summary>

三点改动:①数据只在叶子(内部节点更瘦 → 更矮);②叶子双向链表(范围查/排序极快);③查询都走到叶子(深度一致,性能稳定)。
</details>

<details>
<summary>3. 为什么 AVL 用得少、红黑树用得多?</summary>

AVL 平衡太严(高度差≤1),增删旋转频繁;红黑树弱平衡换更少旋转,查改综合最优,工程更实用。
</details>

<details>
<summary>4. 一棵 B+ 树能存多少数据?为什么常说只有 3 层?</summary>

16KB 页,内部节点一条 14B → 一页约 1170 路标;叶子一行 1KB → 一页 16 行。3 层 ≈ 1170×1170×16 ≈ 2000 万行,根常驻内存实际 2 次 IO。见第八节 A。
</details>

<details>
<summary>5. B+ 树叶子链表是单向还是双向?</summary>

InnoDB 是双向链表,支持正序和逆序扫描(`ORDER BY DESC` 也能顺着走)。
</details>

<details>
<summary>6. 红黑树的 5 条规则里,哪两条合起来保证了"最长≤2倍最短"?</summary>

规则3(红节点孩子必须黑 → 红不相邻)+ 规则4(任一节点到叶子路径黑高相等)。最短路径全黑,最长路径红黑交替,故最长最多是最短 2 倍。
</details>

<details>
<summary>7. 树高为什么是 log n?B+ 树为什么矮?</summary>

平衡保证每层节点数翻倍(二叉 ×2,多叉 ×m),`n ≈ 底数^h` → 反解 `h ≈ log_底数 n`。底数越大越矮:B+ 树 `m≈1170`,高度只有二叉 ~1/10。见 2.1。
</details>

<details>
<summary>8. 红黑树的 5 条规则本质是什么?谁发明的?</summary>

本质:红黑树 ≡ 2-3-4 树(4 阶 B 树)的二叉表示,「黑高相等」=B 树叶子同层的完美平衡,红节点是塞进父节点的额外 key。发明人 Rudolf Bayer(1972),正是 B 树发明人(1970)。见 4.1/4.2。
</details>

<details>
<summary>9. B+ 树和红黑树复杂度都是 O(log n),为什么数据库偏选 B+ 树?</summary>

大 O 忽略底数(换底只差常数)→ 二者理论同阶。但优势藏在被吞掉的常数里:底数 2→1170,层数实际少 10 倍,每层=一次磁盘 IO。大 O 相同 ≠ 实际一样快。见 2.2。
</details>

<details>
<summary>10. 根节点是 [17|35],为什么子节点/叶子里会出现 52、60 这些比 35 大的值?</summary>

因为内部节点 key 是「路标(分界点)」不是「上限」。n 个 key 切成 n+1 段,最右孩子管「≥ 最后一个 key」,敞口无上限。整棵树最大值住在最右叶子,不在根上。见 6.1。
</details>

**毕业标准**:能在白板上①画出四棵树的形状差异;②口算 B+ 树 3 层容量;③讲清「数据库为何选 B+ 树」的三层追问(不用红黑→多叉减 IO;不用 B 树→叶子链表+更瘦内部节点+稳定深度)。
