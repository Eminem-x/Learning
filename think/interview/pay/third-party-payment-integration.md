# 三方支付对接后端链路规范

> 状态：草案
> 日期：2026-07-30
> 适用范围：hertz_pay 支付中台，以及任何需要对接第三方支付渠道的后端服务
> 关联代码：`hertz_pay`（Stripe / Airwallex / 微信支付 / 支付宝 / UseePay）

---

## 0. 这份文档要解决的问题

支付对接的所有资损，几乎都源自同一件事：

> **跨越网络边界时，你永远无法确定对方的状态。**

请求超时了，三方到底执行没执行？回调收到了，是第一次还是第五次？本地写成功了，三方那边是不是已经变了？这些问题在单机事务里不存在，一旦跨出进程就全部涌现。

下面所有机制——幂等键、CAS、补偿任务、对账——本质上都是同一个策略的不同侧面：

> **把不确定性显式地表示出来，然后用可重复执行的动作去收敛它。**

链路分六段：**建单 → 状态更新 → 终态 → 对外通知 → 退款 → 对账**。第 0 段（密钥与初始化）是前置条件。

## 1. 四个必须先分清的概念

### 1.1 干净的失败 vs 脏的失败

| | 表现 | 三方状态 | 处理 |
|---|---|---|---|
| **干净失败** | 连接被拒、DNS 解析失败、TLS 握手失败 | 请求没到，什么都没发生 | 直接返回错误，无需补救 |
| **脏失败** | **超时** | **未知**——可能已执行，只是响应丢了 | 必须有可查证的本地记录 + 补偿动作 |

支付领域的绝大多数资损出在脏失败上。**所有设计决策都应该假设脏失败一定会发生。**

### 1.2 并发 ≠ 重复

| | 定义 | 对策 |
|---|---|---|
| **并发** | 两件事**同时**发生 | 行锁（`SELECT … FOR UPDATE`）或 CAS |
| **幂等** | 同一件事发生**多次**（同时或先后） | 幂等键 + 唯一约束，或 CAS |

**关键：行锁只在事务期间存在，事务一提交就释放。它挡不住"先后到达"的重复。**

举例。微信支付在未收到成功响应时会重试推送，间隔为 15 秒、15 秒、30 秒、3 分钟、10 分钟……24 小时内最多 15 次。假设第一次处理成功但响应超时：

```
10:00:00  回调#1  BEGIN
                  SELECT … FOR UPDATE   → 拿到锁，status = 待支付
                  UPDATE status = 已支付
                  COMMIT                → 锁释放
10:00:01          发事件"支付成功"       → 业务方发货 ✅

10:00:15  回调#2  BEGIN
                  SELECT … FOR UPDATE   → 顺利拿到锁（#1 早已提交，无人占用）
                                         status = 已支付
                  UPDATE status = 已支付  → 又写了一遍
                  COMMIT
10:00:16          发事件"支付成功"       → 业务方重复发货 ❌
```

行锁在 10:00:00 那一瞬间是有效的，但回调 #2 是 15 秒后才来的，锁早已不存在。**行锁从来就没打算解决这个问题。**

### 1.3 CAS（Compare-And-Swap）

一个模式，不是某项具体技术。语义内核只有一句话：

> **把"我预期的旧状态"作为修改的前置条件，让冲突以显式失败的形式暴露出来，而不是静默覆盖。**

各层的实现载体：

| 层次 | 形态 |
|---|---|
| CPU 指令 | `LOCK CMPXCHG`——所有上层实现的物理基础 |
| Go 标准库 | `atomic.CompareAndSwapInt64(&v, old, new) bool` |
| 关系数据库 | `UPDATE … SET 新值 WHERE 主键 = ? AND 旧值条件` + 判 `RowsAffected` |
| Redis | `SET key val NX`、`WATCH` + `MULTI`、Lua 脚本 |
| HTTP | `If-Match: "<etag>"`，不匹配返回 412 |

数据库里的标准写法：

```sql
UPDATE orders
   SET status = 4              -- 已支付
 WHERE order_id = 'X'
   AND status IN (2, 3);       -- 只有当前是"待支付"或"支付中"才改  ← Compare
```

按 `RowsAffected` 分支：

- **= 1** — 条件匹配，是**我**改成功的。往下走：发事件、通知业务方。
- **= 0** — 条件不匹配。要么已被处理过（重复回调），要么状态不允许这样迁移。**不发事件，直接返回成功给渠道。**

回到上面的时间线：

```
10:00:15  回调#2  UPDATE … WHERE order_id='X' AND status IN (2,3)
                  → RowsAffected = 0（status 已是 4，条件不匹配）
                  → 判定已处理过 → 返回 200，不发事件  ✅
```

一行 SQL 条件同时解决了两个问题：**重复投递**和**状态回退**（迟到的"待支付"回调想把 4 改回 2，同样 `RowsAffected = 0`）。

**CAS 不够的场景：** 有些状态迁移本身合法且可重复（如部分退款，一笔订单可退多次）。此时 CAS 会正常执行，因为条件确实匹配。这种情况必须用**幂等键去重表**——它认的是"这个事件"而不是"这个状态"。

### 1.4 CAS、乐观锁、悲观锁的关系

这三个词经常被摆成并列的技术选项，其实**它们不在同一层**。

**乐观并发控制**（Optimistic Concurrency Control，出自 Kung & Robinson 1981）是一个**策略**：读的时候不加锁，写之前校验"我读到的东西有没有被改过"，冲突就中止重试。

**CAS** 是一个**原子原语**，最早是硬件指令（IBM System/370 的 `CS`、x86 的 `CMPXCHG`）。

策略需要一个原子的"校验 + 写入"动作才能落地——否则校验完到写入之间仍有窗口，等于没校验。CAS 正好提供这个。所以：

> **CAS 是实现乐观锁的机制；乐观锁是 CAS 最常见的应用场景之一。**

而 CAS 的应用远不止乐观锁。它还用于无锁队列/栈等 lock-free 数据结构、原子计数器、引用计数——以及自旋锁：

```go
for !atomic.CompareAndSwapInt32(&locked, 0, 1) { runtime.Gosched() }
```

这是一把**悲观锁**，实现却是 CAS。所以「悲观 vs 乐观」是**策略层**的对立，到了**机制层**，两边都可能建在 CAS 之上。

#### 版本号只是 validate 的一种载体

| 载体 | 写法 | 评价 |
|---|---|---|
| **版本号** | `WHERE version = ?` | 最通用。任何字段被改过都能察觉 |
| **业务状态** | `WHERE status IN (2,3)` | 同时表达"防重复"和"迁移是否合法"两层语义 |
| **时间戳** | `WHERE updated_at = ?` | **不推荐**。同毫秒内两次更新会被判为"没变过"；PG 的 `now()` 在同一事务内还是固定值 |
| **校验和 / ETag** | `If-Match: "<etag>"` | HTTP 条件请求，同一思想的网络层形态 |

**这四种全都是 CAS，区别只是 compare 的对象不同。** compare version 就是通用乐观锁，compare 业务状态就是状态机守卫，compare ETag 就是条件请求——语义内核没变。

#### 一个反直觉的点

数据库里的"乐观锁"这个名字起得不好——**它不加显式锁，但底层仍然靠行锁实现**。

`UPDATE … WHERE version = 5` 执行时，PostgreSQL 会对匹配到的行加排他行锁。两个并发请求同时打这条语句，第一个先锁住行，第二个**阻塞等待**；第一个提交后，第二个在 READ COMMITTED 下会用**新版本的行**重新评估 `WHERE` 条件（EvalPlanQual 机制），发现 `version` 已是 6、条件不匹配 → `RowsAffected = 0`。

- **应用层看**是乐观的：没写 `SELECT FOR UPDATE`，没有显式等待，冲突表现为"更新了 0 行"
- **存储引擎层看**仍然加了行锁，只是持有时间被压缩到单条语句内

⚠️ **这个"返回 0 行"的行为依赖 READ COMMITTED。** 若隔离级别提到 REPEATABLE READ，PostgreSQL 不会静默返回 0 行，而是抛 `could not serialize access due to concurrent update`，必须在代码里捕获并重试。本项目用 PG 默认的 READ COMMITTED（`biz/adapter/postgresql/init.go`），所以判 `RowsAffected` 的写法成立——**改隔离级别时这一批代码全部要跟着改**。

#### 实践判据：用 version 还是用业务字段

> **要保护的字段是否单调？单调就用它自己当版本；不单调就加独立 version 列。**

本项目两个模块刚好各用一种，且各自都正确：

**钱包用 version**（`biz/dal/wallet_account_dao.go:78`）——余额**不单调**，可增可减，完全可能变了一圈又回到同一数值。用余额自身当版本会踩 **ABA 问题**：你读到 100，别人扣 50 又充 50，你写回时余额仍是 100、条件匹配，但你基于的那个"100"已经不是同一个了。必须有独立的单调计数器。

**订单该用业务状态**（`biz/dal/order_dao.go:180`，当前仍是无条件 `Updates`，待改）——订单状态机**是单调的**，只能向前推进，`Success` 之后不会回到 `WaitingPayment`。状态本身就是天然的版本号，无需额外加列；而且 `WHERE status IN (2,3)` 比 `WHERE version = ?` 多表达了一层"这条迁移是否合法"，后者只能防重复、管不了状态合不合法。

#### 什么时候该用悲观锁

CAS / 乐观锁适合**一条语句能表达完整更新**的场景。当逻辑是"读出来 → 在代码里算一算 → 再写回去"、跨多条语句时，必须用 `SELECT … FOR UPDATE` 把行锁住，防止两个事务读到同一个旧值。

钱包余额变更属于后者：要读三个余额桶、判断充足性、算新值、生成流水。所以钱包那边"`FOR UPDATE` 拿行 + `WHERE version` 提交"的双保险是对的——行锁保证读到写这段区间内无人插队，版本号 CAS 兜底防止锁不住的意外。

## 2. 第 0 段：密钥与初始化（前置）

术语先对齐：不存在"公签私签"，是一对非对称密钥的两端各归一方。

- **商户私钥** — 你自己持有，用来给发出的请求签名
- **平台公钥 / 平台证书** — 用来验证平台的响应和回调签名

两家国内渠道的机制**不同**，别用同一套心智：

| | 支付宝 | 微信支付 APIv3 |
|---|---|---|
| 模式 | **静态** | **动态** |
| 需提前保存 | 商户私钥 pem + 支付宝公钥 pem（2 个文件） | 商户私钥 pem + 商户证书序列号 + APIv3 密钥（1 文件 + 2 字符串） |
| 平台证书 | 手动维护，换了要自己更新文件 | **SDK 自动定期下载并轮换** |
| 代码位置 | `biz/adapter/alipay/init.go:20-34` | `biz/adapter/wechatpay/init.go:36`（`WithWechatPayAutoAuthCipher`） |

微信做成自动轮换，正是因为平台证书约五年一换、有重叠期，手工维护容易出事故。

**要求：**

1. 密钥**必须**从环境变量或密钥管理服务注入，不得提交进 Git。
2. 初始化失败直接 `panic`，让服务启动即失败，不要降级运行。
3. 密钥文件路径、序列号等配置按环境隔离。

## 3. 第 1 段：建单

### 3.1 正确顺序是四步

```
1. 插入本地订单，状态 = 创建中            ← 唯一约束在这里挡住重复请求
2. 调三方建单
3. 成功 → CAS 回填 pay_link，状态 → 待支付 → 返回上游
   失败 → 状态 → 建单失败，返回错误（记录仍在，可查可补）
   超时 → 状态留在 创建中，交给补偿任务去渠道查证
```

**"创建中"是最有价值的状态**——它明确表达了"我不知道结果"。很多实现里没有这个状态，于是不确定性无处存放。

### 3.2 为什么必须先落库

常见的误解是："如果三方调用失败，我们拿不到支付链接，也就返回不了给用户，用户付不了钱，所以没有风险。"

这个推理对**干净失败**成立，对**脏失败**不成立。先落库要防的是后者：

**它给这笔尝试留了一个锚点。** 本地有记录，后续补救才有抓手——补偿任务能扫到它去查渠道、对账能拿它比对账单、客服排查能查到"我们确实在 10:23 试过建这笔单"。没有这条记录，这次尝试对系统而言**从未发生过**，你连"要去查什么"都不知道。

最坏情况：调用超时但三方实际建单成功，本地无记录。上游收到错误可能走了取消或换渠道逻辑，而渠道那边挂着一笔活的、限时可支付的订单。用户若通过其他路径拿到收银台（很多场景是先跳转再回来，页面已打开），照样能付。钱到账，本地无单，回调找不到对应记录，轮询也扫不到。

**附带收益：挡住并发重复请求。** 先落库 + `order_id` 唯一约束，同一订单号的第二个并发请求在插入时就撞唯一键，立刻知道"正在处理中"，不会重复打三方。

### 3.3 事务边界

> **任何数据库事务里都不该包裹网络调用。** 这是硬规则。

事务会一直占着数据库连接和行锁直到提交。中间夹了 HTTP 请求，事务时长就被**外部服务的响应时间**绑定了。三方抖一下，响应从 200ms 变成 8s，连接池瞬间占满，整个服务的所有数据库操作一起卡住。PostgreSQL 还有额外代价：长事务阻塞 vacuum 回收，导致表膨胀。

所以第 1 步和第 3 步**各自是一个独立的、极短的事务**（各自一条 SQL，隐式事务即可）。

那它们之间的一致性靠什么？

> **靠状态机 + 补偿，而不是靠事务。**

那条"创建中"记录本身就是一致性的载体。由独立的补偿任务扫出停留超时的记录，拿 `out_trade_no` 去渠道查证，查到就补齐，查不到就置失败。

这是 **Saga 模式**的朴素形态——跨网络边界的一致性只能用"每一步可查证 + 有补偿动作"来换，换不到 ACID。**凡是试图用一个大事务包住三方调用来"保证一致性"的，都会在生产上出事。**

### 3.4 第 3 步本身也要 CAS

```sql
UPDATE orders SET pay_link = ?, status = 2    -- 待支付
 WHERE order_id = ? AND status = 1;           -- 只有还在"创建中"才回填
```

否则设想：请求超时 → 补偿任务先跑完把订单置为失败 → 原来那个慢请求的响应回来了 → 无条件把订单改成待支付，**补偿动作被覆盖**。加上 `AND status = 1`，晚到的回填自然失效。

### 3.5 建单幂等

同一个 `order_id` 重复请求时，应先查本地：

- 已有订单且**未过期** → 直接返回原有 `pay_link`，不再调三方
- 已有订单但**已过期** → 视业务决定：重新建单（换新 `out_trade_no`）或直接报错
- 无订单 → 走完整流程

注意各渠道对"同一 `out_trade_no` 重复建单"的行为不一致：支付宝 `trade.precreate` 一般返回已存在交易的二维码，而 Stripe Checkout 会**创建一个全新的 Session**，两个都可支付。不要依赖渠道侧的幂等性。

## 4. 第 2 段：状态更新

### 4.1 双通道：回调为主，轮询为辅

| | 回调（Webhook） | 轮询（定时任务） |
|---|---|---|
| 延迟 | 秒级 | 取决于轮询周期 |
| 可靠性 | 渠道会重试，但你的接口可能宕机 | 自己掌控 |
| 定位 | **主通道** | **兜底，不是替代** |

**两条通道必须都有。** 只有回调 → 接口宕机期间的通知全丢；只有轮询 → 延迟高且压力大。

### 4.2 回调的安全边界是验签，不是 IP

这里最容易搞混方向，拆成两件事看：

| 方向 | 场景 | 要求 |
|---|---|---|
| **出站** | 你调三方 API | 部分平台要求固定来源 IP。需要固定出口 IP / NAT 网关 / 代理 |
| **入站** | 三方回调你 | 需要**公网可达的 HTTPS 地址**，不是固定 IP |

**微信和支付宝都不提供稳定的回调源 IP 段，官方明确说不要依赖 IP 白名单做安全校验。** 入站的安全边界只有一个：**验签**。

回调路由通常在认证白名单里（因为三方不可能带你的 Basic Auth），所以验签是**唯一**防线。缺了验签的回调路由等于完全敞开——任何人都能伪造一条"支付成功"。

验签实现要点：

- 用官方 SDK 的验签方法，不要自己拼
- 时间戳必须参与签名，否则签名可被重放
- 用 `hmac.Equal` 做常量时间比较，不要用 `==`
- 验签失败**不要**把 payload 落库，那是未经验证的外部数据

### 4.3 幂等三道防线

```
入站回调  → event_id / transaction_id 去重表（防渠道重推）
状态更新  → CAS 更新（防状态回退和并发）
出站通知  → 带 event_id（让业务方也能去重）
```

去重表的用法：处理前先插一条，插入成功说明是新事件；撞唯一键说明处理过了，直接返回成功。**幂等必须落在数据库唯一约束上，不要只靠代码逻辑判断**——代码判断和写入之间总有窗口。

去重键取值：Stripe 用 `event.id`，微信用 `transaction_id`，支付宝用 `trade_no`。

### 4.4 状态机

**必须有一张显式的合法迁移表**，而不是散落各处的裸赋值：

```go
var allowedTransitions = map[OrderStatus][]OrderStatus{
    Created:        {WaitingPayment, Closed},
    WaitingPayment: {PaymentIng, Success, Cancelled, Closed},
    PaymentIng:     {Success, Closed},
    Success:        {Refunded},
    // 终态不可迁出
}
```

配合 CAS 更新，把合法前置状态写进 `WHERE` 条件。状态映射函数的 `default` 分支**不要返回一个具体的中间状态**——未识别的渠道状态应该报错并告警，返回"待支付"会导致已成功的订单被改回去。

## 5. 第 3 段：终态（关单与超时）

一笔订单不可能永远停在"待支付"。给它画句号有三个来源：

1. **用户真的付了** → 回调或轮询查到成功
2. **上游主动取消** → 调关单接口
3. **超时** → 系统自己关掉

### 关键：顺序必须是"先关渠道，后改本地"

反过来的话，本地已是"已关闭"、渠道那边订单还活着，用户此时付款成功——你就有一笔已关闭的订单收到了钱。

```
1. 调渠道关单接口
2. 渠道确认关闭成功（或明确返回"交易不存在"）
3. CAS 更新本地状态为已关闭
4. 通知业务方
```

**保守策略同样可接受**：查单时如果渠道侧还能查到活跃交易，就不主动关，等渠道自己把状态推进到"已关闭"再同步。这样本地状态永远是渠道状态的镜像，不会脱钩。

### 常见错误

- **只改本地不通知渠道** — 本地与渠道状态脱钩
- **把"查单失败"当成"订单不存在"** — 一次网络抖动就误关订单。渠道的通用业务失败码（如支付宝 `40004`）覆盖很多子错误，必须用**子错误码**（`ACQ.TRADE_NOT_EXIST`）精确判断，不要用字符串匹配顶层码
- **本地状态与推送的事件不一致** — 本地置 `Cancelled`、事件发 `Closed`，业务方与中台从此分叉

---

## 6. 第 4 段：对外通知

这一段是入站回调的镜像——**你现在是别人的支付平台**，要提供别人向你要的那些保障。

### 必须做到

| 项 | 要求 |
|---|---|
| **签名** | 至少 `HMAC-SHA256(timestamp + "." + body, secret)`，放响应头。`secret` 一商户一份，注册订阅时下发。**时间戳必须参与签名**，否则可重放 |
| **event_id** | 每条通知带唯一 ID，让业务方能去重。你会重试，重试就一定重复 |
| **指数退避** | 不要固定间隔。参考微信自己的策略：15s、15s、30s、3min、10min、20min…24 小时内 15 次 |
| **死信告警** | 重试耗尽后进死信，**必须告警**，并提供人工重投接口。躺在表里没人看的死信等于丢了 |
| **成功判定宽松** | 只认 HTTP 2xx。绝大多数系统的 webhook 接收端只返回 200 空体，不要要求对方返回你的私有响应格式 |
| **失败留痕** | 推送失败也要写投递历史，否则事后无从追查 |

### 可靠投递：Outbox 模式

订单状态更新与事件发布**必须在同一个事务里**，否则一定会出现"状态变了但没通知"或"通知了但状态没变"。

```
事务内：
  1. CAS 更新订单状态
  2. 插入 outbox 表一条待发事件
  COMMIT

事务外（后台任务）：
  3. 扫 outbox 中未发送的记录 → 投递 → 标记已发送
```

**反模式：** 在业务代码里用裸 `go func()` 发事件。它跨事务、错误无人接收、进程重启即丢失，而且经常误用会被取消的请求 `context`。

处理消费端时注意：**早退语句要能真正跳出函数**。把状态检查写在事务闭包里 `return nil`，只会退出闭包，函数会继续执行下游逻辑——幂等守卫形同虚设。

---

## 7. 第 5 段：退款

退款是一条**独立链路**，不是支付链路的分支——它有自己的状态机和自己的幂等键。

| 要点 | 说明 |
|---|---|
| **独立单据** | 一笔支付可对应多笔部分退款。退款要有自己的单号（`out_refund_no`）、状态（申请中/成功/失败）、幂等键 |
| **累计金额校验** | 每次退款前校验「已退总额 + 本次 ≤ 支付金额」。**该校验必须在行锁或 CAS 保护下进行**，否则并发两笔可以退超 |
| **异步终态** | 渠道受理 ≠ 到账，有的要几个工作日。受理成功只能置"退款中"，最终状态靠回调或轮询 |
| **同样要通知** | 退款状态变化走同一套出站通知机制 |
| **时限约束** | 各渠道有退款时限（常见 180 天），超期要在本地拦掉而不是等渠道报错 |

---

## 8. 第 6 段：对账

**最容易被跳过、但最不该跳过的一段。**

前面所有机制——回调、轮询、重试、幂等——都是"尽最大努力保证不出错"。对账是唯一能回答**"到底出了多少错"**的机制。它的价值不在于防止问题，而在于**发现问题**。

### 流程

1. 每天固定时间从渠道下载前一日账单
   - 支付宝：`alipay.data.dataservice.bill.downloadurl.query`
   - 微信：`/v3/bill/tradebill`
   - Stripe：Balance Transaction 报表
2. 逐笔与本地订单比对**三样**：存在性、金额、状态
3. 差异分四类处理：

| 差异类型 | 含义 | 处理 |
|---|---|---|
| **渠道有、本地无** | 漏单——最严重 | 立即告警 + 人工介入。这正是"后落库"会造成的那类 |
| **本地成功、渠道无** | 本地状态是错的 | 告警。可能是回调被伪造或代码 bug |
| **金额不一致** | 汇率或精度问题 | 重点排查有浮点换汇的渠道 |
| **状态不一致** | 通常是回调丢了 | 多数可自动修复 |

4. 差异必须**落表 + 告警**，不能只打日志

### 连带价值

对账是唯一能验证幂等机制真的有效的手段。你以为没有重复入账，只有对账能证明。

**钱包/账务系统还需要一层内部对账**：`余额 == sum(流水)`。这一条不依赖渠道账单，可以高频跑。

## 9. 一页速查

| 段 | 核心动作 | 最容易做错的地方 |
|---|---|---|
| 0 密钥 | 商户私钥 + 平台公钥/证书 | 密钥进 Git；把微信当成支付宝那样手工维护平台证书 |
| 1 建单 | 先落库（创建中）→ 调三方 → CAS 回填 | 后落库导致悬空订单；把三方调用包进事务 |
| 2 状态更新 | 回调为主 + 轮询兜底；三道幂等防线 | 用行锁当幂等；靠 IP 白名单当验签；无状态机守卫 |
| 3 终态 | 先关渠道，后改本地 | 只改本地；把查单失败当订单不存在 |
| 4 对外通知 | 签名 + event_id + 退避 + 死信告警 | 裸 goroutine 发事件；无签名；固定间隔重试 |
| 5 退款 | 独立单据 + 累计校验 + 异步终态 | 无累计金额校验；受理即置成功 |
| 6 对账 | 每日全量比对三样，四类差异 | 直接不做 |
