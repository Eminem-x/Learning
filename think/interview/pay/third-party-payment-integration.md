## 0. 这份文档要解决的问题

支付对接的所有资损，几乎都源自同一件事：

> **跨越网络边界时，你永远无法确定对方的状态。**

请求超时了，三方到底执行没执行？回调收到了，是第一次还是第五次？本地写成功了，三方那边是不是已经变了？这些问题在单机事务里不存在，一旦跨出进程就全部涌现。

下面所有机制——幂等键、CAS、补偿任务、对账——本质上都是同一个策略的不同侧面：

> **把不确定性显式地表示出来，然后用可重复执行的动作去收敛它。**

链路分六段：**建单 → 状态更新 → 终态 → 对外通知 → 退款 → 对账**。第 0 段（密钥与初始化）是前置条件。

**怎么读这份文档：** §1–§3 是概念与机制基础（失败分类、幂等与 CAS、分布式事务范式、Outbox），§4–§10 是链路六段的逐段规范，§11 是一页速查，附录是本项目的现状对照与修复顺序。只想快速定位问题的话，直接看 §11 和附录。

## 1. 四个必须先分清的概念

### 1.1 干净的失败 vs 脏的失败

| | 表现 | 三方状态 | 处理 |
|---|---|---|---|
| **干净失败** | 连接被拒、DNS 解析失败、TLS 握手失败 | 请求没到，什么都没发生 | 直接返回错误，无需补救 |
| **脏失败** | **超时** | **未知**——可能已执行，只是响应丢了 | 必须有可查证的本地记录 + 补偿动作 |

支付领域的绝大多数资损出在脏失败上。**所有设计决策都应该假设脏失败一定会发生。**

### 1.2 并发 ≠ 重复

| | 定义 | 对策 |
|---|---|---|
| **并发** | 两件事**同时**发生 | 行锁（`SELECT … FOR UPDATE`）或 CAS |
| **幂等** | 同一件事发生**多次**（同时或先后） | 幂等键 + 唯一约束，或 CAS |

**关键：行锁只在事务期间存在，事务一提交就释放。它挡不住"先后到达"的重复。**

举例。微信支付在未收到成功响应时会重试推送，间隔为 15 秒、15 秒、30 秒、3 分钟、10 分钟……24 小时内最多 15 次。假设第一次处理成功但响应超时：

```
10:00:00  回调#1  BEGIN
                  SELECT … FOR UPDATE   → 拿到锁，status = 待支付
                  UPDATE status = 已支付
                  COMMIT                → 锁释放
10:00:01          发事件"支付成功"       → 业务方发货 ✅

10:00:15  回调#2  BEGIN
                  SELECT … FOR UPDATE   → 顺利拿到锁（#1 早已提交，无人占用）
                                         status = 已支付
                  UPDATE status = 已支付  → 又写了一遍
                  COMMIT
10:00:16          发事件"支付成功"       → 业务方重复发货 ❌
```

行锁在 10:00:00 那一瞬间是有效的，但回调 #2 是 15 秒后才来的，锁早已不存在。**行锁从来就没打算解决这个问题。**

### 1.3 CAS（Compare-And-Swap）

一个模式，不是某项具体技术。语义内核只有一句话：

> **把"我预期的旧状态"作为修改的前置条件，让冲突以显式失败的形式暴露出来，而不是静默覆盖。**

各层的实现载体：

| 层次 | 形态 |
|---|---|
| CPU 指令 | `LOCK CMPXCHG`——所有上层实现的物理基础 |
| Go 标准库 | `atomic.CompareAndSwapInt64(&v, old, new) bool` |
| 关系数据库 | `UPDATE … SET 新值 WHERE 主键 = ? AND 旧值条件` + 判 `RowsAffected` |
| Redis | `SET key val NX`、`WATCH` + `MULTI`、Lua 脚本 |
| HTTP | `If-Match: "<etag>"`，不匹配返回 412 |

数据库里的标准写法：

```sql
UPDATE orders
   SET status = 4              -- 已支付
 WHERE order_id = 'X'
   AND status IN (2, 3);       -- 只有当前是"待支付"或"支付中"才改  ← Compare
```

按 `RowsAffected` 分支：

- **= 1** — 条件匹配，是**我**改成功的。往下走：发事件、通知业务方。
- **= 0** — 条件不匹配。要么已被处理过（重复回调），要么状态不允许这样迁移。**不发事件，直接返回成功给渠道。**

回到上面的时间线：

```
10:00:15  回调#2  UPDATE … WHERE order_id='X' AND status IN (2,3)
                  → RowsAffected = 0（status 已是 4，条件不匹配）
                  → 判定已处理过 → 返回 200，不发事件  ✅
```

一行 SQL 条件同时解决了两个问题：**重复投递**和**状态回退**（迟到的"待支付"回调想把 4 改回 2，同样 `RowsAffected = 0`）。

**CAS 不够的场景：** 有些状态迁移本身合法且可重复（如部分退款，一笔订单可退多次）。此时 CAS 会正常执行，因为条件确实匹配。这种情况必须用**幂等键去重表**——它认的是"这个事件"而不是"这个状态"。

### 1.4 CAS、乐观锁、悲观锁的关系

这三个词经常被摆成并列的技术选项，其实**它们不在同一层**。

**乐观并发控制**（Optimistic Concurrency Control，出自 Kung & Robinson 1981）是一个**策略**：读的时候不加锁，写之前校验"我读到的东西有没有被改过"，冲突就中止重试。

**CAS** 是一个**原子原语**，最早是硬件指令（IBM System/370 的 `CS`、x86 的 `CMPXCHG`）。

策略需要一个原子的"校验 + 写入"动作才能落地——否则校验完到写入之间仍有窗口，等于没校验。CAS 正好提供这个。所以：

> **CAS 是实现乐观锁的机制；乐观锁是 CAS 最常见的应用场景之一。**

而 CAS 的应用远不止乐观锁。它还用于无锁队列/栈等 lock-free 数据结构、原子计数器、引用计数——以及自旋锁：

```go
for !atomic.CompareAndSwapInt32(&locked, 0, 1) { runtime.Gosched() }
```

这是一把**悲观锁**，实现却是 CAS。所以「悲观 vs 乐观」是**策略层**的对立，到了**机制层**，两边都可能建在 CAS 之上。

#### 版本号只是 validate 的一种载体

| 载体 | 写法 | 评价 |
|---|---|---|
| **版本号** | `WHERE version = ?` | 最通用。任何字段被改过都能察觉 |
| **业务状态** | `WHERE status IN (2,3)` | 同时表达"防重复"和"迁移是否合法"两层语义 |
| **时间戳** | `WHERE updated_at = ?` | **不推荐**。同毫秒内两次更新会被判为"没变过"；PG 的 `now()` 在同一事务内还是固定值 |
| **校验和 / ETag** | `If-Match: "<etag>"` | HTTP 条件请求，同一思想的网络层形态 |

**这四种全都是 CAS，区别只是 compare 的对象不同。** compare version 就是通用乐观锁，compare 业务状态就是状态机守卫，compare ETag 就是条件请求——语义内核没变。

#### 一个反直觉的点

数据库里的"乐观锁"这个名字起得不好——**它不加显式锁，但底层仍然靠行锁实现**。

`UPDATE … WHERE version = 5` 执行时，PostgreSQL 会对匹配到的行加排他行锁。两个并发请求同时打这条语句，第一个先锁住行，第二个**阻塞等待**；第一个提交后，第二个在 READ COMMITTED 下会用**新版本的行**重新评估 `WHERE` 条件（EvalPlanQual 机制），发现 `version` 已是 6、条件不匹配 → `RowsAffected = 0`。

- **应用层看**是乐观的：没写 `SELECT FOR UPDATE`，没有显式等待，冲突表现为"更新了 0 行"
- **存储引擎层看**仍然加了行锁，只是持有时间被压缩到单条语句内

⚠️ **这个"返回 0 行"的行为依赖 READ COMMITTED。** 若隔离级别提到 REPEATABLE READ，PostgreSQL 不会静默返回 0 行，而是抛 `could not serialize access due to concurrent update`，必须在代码里捕获并重试。本项目用 PG 默认的 READ COMMITTED（`biz/adapter/postgresql/init.go`），所以判 `RowsAffected` 的写法成立——**改隔离级别时这一批代码全部要跟着改**。

#### 实践判据：用 version 还是用业务字段

> **要保护的字段是否单调？单调就用它自己当版本；不单调就加独立 version 列。**

本项目两个模块刚好各用一种，且各自都正确：

**钱包用 version**（`biz/dal/wallet_account_dao.go:78`）——余额**不单调**，可增可减，完全可能变了一圈又回到同一数值。用余额自身当版本会踩 **ABA 问题**：你读到 100，别人扣 50 又充 50，你写回时余额仍是 100、条件匹配，但你基于的那个"100"已经不是同一个了。必须有独立的单调计数器。

**订单该用业务状态**（`biz/dal/order_dao.go:180`，当前仍是无条件 `Updates`，待改）——订单状态机**是单调的**，只能向前推进，`Success` 之后不会回到 `WaitingPayment`。状态本身就是天然的版本号，无需额外加列；而且 `WHERE status IN (2,3)` 比 `WHERE version = ?` 多表达了一层"这条迁移是否合法"，后者只能防重复、管不了状态合不合法。

#### 什么时候该用悲观锁

CAS / 乐观锁适合**一条语句能表达完整更新**的场景。当逻辑是"读出来 → 在代码里算一算 → 再写回去"、跨多条语句时，必须用 `SELECT … FOR UPDATE` 把行锁住，防止两个事务读到同一个旧值。

钱包余额变更属于后者：要读三个余额桶、判断充足性、算新值、生成流水。所以钱包那边"`FOR UPDATE` 拿行 + `WHERE version` 提交"的双保险是对的——行锁保证读到写这段区间内无人插队，版本号 CAS 兜底防止锁不住的意外。

## 2. 分布式事务范式与选型

支付链路上的每一段，本质都在解决同一类问题：**跨系统的操作如何保持一致**。这一节给出可选范式的全景和选型判据——后面六段各自选了什么方案，原因都在这里。

### 2.1 两大类

分野的根源是 CAP：**刚性事务**选 CP，牺牲可用性换 ACID；**柔性事务**选 AP，用最终一致性换可用性。

### 2.2 刚性事务

#### 2PC / XA

协调者驱动两阶段：先向所有参与者发 `prepare`（各自锁资源、写 redo/undo，回复"我能提交"），全票通过才发 `commit`。落地实现有 MySQL XA、PostgreSQL 的 `PREPARE TRANSACTION`、Java 的 JTA。

四个致命问题：

- **同步阻塞** — 参与者 prepare 后持锁等协调者
- **协调者单点** — 它挂了，参与者永远悬着
- **commit 阶段部分失败** — 直接不一致
- **性能差** — 锁的持有时间从本地事务延长到全局往返

适用范围很窄：同机房、参与者少、全都是支持 XA 的关系库。**跨服务、跨公网基本不可用**——你不可能让支付宝跟你一起做 2PC。

#### 3PC

在 prepare 前加 `canCommit` 询问阶段，并给参与者加超时自主决策。理论上降低阻塞，实际几乎不用：网络分区下仍不安全，且多一轮 RTT。属于教科书产物。

#### Percolator / Spanner

让 2PC 真正可用的现代工程答案：**2PC + MVCC + 高可用协调者**。Percolator 用 BigTable 存事务元数据，Spanner 用 TrueTime 做全局时序，TiDB 的事务模型即 Percolator。

但这类方案要求**存储层自身实现**它。业务代码用不上——你能享受的是"TiDB 的跨行事务是原子的"，而不是"我可以用它协调两个微服务"。

### 2.3 柔性事务

#### TCC（Try-Confirm-Cancel）

业务层的两阶段：

- **Try** — 预留资源（冻结余额、锁库存）
- **Confirm** — 确认，把预留转成实际扣减
- **Cancel** — 释放预留

与 2PC 的本质区别在**锁在哪一层**。2PC 锁数据库行，TCC 锁业务资源——你自己定义"冻结"的语义，数据库层面每一步都是提交了的短事务。代价是**强侵入**：每个参与方都要实现三个接口。

三个必踩的坑，不处理就会出事：

| 坑 | 场景 | 要求 |
|---|---|---|
| **空回滚** | Try 因网络失败没执行，Cancel 却来了 | Cancel 要能识别"无对应 Try"并直接返回成功，不能真去释放不存在的预留 |
| **悬挂** | Cancel 先到、Try 后到（Try 超时重发） | Try 要能发现"已被取消过"，否则预留出去的资源永远没人释放 |
| **幂等** | Confirm / Cancel 都会被重试 | 两者都必须幂等 |

解法通常是一张事务控制表，记录每个全局事务 ID 的分支状态，Try / Confirm / Cancel 都先查它。

> **本项目的提现流程已经是 TCC 形态**：`WITHDRAWAL_APPLY`（可用 −、提现中 +，建 PENDING 单）= Try；`WITHDRAWAL_COMPLETED`（提现中 −）= Confirm；`WITHDRAWAL_CANCELLED` / `FAILED`（提现中 −、可用 +）= Cancel。`withdrawing_balance` 这个余额桶就是预留资源的载体。
>
> 缺的是空回滚和悬挂防护——`WITHDRAWAL_APPLY` 不查重 `related_order_id`，同一笔可以申请出多个 PENDING 单（见 `biz/handler/wallet/service/handle.go:142`）。

#### Saga

长事务拆成一串本地事务，每步配一个**补偿动作**，失败时反向依次补偿。

与 TCC 的关键区别：**Saga 没有预留阶段**，每步直接提交真实变更，失败靠**语义补偿**（反向操作，不是回滚）。所以中间态对外可见——隔离性差，别人可能读到"钱已扣但货未锁"的状态。

两种协调方式：

| | 编排式 Orchestration | 事件驱动式 Choreography |
|---|---|---|
| 驱动 | 中心协调器显式调用每一步 | 各服务监听事件自行推进 |
| 优点 | 流程集中可见、易调试 | 无中心依赖、耦合低 |
| 缺点 | 协调器成为瓶颈和单点 | 流程散落各处，出问题难追 |

两个实践要点：**补偿必须幂等且可重入**；**有些动作不可补偿**（已发出的邮件、已给出的优惠券、已到账的转账），这类必须放在整个 Saga 最后、前面所有可补偿步骤都成功之后再执行——这一步叫 pivot transaction。

#### 事务性发件箱（Transactional Outbox）

业务数据和待发消息在**同一个本地事务**里写，后台任务扫表投递。这是"本地数据库 + 消息队列"这个最常见组合的标准答案，也是本项目最需要补的一环，详见 §3。

#### 事务消息（RocketMQ 半消息）

把 Outbox 的可靠性下沉到 MQ：先发一条**半消息**（消费者不可见）→ 执行本地事务 → 根据结果 commit 或 rollback 该消息。若 producer 中途挂了，MQ 会**反查**本地事务状态（需要你提供回查接口）。

⚠️ **Kafka 的事务不是这个东西。** Kafka transaction 只保证"跨多个分区的写入原子可见"和 consume-transform-produce 的 exactly-once，**无法把数据库写入和消息发送绑成一个事务**。本项目用 Kafka，所以必须走 Outbox，不能指望 Kafka 事务。

#### 最大努力通知（Best-effort Notification）

定期重试通知 + 提供查询接口让对方主动对账。**适用于接收方不在你控制之下**的场景——这正是支付回调的模型，也是本项目出站通知该有的形态（见 §8）。

它承认"我可能通知不到你"，所以必须配一个查询接口作为逃生口。

#### Seata AT（无侵入自动补偿）

框架代理数据源，在执行业务 SQL 前后拍下数据快照（before / after image）存进 undo log，回滚时**自动生成反向 SQL**。对业务代码零侵入。

代价：所有参与者必须接同一个框架、共享全局锁服务；自动生成的反向 SQL 在有触发器、外键、复杂 SQL 时容易出错。适合内部微服务统一技术栈，不适合跨组织。

### 2.4 两个容易混的东西

**Raft / Paxos 不是分布式事务范式。** 它们解决"同一份数据的多副本如何达成一致"，分布式事务解决"跨不同数据/服务的操作如何原子"。两个正交的问题。它们的联系是：Spanner 用 Paxos 让 2PC 的协调者高可用，从而消掉单点。

**幂等、重试、对账不是范式，是地基。** 上面所有柔性事务方案都建立在这三件事之上。没有幂等，任何重试都会造成重复；没有对账，你永远不知道机制到底漏了多少。

### 2.5 选型判据

按顺序问四个问题：

1. **参与者在你控制之下吗？** 不在（第三方支付、商户系统）→ 只能最大努力通知 + 对账。这是硬约束，没有选择。
2. **参与者只有"本地库 + 消息队列"吗？** 是 → Outbox 或事务消息就够，不要上 Saga 框架。
3. **能容忍中间态被读到吗？** 不能（超卖、超付）→ TCC，用预留把资源锁住。能 → Saga，实现简单得多。
4. **每一步都能语义补偿吗？** 有不可补偿的动作 → 要么改成 TCC 的预留模式，要么把它放到 Saga 最后一步。

### 2.6 映射回本项目

| 链路段 | 适用范式 | 现状 |
|---|---|---|
| 建单（本地 + 三方） | 本地事务 + 补偿查证（简化 Saga） | ❌ 缺"创建中"状态和补偿任务 |
| 状态更新 | 不是分布式事务，是幂等 + 并发控制 | ❌ 缺 CAS 和去重表 |
| 钱包提现 | **TCC**（已经是了） | ⚠️ 缺空回滚 / 悬挂防护 |
| 订单状态 → 通知事件 | **Outbox** | ❌ `event_producer` 只写不读，用裸 goroutine 代替了 |
| 通知业务方 | **最大努力通知** | ❌ 无签名、无重试、无查询逃生口 |
| 兜底 | **对账** | ❌ 完全没有 |

**只要有第三方参与，就没有选择刚性事务的余地。** 支付中台的分布式事务问题本质上只能用"柔性事务 + 对账"这一套解，剩下的自由度只在"用哪种柔性方案"上。

## 3. Outbox 模式详解

**术语**：Outbox 直译"发件箱"，完整叫法**事务性发件箱**。国内（尤其阿里系、Java 生态）更常见的叫法是**本地消息表**，指的是同一个东西。

⚠️ 注意"本地消息表"这个词有时被用得比较松——有些资料只说"把消息存到本地库再异步发"，不强调同事务。而 **Outbox 的定义里"同库同事务"是硬要求**，那是它全部保证的来源。看到有人讲本地消息表却没提事务，那个实现是有缺口的。

### 3.1 它解决什么问题：双写

订单收到支付成功回调，你要做两件事：改订单状态（写数据库）、通知业务方（发消息）。这两个动作**跨了两个系统**，没法放进一个事务。于是只能选顺序，而两个顺序都有坏排列：

| 顺序 | 坏排列 | 后果 |
|---|---|---|
| 先写库，后发消息 | 库成功、发消息失败（MQ 宕机、进程被 kill） | 状态变了但没人知道，业务方永远收不到通知 |
| 先发消息，后写库 | 消息发出、库写失败 | 业务方收到"支付成功"发了货，本地还是待支付；下一轮轮询会**再发一次** |

**换顺序解决不了问题，因为进程随时可能死在两步之间。** 重试也不行——重启后你根本不知道自己死在了哪一步。

这就是**双写问题**（dual write problem），Outbox 是它的标准答案。

### 3.2 核心思想

> **把"我要发一条消息"这件事，也变成一次数据库写入。**

因为同一个数据库的两次写入**可以**放进一个事务：

```sql
BEGIN;
  UPDATE orders SET status = 4 WHERE order_id = ? AND status IN (2,3);  -- 业务变更
  INSERT INTO outbox (aggregate_id, event_id, event_type, payload, status)
       VALUES (?, ?, ?, ?, 'PENDING');                                   -- 待发消息
COMMIT;
```

这之后你得到一个很强的保证：**业务状态变更和"有一条消息待发"这个事实，要么都存在，要么都不存在。** 消息获得了和业务数据完全相同的持久性。

然后由一个**独立的投递进程**（relay / dispatcher）把已记录的消息真正发出去：

```
循环：
  取 status IN (PENDING, FAILED) 且 next_retry_at <= now 的记录（排序 + limit）
  投递到 MQ 或 HTTP
  成功 → 标记 SENT
  失败 → retry_count++，按退避设置 next_retry_at；超上限置 DEAD 并告警
```

**双写被拆成了"一次原子写入" + "一个可以无限重试的投递动作"。** 投递失败不再意味着丢消息，只意味着还没送到。

### 3.3 表结构

```sql
CREATE TABLE outbox (
  id            BIGSERIAL PRIMARY KEY,
  aggregate_id  VARCHAR NOT NULL,    -- 关联业务实体，如 order_id；也用作 MQ 分区键
  event_id      VARCHAR NOT NULL,    -- 幂等键，给下游去重用
  event_type    VARCHAR NOT NULL,
  payload       TEXT    NOT NULL,    -- 消息体快照
  status        VARCHAR NOT NULL,    -- PENDING / SENT / FAILED / DEAD
  retry_count   INT     NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMPTZ,         -- 退避用
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at       TIMESTAMPTZ,
  UNIQUE (event_id)
);
CREATE INDEX ON outbox (next_retry_at) WHERE status IN ('PENDING','FAILED');
```

两个容易忽略的设计点：

**`payload` 必须是快照。** 不能只存 `order_id` 让投递时再回查业务表——否则订单状态又变了，你发出去的是最新状态而不是"当时那个事件"，事件语义就崩了。

**用部分索引。** 已发送记录会堆积成表里的绝大多数，全表索引白白膨胀。

### 3.4 至少一次，不是恰好一次

Outbox **无法做到 exactly-once**：投递成功了，但在标记 `SENT` 之前进程崩了。重启后这条记录还是 `PENDING`，会被再投一次。

这个窗口可以做得很小，但消不掉——除非投递和标记也能原子，而那又回到了双写问题。

> **Outbox 保证不丢，不保证不重。消费端必须幂等。**

这就是为什么 Outbox 总和幂等键（`event_id`）配套出现：生产端负责"一定送到"，消费端负责"重复了也没事"，两边各管一半才构成完整的可靠投递。

### 3.5 两种投递方式

| | 轮询（Polling Publisher） | 日志订阅（Transaction Log Tailing / CDC） |
|---|---|---|
| 怎么发现新消息 | 定时扫 outbox 表 | 订阅数据库 WAL / binlog |
| 工具 | 自己写 cronjob | Debezium、Canal、Maxwell |
| 延迟 | 取决于轮询周期 | 接近实时 |
| 数据库压力 | 有（没消息也在查） | 几乎没有 |
| 是否需要 outbox 表 | 需要 | 可不需要（直接订阅业务表变更） |
| 运维成本 | 低 | 高，多一套组件 |
| 顺序保证 | 靠排序字段 | 天然按事务日志顺序 |

绝大多数团队从轮询开始，量大了再换 CDC。本项目已有 cronjob 框架和 redislock，轮询方案的成本几乎为零。

**多实例部署要防重复投递**：用分布式锁（现成的 `biz/cronjob/lockjob.go` 就能做），或在取记录时用 `SELECT … FOR UPDATE SKIP LOCKED` 让多实例各取一批互不冲突。后者性能更好，`SKIP LOCKED` 正是为这个场景设计的。

### 3.6 对偶：Inbox

Outbox 管发送端，**Inbox** 管接收端：收到消息先把 `event_id` 插入 inbox 表（唯一约束），插入成功才执行业务逻辑，撞唯一键说明处理过了直接返回。

中文圈很少叫"收件箱模式"，通常说**幂等消费表**或**去重表**。§6.3 里"入站回调用 event_id 去重表"就是 Inbox。一发一收合起来才是完整的可靠链路。

### 3.7 常见错误

**用 goroutine 代替 Outbox。** `go func(){ publish() }()` 看似实现了异步发送，实际什么保证都没有：跨事务、错误无人接收、进程重启即丢失，还经常误用会被取消的请求 context。这是最普遍的伪 Outbox。

**outbox 表和业务表不在同一个数据库。** 那还是双写，白做了。Outbox 的全部魔力来自"同库同事务"。

**忘记归档已发送记录。** 表无限膨胀。定期删除，或按时间分区滚动。

**投递失败无退避地重刷。** 下游宕机时把它捶得更惨，自己的日志也被刷爆。

**扫表没有 limit 或没有索引。** 与 `ListOrderNotSuccess` 现在的问题同类。

### 3.8 本项目现状：骨架齐全，三处断电

`event_producer` 这张表**是照着 Outbox 设计的**，字段一个不缺：`status`（消费状态）、`times`（消费次数）、`push_at`、`body`（消息体快照）、`sort`（消费顺序）、`order_id`（聚合 ID）、`client_id`。DAO 里连投递侧的方法都写好了——`ListProducerNeedPush`、`UpdateProducerTime`。

但三处都没通电：

**一、顺序反了。** `biz/domain/events/producer.go:107-120`：先 `publisher.CreateAsyncTask()` 把消息投出去，**之后**才 `dal.CreateEventProducer()` 写表。Outbox 的前提是"先落库、再由投递进程发出"，这里是"先发出、再记一笔"。顺序一反就从可靠性机制退化成审计日志——而且有损：若 `CreateEventProducer` 失败，消息已在路上，表里什么都没有。

**二、不在业务事务里。** 第 115 行 `dal.NewBaseDal(nil)` 开的是全新的独立连接，与上游订单更新完全不在一个事务；且整个 `FirstBatchPublish` 的调用点都包在 `go func(){}` 里。"业务变更和待发消息同时存在"这个核心保证根本不成立。

**三、投递侧从不运行。** `ListProducerNeedPush`（`biz/dal/event_producer_dao.go:54`）和 `UpdateProducerTime`（`:45`）**全仓库零调用方**。`status` 永远停在 `FirstPush`，`times` 永远是 1，`sort` 从未被赋值。三个状态常量只有一个被写过。

所以现在实际承担可靠投递职责的是 Kafka + `async_tasks` 表，`event_producer` 只是旁边一张没人读的日志表。

#### 改造路径

骨架都在，通电的改动不大：

1. **把 `CreateEventProducer` 挪进业务事务**，与订单状态的 CAS 更新放进同一个 `TransactionDo`，去掉 `NewBaseDal(nil)`
2. **把 `CreateAsyncTask` 从这里移走**——事务里不该有网络调用（Kafka publish），投递交给下一步
3. **加一个 relay cronjob**，调已写好的 `ListProducerNeedPush` 取待发记录（补 `limit` 和 `SKIP LOCKED`），投递后用 `UpdateProducerTime` 更新状态，用 `times` 做退避和死信判定
4. **删掉所有 `go func(){ FirstBatchPublish }()`**——约十处，散落在 `payment.go`、`stripe_service.go` 和三个轮询 task
5. **给 `body` 里加 `event_id`**，让业务方能去重

第 3 步是唯一需要新写代码的，其余都是搬位置和删代码。

## 4. 第 0 段：密钥与初始化（前置）

术语先对齐：不存在"公签私签"，是一对非对称密钥的两端各归一方。

- **商户私钥** — 你自己持有，用来给发出的请求签名
- **平台公钥 / 平台证书** — 用来验证平台的响应和回调签名

两家国内渠道的机制**不同**，别用同一套心智：

| | 支付宝 | 微信支付 APIv3 |
|---|---|---|
| 模式 | **静态** | **动态** |
| 需提前保存 | 商户私钥 pem + 支付宝公钥 pem（2 个文件） | 商户私钥 pem + 商户证书序列号 + APIv3 密钥（1 文件 + 2 字符串） |
| 平台证书 | 手动维护，换了要自己更新文件 | **SDK 自动定期下载并轮换** |
| 代码位置 | `biz/adapter/alipay/init.go:20-34` | `biz/adapter/wechatpay/init.go:36`（`WithWechatPayAutoAuthCipher`） |

微信做成自动轮换，正是因为平台证书约五年一换、有重叠期，手工维护容易出事故。

**要求：**

1. 密钥**必须**从环境变量或密钥管理服务注入，不得提交进 Git。
2. 初始化失败直接 `panic`，让服务启动即失败，不要降级运行。
3. 密钥文件路径、序列号等配置按环境隔离。

## 5. 第 1 段：建单

### 5.1 正确顺序是四步

```
1. 插入本地订单，状态 = 创建中            ← 唯一约束在这里挡住重复请求
2. 调三方建单
3. 成功 → CAS 回填 pay_link，状态 → 待支付 → 返回上游
   失败 → 状态 → 建单失败，返回错误（记录仍在，可查可补）
   超时 → 状态留在 创建中，交给补偿任务去渠道查证
```

**"创建中"是最有价值的状态**——它明确表达了"我不知道结果"。很多实现里没有这个状态，于是不确定性无处存放。

### 5.2 为什么必须先落库

常见的误解是："如果三方调用失败，我们拿不到支付链接，也就返回不了给用户，用户付不了钱，所以没有风险。"

这个推理对**干净失败**成立，对**脏失败**不成立。先落库要防的是后者：

**它给这笔尝试留了一个锚点。** 本地有记录，后续补救才有抓手——补偿任务能扫到它去查渠道、对账能拿它比对账单、客服排查能查到"我们确实在 10:23 试过建这笔单"。没有这条记录，这次尝试对系统而言**从未发生过**，你连"要去查什么"都不知道。

最坏情况：调用超时但三方实际建单成功，本地无记录。上游收到错误可能走了取消或换渠道逻辑，而渠道那边挂着一笔活的、限时可支付的订单。用户若通过其他路径拿到收银台（很多场景是先跳转再回来，页面已打开），照样能付。钱到账，本地无单，回调找不到对应记录，轮询也扫不到。

**附带收益：挡住并发重复请求。** 先落库 + `order_id` 唯一约束，同一订单号的第二个并发请求在插入时就撞唯一键，立刻知道"正在处理中"，不会重复打三方。

### 5.3 事务边界

> **任何数据库事务里都不该包裹网络调用。** 这是硬规则。

事务会一直占着数据库连接和行锁直到提交。中间夹了 HTTP 请求，事务时长就被**外部服务的响应时间**绑定了。三方抖一下，响应从 200ms 变成 8s，连接池瞬间占满，整个服务的所有数据库操作一起卡住。PostgreSQL 还有额外代价：长事务阻塞 vacuum 回收，导致表膨胀。

所以第 1 步和第 3 步**各自是一个独立的、极短的事务**（各自一条 SQL，隐式事务即可）。

那它们之间的一致性靠什么？

> **靠状态机 + 补偿，而不是靠事务。**

那条"创建中"记录本身就是一致性的载体。由独立的补偿任务扫出停留超时的记录，拿 `out_trade_no` 去渠道查证，查到就补齐，查不到就置失败。

这是 **Saga 模式**的朴素形态——跨网络边界的一致性只能用"每一步可查证 + 有补偿动作"来换，换不到 ACID。**凡是试图用一个大事务包住三方调用来"保证一致性"的，都会在生产上出事。**

### 5.4 第 3 步本身也要 CAS

```sql
UPDATE orders SET pay_link = ?, status = 2    -- 待支付
 WHERE order_id = ? AND status = 1;           -- 只有还在"创建中"才回填
```

否则设想：请求超时 → 补偿任务先跑完把订单置为失败 → 原来那个慢请求的响应回来了 → 无条件把订单改成待支付，**补偿动作被覆盖**。加上 `AND status = 1`，晚到的回填自然失效。

### 5.5 建单幂等

同一个 `order_id` 重复请求时，应先查本地：

- 已有订单且**未过期** → 直接返回原有 `pay_link`，不再调三方
- 已有订单但**已过期** → 视业务决定：重新建单（换新 `out_trade_no`）或直接报错
- 无订单 → 走完整流程

注意各渠道对"同一 `out_trade_no` 重复建单"的行为不一致：支付宝 `trade.precreate` 一般返回已存在交易的二维码，而 Stripe Checkout 会**创建一个全新的 Session**，两个都可支付。不要依赖渠道侧的幂等性。

## 6. 第 2 段：状态更新

### 6.1 双通道：回调为主，轮询为辅

| | 回调（Webhook） | 轮询（定时任务） |
|---|---|---|
| 延迟 | 秒级 | 取决于轮询周期 |
| 可靠性 | 渠道会重试，但你的接口可能宕机 | 自己掌控 |
| 定位 | **主通道** | **兜底，不是替代** |

**两条通道必须都有。** 只有回调 → 接口宕机期间的通知全丢；只有轮询 → 延迟高且压力大。

### 6.2 回调的安全边界是验签，不是 IP

这里最容易搞混方向，拆成两件事看：

| 方向 | 场景 | 要求 |
|---|---|---|
| **出站** | 你调三方 API | 部分平台要求固定来源 IP。需要固定出口 IP / NAT 网关 / 代理 |
| **入站** | 三方回调你 | 需要**公网可达的 HTTPS 地址**，不是固定 IP |

**微信和支付宝都不提供稳定的回调源 IP 段，官方明确说不要依赖 IP 白名单做安全校验。** 入站的安全边界只有一个：**验签**。

回调路由通常在认证白名单里（因为三方不可能带你的 Basic Auth），所以验签是**唯一**防线。缺了验签的回调路由等于完全敞开——任何人都能伪造一条"支付成功"。

验签实现要点：

- 用官方 SDK 的验签方法，不要自己拼
- 时间戳必须参与签名，否则签名可被重放
- 用 `hmac.Equal` 做常量时间比较，不要用 `==`
- 验签失败**不要**把 payload 落库，那是未经验证的外部数据

### 6.3 幂等三道防线

```
入站回调  → event_id / transaction_id 去重表（防渠道重推）
状态更新  → CAS 更新（防状态回退和并发）
出站通知  → 带 event_id（让业务方也能去重）
```

去重表的用法：处理前先插一条，插入成功说明是新事件；撞唯一键说明处理过了，直接返回成功。**幂等必须落在数据库唯一约束上，不要只靠代码逻辑判断**——代码判断和写入之间总有窗口。

去重键取值：Stripe 用 `event.id`，微信用 `transaction_id`，支付宝用 `trade_no`。

### 6.4 状态机

**必须有一张显式的合法迁移表**，而不是散落各处的裸赋值：

```go
var allowedTransitions = map[OrderStatus][]OrderStatus{
    Created:        {WaitingPayment, Closed},
    WaitingPayment: {PaymentIng, Success, Cancelled, Closed},
    PaymentIng:     {Success, Closed},
    Success:        {Refunded},
    // 终态不可迁出
}
```

配合 CAS 更新，把合法前置状态写进 `WHERE` 条件。状态映射函数的 `default` 分支**不要返回一个具体的中间状态**——未识别的渠道状态应该报错并告警，返回"待支付"会导致已成功的订单被改回去。

## 7. 第 3 段：终态（关单与超时）

一笔订单不可能永远停在"待支付"。给它画句号有三个来源：

1. **用户真的付了** → 回调或轮询查到成功
2. **上游主动取消** → 调关单接口
3. **超时** → 系统自己关掉

### 关键：顺序必须是"先关渠道，后改本地"

反过来的话，本地已是"已关闭"、渠道那边订单还活着，用户此时付款成功——你就有一笔已关闭的订单收到了钱。

```
1. 调渠道关单接口
2. 渠道确认关闭成功（或明确返回"交易不存在"）
3. CAS 更新本地状态为已关闭
4. 通知业务方
```

**保守策略同样可接受**：查单时如果渠道侧还能查到活跃交易，就不主动关，等渠道自己把状态推进到"已关闭"再同步。这样本地状态永远是渠道状态的镜像，不会脱钩。

### 常见错误

- **只改本地不通知渠道** — 本地与渠道状态脱钩
- **把"查单失败"当成"订单不存在"** — 一次网络抖动就误关订单。渠道的通用业务失败码（如支付宝 `40004`）覆盖很多子错误，必须用**子错误码**（`ACQ.TRADE_NOT_EXIST`）精确判断，不要用字符串匹配顶层码
- **本地状态与推送的事件不一致** — 本地置 `Cancelled`、事件发 `Closed`，业务方与中台从此分叉

## 8. 第 4 段：对外通知

这一段是入站回调的镜像——**你现在是别人的支付平台**，要提供别人向你要的那些保障。

### 必须做到

| 项 | 要求 |
|---|---|
| **签名** | 至少 `HMAC-SHA256(timestamp + "." + body, secret)`，放响应头。`secret` 一商户一份，注册订阅时下发。**时间戳必须参与签名**，否则可重放 |
| **event_id** | 每条通知带唯一 ID，让业务方能去重。你会重试，重试就一定重复 |
| **指数退避** | 不要固定间隔。参考微信自己的策略：15s、15s、30s、3min、10min、20min…24 小时内 15 次 |
| **死信告警** | 重试耗尽后进死信，**必须告警**，并提供人工重投接口。躺在表里没人看的死信等于丢了 |
| **成功判定宽松** | 只认 HTTP 2xx。绝大多数系统的 webhook 接收端只返回 200 空体，不要要求对方返回你的私有响应格式 |
| **失败留痕** | 推送失败也要写投递历史，否则事后无从追查 |

### 可靠投递：用 Outbox，不要用 goroutine

订单状态更新与事件发布**必须在同一个事务里**，否则一定会出现"状态变了但没通知"或"通知了但状态没变"。这是双写问题，解法是 Outbox：

```
事务内：
  1. CAS 更新订单状态
  2. 插入 outbox 表一条待发事件
  COMMIT

事务外（后台任务）：
  3. 扫 outbox 中未发送的记录 → 投递 → 标记已发送
```

**完整机制、表结构、投递方式选择与本项目 `event_producer` 的改造路径见 §3。**

两个本段特有的注意点：

**反模式：用裸 `go func()` 发事件。** 它跨事务、错误无人接收、进程重启即丢失，还经常误用会被取消的请求 `context`。本项目约十处都是这个写法。

**消费端的早退语句要能真正跳出函数。** 把状态检查写在事务闭包里 `return nil`，只会退出闭包，函数会继续执行下游逻辑——幂等守卫形同虚设（`biz/adapter/async_task/handler/base.go:58`）。

---

## 9. 第 5 段：退款

退款是一条**独立链路**，不是支付链路的分支——它有自己的状态机和自己的幂等键。

| 要点 | 说明 |
|---|---|
| **独立单据** | 一笔支付可对应多笔部分退款。退款要有自己的单号（`out_refund_no`）、状态（申请中/成功/失败）、幂等键 |
| **累计金额校验** | 每次退款前校验「已退总额 + 本次 ≤ 支付金额」。**该校验必须在行锁或 CAS 保护下进行**，否则并发两笔可以退超 |
| **异步终态** | 渠道受理 ≠ 到账，有的要几个工作日。受理成功只能置"退款中"，最终状态靠回调或轮询 |
| **同样要通知** | 退款状态变化走同一套出站通知机制 |
| **时限约束** | 各渠道有退款时限（常见 180 天），超期要在本地拦掉而不是等渠道报错 |

---

## 10. 第 6 段：对账

**最容易被跳过、但最不该跳过的一段。**

前面所有机制——回调、轮询、重试、幂等——都是"尽最大努力保证不出错"。对账是唯一能回答**"到底出了多少错"**的机制。它的价值不在于防止问题，而在于**发现问题**。

### 流程

1. 每天固定时间从渠道下载前一日账单
   - 支付宝：`alipay.data.dataservice.bill.downloadurl.query`
   - 微信：`/v3/bill/tradebill`
   - Stripe：Balance Transaction 报表
2. 逐笔与本地订单比对**三样**：存在性、金额、状态
3. 差异分四类处理：

| 差异类型 | 含义 | 处理 |
|---|---|---|
| **渠道有、本地无** | 漏单——最严重 | 立即告警 + 人工介入。这正是"后落库"会造成的那类 |
| **本地成功、渠道无** | 本地状态是错的 | 告警。可能是回调被伪造或代码 bug |
| **金额不一致** | 汇率或精度问题 | 重点排查有浮点换汇的渠道 |
| **状态不一致** | 通常是回调丢了 | 多数可自动修复 |

4. 差异必须**落表 + 告警**，不能只打日志

### 连带价值

对账是唯一能验证幂等机制真的有效的手段。你以为没有重复入账，只有对账能证明。

**钱包/账务系统还需要一层内部对账**：`余额 == sum(流水)`。这一条不依赖渠道账单，可以高频跑。

## 11. 一页速查

| 段 | 核心动作 | 最容易做错的地方 |
|---|---|---|
| 0 密钥 | 商户私钥 + 平台公钥/证书 | 密钥进 Git；把微信当成支付宝那样手工维护平台证书 |
| 1 建单 | 先落库（创建中）→ 调三方 → CAS 回填 | 后落库导致悬空订单；把三方调用包进事务 |
| 2 状态更新 | 回调为主 + 轮询兜底；三道幂等防线 | 用行锁当幂等；靠 IP 白名单当验签；无状态机守卫 |
| 3 终态 | 先关渠道，后改本地 | 只改本地；把查单失败当订单不存在 |
| 4 对外通知 | 签名 + event_id + 退避 + 死信告警 | 裸 goroutine 发事件；无签名；固定间隔重试 |
| 5 退款 | 独立单据 + 累计校验 + 异步终态 | 无累计金额校验；受理即置成功 |
| 6 对账 | 每日全量比对三样，四类差异 | 直接不做 |
