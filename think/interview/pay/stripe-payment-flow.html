Stripe · 对象模型与支付流程

Checkout、Intent、发票、优惠券分别在哪一层

这四个概念难理解，是因为它们不在同一个层次上——一个是界面，一个是状态机，一个是账单，一个是折扣规则。 先把层次分清，流程就自然清楚了。

第一步

六个对象，各自一句话

Stripe 的复杂度全在对象关系上。把这六个记住，剩下的都是组合。

Checkout Session

一个收银界面，不是一笔支付。它是个工厂——你告诉它 mode，它去创建真正干活的对象。会话本身只有"开着 / 完成 / 过期"三种状态。

PaymentIntent

一笔支付的状态机。所有真实扣款都要经过它，包括订阅的每一期。它管的是"收集支付方式 → 验证 → 扣款"这个过程。

Customer

一个长期身份。挂载已保存的卡、默认支付方式、发票地址。订阅必须有 Customer，一次性支付可以没有。

Subscription

一份周期性收费的约定。它自己不收钱——它按周期生成发票，由发票去收钱。

Invoice

一张账单。列明这一期收多少、含哪些行项目、打了什么折。账单要被"支付"，而支付它的正是一个 PaymentIntent。

Coupon

一条折扣规则。本身不作用于任何东西，必须被"挂"到某个对象上才生效——挂的位置决定它影响哪些账单。

最关键的一句：Invoice 是账单，PaymentIntent 是付款。这两件事在 Stripe 里是分开的对象，很多困惑来自把它们混为一谈。

第二步

Checkout Session 是个分叉点

同一个接口，靠 mode 参数走向完全不同的两套对象。这是理解全流程的枢纽。

Checkout Session

你调用 · 返回收银台 URL 或 client_secret

mode = payment

PaymentIntent

直接创建一笔支付

扣款成功后产生

Charge

实际的卡交易

mode = subscription

Customer + Subscription

建立长期收费约定

按周期生成

Invoice

每期一张账单

由它来支付

PaymentIntent

又回到同一个状态机

注意两条路最终汇合到同一个 PaymentIntent。区别在于：一次性支付是 Session 直接造一个 Intent； 订阅是 Session 造 Subscription，Subscription 造 Invoice，Invoice 再造 Intent。多绕了两层，但底层扣款机制完全一样。

还有第三个 mode：setup。它只保存卡不扣钱，用于"先绑卡、以后再收费"的场景，产生的是 SetupIntent 而不是 PaymentIntent。

第三步

PaymentIntent 的状态机

这是"钱到底收到没有"的唯一权威。它的状态回答的是过程问题，不是账务问题。

requires_payment_method → requires_confirmation → requires_action → processing → succeeded
分支： requires_capture （授权与扣款分离时） canceled

requires_action 就是 3DS 验证那一步——银行要求用户额外确认。这是最容易卡住的状态， 因为它需要用户在前端完成交互，服务端只能等。

requires_capture 出现在"先授权后扣款"的场景（比如酒店预授权）。如果你的账户配的是自动扣款， 就不会看到这个状态。

一个常见误解：以为要自己轮询 PaymentIntent 的状态。实际上如果你用 Checkout Session， 应该监听 checkout.session.completed；Session 会替你把 Intent 的最终结果反映出来。直接盯 Intent 只在你自己管理 Intent 生命周期时才需要。

第四步

两条完整时序，并排看差异

左边是买一次东西，右边是订阅。注意该监听的 webhook 完全不同。

一次性支付

mode = payment

  1. 后端创建 Checkout Session，带上 line_items 和 client_reference_id（把你的订单号塞进去）
  2. Stripe 返回 session.url（托管页）或 client_secret（嵌入式）
  3. 用户在收银台填卡
  4. Stripe 创建 PaymentIntent，走完状态机（可能经过 3DS）
  5. 扣款成功，产生 Charge 和 BalanceTransaction（手续费在这一步体现）
  6. 推送 checkout.session.completed — 这是你该监听的事件
  7. 退款只能事后发起，产生 Refund，推 refund.created

订阅

mode = subscription

  1. 后端创建 Checkout Session，带上 Price（含周期定义）和 subscription_data.metadata（订单号只能放这里）
  2. 用户填卡并授权周期性扣款
  3. Stripe 建 Customer（如果还没有）和 Subscription
  4. 立即生成首期 Invoice，billing_reason = subscription_create
  5. Invoice 通过一个 PaymentIntent 完成支付
  6. 推送 invoice.payment_succeeded — 这才是"钱到账了"的信号
  7. 此后每个周期自动重复第 4–6 步，billing_reason = subscription_cycle
  8. 改套餐推 subscription_update；取消推 customer.subscription.deleted

订阅不要监听 checkout.session.completed 来确认收款。 它只说明"用户走完了收银台"，真正的钱是 Invoice 收的。订阅场景的权威事件是 invoice.payment_succeeded， 而且要看它的 billing_reason 区分首期、续费、还是套餐变更。

优惠券

挂在哪，决定它影响什么

Coupon 本身是惰性的。理解优惠券的关键不是它的字段，而是它的挂载位置。

挂载位置作用范围典型用法
Checkout Session 只影响这一次结算 一次性活动折扣，用完即弃
Subscription 影响该订阅之后生成的发票 "首月半价"、"前三期打折"
Customer 影响这个客户的所有未来发票 VIP 长期折扣
Invoice 只影响这一张账单 客服补偿、单次调账

Coupon 的三个核心字段：折扣方式（percent_off 按比例 或 amount_off 按固定金额）， 持续方式（once 只打一期 / repeating 打 N 期，配 duration_in_months / forever 永久）， 以及使用上限（max_redemptions）。

Coupon 和 Promotion Code 是两个对象。Coupon 是规则本身，你在后台或 API 里创建； Promotion Code 是面向用户的可输入码（比如 SUMMER50），它指向一个 Coupon。 如果你想让用户在收银台自己输入优惠码，需要的是 Promotion Code；如果是你在后端直接给用户打折，只用 Coupon 就够了。

发票

账单的生命周期，和它为什么重要

一次性支付几乎用不到发票；订阅的一切都围绕发票转。

draft → open → paid 或 void uncollectible

draft 阶段还能改（加行项目、改折扣）；finalize 之后变成 open 就锁定了， 此时 Stripe 会尝试扣款。扣款成功变 paid，主动作废是 void， 多次尝试失败后被标记为 uncollectible（坏账）。

billing_reason 是订阅对账的关键字段，它告诉你这张发票为什么产生： subscription_create（首期）、subscription_cycle（自动续费）、 subscription_update（套餐变更导致的补差价）、manual（手动开票）。 同一个 invoice.payment_succeeded 事件，这三种 reason 对应的业务处理完全不同。

另外有个容易忽略的能力：预览发票（upcoming invoice）。它不是真发票，是 Stripe 帮你算出"下一期会收多少"， 用来在界面上展示续费金额，或者在用户改套餐前告诉他要补多少差价。

对照本项目

hertz_pay 实际用了哪些

知道了标准模型，就能看出本项目哪里跟直觉不符。

本项目接口实际调的 Stripe API返回状态
/stripe/checkout Checkout Session · mode=payment · hosted 托管页 URL 正常
/stripe/payment-intents Checkout Session · mode=payment · embedded client_secret 名不副实
/stripe/subscribe Checkout Session · mode=subscription 托管页 URL 正常
/stripe/unsubscribe Subscriptions.Update · cancel_at_period_end=true — 到期取消
/stripe/subscription/update Subscriptions.Update · proration=always_invoice 状态 + 周期末 立即扣款
/stripe/invoices/list Invoices.List 发票列表 无分页
/stripe/coupon/info Coupons.Retrieve + Prices.List 券详情 带缓存
/stripe/trade_close 什么都不调 假的成功 空实现

/stripe/payment-intents 这个接口不调用 PaymentIntents API。 它底层同样是 Checkout Session，只是把 ui_mode 设成 embedded 然后返回 client_secret。 真正调用 PaymentIntents 的代码在 biz/adapter/stripe/payment_intent.go，但那是死代码，零调用方。 看接口名去理解它会完全跑偏。

优惠券在本项目里的用法：如果调用方直接传了 coupon_id，就引用现成的券； 否则当折扣金额不为零时，会动态创建一个 Coupon（max_redemptions=1，默认 once， 指定了月数则改成 repeating），挂在 Checkout Session 上。所以每次促销下单都会在 Stripe 里留下一个一次性券对象。

发票的用法：订阅每期的 Invoice 整个 JSON 被存进 payment_subscribe.invoices 列； 续费时不更新原记录，而是把旧记录置为终止再插入一条新记录——所以这张表是"每个计费周期一行"，不是"每个订阅一行"。

最后

三个 webhook 分支是坏的

这三个问题都源自同一件事：一次性支付和订阅的记录存在两张不同的表里，而事件处理没有分清。

事件代码去哪张表查实际问题
checkout.session.completed order 订阅的 session 存在 payment_subscribe 里，所以每次订阅支付完成都会报错
checkout.session.expired payment_subscribe 反向对称问题：一次性支付的 session 过期必然报错，实际靠轮询兜底
payment_intent.succeeded order 按 sessions_id 库里存的是 cs_xxx（Session ID），事件带的是 pi_xxx（Intent ID），永远查不到

第三条尤其能说明"分不清层次"的代价：Session 和 Intent 是两个对象，ID 前缀都不一样， 拿一个去查另一个必然落空。这条 handler 是死路径，一次性支付实际是靠 checkout.session.completed 生效的。

还有一个更隐蔽的：webhook 处理失败时只打日志、不写 HTTP 错误响应，于是返回 200， Stripe 认为投递成功、不会重试。数据库抖动就等于永久丢事件。
