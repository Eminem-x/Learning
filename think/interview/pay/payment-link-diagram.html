第一段

收单：从请求到一条待付款订单

这一段是同步的，全程在一次 HTTP 调用里完成。没有统一收单入口——调用方自己决定用哪个渠道，直接打那个渠道的路径。

  1. 上游HTTP

    POST /api/v1/payment/{channel}/checkout…

    业务方带 Basic Auth 和 Client-ID 发起。四种路径命名各不相同：checkout、checkoutlink、qrlink、intent/create。

    router/{channel}/{channel}.go

  3. 中间件Redis 缓存

    middleware.Auth

    用 Client-ID 查 application 表校验 Basic Auth，结果缓存 30 分钟。webhook 路径和事件订阅路径在白名单里，不走这一步。

    middleware/auth_middleware.go:51

  5. Handler

    参数校验

    检查 success_url、line_item、order_id 非空。这段逻辑在五个渠道之间是复制粘贴的，微信那份漏了前两项校验。

    biz/handler/{channel}/{channel}_handler.go

  7. Domain幂等

    payment.PreProcessFlow

    先按 (user_id, order_id, channel) 查已有订单——命中且未过期就直接返回原支付链接，不再调第三方。否则按渠道 switch 定目标币种和过期时间，支付宝和微信在这里会调汇率服务换成 CNY。

    biz/domain/payment/payment.go:56 · calculate.go:26

  9. 第三方

    adapter.{channel} 建单

    调渠道 SDK 拿支付链接或二维码。五个渠道五种形态：三个是包级函数、一个是 Client 结构体、一个是单例，没有统一接口。

    biz/adapter/{channel}/

  11. DB事务

    EndProcessFlow → CreateOrderFrom{Channel}

    写 order 表，状态 WaitingPayment，落原币/目标币金额和汇率快照。六个 CreateOrderFrom 函数是同一段代码复制六份。

    biz/dal/order_dao.go:189–375

  12. go func() · 跨事务

  13. 异步

    FirstBatchPublish(WaitingPayment)

    用裸 goroutine 发出第一条事件，用的还是会被取消的请求 context。订单已经落库、接口已经返回成功，这条事件发没发出去没人检查。

    biz/domain/payment/payment.go:185

第二段

回流：支付结果怎么被系统知道

两条通道并存，而且互相不知道对方存在。它们最终写同一条订单记录，没有任何互斥或状态守卫。

通道 A · 渠道回调

  1. 入站免认证

    POST /payment/{channel}/webhook

    在 Auth 白名单里，所以验签是唯一防线。只有 Stripe、Airwallex、微信真的验了签。

    middleware/auth_middleware.go:32–36

  3. 实现不齐

    各渠道自行处理

    Stripe 同步处理；Airwallex 投 Kafka 异步消费；微信验签后只落库不改订单；UseePay 是空实现，打一行日志就返回成功。

    biz/handler/{channel}/service/

通道 B · 定时轮询

  1. CronRedis 锁

    OrderTask · 每 5 秒

    redislock 抢锁防多实例重复，带 watchdog 续约。抢不到锁时静默返回，没有日志也没有指标。

    biz/cronjob/cronjob.go:25 · lockjob.go:34

  3. 无分页

    ListOrderNotSuccess → 逐个查渠道

    一次捞出所有非终态订单，串行调第三方接口。单轮耗时超过 5 秒就开始堆积。支付宝和 UseePay 只有这一条通道。

    biz/dal/order_dao.go:39 · cronjob/order_task/task.go:16

  1. 无守卫DB

    order.Status 直接赋值 → UpdateOrder

    全仓库十处裸赋值，没有合法迁移表，没有乐观锁，UpdateOrder 是无条件更新。乱序回调或两条通道并发时，已成功的订单可能被改回待付款。

    biz/consts/order_consts.go:24 · biz/dal/order_dao.go:180

渠道对照

五个渠道，五种成熟度

同一个"聚合支付"的名义下，各渠道拿到的实际保障差异很大。

渠道 收单方式 回调 验签 轮询兜底 事件去重 备注
Stripe Checkout Session 有 官方 SDK 有 仅订阅 唯一支持订阅、发票、退款的渠道
Airwallex PaymentIntent 有 HMAC + 时间戳 无 有 轮询分支被注释掉了，回调丢了就永远卡住
微信支付 Native 扫码 只落库 官方 SDK 有 — 验签后不更新订单，实际靠轮询；context 跨 goroutine 传递
支付宝 预下单二维码 / H5 无路由 不适用 有 — notify_url 被注释掉，纯轮询；40004 判断过粗
UseePay 收银台链接 空实现 无 有 — webhook 路由免认证且无验签，等于完全无保护

第三段

通知：把结果送回业务方

这一段有 Kafka、有重试任务、有状态机，看起来最完整，实际上是三段里最容易丢消息的。

    FirstBatchPublish

    同时写两张表：async_tasks 置 SCHEDULED，event_producer 记一条日志。两次写入和上游的订单更新不在同一个事务里。

  2. 分区键 = order_id

  3. Kafka

    watermill publish → consume

    同订单有序。但消费端是 1 秒自动提交 offset 且从最早位点开始，重启或重平衡会重放。

    biz/adapter/async_task/publisher · subscriber

  4. 断点 · 幂等守卫失效

  5. 重复执行

    HandleEvent 状态检查

    "任务不是 SCHEDULED 就跳过"这句 return 只退出了事务闭包，函数继续往下执行 handler。而且事务的返回值根本没被接收。所以 Kafka 一重放，业务逻辑就重跑一次。

    biz/adapter/async_task/handler/base.go:50–79

    查 subscribe 表拿商户回调地址

    一个 client_id 对应一个 domain。这张表可以被任何人未认证修改——订阅相关的四个接口都在 Auth 白名单里，client_id 取自请求体。

    HTTP POST 到商户域名

    裸 POST，没有 HMAC、没有时间戳、没有 event_id。商户无法验证这条通知是不是真的来自支付中台。

链路之外

钱包是一座孤岛

理解钱包最关键的一点：支付回调路径上没有任何一处调用它。资金流转的判断在上游业务方，钱包只负责按指令记账。

available_balance

可用余额。收款入账、余额支付、结算解冻都落在这里。

unsettled_balance

待结算。供应商分账先进这个桶，结算后才释放。

withdrawing_balance

提现处理中。申请时从可用搬进来，完成或失败时销账。

对外只有三个接口，写入口只有 POST /payment/wallet/transaction/submit 一个，靠 business_type 分发到九个处理器，每一种就是一组固定的桶间流转。并发控制是悲观锁加乐观锁双保险： SELECT … FOR UPDATE NOWAIT 拿行，内存里算余额并校验充足性，再用 WHERE version = ? 提交。 余额和流水在同一个事务里写，每条流水都带变动前后余额和账户快照。

设计思路是内行的，但落地有三个洞：余额更新的 UPDATE 语句缺主键条件，会命中所有同 version 的行； 金额不校验正负，传负数能绕过余额检查反向加钱；没有任何对账任务， 账被写坏了也没有机制能发现。另外钱包只按 (owner, platform) 定位，没有 client_id 列——目前是跨商户共享命名空间的。

断点清单

链路上真正会丢钱的地方

按修复优先级排列。前三条都是一到两行的改动。

  1. 出站通知失败即永久丢失

    把 PushEvent 的错误返回出去，失败任务才能进入既有的重试链路。现在它被丢弃了，整套 Kafka 重试机制对这条最关键的路径完全没生效。

    biz/adapter/async_task/handler/callback_handler.go:21

  2. 钱包余额更新缺主键条件

    gorm gen 的 Updates 不会自动补主键，传入的 Model 是空实例。补上 Where(ID.Eq(…)) 即可。不修的话，只要库里有第二个钱包的 version 相同，这条语句就会命中多行。

    biz/dal/wallet_account_dao.go:78

  3. 金额未校验正负

    扣减分支写的是"余额小于金额就报错"，金额为负时这个条件永远不成立，接着做减负数等于加钱。IDL 里没有校验标注，handler 层也没检查。

    biz/domain/wallet/wallet.go:152 · idl/wallet.thrift:82

  4. 异步任务幂等守卫失效

    状态检查的 return 只跳出了闭包。把检查结果传出事务再决定是否提前返回，Kafka 重放才不会重复执行业务逻辑。

    biz/adapter/async_task/handler/base.go:50

  5. 订单状态没有迁移守卫

    改成带前置状态条件的 CAS 更新，才能挡住乱序回调和"轮询与回调并发"造成的状态回退。

    biz/dal/order_dao.go:180

  6. event_producer 不是真正的 outbox

    这张表只写不读，扫描和重推的方法零调用方。把"改订单状态 + 写 outbox"放进同一个事务、由后台任务补投，才能去掉那些裸 goroutine。

    biz/dal/event_producer_dao.go:45–54
