## 0. 30 秒电梯版（盖住全文也要能讲出主线）

> **一笔钱从用户口袋到商户账上，走的是两条独立的线：信息流和资金流。**
>
> - **信息流**（秒级）：用户支付 → 渠道**授权**（authorization，确认钱能扣）→ **请款**（capture，确认真要扣）→ 回调通知商户"支付成功"。**此刻商户账上一分钱都没有**。
> - **资金流**（T+N）：渠道把当天所有交易**清算**（clearing = **算账**：对账、轧差、扣手续费，算出该给商户多少）→ **结算**（settlement = **划钱**：把净额打到商户的结算账户）。
>
> **一句话记住区别**：**清算是算清楚谁该给谁多少钱（算账），结算是钱真的动了（划钱）。**
>
> 五个动作的方向：**收单**=收钱进来、**付款/代付**=钱出去、**退款**=原路退回、**清算**=算账、**结算**=划钱。
> 还有一个必须和退款区分开的：**拒付（chargeback）**——不是商户主动退，是持卡人向发卡行投诉、由银行强制扣回，**商户被动且要交罚金**。

## 1. 全景：一笔支付的完整生命周期

```
【信息流 · 秒级】
 用户下单
   │
   ├─► 收银台：选支付方式 → 提单
   │
   ├─► 授权 Authorization ── 发卡行/账户方确认"这笔钱可以扣"，冻结额度
   │        （预授权场景：授权后不立刻扣，如酒店押金、租车）
   │
   ├─► 请款 Capture ─────── 确认真的要扣这笔（大多数电商场景授权+请款一步完成）
   │
   └─► 回调通知商户"支付成功" ← 商户此刻发货，但【钱还没到商户账上】

━━━━━━━━━━━━━━━━━━━━ 时间分界线：T 日结束 ━━━━━━━━━━━━━━━━━━━━

【资金流 · T+N】
   ├─► 清算 Clearing ────── 算账：
   │      · 对账（渠道账单 ↔ 商户流水）
   │      · 轧差 netting（应收应付相抵，只算净额）
   │      · 计费（扣手续费、算分润/分账）
   │      → 产出：【结算单】= 商户应得净额
   │
   └─► 结算 Settlement ──── 划钱：
          · 按结算周期（T+1 / T+7 / 月结）把净额打到商户结算账户
          · 可能扣留风险准备金（rolling reserve）
```

**面试常问：「为什么不能实时结算？」**
① 要等**对账完成**才知道账对不对，实时打款出了错就追不回来；② 要留**退款/拒付的窗口期**，钱打出去了拒付谁来赔；③ 银行/卡组织的清算体系本身就是**批量、按日**运作的。

## 2. 五个核心动作

### 2.1 收单（Acquiring）——把钱收进来

**定义**：为商户提供收款服务的整个过程。做这件事的机构叫**收单机构 / 收单行 acquirer**。

**卡组织的四方模型**（国际支付必答）：

```
   持卡人 ──── 消费 ────► 商户
     │                      │
  发卡行 issuer ◄─ 卡组织 ─► 收单行 acquirer
  （给用户发卡，       Visa/MC      （给商户提供收款，
    承担授信）        （清算网络）     承担商户风险）
```

**国内的三方模型**：支付宝/微信本身既是账户方也是清算通道（受央行网联/银联监管），链路比四方模型短。

> 💡 **这就是国内和国际支付体验差异的根源**：国际卡支付要跨发卡行 → 卡组织 → 收单行三跳，**成功率天然低于国内**，所以国际收银台的"成功率优化"才是个真命题。

### 2.2 授权 / 请款 / 撤销（Authorization / Capture / Void）——最容易混的三个

| 动作 | 含义 | 场景 |
|---|---|---|
| **授权 Authorization** | 发卡行确认"额度够、卡有效"，**冻结额度但不扣款** | 所有卡支付的第一步 |
| **请款 Capture** | 商户确认"这笔我要了"，真正发起扣款 | 电商一般**授权+请款合并**；酒店/租车/预售会**分离** |
| **撤销 Void** | 在**请款前 / 结算前**取消这笔交易 | 用户下单后立刻取消 |
| **退款 Refund** | 在**结算后**把钱原路退回 | 正常售后退款 |

> **Void 和 Refund 的区别是必考题**：
> **Void 是"这笔交易当没发生过"**，不产生资金流转，用户账单上可能干脆不出现，**没有手续费损失**；
> **Refund 是"钱已经走了，再走一趟回来"**，是一笔**新的反向资金流**，**原交易的手续费通常不退**。
> **所以系统设计上：结算前的取消要优先走 Void，能省一笔手续费。**

**预授权的两个坑**：① **授权有效期**（通常 7~30 天，过期自动释放）；② **部分请款**（授权 1000 只请款 800，剩余 200 释放）——酒店场景必须支持。

### 2.3 付款 / 代付（Payout / Disbursement）——把钱打出去

**和收单方向相反**。场景：给主播/骑手/卖家结算、提现、退税、跨境打款。

**收单和付款的风险模型完全不同**：
- 收单的风险是**收不到钱**（拒付、盗刷）
- 付款的风险是**钱打错了/打给了坏人**（洗钱、诈骗、打错账户）→ 所以付款侧的 **KYC/AML、名单筛查、限额、双人复核**要求远高于收单

💰 **工程要点**：付款接口**超时必须走查询确认**，绝不能重试成两笔——出款的资损是**不可逆**的（收单错了还能退，出款错了钱就没了）。

### 2.4 退款（Refund）

| 维度 | 要点 |
|---|---|
| 路径 | **原路退回**（退回原支付方式，合规首选）vs 退到平台余额（体验好但有合规风险） |
| 部分退款 | 必须支持；累计退款额 **≤** 原支付额（见 [速成包 §2.4](../bytedance-global-payment-prep-20260805.md) 的并发防超额 SQL） |
| 时效 | 渠道通常限制**一年内**可原路退；超期只能走线下/余额 |
| 失败 | 卡注销、账户冻结、渠道余额不足 → 退款是**可能失败的异步流程**，必须有状态机和重试 |
| 手续费 | **原交易手续费一般不退**——所以高退款率的商户实际成本很高 |

### 2.5 拒付（Chargeback）——和退款完全不同的东西

```
持卡人向【发卡行】投诉（我没买 / 货不对 / 盗刷）
   → 发卡行强制从收单行扣回款项（商户被动扣款 + 拒付手续费）
   → 商户举证申诉 representment（提供物流、IP、签收记录）
   → 仲裁 arbitration（卡组织裁决）
```

| | 退款 Refund | 拒付 Chargeback |
|---|---|---|
| 发起方 | **商户主动** | **持卡人 → 发卡行** |
| 商户成本 | 手续费不退 | **扣款 + 拒付罚金 + 举证成本** |
| 红线 | 无 | **拒付率超阈值（业界通常按 1% 量级管控）会被卡组织罚款甚至停止收单** |

> **所以风控要前置**：拒付是事后的、不可控的，唯一的办法是**在收单时就把高风险交易挡掉**（3DS 验证、设备指纹、黑名单）。**这也是收银台要做"风控前置编排"的原因。**

## 3. 清算 vs 结算（这一对必须能秒答）

| | **清算 Clearing** | **结算 Settlement** |
|---|---|---|
| 干什么 | **算账**：算清谁该给谁多少 | **划钱**：资金实际转移 |
| 产出 | 清算结果 / 结算单（应付净额） | 一笔真实的资金划拨 |
| 包含 | 对账、轧差、计费、分账计算 | 打款、扣准备金、生成结算凭证 |
| 时间 | T 日交易，T+0/T+1 清算 | T+1 / T+7 / 月结 |

**三个关键概念**：

- **轧差（netting）**：A 欠 B 100、B 欠 A 80 → 只划 20。**大幅降低实际资金划转次数和成本**，是清算体系的核心优化
- **结算周期 T+N**：T+1 最常见；风险高的行业（预售、虚拟商品）会拉长到 T+7 甚至月结，**因为要覆盖退款/拒付窗口**
- **风险准备金（rolling reserve）**：从每笔结算款里扣留一定比例（如 5%~10%）滚动持有一段时间（如 90~180 天），用于覆盖后续的拒付。**新商户、高风险行业必有**

💰 **面试加分句**：「结算周期和风险准备金本质上是**用商户的资金占用成本，换取平台的风险敞口覆盖**——所以定这个参数是风控和 BD 的博弈，不是技术决策。」

## 4. 分账、备付金与合规（国内特有，但很爱考）

### 4.1 分账 / 分润（Split）

平台电商的典型场景：用户付 100 → 商家 90 + 平台佣金 8 + 物流 2。

**两种做法**：
1. **渠道分账**（合规做法）：调用渠道的分账接口，由**持牌机构**完成资金分配
2. **平台自己收全款再转给商家**（❌ **这就是"二清"**）

### 4.2 二清（必须知道的红线）

> **二清 = 没有支付牌照的平台，代替持牌机构完成资金的清分和结算。**

平台先把所有钱收到自己账户，再自行分给各商户——**这在国内是违规的**（涉嫌无证经营支付业务）。
**合规解法**：用持牌机构的**分账产品** / **子商户进件**，让资金**从不进入平台自有账户**，由持牌机构直接结算给各商户。

### 4.3 备付金

用户充值进钱包的钱、还没结算给商户的钱，都是**客户备付金**——**不是支付机构的钱**。国内要求 **100% 集中交存人民银行**，机构不得挪用、不享受利息。

> 💰 这解释了一件事：**为什么钱包充值余额必须和平台自有资金严格隔离记账**——这不是技术洁癖，是监管要求。

## 5. 账户体系与记账（系统设计题里的隐藏考点）

### 5.1 账户分类

| 账户 | 用途 |
|---|---|
| 用户账户 | 余额、冻结额、可用额 |
| 商户账户 | 待结算余额、已结算 |
| 平台账户 | 佣金、手续费收入 |
| **中间/在途账户** | 资金"在路上"的临时归属（已扣款未入账、结算中） |
| 手续费账户 / 汇兑损益账户 | 费用与汇率差额的归集 |

### 5.2 复式记账（能讲出来就是懂账务的人）

**每一笔资金变动，至少产生两条方向相反、金额相等的分录，借贷必相等。**

```
用户支付 100 元：
  借：应收账款（渠道在途）  100
  贷：用户应付款（商户待结算）100

结算给商户 98（扣 2 手续费）：
  借：用户应付款  100
  贷：银行存款     98
  贷：手续费收入    2
```

**为什么支付系统必须复式记账**：单边记账（只改余额）**没有自校验能力**；复式记账可以做**试算平衡**——全系统所有分录的借方合计必须等于贷方合计，**不等就是账错了**，这是资金安全的最后一道数学防线。

> 💰 这一条直接接上 [速成包 §2.6](../bytedance-global-payment-prep-20260805.md) 的**第三层对账：账实核对（余额 = 流水累加）**。

### 5.3 单据分层（系统设计题的标准答案结构）

```
支付单（交易维度）→ 账务单/分录（记账维度）→ 清算单（对账与计费维度）→ 结算单（打款维度）
```
**四层单据一一对应、可正反向追溯**，是支付系统"可追溯"的物理载体。

## 6. 费率结构（问到"成本"时能答上）

**国际卡支付的商户扣率 MDR（Merchant Discount Rate）由三部分组成**：

```
MDR = Interchange（发卡行拿，大头，卡组织规定）
    + Scheme Fee（卡组织拿）
    + Acquirer Markup（收单机构的加价，唯一可谈判的部分）
```

其他费用：**跨境费、货币转换费（DCC）、拒付费、退款费、提现费**。

> 💰 **加分洞察**：「收银台做**渠道路由**时，不只看成功率，还要看**成本**——同一笔交易走不同渠道的费率可能差一倍。**成功率优先还是成本优先，本身就是一个可配置的路由策略。**」

## 7. 跨境特有概念（你的差异化优势）

| 概念 | 说明 |
|---|---|
| **本地收单 vs 跨境收单** | 用当地实体做本地收单，成功率显著更高、费率更低，但需要当地牌照/实体；跨境收单省事但成功率低、还有跨境费 |
| **PSP**（Payment Service Provider） | 支付服务商，只提供通道（Stripe、Airwallex 属此类） |
| **PayFac**（Payment Facilitator） | 聚合支付服务商，**自己是主商户，下挂子商户**，负责子商户进件与风控 |
| **MOR**（Merchant of Record） | **法律上的销售方**，承担**税务、合规、拒付**责任（Paddle 这类）。用 MOR 可以免掉自己在各国注册税号的麻烦，代价是费率高 |
| **资金归集与结售汇** | 各国收到的钱要归集回主体、按需结汇；涉及外汇管制 |
| **三币种分离** | 定价币种 / 结算币种 / 记账币种（见 [速成包 §7.1](../bytedance-global-payment-prep-20260805.md)） |

## 8. 高频面试题（配答题要点）

### Q1. 清算和结算有什么区别？
**清算是算账**（对账、轧差、计费，算出应付净额）；**结算是划钱**（按周期把净额打给商户）。清算的产出是结算单，结算的产出是一笔真实资金划拨。

### Q2. 用户支付成功了，商户是不是马上就拿到钱了？
**不是。** 支付成功走的是**信息流**（授权+请款完成），钱还在渠道/收单机构手里；要等 **T+N 清算结算**后才划到商户结算账户。**这个时间差正是退款、拒付、风险准备金存在的空间。**

### Q3. 退款、撤销、拒付三者的区别？
- **撤销 Void**：结算前取消，交易当没发生，**不产生反向资金流，手续费不损失**
- **退款 Refund**：结算后原路退回，是一笔新的反向资金流，**原手续费一般不退**
- **拒付 Chargeback**：**持卡人向发卡行发起**，商户被动扣款 + 罚金，**拒付率超标会被停止收单**

### Q4. 为什么不能实时结算？
① 要等对账确认账目正确；② 要留退款/拒付窗口；③ 银行与卡组织的清算体系本身是按日批量运作的。

### Q5. 平台电商怎么把钱分给商家？
走渠道的**分账产品**或**子商户进件**，让资金**不经过平台自有账户**。平台先收全款再自行转账 = **二清**，属违规。

### Q6. 为什么支付系统要复式记账？
单边改余额没有自校验能力；复式记账可做**试算平衡**（借方合计 == 贷方合计），是资金安全的数学防线，也是"账实核对"这一层对账的基础。

### Q7. 一笔支付调渠道超时了，怎么处理？
**超时的语义是"未知"不是"失败"** → 置为处理中 → 用**相同幂等键**主动查询渠道确认 → 定时补偿 → 对账兜底。（详见 [TCP/IP 速查 §11](../../network/tcp-ip-interview-cram-20260805.md)）

### Q8. 收单和付款（出款）的系统设计有什么本质不同？
风险模型相反：收单怕**收不到钱**（拒付、盗刷），付款怕**钱打错/打给坏人**（洗钱、诈骗）。所以付款侧的 **KYC/AML、名单筛查、限额、复核**要求高得多，且**出款资损不可逆**——超时绝不能盲目重试。

## 附录：自我思考

### 一、我以前只做了"信息流"，没碰过"资金流"

复盘我做的统一支付网关：下单、回调、退款、幂等、对账——**全部集中在信息流这一段**。清算（轧差、计费、分账计算）和结算（打款、准备金、结算单）这两块，在我们的业务里是**渠道帮我们做掉的**（我们是商户侧，不是收单侧）。

这个认知差必须在面试前想清楚，否则被问到"你们的清算怎么做的"会答成"我们做了对账"——**对账只是清算的第一步，不是清算本身**。

**诚实的讲法**：「我们是商户侧，清结算由渠道完成，我做的是商户侧的**对账与账务**——渠道对账、内部账实核对、差错处理。**完整的清算（轧差、计费、分账）我没有直接实现过，但我清楚它的输入输出和它为什么必须和结算分开。**」

### 二、这一层概念是"懂不懂这行"的分水岭

技术能力（幂等、一致性、高可用）是可以从别的领域迁移过来的，但**清结算、拒付、二清、备付金这些概念，只有真在支付行业待过才会知道**。面试官用它们来判断的不是你的技术水平，是**你到底是"做过一个支付功能"还是"在支付行业工作过"**。

好消息是：**这一层是纯记忆，一天能补完**，而且补完之后，我"跨境电商支付 + 五渠道 + 多币种"的经历会显得可信度高得多——因为我能用行业的语言描述它。
