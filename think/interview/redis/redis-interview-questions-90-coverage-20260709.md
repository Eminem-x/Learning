## 30 秒电梯版（盖住全文也要能背出主线）

Redis 面试就九条主线：

1. **数据结构**：5 基础（String/List/Hash/Set/ZSet）+ 4 扩展（Bitmap/HyperLogLog/GEO/Stream）；每种类型底层有**两套编码**，小数据用紧凑编码（ziplist/listpack/intset），大了转标准结构（hashtable/skiplist/quicklist）。ZSet = **跳表 + 哈希表**双结构。
2. **单线程模型**：命令执行单线程（避免锁、无竞态），靠 **I/O 多路复用（epoll）** 扛并发；6.0 起 **I/O 多线程**只并行「读网络/解析/回写」，命令执行仍单线程。快的根因：纯内存 + 高效数据结构 + 单线程无锁 + 多路复用。
3. **持久化**：**RDB**（内存快照、二进制紧凑、恢复快、会丢数据）、**AOF**（命令追加日志、更安全、文件大、恢复慢）、**混合持久化**（RDB 全量 + AOF 增量，7.x 默认推荐）。`fork` + COW 是 RDB/AOF rewrite 的共同机制。
4. **过期删除**：**惰性删除**（访问时才删）+ **定期删除**（周期抽样删）双管；过期 key 不保证被立即清，靠内存淘汰兜底。
5. **内存淘汰**：`maxmemory` 到顶后按 8 种策略淘汰，主力是 **allkeys-lru / allkeys-lfu / volatile-ttl**；LRU 是近似 LRU（随机采样），LFU 带访问频率 + 时间衰减。
6. **缓存三大问题**：穿透（查不存在的 key → 布隆过滤器/缓存空值）、击穿（热点 key 过期瞬间 → 互斥锁/逻辑过期/不过期）、雪崩（大量 key 同时过期或宕机 → 过期时间加随机 + 多级缓存 + 高可用）。
7. **缓存一致性**：更新策略选 **Cache-Aside + 先更新 DB 再删缓存（延迟双删兜底）**；根因是「双写无法原子」，只能做到最终一致。
8. **分布式锁**：`SET key val NX PX ttl` + **唯一值 + Lua 原子释放**；进阶看门狗续期（Redisson）、Redlock 多节点（有争议）。
9. **高可用**：**主从复制**（读写分离、数据冗余）→ **Sentinel**（哨兵，自动故障转移，不解决容量）→ **Cluster**（分片，16384 槽，解决容量 + 高可用）。

卡在哪一条，就往对应章节回挖。

## 一、数据结构与底层编码（考频 ★★★★★）

### Q1. Redis 有哪些数据类型？各自典型场景？

**5 种基础 + 4 种扩展**：

| 类型 | 典型场景 |
|------|---------|
| **String** | 缓存对象（JSON）、计数器（`incr`）、分布式锁、限流、Session |
| **List** | 消息队列（`lpush`/`brpop`）、最新列表、栈/队列 |
| **Hash** | 存对象（字段可单独改）、购物车 |
| **Set** | 去重、共同好友（`sinter` 交集）、抽奖（`spop`）、标签 |
| **ZSet（有序集合）** | 排行榜（`zrevrange`）、延迟队列（score=时间戳）、带权重的优先级 |
| **Bitmap** | 签到、活跃用户统计（位运算，1 亿用户仅 12MB） |
| **HyperLogLog** | 海量 UV 基数统计（12KB 估算亿级，误差 0.81%，**不精确**） |
| **GEO** | 附近的人、地理位置（底层是 ZSet + GeoHash） |
| **Stream** | 消息队列（5.0+，支持消费者组、ACK、持久化，替代 List/pub-sub） |

### Q2. 每种类型的底层编码是什么？（必背，最容易追）

Redis 对象（`redisObject`）有 `type`（数据类型）和 `encoding`（底层编码）两层。**同一类型按数据量自动切换编码**——小数据用内存紧凑的、大数据用性能稳定的。用 `OBJECT ENCODING key` 查。

| 类型 | 小数据编码 | 大数据编码 | 切换阈值（可配） |
|------|-----------|-----------|-----------------|
| **String** | `int`（整数）/ `embstr`（≤44 字节，与 redisObject 连续分配一次 malloc） | `raw`（>44 字节，SDS 独立分配） | 44 字节 |
| **List** | `listpack`（7.0+，替代 ziplist） | `quicklist`（listpack 双向链表） | `list-max-listpack-size` |
| **Hash** | `listpack` | `hashtable` | `hash-max-listpack-entries`(128) / `-value`(64) |
| **Set** | `intset`（全整数）/ `listpack`（7.2+） | `hashtable` | `set-max-intset-entries`(512) |
| **ZSet** | `listpack` | `skiplist`（+ dict） | `zset-max-listpack-entries`(128) / `-value`(64) |

> **趋势**：7.0 起用 **listpack 全面替代 ziplist**。ziplist 有「连锁更新」缺陷（见 Q4），listpack 每个 entry 独立记录自己长度、不再存前一节点长度，从设计上消除连锁更新。

### Q3. String 底层的 SDS 是什么？比 C 字符串好在哪？

**SDS（Simple Dynamic String，简单动态字符串）**，Redis 自己的字符串实现，不用 C 原生 `char*`：

- **O(1) 取长度**：结构体存 `len`，不用像 C 那样遍历到 `\0`。
- **二进制安全**：靠 `len` 界定边界，能存 `\0`、图片、序列化数据；C 字符串遇 `\0` 就截断。
- **杜绝缓冲区溢出**：拼接前检查 `alloc` 空间，不够自动扩容。
- **预分配 + 惰性释放**：扩容时多分配（`<1MB` 翻倍、`≥1MB` 每次多 1MB），减少 realloc；缩短时不立即回收内存（存 `alloc`）。
- **省内存**：5 种 header（sdshdr5/8/16/32/64）按字符串长度选最小的 `len`/`alloc` 字段类型。

### Q4. ziplist / listpack 是什么？为什么要有？连锁更新是什么？

- **ziplist（压缩列表）**：一段**连续内存**，紧凑存放多个元素，省内存、缓存友好。用于小 Hash/List/ZSet。缺点：查找是 O(n)、更新可能触发**连锁更新**。
- **连锁更新（cascade update）**：ziplist 每个 entry 存「前一个 entry 的长度 `prevlen`」，用 1 字节（前节点 <254B）或 5 字节表示。如果一堆 250~253 字节的节点排一起，某处插入一个大节点，导致后一个的 `prevlen` 从 1 字节涨到 5 字节 → 它自己变长 → 又触发它后面的 `prevlen` 扩张……**多米诺式连环 realloc**，最坏 O(n²)。
- **listpack（紧凑列表，7.0 全面启用）**：每个 entry 记录**自己的长度**（放在 entry 末尾，可反向遍历），不再存前节点长度 → **根除连锁更新**。

### Q5. ZSet 为什么用「跳表 + 哈希表」两个结构？

ZSet 大数据量时底层是 **skiplist + dict（哈希表）** 双结构，同一份数据两种索引：

- **哈希表 dict**：`member → score` 映射，让 `ZSCORE`（按成员查分值）达到 **O(1)**。
- **跳表 skiplist**：按 score 排序，让 `ZRANGE`/`ZRANK`/范围查询达到 **O(log n)**，且天然支持范围遍历。
- **为什么不用平衡树（红黑树/AVL）？** ① 跳表实现简单得多，范围查询直接顺链表走、不用中序遍历；② 并发/内存友好；③ 作者 antirez 明确说「跳表更简单、内存可控（每层节点数靠概率 p=0.25 控制）、范围操作更自然」。
- **两个结构共享同一份 member/score 对象**（指针指向同一份），不是存两遍，额外内存只是索引指针。

### Q6. 跳表（skiplist）原理？查询为什么 O(log n)？

跳表是「**多层链表 + 概率索引**」：底层是完整的有序链表，往上每一层是下一层的「稀疏索引」，每个节点以概率 `p=0.25` 决定是否「长高一层」。

- **查找**：从最高层开始，能往右走就往右（跳过大段节点），走过头就下一层，逐层逼近。像「先坐高铁跨省，再换地铁进城，最后步行到门口」。
- **复杂度**：每层期望节点数是下层的 `1/p`，层数期望 `log_{1/p} n`，每层期望走 `1/p` 步 → **O(log n)**。
- **对比 B+ 树**：跳表是内存结构，不追求「压矮减少磁盘 IO」；B+ 树是磁盘结构，靠多叉压矮树减少 IO。选型看介质——详见 [四棵树对比](../mysql/tree-structures-bplus-btree-rbtree-20260708.md)。

## 二、单线程与线程模型（考频 ★★★★★）

### Q7. Redis 为什么快？（必背，多角度）

1. **纯内存操作**：数据在内存，读写不走磁盘（持久化是旁路）。
2. **单线程无锁**：命令执行单线程，没有多线程的锁竞争、上下文切换、竞态问题。
3. **I/O 多路复用（epoll）**：一个线程用 epoll 同时监听成千上万个连接，就绪才处理，不为每连接开线程。
4. **高效数据结构**：SDS、跳表、listpack、intset 等针对场景高度优化。
5. **简洁的协议（RESP）**：文本协议，解析快。

### Q8. Redis 是单线程还是多线程？（陷阱题，要分清）

**「核心命令执行是单线程，但整体是多线程。」** 分层说：

- **命令处理（主流程）**：始终**单线程**——读命令、执行、写数据都在一个「主线程」的事件循环里，保证原子性、无需加锁。
- **后台线程（很早就有）**：`bio` 线程负责耗时的异步任务——`AOF fsync`、异步删除大 key（`UNLINK`/`FLUSHALL ASYNC`）、关闭文件描述符。避免这些操作阻塞主线程。
- **I/O 多线程（6.0+，默认关闭）**：`io-threads` 让**网络 I/O 的读取解析 + 结果回写**并行化（多核 CPU 下网络收发是瓶颈时开启），但**命令的实际执行仍是单线程**。
- **7.x/8.0**：I/O 多线程进一步增强，但「一条命令怎么执行」这件事永远单线程。

### Q9. epoll 相比 select/poll 好在哪？（接操作系统格 2）

- **select/poll**：每次调用要把**全部 fd 集合**从用户态拷到内核态，返回后还要**遍历所有 fd** 找就绪的，O(n)；select 还有 1024 上限。
- **epoll**：内核维护一个**红黑树**存关注的 fd（增删 O(log n)），就绪的 fd 通过**回调**放进一个**就绪链表**；`epoll_wait` 直接返回就绪列表，**只处理活跃连接**，O(活跃数)，不随总连接数线性劣化。
- **Redis 的封装**：`ae.c` 事件驱动库，按平台自动选 epoll(Linux)/kqueue(BSD/Mac)/evport/select，对上暴露统一的 `aeApiPoll`。

### Q10. 单线程会不会被一条慢命令堵死？

**会——这是单线程的最大风险。** 一条 `keys *`、`hgetall 大hash`、`sort`、`flushdb`（同步）在执行时会**独占主线程**，后面所有命令排队阻塞。

- **规避**：禁用 `keys *`（用 `scan` 游标渐进遍历）；大 key 拆分或用 `hscan`；删大 key 用 `unlink`（异步）；`flushall async`。
- **慢查询定位**：`slowlog get`（`slowlog-log-slower-than` 微秒阈值），排查阻塞元凶。

## 三、持久化（考频 ★★★★★）

### Q11. RDB vs AOF 对比？

| | RDB | AOF |
|--|-----|-----|
| **本质** | 内存**快照**（某时刻全量二进制） | **命令追加日志**（记录每条写命令） |
| **文件** | 紧凑二进制，小 | 文本命令，大 |
| **恢复速度** | 快（直接加载） | 慢（重放命令） |
| **数据安全** | 差（两次快照间宕机全丢） | 好（最多丢 1s，看 fsync 策略） |
| **性能影响** | fork 时短暂阻塞 | 每条命令写 buffer + 定期 fsync |
| **触发** | `save`(阻塞)/`bgsave`(fork 后台)/配置 `save 900 1` | 每条写命令 append |
| **适用** | 备份、灾备、能容忍丢数据 | 对数据安全要求高 |

### Q12. AOF 的三种 fsync 策略？重写（rewrite）是什么？

**`appendfsync` 三档**：
- `always`：每条命令都 fsync，最安全、最慢。
- `everysec`（默认）：每秒 fsync 一次，宕机最多丢 1s，性能与安全平衡。
- `no`：交给 OS（一般 30s），最快最不安全。

**AOF 重写（rewrite）**：AOF 会越写越大（同一 key 反复改会留一堆历史命令）。重写 = 扫描当前内存数据，生成「能重建现状的最小命令集」（如 100 次 `incr` 压成一条 `set n 100`）。`bgrewriteaof` fork 子进程后台做，期间新命令写进 **AOF 重写缓冲区**，重写完追加进去。

### Q13. 混合持久化（RDB + AOF）是什么？为什么推荐？

- **痛点**：RDB 恢复快但丢数据多；AOF 安全但文件大、恢复慢。
- **混合持久化（4.0+，7.x 建议开 `aof-use-rdb-preamble yes`）**：AOF **重写时**，把当前内存以 **RDB 格式**写进 AOF 文件头部（全量、紧凑），重写之后的增量命令再以 **AOF 格式**追加在后。
- **好处**：恢复时先加载 RDB 部分（快）+ 重放少量 AOF 增量（安全）→ **兼得快恢复 + 少丢数据**。这是生产推荐配置。

### Q14. fork 和 COW（写时复制）在持久化里的作用？

- **fork**：`bgsave` / `bgrewriteaof` 都 fork 一个**子进程**做持久化，主进程继续服务。fork 时子进程共享父进程内存页（不真拷贝）。
- **COW（Copy-On-Write，写时复制）**：fork 后父子共享物理内存页（只读）；主进程有写入时，**只复制被写的那一页**，改副本，子进程仍看到 fork 那一刻的旧数据 → 保证快照一致性。
- **fork 的代价**：fork 本身要复制**页表**，内存越大越慢（几 GB 可能阻塞几十~上百 ms）；且写入越频繁 COW 复制的页越多，内存可能翻倍。所以大实例要控内存、错峰持久化。

## 四、过期与内存淘汰（考频 ★★★★★）

### Q15. Redis 怎么删除过期 key？（过期删除策略）

**惰性删除 + 定期删除 双管齐下**（不用定时删除，因为每个 key 一个定时器太耗 CPU）：

- **惰性删除（lazy）**：key 被**访问时**才检查是否过期，过期就删。优点省 CPU，缺点过期了没人访问就一直占内存。
- **定期删除（periodic）**：每隔一段时间（`hz` 控制频率，默认每秒 10 次）**随机抽样**一批设了过期时间的 key，删掉其中过期的；若过期比例超 25% 就再抽一批，直到降下来（有时间上限，不长时间阻塞）。
- **兜底**：以上都漏了（过期但没被访问、也没抽到）→ 靠**内存淘汰策略**在内存到顶时清理。

### Q16. 内存淘汰策略有哪几种？（`maxmemory-policy`）

`maxmemory` 到顶后触发，**8 种**：

| 策略 | 范围 | 规则 |
|------|------|------|
| `noeviction` | — | 不淘汰，写命令直接报错（默认） |
| `allkeys-lru` | 所有 key | 淘汰最久未使用（**最常用**做纯缓存时） |
| `allkeys-lfu` | 所有 key | 淘汰使用频率最低（4.0+，热点更稳） |
| `allkeys-random` | 所有 key | 随机淘汰 |
| `volatile-lru` | 设了过期的 key | LRU |
| `volatile-lfu` | 设了过期的 key | LFU |
| `volatile-random` | 设了过期的 key | 随机 |
| `volatile-ttl` | 设了过期的 key | 淘汰剩余 TTL 最短的 |

> **选型口诀**：纯缓存用 `allkeys-lru`（或 lfu）；缓存 + 持久数据混存用 `volatile-*`（只淘汰能淘汰的）；不允许丢用 `noeviction` + 监控告警。

### Q17. Redis 的 LRU 是真 LRU 吗？LFU 怎么算频率？

- **近似 LRU（不是精确 LRU）**：精确 LRU 要维护一个全局双向链表，每次访问移动节点，内存和性能开销大。Redis 改为**随机采样**——每个对象的 redisObject 里存一个 24 位 `lru` 时间戳，淘汰时随机取 `maxmemory-samples`（默认 5）个 key，淘汰其中最旧的。采样越多越接近真 LRU，但更耗 CPU。
- **LFU（Least Frequently Used，4.0+）**：那 24 位拆成 **16 位上次访问时间 + 8 位访问计数（logc）**。计数用**对数递增**（访问越多涨得越慢，防止某 key 一时暴热就永远淘汰不掉）+ **随时间衰减**（`lfu-decay-time`，久不访问频率会降）。比 LRU 更抗「偶发扫描污染」。

## 五、缓存三大问题与一致性（考频 ★★★★★）

### Q18. 缓存穿透、击穿、雪崩，分别是什么、怎么解决？（核心必背）

| 问题 | 定义 | 解决方案 |
|------|------|---------|
| **穿透** | 查一个**数据库里也不存在**的 key（如恶意刷 id=-1），每次都绕过缓存打到 DB | ① **缓存空值**（`set key null ex 60`）；② **布隆过滤器**（拦掉一定不存在的）；③ 接口层校验、限流 |
| **击穿** | **单个热点 key 过期的瞬间**，大量并发同时打到 DB（热点失效） | ① **互斥锁**（只让一个线程重建缓存，其余等待）；② **逻辑过期**（value 里存过期时间，不真过期，异步重建）；③ 热点 key **永不过期** |
| **雪崩** | **大量 key 同时过期** 或 **Redis 宕机**，请求集体打到 DB，DB 被压垮 | ① 过期时间**加随机抖动**（`ttl + random`）；② **多级缓存**（本地缓存 + Redis）；③ **高可用**（Sentinel/Cluster）防宕机；④ **限流 + 熔断降级**兜底 |

**一句话记忆**：穿透 = 查**不存在**的（打穿到 DB）；击穿 = **单个热点**过期（一点被击破）；雪崩 = **大量**同时失效（一片崩塌）。

### Q19. 布隆过滤器原理？为什么能防穿透？有什么缺陷？

- **原理**：一个位数组 + k 个哈希函数。存入 x 时，k 个哈希算出 k 个位置全置 1；查询 x 时，k 个位置**只要有一个是 0 → 一定不存在**；全是 1 → **可能存在**（有误判）。
- **特性**：**有误判、无漏判**——「说不存在就一定不存在，说存在可能不存在」。刚好适合防穿透：把 DB 里所有 id 灌进去，查询前先过一遍，不存在的直接挡回。
- **缺陷**：① 有假阳性（漏放极少量本该拦的）；② **不支持删除**（删一个可能影响别的 key 的位）→ 需要计数布隆过滤器或 **Cuckoo Filter**；③ 需预估容量。Redis 用 `RedisBloom` 模块或自己用 Bitmap 实现。

### Q20. 缓存有哪几种读写模式？（Cache-Aside / Read-Through / Write-Through / Write-Behind）

这是「缓存模式」的经典四件套，面试问「你了解哪些缓存策略」时的标准答案。**核心区别在于：谁负责读回源、谁负责写落库、写是同步还是异步。**

| 模式 | 读怎么走 | 写怎么走 | 特点 / 经典 case |
|------|---------|---------|-----------------|
| **Cache-Aside（旁路缓存）** | **应用**查缓存，miss 则查 DB 并**回填**缓存 | **应用**更新 DB，然后**删缓存**（见下面 Q21） | 最常用；缓存与 DB 解耦；应用要自己管一致性。**Redis 默认就是这个** |
| **Read-Through（读穿透）** | 应用**只问缓存**，miss 时由**缓存组件自己**回源 DB 并回填 | （通常配 Write-Through） | 对应用透明，回源逻辑收敛到缓存层；需缓存中间件支持（Caffeine `LoadingCache`、Ehcache） |
| **Write-Through（写穿透）** | 同 Read-Through | 应用**只写缓存**，缓存组件**同步**把数据写进 DB（缓存、DB 一起更新） | **强一致**（缓存永远和 DB 同步）；但每次写**两跳、延迟高**；宕机不丢（DB 已同步落） |
| **Write-Behind / Write-Back（写回/异步写）** | 同上 | 应用**只写缓存立即返回**，缓存**异步批量**刷回 DB | **写极快 + 可合并写**；但**宕机丢数据、一致性弱**。OS page cache、MySQL buffer pool 刷脏页、Redis AOF 缓冲都是这个思路 |

**几个必答的辨析（经典 case）**：

- **Write-Through vs Cache-Aside 的写**：Write-Through 是「写缓存 → 缓存同步写库」，缓存**始终有最新值**；Cache-Aside 是「写库 → **删**缓存」，下次读再回填，缓存写完短暂为空。前者读命中率高、一致性强，代价是写慢、且写了不一定被读（浪费）。
- **Write-Through vs Write-Behind**：唯一区别是**同步还是异步落库**。同步 = 强一致 + 慢；异步 = 快 + 可能丢（进程/机器宕机时缓存里没刷的数据没了）。Write-Behind 靠「攒批 + 合并」把 N 次写压成 1 次落库，写密集场景吞吐高。
- **为什么 Redis 场景几乎只用 Cache-Aside**：Read/Write-Through 要求缓存层「认识」数据源、能自己回源/回写，而 **Redis 是独立缓存，不知道你的 MySQL 长什么样**——回源和落库逻辑只能写在应用里，那本质就是 Cache-Aside。Write-Through/Behind 更多出现在**本地缓存框架**（Caffeine/Ehcache/Spring Cache 抽象）或**自带缓存的存储**（DynamoDB DAX）里。面试若问「Redis 用哪种」，答 **Cache-Aside**，再补一句「Write-Through/Behind 需要缓存组件感知数据源，Redis 独立部署时不具备」。

### Q21. Cache-Aside 下缓存与数据库一致性怎么保证？先删缓存还是先更新库？

**根因**：更新 DB 和更新缓存是两次独立操作，**无法原子**，并发下必有窗口不一致。只能追求**最终一致**。

**四种组合分析**（更新场景）：
- **先更新 DB，再更新缓存**：❌ 并发写会乱序覆盖（A 更新 DB 为 1、B 更新 DB 为 2，但缓存写入顺序可能反了）；且缓存可能永远用不到，浪费。
- **先更新缓存，再更新 DB**：❌ 缓存成功 DB 失败 → 脏数据。
- **先删缓存，再更新 DB**：❌ 删完缓存、DB 还没更新时，读请求把**旧值**又加载回缓存 → 长期脏。
- **先更新 DB，再删缓存（Cache-Aside，推荐）**：✅ 相对最优。极端并发下仍有小概率不一致（读线程在「删缓存」前读到旧 DB 值、又在删之后写回），但概率极低。

**兜底方案**：
- **延迟双删**：先删缓存 → 更新 DB → **延迟一会（如 500ms）再删一次**，清掉期间被读线程写回的旧值。
- **给缓存设 TTL**：即使不一致，过期后自动纠正（最终一致的保底）。
- **订阅 binlog（Canal）异步删缓存**：把「删缓存」从业务代码解耦，DB 变更 → binlog → 消息队列 → 删缓存，更可靠。

## 六、分布式锁（考频 ★★★★★）

### Q22. 用 Redis 实现分布式锁，正确姿势？（一步步演进）

**最终正确写法**：
```
SET lock_key unique_value NX PX 30000     -- 加锁：不存在才设 + 30s 自动过期
-- ... 执行业务 ...
-- 释放锁必须用 Lua 保证「判断+删除」原子：
if redis.call('get', KEYS[1]) == ARGV[1]
then return redis.call('del', KEYS[1]) else return 0 end
```

**为什么每个细节都不能少（追问链）**：
- **为什么用 `NX`**：`SET NX` = 不存在才设置，天然互斥（老写法 `setnx` + `expire` 两条命令非原子，中间宕机会死锁；`SET ... NX PX` 一条命令搞定）。
- **为什么要 `PX` 过期时间**：防止持锁进程崩溃后锁永不释放 → **死锁**。
- **为什么 value 要唯一值（如 UUID/线程 ID）**：防止**误删别人的锁**——A 的锁超时自动释放，B 拿到锁，A 业务执行完来 `del` 会删掉 B 的锁。释放时先校验 value 是不是自己的。
- **为什么释放要用 Lua**：`get` 判断和 `del` 删除是两步，非原子 → 判断通过后、del 前锁刚好过期被 B 拿走，还是会误删。Lua 脚本在 Redis 里**原子执行**。

### Q23. 锁的过期时间设多长？业务没执行完锁就过期了怎么办？

- **矛盾**：设短了业务没跑完锁就没了（别人进来）；设长了崩溃后要等很久才释放。
- **看门狗（watchdog）自动续期**：**Redisson** 的方案——加锁默认 30s，起一个后台线程每 `10s`（1/3 过期时间）检查业务还在跑就**续期到 30s**，直到业务结束或进程死亡（进程死了续期停止，锁自然过期）。这是生产首选。
- 手写要自己实现续期线程 + Lua 续期脚本。

### Q24. Redlock 是什么？为什么有争议？

- **单点问题**：单 Redis 或主从下，主库加锁成功但**还没同步到从库就宕机**，从库升主 → 锁「丢了」，两个客户端同时持锁。
- **Redlock（红锁）**：antirez 提出，向 **N 个独立 Redis 节点**（无主从关系）依次加锁，**多数派（N/2+1）成功且总耗时小于锁有效期**才算加锁成功。
- **争议**：分布式系统专家 **Martin Kleppmann** 撰文质疑——Redlock 依赖**时钟同步**（GC 停顿、时钟漂移会破坏安全性），且不如基于 fencing token（单调递增令牌）+ 一致性存储（Zookeeper/etcd）的方案可靠。**结论**：强一致场景用 **etcd/Zookeeper**（基于 Raft/ZAB 共识）；一般业务单节点 `SET NX` + 看门狗够用，别盲目上 Redlock。

## 七、主从、哨兵、集群（考频 ★★★★★）

### Q25. 主从复制原理？全量 vs 增量？

**作用**：读写分离、数据冗余、故障恢复的基础。写主库、读从库。

**首次全量同步（full resync）**：
1. 从库发 `PSYNC ? -1`，主库执行 `bgsave` 生成 **RDB** 快照发给从库。
2. 生成 RDB 期间的新写命令，缓存进 **replication buffer**，RDB 传完后补发。
3. 从库清空自己数据、加载 RDB，再执行补发命令 → 追平。

**增量同步（断线重连，2.8+ 的 partial resync）**：
- 主从各维护 **复制偏移量 offset** + 主库有一个环形 **repl_backlog_buffer**（复制积压缓冲区）。
- 从库断线重连，带上自己的 offset 和主库 `runid`，若断线期间的数据**还在 backlog 里** → 只补发缺失部分（增量）；若 backlog 已被覆盖 → 退化为全量同步。
- 之后是**命令传播**：主库每条写命令实时发给从库。

### Q26. Sentinel（哨兵）是什么？怎么做故障转移？

**Sentinel 解决主从的「主库宕机需人工切换」问题**，是独立进程集群（一般 3/5 个，奇数）：

- **监控**：每秒 `ping` 主从和其他哨兵。
- **主观下线（SDOWN）**：单个哨兵 ping 不通某主库 → 主观认为它下线。
- **客观下线（ODOWN）**：达到配置的 **quorum** 个哨兵都认为主库下线 → 确认客观下线。
- **选举 Leader 哨兵**：用 **Raft** 类算法选一个哨兵负责故障转移。
- **故障转移**：从所有从库里选一个新主库（依据：优先级 → 复制 offset 最大 → runid 最小），`slaveof no one` 提升为主，其余从库改指向新主，通知客户端。
- **局限**：哨兵**只保证高可用，不解决容量/写扩展**（还是单主写）。数据量大要上 Cluster。

### Q27. Redis Cluster（集群）原理？16384 个槽是怎么回事？

**Cluster 解决单机容量和写并发瓶颈**——数据分片（sharding），去中心化。

- **哈希槽（hash slot）**：共 **16384 个槽**，每个 key 用 `CRC16(key) % 16384` 定位到一个槽，槽分配给不同主节点。加/减节点时**迁移槽**（迁的是槽，不是逐个 key 重算）。
- **为什么是 16384（2^14）而非 65536**：① 节点间用心跳交换槽位图（bitmap），16384 位 = 2KB，65536 位 = 8KB，心跳包省带宽；② 集群一般不超 1000 节点，16384 够分。（作者原话）
- **去中心化**：节点间用 **Gossip 协议** 互相传播集群状态（谁负责哪些槽、谁下线），无中心节点。
- **重定向**：客户端请求的 key 不在本节点 → 返回 `MOVED`（槽已迁走，客户端更新缓存重连）或 `ASK`（槽正在迁移中，临时重定向）。智能客户端会缓存槽映射，直连正确节点。
- **高可用**：每个主节点带从节点，主挂了从节点自动升主（集群内部自己做故障转移，不需要哨兵）。

### Q28. Cluster 下多 key 操作（如 `mget`、事务、Lua）为什么会报错？hash tag 是什么？

- **问题**：多个 key 可能分布在不同节点，`mget k1 k2`、事务、Lua 涉及的 key 不在同一节点 → 报 `CROSSSLOT` 错。
- **hash tag（哈希标签）**：给 key 用 `{}` 包一段，**只用花括号内的部分算槽**——`user:{123}:name` 和 `user:{123}:age` 都按 `123` 算槽 → 落同一节点，就能一起操作。用于强制相关 key 同槽。

### Q29. 三种高可用方案怎么选？（Sentinel vs Cluster vs 主从）

| 方案 | 解决什么 | 不解决什么 | 场景 |
|------|---------|-----------|------|
| **主从复制** | 数据冗余、读扩展 | 自动故障转移、写扩展、容量 | 读多写少、能接受手动切换 |
| **哨兵 Sentinel** | 主从 + **自动故障转移** | 写扩展、容量（仍单主写） | 数据量不大、要高可用 |
| **集群 Cluster** | 分片 → **容量 + 写扩展 + 高可用** | 跨槽事务/多 key（受限） | 大数据量、高并发写 |

> 演进路线：**单机 → 主从 → 哨兵 → 集群**，按「容量和并发是否到顶」逐级上。

## 八、事务、Lua、Pipeline（考频 ★★★）

### Q30. Redis 事务（MULTI/EXEC）是什么？和 MySQL 事务的区别？

- **用法**：`MULTI` 开启 → 命令入队（不立即执行）→ `EXEC` 一次性顺序执行 → `DISCARD` 取消。`WATCH key` 做乐观锁（key 被改则 EXEC 失败）。
- **和 MySQL 事务的本质区别**：
  - **不保证原子性回滚**！事务中若某命令**运行时出错**（如对 String 用 `lpush`），其他命令**照常执行**，不回滚。Redis 认为这类错误是程序 bug，不该靠回滚兜底。只有**入队时语法错**才会整体不执行。
  - **无隔离级别概念**（单线程，命令串行执行，天然「隔离」）。
  - 弱事务，实际项目更常用 **Lua 脚本**替代事务保证原子性。

### Q31. 为什么 Lua 脚本能保证原子性？和 Pipeline 区别？

- **Lua 原子性**：Redis 把整个 Lua 脚本当**一条命令**在单线程里跑完，中间不会插入其他命令 → 天然原子（分布式锁释放、库存扣减常用）。注意：脚本里别写死循环/慢操作，会阻塞整个 Redis。
- **Pipeline（管道）**：客户端把多条命令**打包一次性发送**，减少 **RTT（网络往返）** 次数，服务端依次执行后一次性返回。**Pipeline 不保证原子**（中间可能插入别人的命令），它只是**批量减少网络开销**的优化，不是事务。
- **区别**：Lua = 原子 + 服务端逻辑；Pipeline = 批量网络优化，不原子。

## 九、生产运维与其余高频（考频 ★★★★）

### Q32. bigkey（大 key）和 hotkey（热 key）是什么？危害与解决？

**bigkey（大 key）**：单个 key 的 value 过大（String >10KB，或集合类元素过多 >5000）。
- **危害**：① 内存分布不均；② 操作（`del`/`hgetall`）耗时长，阻塞单线程；③ 删除时集中释放内存卡顿；④ 网络传输大、Cluster 迁移慢。
- **排查**：`redis-cli --bigkeys`、`MEMORY USAGE key`、`SCAN` + 分析。
- **解决**：拆分（大 Hash 按 field 哈希分成多个小 Hash）；删除用 `unlink`（异步）；压缩 value；集合类用 `hscan` 分批读。

**hotkey（热 key）**：某 key 访问量远超其他（爆款商品、明星微博），压垮单个节点。
- **排查**：`redis-cli --hotkeys`（需 LFU 策略）、`MONITOR`（慎用）、业务埋点。
- **解决**：① **本地缓存**（多级缓存，热点在应用内存挡一层）；② **key 拆分/加随机后缀**打散到多节点（`hotkey_1`~`hotkey_N` 随机读）；③ 读写分离扩从库。

### Q33. Redis 做延迟队列怎么实现？

- **ZSet 方案**：`score` 存执行时间戳，`zadd delay_queue <到期时间> <任务>`；消费者轮询 `zrangebyscore delay_queue 0 <当前时间>` 取到期任务，取到后 `zrem` 删除（要用 Lua 或事务保证「取 + 删」原子，防重复消费）。
- **Stream 方案**：5.0+ 原生消息队列，支持消费者组 + ACK + 重试，比 List/ZSet 更完善。
- 生产更常用专业 MQ（RabbitMQ 死信队列 / RocketMQ 延迟消息 / Kafka）。

### Q34. Redis 做限流有哪些方式？

- **固定窗口**：`incr key` + 首次 `expire`，超阈值拒绝。缺点：窗口边界突刺（临界两秒双倍流量）。
- **滑动窗口**：用 ZSet，`score` = 时间戳，`zremrangebyscore` 清过期 + `zcard` 数当前窗口请求数。
- **令牌桶 / 漏桶**：Lua 脚本实现，更平滑。Redis 4.0+ 有 `redis-cell` 模块（`CL.THROTTLE`）原生令牌桶。

### Q35. Pub/Sub 和 Stream 的区别？为什么消息队列更推荐 Stream？

- **Pub/Sub（发布订阅）**：实时广播，**不持久化**——订阅者不在线就丢消息，无 ACK、无回溯。适合实时通知（如配置变更广播），不适合可靠消息队列。
- **Stream（5.0+）**：**持久化** + **消费者组**（多消费者分摊）+ **ACK 确认**（`XACK`）+ **消息回溯**（`XRANGE`）+ **Pending 列表**（未确认消息可重投）。是 Redis 里唯一「可靠 MQ」实现。

### Q36. 缓存预热、缓存降级是什么？

- **缓存预热**：系统上线/重启前，提前把热点数据加载进缓存，避免上线瞬间大量请求全打到 DB（冷启动雪崩）。
- **缓存降级**：极端情况（Redis 挂了/压力过大），暂时关闭非核心缓存逻辑、直接读 DB 或返回兜底默认值/旧数据，保证核心链路可用（服务可用性 > 数据实时性）。

## 十、底层机制 + 高可用深水区（高频补充，考频 ★★★★）

> 这一章是「区分度题」——前九章答好算合格，这一章答好算亮点。多是底层机制和高可用的坑，面试官最爱往这里追。

### Q37. Redis vs Memcached？（经典对比开场题）

| 维度 | Redis | Memcached |
|------|-------|-----------|
| **数据结构** | 丰富（String/List/Hash/Set/ZSet/Bitmap/HLL/GEO/Stream） | 只有 KV（String） |
| **持久化** | RDB/AOF | ❌ 纯内存，重启全丢 |
| **高可用** | 原生主从/哨兵/Cluster | ❌ 无原生，靠客户端分片 |
| **线程模型** | 单线程（6.0+ I/O 多线程） | 多线程 |
| **内存管理** | 灵活，可能有碎片 | **slab 预分配**，固定规格，碎片少 |
| **value 上限** | String 512MB | 默认 1MB |
| **功能** | 事务/Lua/发布订阅/Stream/过期通知 | 基本没有 |

**结论**：绝大多数场景选 **Redis**（功能全面）。Memcached 只在「纯 KV、超大规模、多核纯缓存、value 大小固定」的边缘场景还有一点点优势（多线程 + slab 抗碎片），实际已基本被 Redis 取代。

### Q38. 渐进式 rehash 是什么？dict 扩容为什么不阻塞？

Redis 底层的 **dict（哈希表）** 会因负载因子过高而扩容（默认 >1 且当前无 bgsave/bgrewriteaof 时扩，>5 强制扩）、过低而缩容。百万级 key 一次性 rehash 会长时间独占单线程 → 用**渐进式 rehash** 摊开：

- dict 内含**两个哈希表** `ht[0]`、`ht[1]`。扩容时先给 `ht[1]` 分配更大空间（2 的幂），置 `rehashidx=0`。
- **不一次搬完**：每次对 dict 的增删改查操作，**顺带**把 `ht[0]` 在 `rehashidx` 处的一个桶迁到 `ht[1]`，`rehashidx++`；后台 `serverCron` 也每次限时搬一批。
- **rehash 期间读写规则**：新增只写 `ht[1]`（保证 `ht[0]` 只减不增，最终清空）；查/改/删先查 `ht[0]` 再查 `ht[1]`。
- 全部搬完，`ht[1]` 变 `ht[0]`，释放旧表。
- **代价**：rehash 期间两表并存，**内存短暂翻倍**。好处是把一次大停顿摊成每次 O(1)，不阻塞。

### Q39. 为什么禁用 `keys *`？SCAN 怎么做到渐进遍历、不重不漏？

- **`keys *` 一次性返回所有 key，O(n) 独占单线程**，key 多时直接卡死，生产**禁用**。
- **SCAN 游标式遍历**：`SCAN cursor` 每次返回一小批 key + 下一个游标，`cursor=0` 开始、再次返回 `0` 结束。单次只扫一小段，不阻塞。
- **保证与不保证**：① 遍历全程**未变动**的 key 一定被返回（不漏）；② 但**期间新增/删除**的 key 是否返回不确定；③ **同一 key 可能返回多次**，业务要自己去重。
- **关键机制——高位进位游标（reverse binary iteration）**：游标的二进制**从高位往低位加**，这样即使遍历途中 dict 发生了扩容/缩容（桶数变化），已遍历和未遍历的桶也不会错乱，从而在 rehash 中仍**不漏**。这是 SCAN 设计的精髓。
- **家族**：`HSCAN`/`SSCAN`/`ZSCAN` 渐进遍历大 hash/set/zset，是处理 bigkey 的标准手段。`COUNT` 只是「每次扫多少桶」的 hint（非精确条数），`MATCH` 是返回后过滤（不减少扫描量）。

### Q40. 主从复制下，过期 key 怎么处理？（经典陷阱）

**核心：从库不主动删除过期 key，一切以主库为准。**

- **从库不会自己删过期 key**。当从库读到一个逻辑上已过期的 key 时（Redis 3.2+），**对外返回 nil（当作不存在）**，但**并不真正删除**它。
- 真正的删除由**主库**做（惰性 + 定期），主库删除后会**向从库发一条 `DEL`/`UNLINK`** 命令，从库据此删除。
- **为什么这么设计**：保证主从数据严格一致、以主库为准。若从库自行删除，可能出现「主库还没删、从库已删」的不一致。
- **老坑**：3.2 之前的从库读过期 key 可能返回**旧值**（脏读），3.2 起修复为返回 nil。

### Q41. Redis 什么情况下会丢数据？脑裂是什么？（高可用必问）

**两大丢数据场景**：
1. **异步复制丢数据**：主库写完**立即返回客户端**（复制是异步的），若此刻主库宕机、数据还没同步到从库 → 从库升主 → 这批数据丢失。
2. **脑裂（split-brain）**：主库与哨兵/从库之间**网络分区**，哨兵误判主库已死、选出新主；但老主库其实还活着，仍在接收部分客户端的写。此时集群有**两个主库**。网络恢复后，老主库降级为从库并**全量同步新主**，它在分区期间接收的写**被覆盖丢失**。

**缓解（只能降低概率，不能根治，Redis 本质是 AP）**：
- **`min-replicas-to-write N` + `min-replicas-max-lag S`**（旧名 `min-slaves-*`）：主库必须至少有 N 个从库连接、且复制延迟在 S 秒内，才接受写。脑裂时老主库连不上足够从库 → **拒绝写** → 大幅减少脑裂丢数据。
- 强一致场景改用 **etcd/Zookeeper（Raft/ZAB 共识）**，或用 `WAIT` 命令做「写后等 N 个从库确认」的准同步。

### Q42. 内存碎片是什么？怎么监控和处理？

- **成因**：① **内部碎片**——分配器（jemalloc）按固定规格分配，申请 size 和实际分配对不齐；② **外部碎片**——key 频繁改大小/删除，内存还给了分配器但没还给 OS。
- **监控**：`INFO memory` 的 **`mem_fragmentation_ratio` = used_memory_rss / used_memory**。
  - `> 1.5`：碎片严重（物理内存占用远大于实际数据）→ 该处理。
  - `< 1`：发生了 **swap**（内存不够、用到磁盘），性能暴跌，更危险。
- **处理**：① 重启节点（重新加载最彻底，但需主从切换避免中断）；② **`activedefrag yes`**（4.0+ 在线自动碎片整理，牺牲少量 CPU）；③ `MEMORY PURGE`。
- **预防**：避免大量变长、频繁增删的 key。

### Q43. 工程细节速记（RESP / EVALSHA / 可重入锁 / 容量上限）

- **RESP（Redis Serialization Protocol）**：客户端-服务端通信协议，用**首字节区分类型**（`+`简单串 / `-`错误 / `:`整数 / `$`批量串 / `*`数组），文本为主、解析快。**RESP3（6.0）** 新增 map/set/double 等类型，并支持服务端**推送**（client-side caching 的基础）。
- **EVAL vs EVALSHA**：`EVAL` 每次传整段脚本；`EVALSHA` 只传脚本的 **SHA1**（脚本已缓存在服务端）→ 省带宽。先 `SCRIPT LOAD`，再 `EVALSHA`，遇 `NOSCRIPT` 回退 `EVAL`。
- **可重入锁（Redisson）**：用 **Hash 结构**存锁——field = 线程唯一标识、value = 重入次数。同线程再次加锁 value+1，释放时 -1，减到 0 才真删 → 支持**可重入**。配合看门狗续期（见 Q23）。
- **容量上限**：单个 String 最大 **512MB**；单 key 的集合类元素理论上限 2³²-1。

### Q44. Redis 各版本关键新特性（时效性速记）

- **6.0**：**I/O 多线程**（`io-threads`）、**ACL 权限**、**RESP3**、**客户端缓存（tracking）**、SSL/TLS。
- **7.0**：**Function**（替代部分 Lua）、**多 AOF 文件（Multi-Part AOF）**、**Sharded Pub/Sub**、**listpack 全面替代 ziplist**。
- **7.2 / 8.0**：性能优化、**向量搜索**（8.0 集成查询引擎/vector sets）、Set 用 listpack 等。

> 面试答到「6.0 引入 I/O 多线程 + ACL、7.0 引入 Function + 多 AOF + listpack 替代 ziplist」基本够用，其余点到即止。
