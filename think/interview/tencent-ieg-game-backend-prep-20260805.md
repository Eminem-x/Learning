## 0. 一页纸速查（进面试前 10 分钟扫一遍）

| 必答项 | 一句话答案 |
|---|---|
| GMP | G 协程 / M 内核线程 / P 调度上下文；P 的数量 = `GOMAXPROCS`，**只有拿到 P 的 M 才能跑 G**；本地队列满了送一半到全局；空闲 P 会 **work-stealing** 偷一半；系统调用阻塞时 **M 与 P 解绑**，P 交给别的 M 继续跑 |
| GC | **三色标记 + 混合写屏障**，两次极短 STW（mark setup / mark termination）；痛点不在 STW 在 **mark 阶段扫指针 + mutator assist 拖高业务延迟**；`GOGC=100` → 堆目标 = 存活量 ×2；用 **`GOMEMLIMIT`** 设软上限 |
| context 取消 | `Done()` 返回 `chan struct{}`，cancel 时 **`close(ch)`** → 所有 select 它的 goroutine 同时唤醒（**close 是天然的一对多广播**）；cancelCtx 持有 children，**沿树向下递归取消** |
| sync.Pool | **减少分配，不是缓存**——每轮 GC 开始时清空（1.13+ 有 victim cache 缓一轮）；P-local 的 private + shared，无锁快路径 |
| channel | `hchan` = 环形缓冲 + sendq/recvq 等待队列 + 一把互斥锁；有等待接收者时**直接内存拷贝，跳过缓冲区** |
| Protobuf | TLV（field_number<<3 \| wire_type）+ **varint 变长** + 有符号数 **zigzag**；兼容规则：**只增不改不复用字段号**，删字段要 `reserved` |
| gRPC | 底层 **HTTP/2**：多路复用（一条 TCP 跑多 stream）+ HPACK 头压缩；**TCP 层队头阻塞仍在**（HTTP/3 才解决）；四种模式：一元 / 服务端流 / 客户端流 / 双向流 |
| OTel | TraceID/SpanID **跨进程靠 W3C `traceparent` 头**，进程内靠 **`context.Context` 携带**；头部采样 vs 尾部采样 |
| 状态同步 vs 帧同步 | FPS 走**状态同步 + 服务器权威**（防外挂），配**客户端预测 + 服务器回滚 + 延迟补偿**；MOBA/RTS 常走帧同步（只同步操作指令，省带宽但要求确定性） |
| 为什么游戏用 UDP | TCP 的**重传 + 拥塞控制 + 队头阻塞**对实时性是灾难：一个包丢了，后面到了的包也不能交付。KCP = 在 UDP 上做**可靠但不保序、更激进重传**的协议，牺牲带宽换延迟 |
| 有状态服务的核心难点 | 状态在内存 → **请求必须路由到持有状态的节点**；杀一个 Pod = 一批玩家掉线 → 扩缩容要**先摘流量、等对局打完**再下线 |

### 2.1 `sync.Pool`（游戏后台高频考，因为每帧每包都在分配对象）

**它是什么**：**减少分配的对象复用池，不是缓存**——放进去的东西随时可能消失。

```go
var bufPool = sync.Pool{New: func() any { return new(Packet) }}

p := bufPool.Get().(*Packet)
defer func() { p.Reset(); bufPool.Put(p) }()   // 必须 Reset，否则脏数据泄漏到下一个使用者
```

**三个必答点**：
1. **什么时候被清空**：每轮 **GC 开始时**清理。1.13+ 引入 **victim cache**（本轮的池降级为 victim，再过一轮才真丢），所以对象大约能活过一个 GC 周期。**→ 所以它不能当缓存用**
2. **为什么快**：每个 P 有自己的 `private`（单个对象，无锁）+ `shared`（双向链表，可被其他 P 偷）。**快路径完全无锁**
3. **在游戏后台的价值**：网关每秒几十万个包，每个包都 `new` 一个 buffer → GC 压力巨大。**用 Pool 后分配次数下降一个数量级，GC 频率随之下降**——这就是"减少 GC 压力"的物理解释

### 2.2 百万连接怎么扛：goroutine-per-conn vs Reactor

**先会算账**（面试官爱让你口算）：

```
长连接网关通常一个连接起 2 个 goroutine（读循环 + 写循环）
10w 连接 = 20w goroutine
单 goroutine 初始栈 2KB → 20w × 2KB ≈ 400MB（这只是栈，还没算读写 buffer）
每连接读写 buffer 各 4KB → 再加 800MB
```

**两种模型的取舍**：

| 模型 | 优点 | 代价 |
|---|---|---|
| **goroutine-per-conn**（Go 标准写法） | 代码简单、逻辑同步、Go 调度器已经帮你做了 IO 多路复用（netpoller 底层就是 epoll） | goroutine 和栈的内存开销、连接数极大时调度压力上升 |
| **Reactor / 单 goroutine 多连接**（gnet、evio） | 内存省一个数量级、连接数上限高 | **回调式代码，业务逻辑写起来痛苦**；且会绕开 Go 的 netpoller，出问题不好查 |

**面试口径**：「**Go 的 netpoller 已经把 epoll 封在下面了，goroutine-per-conn 本质上就是同步写法 + 底层多路复用**，一般到十万级连接是够的。真到百万级、且内存吃紧，才考虑 gnet 这类 Reactor 方案，代价是业务代码退化成回调。**我会先压测拿到单机连接上限的真实数字再决定**，而不是一上来就上 Reactor。」

### 2.3 pprof 实战闭环（JD 写了"性能调优经验"，必被追问）

**准备一个完整故事，四段式**：`现象 → 用什么 profile → 看到什么 → 改了什么 + 前后数据`

```bash
go tool pprof http://ip:port/debug/pprof/profile?seconds=30   # CPU：热点函数
go tool pprof http://ip:port/debug/pprof/heap                 # 内存：谁在分配 / 谁没释放
curl 'http://ip:port/debug/pprof/goroutine?debug=2'           # goroutine：泄漏时直接看阻塞在哪一行
go tool pprof http://ip:port/debug/pprof/mutex                # 锁竞争 ← 游戏后台典型瓶颈
go tool pprof http://ip:port/debug/pprof/block                # 阻塞：channel/syscall 等待
```

> **`mutex` 和 `block` profile 默认是关的**，要先 `runtime.SetMutexProfileFraction(n)` / `runtime.SetBlockProfileRate(n)`。**知道这一点会显得你真用过。**

**四个最常见的 Go 性能坑（游戏后台版）**：

| 坑 | 现象 | 解法 |
|---|---|---|
| 大锁保护全局 map（玩家表/房间表） | mutex profile 里一条独大，CPU 上不去 | **分片锁**（按玩家 ID hash 到 N 个桶）或 `atomic.Pointer` 换整张表 |
| 每包分配新对象 | heap profile 里 alloc 巨大、GC 频繁 | `sync.Pool` 复用 |
| 大 map 常驻堆 | GC mark 阶段 CPU 高、P99 抖动 | 去指针化 / `GOMEMLIMIT` / 堆外缓存 |
| goroutine 泄漏 | `NumGoroutine` 只涨不跌 | 无缓冲 channel 写侧没有 `select ctx.Done()`；见复盘 §3.2② |

## 3. 【P0】gRPC / Protobuf：简历空白，但半天能补完

### 3.1 Protobuf 编码（必考）

**结构**：每个字段 = `Tag + [Length] + Value`，Tag = `(field_number << 3) | wire_type`。

**varint 变长编码**：每字节用低 7 位存数据、最高位是"还有后续字节"标志。**小数字只占 1 字节**——这是它比 JSON 小的主因之一（JSON 里数字 `1` 也要占 1 字节字符 + 字段名一整串）。

**zigzag（有符号数为什么要它）**：varint 对负数很不友好——`-1` 的补码是全 1，直接 varint 编码要占 10 字节。zigzag 把有符号数映射成无符号数：

```
 0 → 0,  -1 → 1,  1 → 2,  -2 → 3,  2 → 4 ...
公式：(n << 1) ^ (n >> 31)     // 让绝对值小的数，编码后也小
```
**`sint32/sint64` 才用 zigzag，`int32/int64` 不用**——所以存负数要用 `sint`，这是个爱考的细节。

**兼容性规则（最爱考）**：

| 操作 | 允许？ | 原因 |
|---|:--:|---|
| 新增字段（用新字段号） | ✅ | 老代码遇到不认识的字段号会跳过（存进 unknown fields） |
| 删除字段 | ⚠️ | **必须 `reserved` 掉字段号和名字**，否则以后有人复用会导致数据错乱 |
| **复用已删除的字段号** | ❌ | 老数据里那个字段号还有旧值，会被解析成新字段 → **静默数据错误** |
| 改字段名 | ✅ | 编码只认字段号，不认名字（但 JSON 映射会变） |
| 改字段类型 | ❌ 大多不行 | 少数兼容（int32↔int64↔bool 的 varint 家族） |

> **为什么比 JSON 快**：① 二进制无需解析文本；② 不传字段名，只传字段号；③ varint 压缩数字；④ **代码生成，无反射**（Go 的 encoding/json 走反射）。

### 3.2 gRPC

**四种模式**（记住它们对应什么场景）：

| 模式 | 场景 |
|---|---|
| 一元 Unary | 普通 RPC，90% 的调用 |
| 服务端流 | 服务端持续推送——**游戏里的状态广播候选** |
| 客户端流 | 客户端持续上报——埋点、日志上传 |
| **双向流** | 长连接双向通信——**和 WebSocket 是同一生态位** |

**底层是 HTTP/2，三件事必答**：
1. **多路复用**：一条 TCP 连接上跑多个 stream，各 stream 独立——解决了 HTTP/1.1 的**应用层队头阻塞**
2. **HPACK 头压缩**：静态表 + 动态表 + 哈夫曼，RPC 场景头部高度重复，压缩收益极大
3. **⚠️ TCP 层的队头阻塞仍然存在**：一个 TCP 包丢了，后面所有 stream 的数据都得等它重传。**这才是 HTTP/3 换 QUIC(UDP) 的理由**——这句话说出来，等于同时答了 HTTP/2 和 HTTP/3

**工程细节**：
- **拦截器 Interceptor**：`Unary/StreamInterceptor`，是挂鉴权、trace、限流、panic 恢复的统一入口。**→ OTel 的 trace 注入就挂在这里**
- **Deadline 传播**：客户端设的 deadline 会随请求头传到服务端，服务端的 `ctx` 会自动带上——**这就是 context 取消跨进程传播**，和 §0 那条打通
- **keepalive**：`Time`/`Timeout` 参数，长连接必须配，否则 NAT/LB 会静默断连
- **和 Kitex/Thrift 的对比（你的差异化优势）**：「我在字节主要用 Kitex + Thrift。Thrift 的 IDL 和编码更紧凑、Kitex 的性能优化更激进；**gRPC 的优势是生态和跨语言统一，尤其是 HTTP/2 原生流式和 OTel 的开箱集成**。两者在服务治理上的思路是一致的：IDL 先行、代码生成、拦截器做横切。」

## 5. 【P1】游戏后台概念：补到「能对话」就够

> 面试官**不指望跨界候选人有游戏经验**，但会看你能不能跟上、有没有认真准备。**只看粗体也够用。**

### 5.1 同步模型

- **状态同步**：服务端跑权威世界，定期把状态广播给客户端。**FPS 用这个**，因为服务器权威才能防外挂。代价是带宽大
- **帧同步（lockstep）**：只同步玩家操作指令，各客户端跑同样的确定性逻辑。**MOBA/RTS 常用**，省带宽，但要求**逻辑完全确定性**（浮点数都不敢随便用），且一处不同步全场崩
- **配套三件套**：**客户端预测**（本地先动，不等服务器）→ **服务器回滚/和解**（服务器判定后纠正客户端）→ **延迟补偿 lag compensation**（服务端回滚到玩家开枪那一刻的世界状态再判命中）

### 5.2 长连接网关

- **粘包拆包**：TCP 是字节流没有边界 → **长度前缀帧**（4 字节长度 + body）或分隔符
- **心跳**：应用层心跳，用来**探活 + 保持 NAT 映射**（TCP keepalive 默认 2 小时，没用）
- **断线重连**：**session 与连接解耦**——连接断了 session 还在（保留 N 秒），重连时凭 token 恢复，避免掉线即掉游戏
- **为什么用 UDP/KCP**：TCP 的**重传 + 拥塞退避 + 队头阻塞**对实时性是灾难。KCP 是在 UDP 上做的**可靠不保序 + 更激进重传**，用带宽换延迟

### 5.3 有状态服务（**你和这个岗最大的认知差，重点想**）

| 维度 | 无状态 Web 后端（你熟） | 有状态游戏服（要补） |
|---|---|---|
| 路由 | 任意节点都能处理，轮询即可 | **必须路由到持有该玩家/房间状态的节点**（一致性哈希 / 网关维护 session→node 路由表） |
| 扩容 | 加 Pod 立即生效 | 加了 Pod 只能接**新**房间，老房间搬不了 |
| 缩容 / 发版 | 杀 Pod 无感 | **杀 Pod = 一批玩家掉线**；要**先摘流量、等对局自然结束、再下线**（K8s `preStop` + 较长的 `terminationGracePeriodSeconds`） |
| 数据 | 都在 DB，进程无状态 | 状态在内存，**落库靠定时快照 + 关键节点（结算/退出）双保险** |
| K8s 对象 | Deployment | **StatefulSet**（稳定网络标识和存储） |

### 5.4 匹配 / DS 调度 / 聊天

- **匹配**：按 **MMR/ELO 分段**入队 → 匹配器按段位和延迟组队 → **等待超时后逐步放宽条件（扩圈）**。核心取舍是**匹配质量 vs 等待时长**
- **DS（Dedicated Server）调度**：一局游戏 = 一个 DS 进程。要点：**池化预热**（现拉起进程玩家等不起）、分配后标记占用、对局结束回收、**异常退出的兜底回收**。业界标准方案是 **Agones**（K8s 上的游戏服编排）——提这一句就说明你做过功课
- **关系链**：好友用 Redis **Set/ZSet**，在线状态用 Hash + 过期
- **聊天**：**写扩散**（发消息时写进每个接收者的收件箱，读快写慢，适合小群/私聊）vs **读扩散**（只存一份，读时聚合，写快读慢，适合世界频道/大群）；世界频道必须**广播限流 + 合批**

## 7. 【P1】OpenTelemetry（JD 点名，且和你的 context 短板是同一条线）

- **三支柱**：Traces / Metrics / Logs。OTel 的价值是**统一 SDK + OTLP 协议**，后端可随意换（Jaeger / Tempo / Prometheus / Loki）
- **核心机制（必考）**：一次调用生成 **TraceID**，每一跳生成 **SpanID** 并记录 **parent SpanID**，串成一棵树。
  - **跨进程**：靠 **W3C `traceparent` 请求头**传播（格式：`版本-TraceID-SpanID-flags`）
  - **进程内**：靠 **`context.Context` 一路带下去** ← **这就是你上一场答不出的 context 传播，换个场景又考了一遍**
  - **gRPC 里挂在哪**：**拦截器**（客户端拦截器注入头，服务端拦截器提取头）
- **采样**：
  - **头部采样**：入口决定采不采，简单、成本低，**但会漏掉出错的链路**
  - **尾部采样**：等整条链路结束再决定（比如"只要有 error 或耗时 > 1s 就全采"），**能保住有问题的链路**，代价是要在 Collector 缓存全链路
- **你有现成素材**：「ETL 的静默失效」「P99 5s 的定位」都可以重讲成——**「如果当时有全链路 trace，我第一步会看哪一段 span 最长」**

## 8. 【P2】压测与容量评估（JD 写了，但优先级最低）

**准备一套能口算的容量模型**：

```
在线人数 → 连接数 → 单机连接上限（受限于：内存 / FD 上限 / goroutine 数）→ 需要几台网关
每人每秒消息数 × 平均包大小 × 在线数 → 上下行带宽 → 网卡会不会打满
房间数 = 在线数 / 每房人数 → DS 进程数 → 单机能跑几个 DS（CPU 密集）→ 需要几台 DS 机器
```

**工具口径**：`wrk`（HTTP）/ `ghz`（gRPC 压测）/ **自研机器人客户端**（游戏后台标配——因为要模拟长连接 + 有状态的玩家行为，通用压测工具压不了）。

**压测方法论（上一场被打穿的地方，这次要说对）**：
1. 先定**指标口径**：并发梯度、数据集、预热、跑多久、看 P99 而非平均
2. **单机压到瓶颈**，找出**瓶颈在哪个资源**（CPU / 内存 / 网卡 / 下游）——**说不出瓶颈在哪，压测就白做**
3. 再压**集群**，验证水平扩展是否线性
4. 最后做**容量规划**：按峰值 × 冗余系数倒推机器数

## 附录：自我思考

### 一、这个岗的真实门槛不在游戏，在 Go

我第一反应是「我不懂游戏，劣势很大」。但把 JD 逐条拆完发现：**硬性技术要求里，游戏相关的只有"大厅/房间/匹配"这一条业务描述，其余（Go、并发、性能、微服务、gRPC、K8s、OTel、压测、稳定性）全是通用后端能力**。

面试官招一个跨界候选人时，**不会指望他懂游戏**——游戏业务知识入职两周就补上了。他真正在测的是：**Go 底子够不够硬、能不能扛住有状态服务的复杂度、以及你是不是真想来**。

**所以准备顺序必须是：Go > gRPC > 跨界叙事 > 游戏概念。** 我一开始的本能是先去补游戏知识（因为那是"我不会的"），这是错的——**在"最不会的地方"花时间，不等于在"最扣分的地方"花时间**。

### 二、上一场的教训必须带过来

模拟面试的三个模式级问题在这场依然会犯：

1. **归因不闭环** → 讲性能优化时，必须给「现象 → 证据 → 根因（卡在哪条物理约束）→ 方案与代价」，不能再说"我换了 Go 所以快了"
2. **数字扛不住反推** → QPS/延迟那组数要主动交代口径
3. **可靠性夸大** → 讲异步任务框架要说 **at-least-once**，不要说"保证不丢"

**这三条比任何一个知识点都值钱**，因为它们决定的是面试官对我"是否理解自己做过的事"的判断。

### 三、跨界的正确姿势是「翻译」，不是「道歉」

容易犯的错是把跨界讲成弱点——「我虽然没做过游戏，但是……」。这个句式一出口就输了。

正确的姿势是**翻译**：把我做过的事**翻译成对方的语言**。支付幂等 = 道具发放幂等；异步任务框架 = 异步结算；oncall = 停服事故处理。**这些不是"相关经验"，就是同一件事在不同业务里的名字。** 我要做的不是证明我懂游戏，是证明**我的能力和这个岗是同构的**。
