# OLAP 服务层选型：Elasticsearch / ClickHouse / StarRocks 对比

> 面试加分项。这三者你都"了解"，但最容易混：它们其实解决**三类不同的查询问题**。
> 一句话先记住定位：**ES 管搜索、ClickHouse 管单表狂算、StarRocks 管多表实时数仓对外服务。**

---

## 0. 先建立全局认知：它们在数据链路里的位置

先想清楚一件事：这三个都不是你原始数据的"家"，它们是**服务层 / 查询加速层**。

```
   数据来源                数据处理(数仓)             服务层(本文主角)          消费方
┌──────────┐          ┌──────────────────┐      ┌──────────────────┐    ┌─────────┐
│ 埋点/日志 │          │  Hive / Spark    │      │  Elasticsearch   │    │ 搜索框   │
│ 业务库CDC │  ──ETL──▶│  离线数仓         │─sink▶│  ClickHouse      │───▶│ BI报表   │
│ Kafka    │          │  (算法/宽表/聚合) │      │  StarRocks       │    │ 产品API  │
└──────────┘          └──────────────────┘      └──────────────────┘    └─────────┘
```

**关键关系：Hive/Spark 负责"把数据算好"（离线、批量、慢但能扛超大规模），算好的结果 sink 到 ES/CH/SR 里供"查得快"。**

- Hive/Spark：面向 **ETL 加工**，一次跑几分钟到几小时，吞吐大但延迟高，不适合直接对用户查询。
- ES/CH/SR：面向 **查询服务**，毫秒到秒级响应，是"数仓的出货窗口"。

所以选型问题的本质是：**你要对外提供的是哪一类查询？** 搜索、单表分析、还是多表实时服务。

## 1. Elasticsearch（ES）—— 搜索引擎，不是数据库

### 本质
基于 **Lucene** 的分布式搜索引擎，核心数据结构是**倒排索引（Inverted Index）**。它诞生的目标是"搜文本"，后来才被拿来做日志分析（ELK）。记住：**ES 首先是搜索引擎，其次才勉强算个分析工具。**

### 核心：倒排索引是什么，为什么适合搜索

普通数据库（正排/正向索引）是 **文档 → 内容**：

```
doc1 → "the quick brown fox"
doc2 → "the lazy brown dog"
```

想找"哪些文档包含 brown"，正排索引得**扫每一行**。

倒排索引反过来，是 **词(term) → 文档列表(posting list)**：

```
brown → [doc1, doc2]
quick → [doc1]
fox   → [doc1]
lazy  → [doc2]
dog   → [doc2]
```

查"brown"直接命中 `[doc1, doc2]`，**O(1) 定位到词，再拿文档列表**，完全不用扫全表。多词查询（"brown AND fox"）就是对两个 posting list 求交集。这就是搜索引擎快的根本原因，也是它和列存 OLAP 完全不同的基因。

配套还有：**分词器（analyzer）** 把文本切成词、**TF-IDF / BM25** 算相关性打分排序（搜索结果为什么这条排前面）、**近实时（NRT）** 写入后约 1 秒（refresh 间隔）可被搜到。

### 强项
- **全文检索**：分词、模糊、相关性排序、高亮——这是 CH/SR 完全不具备的。
- **任意字段灵活过滤**：schema-free（动态 mapping），字段随便加，任意组合过滤条件都有索引撑着。
- **近实时**：写入约 1s 可查，适合日志这种"刚产生就要看"的场景。

### 弱项
- **大规模聚合分析不如列存 OLAP**：ES 做 aggregation 是行式 + 索引结构，大数据量下 group by / sum 明显慢于 CH/SR，还容易把内存打爆。
- **资源消耗大**：倒排索引 + 原始 `_source` + doc_values，存储和内存都很吃，JVM 堆调优是常态。
- **JOIN 能力弱**：几乎没有真正的多表 JOIN（只有 nested / parent-child / 应用层拼），设计上要求数据**宽表化冗余**。

### 典型场景
- 搜索框、商品搜索、站内搜索
- 日志检索与排障（ELK：Elasticsearch + Logstash + Kibana）
- 需要"任意维度灵活过滤 + 关键词搜索"的明细查询

## 2. ClickHouse（CH）—— 单表聚合怪兽

### 本质
**列式存储（Columnar）+ 向量化执行（Vectorized）** 的 OLAP 数据库。为"在一张超大宽表上做聚合扫描"这一件事做到了极致。

### 为什么快（面试重点）
1. **列存**：分析查询通常只用到少数几列（`SELECT country, sum(amount)` 只碰 2 列），列存只读这 2 列的数据块，行存要把整行都读进来。IO 直接省一个数量级。
2. **高压缩率**：同一列数据类型一致、值相近，压缩效果极好（LZ4/ZSTD + Delta 等编码）。压缩既省存储又进一步省 IO。
3. **向量化执行**：一次处理一批（一个 column 的一段），充分利用 CPU 的 SIMD 指令和 cache，而不是一行一行地走火车。
4. **常驻进程 + 稀疏索引（主键排序）**：C++ 写的、没有 JVM GC 包袱；数据按主键有序存储，配稀疏索引快速跳过无关数据块。

### MergeTree 引擎家族（点到为止）
ClickHouse 的核心存储引擎是 **MergeTree**，名字来自 LSM 思路："先写小块，后台不断合并（merge）成大块"。要记住的是它是一个**家族**：
- `MergeTree`：基础，按主键排序、分区。
- `ReplacingMergeTree`：后台合并时按主键去重（"最终"去重，不保证实时）。
- `SummingMergeTree` / `AggregatingMergeTree`：合并时自动预聚合（存明细，后台滚成汇总）。
- `ReplicatedMergeTree`：带副本的版本。

要点：这些"更新/去重"都是**后台异步 merge 时才发生**，不是即时的——这正是它更新弱的根源。

### 强项
- **单表超大数据量聚合扫描极快**：几十亿行的埋点表做 group by 聚合，秒级返回，这是它的看家本领。
- **写入以 append 为主，吞吐高、压缩率高**：适合日志、埋点这种"只追加、少改动"的数据。

### 弱项
- **JOIN 弱**：分布式 JOIN 能力和优化器远不如 StarRocks，大表 JOIN 大表容易性能崩或 OOM。实践上要求**尽量宽表化，避免 JOIN**。
- **更新/删除弱**：偏 append 设计。`UPDATE`/`DELETE` 是 `ALTER TABLE ... MUTATION`，属于重量级异步操作（重写数据块），不能当 OLTP 那样频繁改。
- **高并发点查不是强项**：为"少量大查询"优化，不是"海量小查询"。QPS 很高的点查场景不合适。
- **不支持事务**：没有 ACID 事务概念。

### 典型场景
- 用户行为埋点分析、日志分析、监控指标（时序）
- 大宽表的即席分析（ad-hoc）、漏斗/留存/UV 计算
- 数据基本不改、只追加的分析型场景

## 3. StarRocks（SR）—— 能扛在线服务的实时数仓

### 本质
**MPP（Massively Parallel Processing，大规模并行处理）架构的 OLAP 数据库**，从 Apache Doris 分支演进而来，用 C++ 重写了执行引擎。既支持**存算一体**（数据在本地盘），也支持**存算分离**（数据放对象存储 S3，计算节点弹性伸缩）。

它的定位和 CH 有本质区别：CH 是"给分析师算大表"，**SR 是"能直接扛在线产品查询的实时数仓"**。

### 强项
- **多表 JOIN 强**：有成熟的 CBO（基于代价的优化器）、Runtime Filter、Colocate Join、Shuffle/Broadcast Join 自动选择。**这是它和 ClickHouse 最大的区别**——SR 可以直接查星型/雪花模型多表关联，不强求宽表。
- **实时更新（主键模型 Primary Key Model）**：支持按主键 upsert/delete，配合 Flink/CDC 做**实时更新的数仓**（订单状态实时变更也扛得住），这是 CH 做不好的。
- **高并发**：为对外产品级服务设计，能支撑较高 QPS 的并发查询，适合直接放在 BI / 产品 API 后面。
- **物化视图（含异步/实时）**：可以定义预聚合的物化视图，查询自动路由改写（query rewrite），命中物化视图直接读预聚合结果。

### 数据模型（了解即可）
- **明细模型（Duplicate Key）**：存明细，类似 CH。
- **聚合模型（Aggregate Key）**：导入即预聚合。
- **主键模型（Primary Key）**：支持高效实时 upsert/delete —— **实时更新的关键，也是对标 CH 弱项的杀手锏**。
- **更新模型（Unique Key）**：早期的按主键覆盖模型。

### 弱项 / 代价
- 相比 CH，**极致单表扫描的绝对性能**略逊（但差距在缩小，换来的是 JOIN 和更新能力）。
- 架构更复杂（FE 元数据节点 + BE 计算存储节点），运维成本高于单机友好的 CH。

### 典型场景
- **对外提供产品级 OLAP 服务**：卖家后台、数据看板、面向客户的实时报表 API。
- 实时数仓：Flink/CDC → StarRocks，多表关联 + 主键实时更新。
- 需要多表 JOIN、又要高并发、又要数据能实时更新的综合场景。

## 4. 横向对比（重头戏）

### 4.1 能力对比表

| 维度 | Elasticsearch | ClickHouse | StarRocks |
|------|---------------|------------|-----------|
| **本质** | Lucene 搜索引擎 | 列存 OLAP 数据库 | MPP OLAP 数据库 |
| **核心数据结构** | 倒排索引 | 列存 + MergeTree | 列存 + MPP 执行 |
| **全文检索/搜索** | ⭐⭐⭐⭐⭐ 唯一强项 | ❌ 基本没有 | ❌ 基本没有 |
| **任意字段灵活过滤** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| **单表聚合扫描** | ⭐⭐ | ⭐⭐⭐⭐⭐ 最强 | ⭐⭐⭐⭐ |
| **多表 JOIN** | ❌ 极弱 | ⭐⭐ 弱 | ⭐⭐⭐⭐⭐ 最强 |
| **实时更新/删除** | ⭐⭐⭐ 可更新但重 | ⭐ 很弱(异步mutation) | ⭐⭐⭐⭐⭐ 主键模型强 |
| **高并发(高QPS)** | ⭐⭐⭐ | ⭐⭐ 弱 | ⭐⭐⭐⭐⭐ 最强 |
| **写入模式** | 近实时写入 | append 为主 | 批量 + 实时 upsert |
| **数据规模** | 大(资源吃得多) | 超大(压缩率高) | 大 |
| **事务** | 无 | 无 | 弱(非 OLTP) |
| **典型场景** | 搜索框、日志检索(ELK) | 埋点/日志单表分析 | 实时数仓、对外产品服务 |

### 4.2 选型决策树 / 口诀

```
要不要全文搜索(关键词/分词/相关性排序)?
   ├── 要 ────────────────────────────────────▶ Elasticsearch
   └── 不要
        └── 主要是单表超大数据量狂算(埋点/日志),很少 JOIN、几乎不更新?
             ├── 是 ───────────────────────────▶ ClickHouse
             └── 否(要多表 JOIN / 要实时更新 / 要高并发对外服务)
                  └────────────────────────────▶ StarRocks
```

**一句话口诀：**
> **要搜索 → ES；单表狂算日志埋点 → ClickHouse；多表 + 实时更新 + 高并发对外服务 → StarRocks。**

更细的记忆锚点：
- **ES**：关键词、模糊、"搜"这个字出现 → ES。
- **CH**：一张大宽表、group by、"分析师看板"、数据不改 → CH。
- **SR**：多张表关联、订单状态实时变、直接给用户/产品查 → SR。

### 4.3 它们和 Hive/Spark 数仓的关系（再强调）

**Hive/Spark 是"厨房"（把菜做好），ES/CH/SR 是"出菜窗口"（快速端给客人）。**

- 离线数仓（Hive/Spark）把复杂加工、宽表、算法结果算好 → **sink** 到 ES/CH/SR。
- 用户 / BI / 产品的查询打到 ES/CH/SR，毫秒~秒级返回，绝不会直接去 Hive 上跑（那要等分钟级起 Spark job）。
- 本项目里典型链路：`Hive nebula_entity.* 宽表 → sink → ES 索引 / StarRocks 表 → 对外看板 API`。

## 5. 补充概念：为什么这些都比 Hive 查得快？

维护 ETL 多年会习惯 Hive 的"慢"，这里点破为什么服务层能快几个数量级。**四个原因叠加：**

1. **常驻进程 vs 起 Spark Job**
   Hive/Spark 每次查询要**申请资源、启动 executor、调度 DAG**，光启动就几十秒。ES/CH/SR 是**常驻服务进程**，请求进来直接算，省掉了冷启动。这是"秒级 vs 分钟级"最直接的差距。

2. **列式存储 + 向量化（CH/SR）**
   分析查询只读用到的列（列存），且一次处理一批数据走 SIMD（向量化），CPU 和 IO 效率碾压逐行处理。

3. **索引（ES 倒排 / CH 稀疏索引 / SR 前缀索引+bitmap）**
   有索引就能跳过大量无关数据，而不是全表扫描。

4. **预聚合 / 物化视图**
   把"常查的聚合结果"提前算好存下来，查询直接读结果，不用每次重算。

### 预聚合 / 物化视图是什么

- **预聚合（Pre-aggregation）**：不等查询来才 `sum/count`，而是**在写入或后台时就把汇总算好存起来**。查询 1 亿行明细的日 GMV，如果已经预聚合成"每天一行汇总"，查询只需读 365 行。CH 的 `SummingMergeTree`/`AggregatingMergeTree`、SR 的聚合模型都是这个思路。

- **物化视图（Materialized View）**：把一段查询（通常含聚合/JOIN）的**结果物理存下来**，并随基表更新而维护。
  - 和普通视图区别：普通视图是"每次查都重跑 SQL"，物化视图是"结果已经算好落盘了"。
  - **StarRocks 的杀手锏——查询自动改写（query rewrite）**：你查明细表，优化器发现有能命中的物化视图，**自动改成读物化视图**，用户 SQL 不用改就享受到加速。

  > 注：本项目的 Hive/Spark 侧也有"materialize 中间结果到临时表断开 lineage"的实践（见 CLAUDE.md §3.5），思想一脉相承——**用空间换时间，避免重复计算**。

## 6. 面试高频问题 + 答题要点

**Q1. ES / ClickHouse / StarRocks 怎么选？（最核心）**
按查询类型分：**要全文搜索/关键词/相关性排序 → ES**；**单表超大数据量聚合、日志埋点、数据只追加不改 → ClickHouse**；**多表 JOIN + 实时更新 + 高并发对外服务 → StarRocks**。一句话：ES 管搜索，CH 管单表狂算，SR 管实时数仓对外服务。别硬背，抓"搜索 / 单表 / 多表实时"三个关键词。

**Q2. 倒排索引的原理？为什么适合搜索？**
正排是"文档→内容"，查关键词要扫全表；倒排是"词→文档列表(posting list)"。查一个词直接命中它的文档列表，多词查询就是对多个 posting list 求交/并集。配合分词器把文本切词、BM25 算相关性排序。所以搜索场景（尤其全文）ES 快，而这恰恰是列存 OLAP 不具备的能力。

**Q3. ClickHouse 为什么快？**
四点：①列存——分析只读用到的列，IO 省一个数量级；②高压缩——同列同类型压缩率极高，进一步省 IO；③向量化执行——批量 + SIMD，吃满 CPU；④C++ 常驻进程无 GC + 主键有序 + 稀疏索引跳过无关块。核心一句：**为"单表大聚合"这一件事把列存+向量化做到极致。**

**Q4. ClickHouse 为什么不适合频繁更新/删除？**
它是 append-oriented 的 MergeTree 设计。`UPDATE`/`DELETE` 是 `ALTER TABLE ... MUTATION`，会**重写整个数据块**，是重量级异步操作；`ReplacingMergeTree` 的去重也是**后台 merge 时才生效、不保证实时**。所以频繁点更新会拖垮它，它面向"数据写进去基本不动"的分析场景。

**Q5. StarRocks 和 ClickHouse 的区别？（高频）**
同是列存 OLAP，但定位不同：
- **JOIN**：SR 有 CBO 优化器 + Runtime Filter，多表 JOIN 强；CH 的 JOIN 弱，要求宽表化。
- **更新**：SR 有主键模型，支持高效实时 upsert/delete；CH 更新弱（异步 mutation）。
- **并发**：SR 为高 QPS 对外服务设计；CH 面向少量大查询，高并发点查弱。
- **极致单表性能**：CH 略强于 SR。
一句话：**CH 是"给分析师算大宽表的单机怪兽"，SR 是"能扛在线产品查询、支持多表实时更新的数仓"。**

**Q6. 为什么这些比 Hive/Spark 查得快？**
①常驻进程 vs 每次起 Spark job（省冷启动，秒级 vs 分钟级）；②列存 + 向量化；③索引跳过无关数据；④预聚合/物化视图。本质：Hive/Spark 面向"批量 ETL 加工吞吐"，这三者面向"查询低延迟服务"，定位不同。

**Q7. 什么是物化视图 / 预聚合？为什么能加速？**
预聚合是提前把汇总结果算好存下来，查询直接读汇总而非扫明细（1 亿行汇成几百行）。物化视图是把含聚合/JOIN 的查询结果物理落盘并随基表维护，普通视图每次重跑、物化视图直接读结果。StarRocks 还能**自动 query rewrite**：查明细表时优化器自动改读命中的物化视图，用户 SQL 无感加速。本质是空间换时间。

**Q8. ES 能不能替代数据库做 OLAP 分析？为什么一般不推荐？**
能做简单聚合，但不推荐扛大规模分析：①ES 聚合是行式+索引结构，大数据量 group by 慢、易 OOM；②几乎没有真正的多表 JOIN；③倒排索引+_source 资源消耗大、成本高。ES 的正确定位是**搜索和明细检索（含日志）**，重聚合分析该交给 CH/SR。

**Q9. 这三者和数仓（Hive/Spark）是什么关系？会互相替代吗？**
不替代，是分工。Hive/Spark 做离线批量加工（把数据算好），ES/CH/SR 是服务层（把结果查得快）。典型链路：数据源 → Spark 离线数仓算宽表/聚合 → sink 到 ES/CH/SR → 对外提供搜索/看板/API 查询。数仓是"厨房"，服务层是"出菜窗口"。

**Q10.（进阶）StarRocks 的存算分离是什么，解决什么问题？**
存算一体时数据在 BE 本地盘，扩容要搬数据、成本高。存算分离把数据放对象存储（S3/OSS），计算节点无状态、可弹性伸缩，本地盘只做 cache。好处：**存储成本降低 + 计算弹性扩缩容 + 计算存储独立扩展**，适合云上和潮汐负载。（对标 CH 传统上更偏存算一体单机友好。）

## 7. 一句话速查

> **要搜索选 ES（倒排索引）；单表狂算日志埋点选 ClickHouse（列存向量化、更新弱）；多表 JOIN + 实时更新 + 高并发对外服务选 StarRocks（MPP、主键模型、物化视图）。三者都是数仓算好结果后的"出菜窗口"，比 Hive 快是因为常驻进程 + 列存向量化 + 索引 + 预聚合。**
