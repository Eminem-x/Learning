# ETL 链路架构评审：风险清单与改造路线图

> 来源：个人思考 + 工作实践梳理
> 收录时间：2026-07-23 CST
>
> 配套：[ETL 链路深挖（架构与讲法）](./08-etl-pipeline-deep-dive-20260723.md)
>
> **本篇用途有二**：
> 1. **工程用**——这条链路真实存在的风险排序与改造建议，可以直接拿去开技术评审。
> 2. **面试用**——回答「你觉得你们现在的架构有什么问题 / 如果重做你怎么做」。这道题几乎必考，而且是**区分「维护过」和「想过」的分水岭**。

---

## 0. 评审结论（30 秒版）

> 这条链路的**性能问题都是响的**（S3 限流会报错、shard 过多会变慢、OOM 会 137），已经被踩过、被处理过；**真正的软肋是三处「静默失效」加一个「过短的恢复窗口」**。
>
> - **静默失效**：上游 crawl 没有就绪信号，数据不全照跑不报错；ES 写入若未绑定 `_id`，重试会静默产生重复；维度快照的链式依赖让某一天的错误一路继承下去。这三处的共同特征是——**出错时系统认为自己是成功的**。
> - **恢复窗口过短**：SR 留 2 天、ES 留 4 天，而恢复能力受限于**上游 S3 的保留期**。静默错误的发现延迟（天级）一旦超过保留期，就是**永久数据丢失**。
> - **可用性上**最大的单点是 client 模式：driver 寄生在 Airflow worker 容器内，一个作业撑爆内存杀掉的是**整台 worker 上的所有 task**。
>
> **一句话**：这套架构在「快速铺开 15 个市场」这个目标下做得不错，取舍是清醒的；但它当前的**风险重心不在性能，在正确性与可恢复性**——而这两项恰恰没有任何自动化防线。

## 1. 先说做对的地方（评审不是挑刺，判断力体现在能分清好坏）

| 决策 | 为什么是对的 |
|---|---|
| **采集层保留原始 JSON** | schema-on-read，上游字段一变不至于全链路断；且出问题能直接下载 grep——**运维可读性也是收益** |
| **中间结果全部回落 S3** | 每层可独立重跑、可独立排查、可被其他引擎消费；比「一个大作业算到底」的可恢复性高一个量级 |
| **15 个市场在表名层隔离** | 物理隔离，一个市场数据错乱不污染其他市场；代价（DDL 改 15 遍）已经用 validator 脚本对冲了 |
| **同一个 DAG 内表达依赖** | 避开了 `ExternalTaskSensor` 的轮询语义和跨 DAG schedule 对不齐的经典坑，这是对的选择 |
| **StarRocks 选主键模型 + 日期分区** | 写时合并使查询不付 merge 代价；日期分区让保留策略退化成 `DROP PARTITION` 这个秒级元数据操作 |
| **ES 用 alias 而不是直接写固定索引** | 原子切换、零停机重建、回滚一步到位，还绕开了「mapping 不可改」的硬约束 |
| **生命周期用代码管而非全靠 lifecycle rule** | 保留策略本质是业务决策，写在代码里可 review、可测试、跟表定义一起演进 |
| **ES 4 天不做 warm/cold 分层** | 4 天内数据全是热的，硬套 ILM 四阶段只会增加复杂度没有收益——**克制也是一种设计能力** |

> 📌 面试里先说这一段，再讲问题。**上来就批评前人的候选人会被判定为「不懂约束」**；能先讲清「当时为什么这么选是合理的」，后面的批评才有分量。

## 2. 风险清单

评审优先级按 **正确性 > 可恢复性 > 可用性 > 效率/成本** 排。理由：算错的数比算慢的数危险，丢了的数比错了的数更危险。

---

### 🔴 P0-1｜上游 crawl 无就绪信号，数据不全会静默通过

| | |
|---|---|
| **现状** | crawl 是采集侧独立的异步调度，「能爬多少是多少」；ETL 在 UTC 00:00 到点起跑，不检查上游是否完成 |
| **风险类型** | 正确性 —— **静默失效** |

**具体失败场景**：
> 某天 crawl 因源站限流/任务积压，到 UTC 00:00 只完成了 60% 的抓取。Airflow 准时起跑，Spark 读到 S3 上**不完整的分区**，一路算下去——ODS 少了 40%、DWD 少了、DWS 的聚合指标偏低、ADS 出的榜单缺了大量条目、写进 ES 和 StarRocks 对外服务。
> **整条链路 300~400 个 task 全部绿色，无一失败，无一告警。**
> 问题最终由业务方反馈「今天榜单怎么少了一半」发现——通常是 1~3 天后。此时 SR 的 2 天窗口已经快到期，ES 的 4 天也在倒数。

**为什么这是 P0**：它同时命中了三个最坏属性——**发生概率高**（爬虫本来就不稳定）、**完全静默**（没有任何信号）、**发现延迟长**（靠人工反馈，天级）。而发现延迟一旦超过保留期，就升级成 P0-2 的永久丢失。

**改进方案（按投入从低到高）**：

1. **【最低成本，先做这个】行数环比校验**
   在 ODS 层加一个校验 task：本日分区行数 vs 前 7 日中位数，偏离超过阈值（如 ±30%）就 **fail 掉整个 DAG** 而不是继续往下算。
   > 关键设计：**要 fail，不要只告警**。告警会被忽略，fail 会阻断污染传播——「宁可今天没数，不要今天有错数」。错数会被下游消费、被写进 ES/SR、被业务当真；没数只是缺一天。

2. **【推荐，需要采集侧配合】`_SUCCESS` 标记 + Sensor 等待**
   crawl 完成一个市场/一个批次后，往 S3 对应分区路径写一个空的 `_SUCCESS` 文件；Airflow 侧用 `S3KeySensor`（**用 `reschedule` 模式或 deferrable operator，不要用默认的 poke 模式常驻占并发槽**）等它出现，超时后走降级分支。
   > 这是把「隐式的时间约定」升级成「显式的数据契约」——本质上和 Hadoop 生态里 `_SUCCESS` 文件的用途完全一致，是行业标准做法。

3. **【长期】把完整性作为可观测指标**
   记录每天每市场的抓取量、预期量、完成时间，画趋势图。让「今天爬得少」在**业务发现之前**先被看到。

**验证方式**：人为构造一个只有 50% 数据的分区，确认 DAG 会 fail 而不是绿色通过。

### 🔴 P0-2｜恢复窗口未被显式定义，可能小于故障发现窗口

| | |
|---|---|
| **现状** | StarRocks 留 2 天，ES 留 4 天，S3 各表保留期由代码管理、**各不相同**；已发生过误删事故，靠重跑 to_es 恢复但「比较慢」 |
| **风险类型** | 可恢复性 —— **永久数据丢失** |

**核心认知：恢复能力受限于链条上最短的那个保留期。**

```
crawl ──► S3 (N 天?) ──► StarRocks (2 天)
                    └──► ES (4 天)

能恢复 ES 第 4 天的数据  ⟺  S3 上对应的源表分区还在
若 S3 该表只留 3 天  ⟹  ES 第 4 天的数据一旦删错，永久丢失
```

**具体失败场景**：
> 结合 P0-1：周一的数据因 crawl 不全而错误，无人发现。周四业务反馈异常，此时想回补周一——但 ODS 那张表的 S3 保留期是 3 天，周一的原始分区已被清理任务删除。crawl 侧的原始数据要么已经不可重爬（源站数据已变），要么重爬成本极高。
> **结果：周一的数据永久错误，且无法修正。**

**为什么这是 P0**：这不是「恢复慢」，是「**不可恢复**」。而且它是**隐性的**——没人算过这笔账，直到需要恢复时才发现源头没了。

**改进方案**：

1. **【立刻做，零成本】把「恢复窗口」显式算出来**
   拉一张表，逐表核对：

   | 表 | S3 保留期 | 下游 | 下游保留期 | 恢复窗口 | 是否达标 |
   |---|---|---|---|---|---|
   | ods_xxx | ? 天 | — | — | ? | |
   | dws_xxx | ? 天 | SR | 2 天 | min(S3) | |
   | ads_xxx | ? 天 | ES | 4 天 | min(S3) | |

   **判定标准**：`S3 保留期 ≥ 下游保留期 + 故障平均发现时间 + 修复所需时间`。
   目前故障发现主要靠业务反馈（天级），所以这个安全边际建议至少 **7~14 天**。

2. **【成本可控】把关键层（ODS + 维度快照）的 S3 保留期拉长**
   Parquet + 压缩后，多留 10 天的成本通常远低于一次数据事故。可以对**冷分区转低频存储类型**（S3-IA / COS 低频）来对冲成本——这正是 lifecycle rule 的正确用法（转存储级别，而非删除）。
   > 特别注意：**维度快照因为是链式依赖（见 P1-2），它的保留期要求比事实表更高**——回补第 N 天需要第 N-1 天的快照存在。

3. **【长期】用 Iceberg 的快照机制替代「靠保留期兜底」**
   Iceberg 的 snapshot + time travel 让「回到误删之前的状态」变成一次元数据回滚（秒级），而不是重跑整条链路。这是对「误删要重跑 to_es，比较慢」这个痛点的正解。

**验证方式**：做一次**恢复演练**——随机挑一天，假装 ES 索引被误删，实测从零恢复要多久、需要哪些源数据还在。**没演练过的恢复方案等于没有恢复方案。**

### 🔴 P0-3｜client 模式 + CeleryExecutor，OOM 爆炸半径不可控

| | |
|---|---|
| **现状** | Spark driver 跑在 Airflow worker 容器内，一个 worker 并发跑多个 driver；已发生过 OOM，处理方式是降并发/加内存 |
| **风险类型** | 可用性 —— **故障放大** |

**根因链条**（详见[深挖篇环节 4.2 / 5.1](./08-etl-pipeline-deep-dive-20260723.md)）：

```
CeleryExecutor 无 per-task 内存 limit
  └─► worker 容器内存是「静态、共享」的池子
        └─► 池子里住着 worker_concurrency 个 Spark driver JVM
              └─► 任一 driver 堆/堆外涨 → 容器 RSS 触碰 limit
                    └─► 内核 OOMKill 整个容器（137）
                          └─► 该 worker 上所有正在跑的 task 一起死
```

**具体失败场景**：
> 某个市场的 ADS 作业因数据量增长触发了一次 `collect()` 或 broadcast 组装，driver 堆外内存涨了 2GB。worker 容器被 OOMKilled。此时这台 worker 上还并发跑着另外 N-1 个其他市场的 task——**全部被杀**。它们各自 retry，重新排队，把已经紧张的资源再挤一遍，形成**重试风暴**。整体产出时间被拖后数小时。

**为什么当前的解法是治标**：降低 `worker_concurrency` 和加机器内存，都是**给静态内存池留余量**。余量留多少取决于「最坏情况下的 driver 内存」，而这个值随数据增长在变——今天够用不代表下季度够用，而且留余量本身就是**资源浪费**（平时用不到的内存一直占着）。

**改进方案（三选一，按迁移成本排序）**：

| 方案 | 做法 | 收益 | 成本 |
|---|---|---|---|
| **A. 短期兜底** | 给 Airflow worker pod 设合理的 requests/limits，并**给每个 Spark driver 显式设 `--driver-memory` 和 `spark.driver.memoryOverhead`**，使 `Σ(driver 内存) + worker 自身 < 容器 limit` | 让 OOM 从「随机发生」变成「可算出来」 | 低，改配置 |
| **B. 换 executor** | CeleryExecutor → **KubernetesExecutor**，每个 task 一个独立 pod，有自己的 requests/limits | **彻底消除连坐**；弹性伸缩；不用再为并发数纠结 | 中，改 Airflow 部署；需接受 pod 启动开销 |
| **C. 换提交模式**（治本） | client → **cluster 模式**，driver 变成独立的 K8s driver pod（`SparkKubernetesOperator` + Sensor 跟状态） | driver 有独立资源上限；Airflow worker 变回纯调度、内存占用可预测 | 中高，需要处理 pod 生命周期、RBAC、**日志采集**（client 模式最大的便利就在日志） |

> **推荐路径：先 A（本周就能做，止血），再评估 B 或 C。**
> B 和 C 不冲突甚至可以叠加，但如果只能做一个——**B（KubernetesExecutor）的收益/成本比更好**，因为它顺带解决了所有 task 类型的隔离问题，不只是 Spark task；而 C 要额外付日志采集的改造成本，那正是当初选 client 模式的核心理由。

### 🟠 P1-1｜ES 写入幂等性存疑（可能正在产生重复数据）

| | |
|---|---|
| **现状** | Spark 直写 ES，有 alias + 索引别名；`es.mapping.id` 是否配置**未确认** |
| **风险类型** | 正确性 —— **静默失效** |

**两种可能，结论完全相反**：

| 实际模式 | 幂等性 | 后果 |
|---|---|---|
| 每天写**新索引** → 校验 → 切 alias | ✅ 幂等 | 重跑 = 重写整个新索引，安全 |
| 固定索引追加写 + **配了** `es.mapping.id` | ✅ 幂等 | 按业务 `_id` upsert，安全 |
| 固定索引追加写 + **没配** `es.mapping.id` | ❌ **不幂等** | ES 自动生成随机 `_id`，**retry 3 次 = 数据最多翻 4 倍，且全程不报错** |

**为什么这条排 P1 而不是 P0**：因为最可能的情况（每天新索引 + 切 alias）是安全的。但**你必须去代码里确认一次**——如果落在第三种，这就不是未来风险，是**正在发生的数据正确性问题**，要立刻升 P0。

**改进方案**：
1. 去 Spark 侧 ES sink 的配置里确认 `es.mapping.id` / `es.write.operation`（`index` 是 upsert，`create` 遇到已存在会失败，`upsert` 显式更新）。
2. 无论哪种模式，都建议**显式绑定业务主键为 `_id`**——即使当前靠新索引+alias 保证了幂等，绑定 `_id` 是零成本的第二道保险。
3. 加一个**写后校验 task**：切 alias 之前先 count 一次新索引的文档数，与源表行数比对，不一致就不切。**alias 模式最大的价值就是「切换前有一个可校验的中间态」——不用白不用。**

### 🟠 P1-2｜维度快照链式依赖，回补成本 O(n) 且错误会传播

| | |
|---|---|
| **现状** | 维度每天拉最新，与前一天快照 union 合并 |
| **风险类型** | 可恢复性 + 正确性传播 |

**问题本质**：`快照(D) = f(增量(D), 快照(D-1))`，这是一条**递推链**。

- **错误传播**：某天合并逻辑出错或输入不全 → 错误的行进入快照 → **第二天把它当作正确的历史继承下去** → 错误永久固化在链上，而且随时间越走越远。
- **回补成本**：要修第 D 天，必须从 D 开始**串行**重跑 D、D+1、D+2……到今天，无法并行，O(n)。
- **与保留期耦合**：回补第 D 天需要第 D-1 天的快照存在。**快照的保留期直接决定了最远能回补到哪一天**。

**具体失败场景**：
> 某个市场的维度合并因 PG 侧一次超时只拉到了部分数据，当天快照里少了一批 key。第二天的合并把这个残缺快照当作「历史全量」继承。三周后发现某类实体在数仓里"消失"了——回补需要串行重跑 21 天，且第一天的输入 PG 快照早已不存在。

**改进方案**：

1. **【低成本，高收益】给快照加断言**
   合并任务里加一条硬校验：`今日快照行数 ≥ 昨日快照行数 × 0.95`（维度表通常只增不减或缓慢变化）。不满足直接 fail，**阻断链式传播**。这一条能挡住绝大多数事故。
2. **【中成本】增量快照与合并快照分开存**
   把「今天从 PG 拉到的原始增量」单独落一份并长期保留。这样回补时不需要重新打 PG（源可能已变），且可以从任意一天重建整条链。
3. **【长期】评估改成拉链表或 Iceberg MERGE INTO**
   拉链表用 `start_date/end_date` 表达历史，可单点修复；Iceberg 支持行级 `MERGE INTO`，不用整分区重写。但两者都是**大改**，且当前保留期只有几天——**快照方案的存储劣势没有暴露，链式劣势却全暴露了**，这个矛盾值得单独讨论一次。

### 🟠 P1-3｜PG 既是业务维度源又（可能）是 Metastore 后端，双重单点

| | |
|---|---|
| **现状** | Spark JDBC 直读 PG 取 gmv/sold_count 等核心指标；Hive Metastore 的后端库也是 PG。⚠️ **是否同一实例未确认** |
| **风险类型** | 可用性 + 性能干扰 |

**两个独立问题叠在一起**：

**(a) JDBC 直读打业务库**
- `spark.read.jdbc` **默认单分区单连接**——一个 executor 一个连接拉全量，慢且是单点；
- 要并行必须给 `partitionColumn/lowerBound/upperBound/numPartitions`，但并行度一高，300~400 个 task 里的多个读 PG 任务会同时压在业务库上；
- `fetchsize` 默认很小（PG JDBC 默认取决于驱动配置），读大表时网络往返成为瓶颈；
- 长事务/大查询还会影响 PG 的 vacuum 与复制（接你的 [PG WAL 笔记](../../infra/postgresql-wal-replication-and-amplification.md)）。

**(b) 如果 Metastore 和业务 dim 在同一个 PG 实例**
- Metastore 是**全数仓的元数据中枢**——它挂了，所有 Spark 作业在 SQL 解析阶段就失败，整条链路瘫痪；
- 而业务侧的大查询/长事务会直接影响它的响应；
- 这是把「链路的生死开关」和「一个高负载的业务库」放在了同一个故障域里。

**改进方案**：
1. **【立刻确认】Metastore 的 PG 是不是业务 PG 同实例**。如果是 → **拆开**，这是 P0 级别的改动（成本低、收益极高）。
2. **【推荐】改成「一次 dump，多次消费」**：每天一个专门任务把 PG 需要的表快照卸载到 S3，下游所有作业读 S3。对业务库的压力从 O(任务数) 降到 O(1)，且快照可重放——重跑不用再打库。
3. **【中期】读从库而非主库**；确认 Metastore PG 有主从和备份。

### 🟠 P1-4｜YAML 动态生成 DAG 可能拖垮 Scheduler

| | |
|---|---|
| **现状** | DAG 由 YAML 描述，单 DAG 300~400 task，15 个市场 |
| **风险类型** | 可用性/效率 —— **隐性性能衰减** |

**问题**：Airflow 的 DagFileProcessor 会**周期性重新解析所有 DAG 文件**（`min_file_process_interval` 默认 30 秒）。如果 YAML 的读取/解析/展开写在模块**顶层代码**里，就是每 30 秒把几千个 task 定义重建一遍。

**症状识别**（如果出现下列现象，基本就是它）：
- task 依赖明明满足了，却要等几分钟才被调度；
- Airflow UI 上 DAG 的 **parse time** 指标很高（关注 `dag_processing.last_duration`）；
- scheduler 容器 CPU 长期高位但没有任务在跑。

**改进方案**：
1. 先**测量**：看 Airflow 的 DAG parse time 指标，超过 `min_file_process_interval` 就是明确的红灯。
2. YAML 解析结果**缓存**；避免在顶层代码做任何 IO/网络调用（顶层执行的东西每次 parse 都会跑一遍）。
3. 调大 `min_file_process_interval`（比如到 120s）——DAG 定义本来就不常变，没必要 30 秒扫一次。
4. 关注 `dag_file_processor_timeout`——解析超时会导致 DAG **直接从 UI 消失**，非常迷惑人。

## 4. 「如果给我一个季度」改造路线图

### 第一阶段：止血（1~2 周，全部是低成本高收益项）

1. **核对恢复窗口**：拉出每张表的 S3 保留期 vs 下游保留期表，不达标的立刻延长（P0-2）
2. **ODS 层行数环比校验，不达标 fail DAG**（P0-1）
3. **确认 `es.mapping.id`**，未配则立即补上（P1-1）
4. **确认 Metastore PG 是否与业务 PG 同实例**，是则安排拆分（P1-3）
5. **维度快照加行数断言**，阻断链式传播（P1-2）
6. **给 Spark driver 显式设内存上限**，让 worker 容器内存可算（P0-3A）
7. **清理任务加 dry-run 与删除清单日志**（P2-2）

> 这一阶段的特征：**不动架构，只加防线**。目标是让「静默失效」变成「响亮失败」。

### 第二阶段：解耦（1~1.5 个月）

8. **上游数据契约**：推动 crawl 侧写 `_SUCCESS`，Airflow 侧接 Sensor（P0-1 完整版）
9. **PG 改为「一次 dump，多次消费」**，下游读 S3 快照（P1-3）
10. **Airflow 换 KubernetesExecutor**，消除 OOM 连坐（P0-3B）
11. **补 SLA 告警**（P2-1）

> 这一阶段的特征：**拆开耦合的故障域**。上游/下游解耦、调度/计算解耦、元数据/业务解耦。

### 第三阶段：升级（剩余时间，需要单独立项）

12. **评估 Iceberg**：一次性解决 rename 风暴（P2-3）、误删回滚（P0-2）、行级更新（P1-2）三个痛点
13. **数据质量层**（P2-6）

> **注意这个排序的逻辑**：Iceberg 看起来能一口气解决三个问题，很诱人——但它是**架构级改动**，而前两阶段的十几项加起来的收益更大、风险更小、见效更快。**先把便宜的防线补齐，再谈换地基。**

## 5. 面试话术：「你觉得你们现在的架构有什么问题？」

这道题的**陷阱在于**：答不出来 → 显得没思考过；一通乱批 → 显得不懂约束、不好合作。用下面这个四段式结构：

### 模板

**① 先给判断（10 秒）**
> 「我觉得这套架构在『快速支撑 15 个市场的 T+1 产出』这个目标上是称职的，取舍也比较清醒。但它的**风险重心不在性能，在正确性和可恢复性上**——而恰恰这两块没有自动化防线。」

**② 讲一个最有代表性的问题，讲透（1~2 分钟）**
> 「最典型的是**上游数据完整性**。我们的采集侧是独立调度的爬虫，『能爬多少是多少』，而 ETL 是到点起跑，中间**没有任何就绪信号**。这意味着如果某天只爬到 60%，整条链路 400 个 task 会**全绿通过**，算出偏低的指标，写进 ES 和 StarRocks 对外服务——系统全程认为自己成功了。
> 更麻烦的是它和另一个设计叠在一起：我们的 StarRocks 留 2 天、ES 留 4 天，而真正的恢复能力取决于**上游 S3 的保留期**。这类静默错误通常要靠业务反馈才发现，是天级延迟——**等发现的时候，用来修复的源头数据可能已经被清理任务删了**。所以这两件事乘起来，最坏情况不是『数据错了』，是『数据错了而且改不回来』。」

**③ 给方案，并且要有优先级和成本意识（1 分钟）**
> 「我的判断是**先加防线，不动架构**。最低成本的一步是在 ODS 层加行数环比校验——本日行数对比前 7 日中位数，偏离超阈值直接 **fail 掉 DAG**。注意是 fail 不是告警，因为**告警会被忽略，fail 能阻断污染往下游传播**——宁可今天没数，不要今天有错数。
> 再往上一步是推动采集侧写 `_SUCCESS` 标记，我们用 Sensor 等它，把隐式的时间约定变成显式的数据契约。
> 同时把每张表的『恢复窗口』显式算一遍：S3 保留期必须大于下游保留期加上故障发现时间。这两件事加起来成本很低，但能把最坏情况从『不可恢复』拉回『可恢复』。」

**④ 展示你分得清主次（30 秒）**
> 「架构层面确实还有更根本的改法——比如上 Iceberg，能一口气解决对象存储的 rename 风暴、误删的快照回滚、维度的行级更新三个问题。但我会**把它排在后面**：那是地基级改动，而前面那些防御性检查加起来的收益更大、风险更小、一两周就能见效。**先用低成本把最坏情况兜住，再考虑换地基**，这个顺序我觉得比反过来更负责任。」

### 为什么这个结构有效

| 段落 | 展示的能力 |
|---|---|
| ① 先肯定再批评 | **理解约束**，不是事后诸葛亮 |
| ② 讲透一个而非罗列十个 | **深度 > 广度**；且「两个问题乘起来」体现系统性思维 |
| ③ 方案带优先级和成本 | **工程判断力**，不是只会说「应该上 XX」 |
| ④ 主动否掉最炫的方案 | **成熟度**——知道什么时候不该用新技术，这比会用新技术更难 |

> ⚠️ **不要犯的错**：
> - 不要说「这是前人挖的坑」——即使是事实。说「这个选择在当时的约束下是合理的，但随着规模增长代价开始超过收益」。
> - 不要罗列七八个问题——面试官会追问其中一个，你必须有一个能讲到底的。**准备一个讲透的，比准备十个讲浅的强。**
> - 不要只讲问题不讲成本——「应该上 Iceberg / Flink / 数据湖」这种答案，如果没有成本和优先级的讨论，听起来像是没做过决策的人说的。

## 附录：自我思考

### 评审的第一性问题不是「哪里不够好」，是「哪里会静默出错」

一开始梳理的时候，我下意识在找**性能问题**——因为性能问题是我平时救火最多的。但列完清单才发现，**所有让我熬夜的问题（S3 限流、OOM、shard 过多）都有一个共同的好处：它们会报错**。报错的问题会被发现、被定位、被修复，损失是有界的。

真正没被处理的是另一类：**系统认为自己成功了，但结果是错的**。crawl 少爬一半、ES 重复写入、快照继承了错误——这三件事发生时，Airflow 一片绿。

这个视角切换让我意识到一件事：**我这四年的排障能力，训练的全是「响的问题」**。而一个更资深的工程师，值钱的地方在于能在系统还没出声的时候，就知道哪里会哑火。

### 保留期是一个被严重低估的架构决策

「SR 留 2 天、ES 留 4 天」，我一直把它当成本问题。写完这篇才想明白：**保留期定义的是「你能犯错多久还能改回来」**，它是一个可靠性参数，不是成本参数。

而且它和「故障发现速度」是**乘法关系**——发现越慢，需要留越久。我们的发现速度是「等业务反馈」，天级；保留期是 2~4 天。这两个数字放在一起看，等式是不成立的。

更讽刺的是：我们选了每日全量快照（存储换简单），却又把保留期压到几天——**等于付了快照的链式回补成本，却没享受到快照本该有的「随时可回到任意一天」的好处**。

### 「加一条 assert」和「上 Iceberg」的收益比，可能是反直觉的

左上角象限那六项，全是「加一条校验」「查一个配置」这种听起来毫无技术含量的事。而 Iceberg、Flink、KubernetesExecutor 这些听起来「有技术含量」的，全在右边。

我以前会本能地觉得前者是杂活、后者才是"做架构"。但按收益/成本排下来，**一条行数环比断言挡住的损失，可能比一次架构升级还大**——因为它挡的是「不可恢复的数据丢失」，而架构升级换来的往往是「更好、更快、更优雅」。

这大概就是我和真正资深的人之间那层窗户纸：不是不知道 Iceberg 好，是**没有养成先问「最坏会怎样、代价多低能兜住」的习惯**。

### 这篇评审本身就是最好的面试素材

写完发现，这份清单比任何「项目介绍」都更能说明我对这条链路的理解程度。面试官问「你负责什么」，谁都能背出组件列表；但能说出「这套架构的风险重心在哪、为什么、我会按什么顺序改」的人，是另一个层级。

**「维护过」和「想过」的差距，就在这份清单上。**
