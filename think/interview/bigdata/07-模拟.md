# 📝 参考答案要点（得分点清单）

> 下面是面试官打分时在心里勾的点。你不必字字命中，但主要得分点漏了就是没答透。

## 第一轮

**Q1 OLTP/OLAP**
- OLTP＝在线事务处理：单行/少量行的增删改查、强事务、高并发、低延迟（MySQL/Mongo，业务库）。
- OLAP＝在线分析处理：海量行扫描聚合、读多写少、吞吐优先（Spark/StarRocks/ClickHouse，数仓/报表）。
- 加分：一句话＝OLTP 面向"操作"，OLAP 面向"分析"；这是选型的根本分水岭。

**Q2 列存为什么快**
- ① 列裁剪：查询只读用到的列，不读整行 → 少读大量数据。
- ② 高压缩：同一列同类型数据相邻，压缩率远高于行存 → 少读磁盘 + 省 IO。
- ③ 向量化：按列成批处理，配合 CPU SIMD。
- 加分：还有谓词下推（Parquet 存了 min/max，能跳过整个 row group）。

**Q3 宽窄依赖**
- 窄依赖：父分区被子的**一个**分区消费（map/filter），不用跨节点，可在同一 stage 内 pipeline。
- 宽依赖：父分区被子的**多个**分区消费（groupBy/join/distinct/repartition），要 shuffle。
- 关系：**stage 的边界就是宽依赖（shuffle）**；一次 shuffle 切一刀。
- 追问答案：groupByKey/reduceByKey/join/distinct/repartition/sortByKey 等。

**Q4 多 action 重算**
- 机制：Spark lazy，transformation 不执行；每个 action 都会**从头沿 lineage 重算**上游。N 个 action 共享的上游就跑 N 次（含所有 JOIN/shuffle）。
- 后果：shuffle 量翻 N 倍，可能触发 S3 限流甚至 job abort。
- 解法：① `cache`/`persist`（上游被 ≥2 action 依赖且含重操作时）；② 物化到临时表断开 lineage；③ 减少 action 数（多个聚合 UNION 成一个）。

**Q5 退出码 137**
- 137 = 128+9 = 被 SIGKILL，通常是**容器超内存被 OOMKilled**（堆外/overhead 超了，不是 JVM 堆 OOM）。
- 不该无脑调 `executor.memory`：如果是堆外超限，调堆没用甚至更糟（挤占 overhead）。
- 排查：先分清 Driver 还是 Executor 挂、是 JVM OOM（有 heap dump/日志）还是容器 OOMKilled（137）；后者调 `memoryOverhead`/`memoryOverheadFactor`。
- 加分：读 S3/shuffle 密集的场景堆外需求大，overhead 常是真凶。

**Q6 数据倾斜**
- 是什么：数据按 key 分布不均，某个/某几个 key 数据量极大 → 对应 task 拖死整个 stage（其他 task 早跑完在等）。
- 定位：Spark UI 看某 stage 里个别 task 的耗时/输入数据量远超中位数（长尾）。
- 解法：加盐打散（大 key 拆成多个）、两阶段聚合（局部+全局）、大表 join 小表改 broadcast、单独处理热点 key。

**Q7 fact/dim/粒度**
- 事实表：记"发生了什么"，一行一事件，量大，含度量值 + 指向维表的外键（订单/点击）。
- 维表：记"是什么"，描述性，量小（商品/用户/时间/地区）。
- 粒度：一行代表什么（一笔订单？一天一店？）。必须先定粒度，否则聚合口径、能不能 join、度量可不可加全都说不清。

**Q8 数仓分层**
- ODS 贴源 → DWD 明细清洗 → DWS 轻度汇总 → ADS 应用；DIM 层放维表。
- 为什么：复用（中间层被多个下游共享，不重复算）、解耦（改一层不炸全链路）、口径统一（指标只在一处定义）。
- 不分层：逻辑烟囱式重复、口径打架、难维护难排查。

**Q9 Trino vs Spark**
- Trino：MPP 交互式查询引擎，全内存 pipeline，秒级 ad-hoc，不落盘、query 失败整个重来，不适合重型 ETL。
- Spark：批处理引擎，可落盘、容错好，适合大规模 ETL、跑得动重活但启动/调度有开销。
- 用 Trino：交互式探查、跨源查询、BI 即席查询。用 Spark：定时重型 ETL、超大数据清洗聚合。

**Q10 OLAP 选型**
- (a) → **ES**：全文检索 + 灵活过滤是倒排索引的主场。
- (b) → **ClickHouse**：单表超大规模聚合、列存向量化最强，日志埋点 append 场景。
- (c) → **StarRocks**：多表 JOIN + 实时更新（主键模型）+ 高并发，对外服务型实时数仓。
- 口诀：搜→ES，单表狂算→CH，多表实时对外→SR。

**Q11 execution_date + 幂等**
- execution_date/logical_date：这批数据的**逻辑日期**（数据所属的业务日期），不是实际运行时刻。T+1 里今天凌晨跑的 execution_date 是昨天。
- 幂等：同一任务重跑/回补，结果一致不重复不出错。
- 怎么做：按 execution_date 分区 **OVERWRITE** 覆写，而不是 append；避免依赖"当前时间/随机数"。

## 第二轮

**Q12 Partition 双义**
- 反问："你是指 Hive 表分区还是 Spark 的 RDD 分区？"
- Hive 表分区：物理按 date/country 分目录，**存储概念**，解决"查询只扫需要的分区"（分区裁剪）。
- Spark 分区：一份数据在内存里切成 N 块并行处理，**并行度概念**（`spark.sql.shuffle.partitions`）。

**Q13 shuffle 为什么贵**
- 磁盘：map 端结果要 shuffle write 落盘。
- 网络：reduce 端跨节点拉数据（shuffle read）。
- 资源：排序/序列化/大量小文件；文件数 = map数 × reduce数，易触发对象存储限流。
- 触发：join / groupBy / distinct / repartition / 窗口 / sort 等宽依赖。

**Q14 broadcast join**
- 把**小表**完整复制到每个 executor，让大表在本地完成 join，**避免 shuffle**（用空间换 shuffle）。
- 自动触发：小表估算 < `autoBroadcastJoinThreshold`（默认 10MB，可调，如项目里 100MB）。
- 不该用：两张表都大 → broadcast 会撑爆 executor 内存/本地盘；估算不准时可能 OOM。

**Q15 内存模型**
- 堆内：execution（shuffle/sort/join 计算）、storage（cache）、user（用户数据结构）、reserved。
- 堆外 memoryOverhead：JVM 之外的开销——netty 网络缓冲、S3 client、本地缓冲等；读 S3/shuffle 密集时需求大。
- 判断：JVM 堆 OOM（日志有 OutOfMemoryError、heap dump）→ 调 executor.memory / 减少单分区数据；容器 OOMKilled（退出码 137）→ 调 memoryOverhead。

**Q16 Hive 本质**
- 不是数据库。现在说 Hive 通常指 **Hive Metastore（元数据）+ 表格式**，不是它老的 MapReduce 执行引擎。
- Metastore 存：表 → S3/HDFS 路径映射、schema（列名类型）、分区 → 目录映射、SerDe/格式等。
- 一句话：Hive 给对象存储上一堆文件套了一层"表"的抽象。

**Q17 分区裁剪 & 小文件**
- 分区裁剪：查询带分区过滤（如 date='...'）时，只扫对应目录，跳过其余 → 少读海量数据。
- 小文件：太多小文件 → NameNode/元数据压力、task 数爆炸、每个文件固定开销放大、list/open 慢。
- 治理：合并/compaction、控制写出分区数（coalesce/repartition）、避免过细分区、定期归档。

**Q18 联邦查询**
- 联邦查询：一套 SQL 查多种异构数据源（Hive/MySQL/ES/Kafka…），甚至跨源 JOIN。
- 机制：Connector 抽象，每种源一个 connector 适配。
- 内存不够：Trino query 直接失败（不 spill）；Spark 能 spill 落盘继续（慢但不挂）。

**Q19 倒排索引**
- 结构：词（term）→ 包含该词的文档列表（posting list）；查询时对多个词的 posting list 求交/并。
- 适合搜索：直接按词定位文档，不用全表扫；配分词、相关性打分（BM25）。
- 聚合不如 CH：ES 面向检索不是列存分析，大规模聚合内存开销大、慢，且资源消耗高。

**Q20 ClickHouse 特性**
- 快：列存 + 向量化 + 高压缩 + 常驻进程（无 Spark 起 job 开销）+ MergeTree 有序存储利于范围扫。
- 不适合频繁更新：MergeTree 以 append + 后台 merge 为主，update/delete 代价高（异步、非实时）。
- 不适合高并发点查/复杂多表 join：为大扫描聚合设计，join 弱、无强事务。

**Q21 星型/雪花/宽表**
- 星型：维表不再拆，冗余存储，join 少、查询简单快。
- 雪花：维表按范式拆多层，省空间但 join 多、复杂。
- 大数据偏星型：存储便宜、join 是瓶颈，用冗余换查询性能。
- 宽表：多表打平成一张，省 join；滥用＝把跨语义字段塞一起造成语义耦合、维护灾难（别污染单一职责的维表）。

**Q22 Airflow 概念**
- DAG 无环：有环＝循环依赖，无法确定执行顺序、会死锁；无环才能拓扑排序。
- backfill：手动补跑一段历史区间；catchup：DAG 上线/暂停后自动把错过的调度周期补齐。
- Sensor：一种等待型 task，轮询/等待外部条件满足（文件到达、分区就绪）才放行下游。

## 第三轮

**Q23 S3 限流调优**（至少 3 点）
- 降 shuffle 文件数：`spark.sql.shuffle.partitions` 调小、合并输出。
- 断重算：把被多 action 依赖的重上游物化到临时表（消除 N 倍 shuffle）。
- S3 相关 conf：关批量删除（`multiobjectdelete.enable=false` 避开 SlowDown）、加 retry 间隔、broadcast 小表减 shuffle。
- 根治优先物化 + 减 action，conf 只是缓解。

**Q24 CPU 误诊**
- 别听"加核数"就加。看 Spark UI 指标定位真瓶颈。
- `cpu/run` 只有 7% → CPU 基本闲着，不是 CPU 瓶颈；spill=0 → 也不是内存不够。
- 说明是 **IO-bound**（S3 读 / shuffle 网络 / 磁盘），加 CPU/内存无用，要治 IO（减 shuffle、减重复读、物化）。
- 纪律：先看实测指标再开药，别凭直觉。

**Q25 无 cache 的 lineage 治理**
- 物化到临时 Hive 表：`save ... to hive."tmp_xxx"` → 再 `load` 回来同名，后续 action 从物理表读，lineage 断开。
- 或减少 action 数（多聚合 UNION ALL 成一个 print/save）。
- 代价：1 次 disk write + read，但换掉 N 次重算 join。

**Q26 建模红线**
- 问题：把"卖家身份"塞进"渠道占比"维表，两个无关语义硬绑 → 语义耦合，改占比算法时易误伤身份字段，维表职责不再单一。
- 收益 vs 代价：省的那次 join << 引入的耦合维护成本。
- 正确：身份字段留在它该在的表；真要合就新建一张语义明确的 wide 表，别污染单一职责维表。

**Q27 execution_date 坑**
- 问题：用"当前日期"过滤 → 补跑上周一时当前日期是今天，取错了数据区间。
- 正确：用 `execution_date`（逻辑日期）参数化过滤和写分区，任务结果只依赖 execution_date、不依赖运行时刻 → 天然可回补、幂等。

**Q28 数据流综合**（参考链路）
- App 下单 → 业务库（MySQL/Mongo，OLTP）→ CDC/抽取 → S3 原始文件（数据湖）→ Hive 建表 → Spark 清洗聚合（Airflow 定时调度、按 date 分区、幂等覆写）→ 结果 sink 到 StarRocks/ClickHouse → 报表/BI 查询。Trino 可随时对湖做即席核对。
- 能把每环对上一个技术就满分。

**Q29 批 → 流**
- 批：T+1，Spark 定时跑分区。
- 流：数据源接 **Kafka**（消息队列）→ **Flink**（流计算，事件驱动、状态计算、窗口）→ 实时写 StarRocks/ClickHouse/ES 供秒级查询。
- 引入概念：exactly-once、watermark（处理乱序/延迟）、状态管理。
- 加分：很多场景是 Lambda/Kappa 架构，批流结合。

**Q30 讲事故**（结构）
- 现象（带数字）→ 定位过程（看了哪些指标/日志）→ 根因 → 解决 → 复盘教训。
- 例：13 个 print 的诊断脚本 job abort → 查到 base join 被重算 13 次、shuffle 放大 13× 触发 S3 SlowDown → 根因是 lazy 多 action 重算 → 物化中间表断 lineage → 教训：lazy 引擎里多 action 必须先物化/cache。
- 会讲故事（有数字、有排查链路、有根因）比答对十道概念题更打动面试官。
