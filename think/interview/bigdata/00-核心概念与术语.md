# 大数据核心概念与术语速查

> 面试底座 / 术语大全 · 跨技术通用概念

## 写在前面：一个记忆框架

大数据这个领域看起来术语一大堆，但你只要抓住一条主线就不慌：

**几乎每一个术语，都是"某个具体的数据问题或性能问题"的名字。**

- 数据太大，一台机器装不下、算不完 → 于是有了**分区(Partition)**、**Shuffle**、**并行度**。
- 内存放不下 → 于是有了 **Spill(溢写)**。
- 某个 key 数据特别多 → 于是有了**数据倾斜(Data Skew)**。
- 存储和计算的增长速度不一样 → 于是有了**存算分离**。
- 分析型查询只读几列却要扫全表 → 于是有了**列存**。
- 任务失败要重跑 → 于是有了**幂等(Idempotent)**。
- 历史数据算错了要重算 → 于是有了 **Backfill(回补)**。

所以面试答题的套路永远是：**这个词是为了解决什么问题而存在的**。你把"问题 → 方案 → 代价"三段讲清楚，就已经赢了 80% 只会背定义的人。

下面按这个思路逐个拆解。

## 1. OLTP vs OLAP —— 最根本的分水岭

**一句话定义**：OLTP 是"面向交易的在线处理"（增删改查单条记录），OLAP 是"面向分析的在线处理"（对海量数据做聚合统计）。

**解决什么问题**：两类业务对数据库的要求天差地别，一套系统同时做好几乎不可能，所以要分家。

- OLTP：一次操作动几行，要求强一致、低延迟、高并发。典型是"下单、扣库存、转账"。
- OLAP：一次查询扫几百万行做 `SUM/GROUP BY`，要求高吞吐、能扫大数据，单条延迟不敏感。典型是"统计上个月各国 GMV"。

**例子**：

| 维度 | OLTP | OLAP |
|------|------|------|
| 典型操作 | `INSERT/UPDATE/DELETE` 单行 | `SELECT ... GROUP BY` 全表聚合 |
| 数据量/次 | 几行 | 百万~亿行 |
| 关注指标 | 事务、并发、延迟 | 吞吐、扫描速度 |
| 存储倾向 | 行存 | 列存 |
| 代表系统 | MySQL、PostgreSQL、MongoDB | Trino、StarRocks、ClickHouse、Hive |

一句话记忆：**OLTP 管"业务在跑"，OLAP 管"业务跑得怎么样"**。你维护的 ETL 管道，本质就是把 OLTP 系统产生的业务数据，搬到 OLAP 系统里供分析。

## 2. 批处理 vs 流处理（Batch vs Streaming）

**一句话定义**：批处理是"攒一批数据一起算"（如每天算一次），流处理是"数据来一条算一条"（近实时）。

**解决什么问题**：不同业务对"数据新鲜度"的要求不同。财务日报 T+1 就够；风控、实时大盘要求秒级。

- **批处理（Batch）**：有明确的数据边界（如"昨天全天的数据"），周期性触发，吞吐高、延迟高。俗称 **T+1**（今天算昨天的）。
- **流处理（Streaming）**：数据是无界的持续流，来一条处理一条，延迟低（毫秒~秒级），但要处理乱序、迟到、状态管理等复杂问题。

**例子**：

| 维度 | 批处理 | 流处理 |
|------|--------|--------|
| 数据边界 | 有界（昨天一整天） | 无界（持续不断） |
| 延迟 | 分钟~小时（T+1） | 毫秒~秒 |
| 代表技术 | Spark、Hive、Airflow 调度 | Flink、Kafka Streams、Spark Streaming |
| 典型场景 | 每日报表、离线数仓 | 实时大盘、风控、监控告警 |

你的 ETL 管道用 Airflow 调度 Spark 跑 T+1，就是典型批处理。面试若被问"你们为什么不上实时"，标准答法是：**业务对新鲜度要求是天级，批处理成本更低、逻辑更简单、可重跑，没必要为实时付出复杂度代价。**

## 3. 存算分离 —— 现代数据平台的地基

**一句话定义**：把"数据存储"和"计算引擎"拆成两个独立可扩展的层，存储放对象存储（如 S3），计算引擎按需拉起。

**解决什么问题**：传统"存算一体"（如早期 Hadoop HDFS + MapReduce，数据存哪就在哪算）有两个硬伤：

1. **存储和计算的增长不同步**：数据一直涨（要扩存储），但计算高峰只在白天（要弹性扩缩容）。绑在一起就得两个都按峰值买，浪费。
2. **扩容要搬数据**：加计算节点得做数据 rebalance，很重。

**存算分离**后：

- 存储层：S3 / 对象存储，无限扩容、便宜、只管存。
- 计算层：Spark / Trino / StarRocks 计算节点，用完即走，按需弹性伸缩，多个引擎共享同一份数据。

**例子**：你的项目里 Hive 表数据实际落在 **S3**，Spark 任务跑的时候临时拉起 executor 从 S3 读数据、算完写回 S3、然后释放节点。存储（S3）和计算（Spark 集群）互不绑定——这就是存算分离。**代价**是计算要走网络读远端存储（比本地盘慢），所以才有 shuffle S3 限流、数据本地性下降等问题。

| 维度 | 存算一体（传统 Hadoop） | 存算分离（现代） |
|------|------------------------|-----------------|
| 数据位置 | 计算节点本地盘（HDFS） | 远端对象存储（S3） |
| 扩容 | 存算一起扩，要搬数据 | 各自独立弹性伸缩 |
| 成本 | 按峰值配置，浪费 | 计算用完即走 |
| 短板 | 弹性差 | 读远端有网络开销 |

## 4. 行存 vs 列存 —— 为什么 OLAP 用列存

**一句话定义**：行存把"一行的所有列"连续存一起，列存把"同一列的所有值"连续存一起。

**解决什么问题**：分析查询往往"只查几列，但要扫很多行"。行存下即使只 `SELECT price`，磁盘也得把每行的全部列都读进来再挑出 price，浪费大量 IO。列存则只读 price 这一列的数据块。

**列存三大红利**：

1. **只读需要的列**：`SELECT SUM(price)` 只扫 price 列，IO 大幅下降。
2. **压缩率极高**：同一列数据类型相同、值相近（比如国家列全是几十个国家名反复出现），压缩比行存好几倍。
3. **向量化执行（Vectorization）**：同一列同类型的数据可以成批（一个 batch 上千行）用 CPU 的 SIMD 指令一次性处理，而不是一行一行走。ClickHouse、StarRocks 快就快在这里。

**例子**：

```
行存（MySQL）:  [id=1,name=A,price=10][id=2,name=B,price=20]...
              查 SUM(price) → 每行都得读进来
列存（Parquet）: id列[1,2,...] name列[A,B,...] price列[10,20,...]
              查 SUM(price) → 只读 price 那一段，还能整段压缩+向量化
```

| 维度 | 行存 | 列存 |
|------|------|------|
| 存储方式 | 一行连续 | 一列连续 |
| 擅长 | 按主键读整行、频繁更新 | 少列多行的聚合分析 |
| 压缩率 | 一般 | 高（同列同类型） |
| 向量化 | 难 | 天然适合 |
| 代表 | MySQL、行式 OLTP | Parquet、ORC、ClickHouse、StarRocks |

记忆点：**OLTP 要整行 → 行存；OLAP 要几列聚合 → 列存**。你项目里 Hive 表用 Parquet 就是列存格式。

## 5. Source / Sink —— 数据流的读端与写端

**一句话定义**：Source 是数据管道的"输入端/读数据的地方"，Sink 是"输出端/写数据的地方"。

**解决什么问题**：任何数据处理都是"从哪读 → 怎么处理 → 写到哪"。给读端写端起统一的名字，方便描述管道拓扑。

- **Source（源）**：数据从哪来。如 Kafka topic、S3 上的 Parquet、MySQL binlog。
- **Sink（汇）**：数据往哪去。如写入 StarRocks、ES 索引、另一张 Hive 表。
- **Upstream / Downstream（上游 / 下游）**：相对位置。给我提供数据的是上游，消费我输出的是下游。

**例子**：一条典型链路
```
MySQL(source) → CDC → Kafka → Spark 处理 → StarRocks(sink)
                                  ↑上游是Kafka  ↓下游是StarRocks
```
在你的 ETL 里：`load hive` 读的表是 source，`save ... to hive` 写的表是 sink。当有人说"上游改了 schema 导致我这个字段全 NULL"，意思就是给你供数的那个环节变了。

## 6. Shuffle —— 按 key 跨节点重排，为什么贵

**一句话定义**：Shuffle 是把分散在各节点上的数据，按某个 key 重新分发、使"相同 key 的数据汇聚到同一节点"的过程。

**解决什么问题**：`GROUP BY user_id`、`JOIN ON user_id` 这类操作，要求同一个 user_id 的所有数据必须在同一个节点才能算。但数据一开始是随机散落在各节点的，所以必须做一次跨节点的重新洗牌——这就是 shuffle。

**为什么贵（面试高频）**：

1. **落磁盘**：shuffle 前每个节点要把数据按目标分区写成 shuffle 文件（写盘）。
2. **走网络**：再跨节点拉取（网络传输）。
3. **文件数爆炸**：`map 端分区数 × reduce 端分区数` 个文件，存算分离下写 S3 还会触发限流（你项目里踩过的 `MultiObjectDeleteSupport: SlowDown`）。
4. **是 stage 的分界线**：Spark 以 shuffle 为界切 stage，shuffle 就是"宽依赖"，必须等上游全部算完才能开始下游。

**例子**：
```sql
SELECT country, SUM(gmv) FROM orders GROUP BY country
```
各节点先局部按 country 分组，然后把相同 country 的数据 shuffle 到同一节点做最终汇总。数据量越大、分区越多，shuffle 开销越大。**优化方向**：能广播就广播（见下条）、减少 shuffle 分区数、预聚合（map 端 combine）。

## 7. Broadcast —— 小表广播，用空间换 shuffle

**一句话定义**：把 JOIN 中的小表完整复制一份发到每个计算节点，让大表在本地就能完成 JOIN，从而避免对大表做 shuffle。

**解决什么问题**：普通 JOIN 要对两张表都按 join key 做 shuffle，大表 shuffle 非常贵。但如果一张表很小（几十 MB），把它整个广播到每个节点，大表就不用动了——每个节点用本地的小表副本直接匹配。

**代价**：小表要占每个 executor 的内存（用空间换 shuffle）。所以只对"足够小"的表广播，太大反而 OOM。

**例子**：
```sql
-- 大表 orders(亿行) JOIN 小表 dim_country(几百行)
-- 广播 dim_country 到每个节点，orders 不用 shuffle
```
Spark 有 `spark.sql.autoBroadcastJoinThreshold`（如 100MB）自动判断：小于阈值的表自动走 broadcast join。你项目 CLAUDE.md 里就有这个 conf。**Broadcast Join vs Shuffle(Sort-Merge) Join** 是面试常考对比：

| 维度 | Broadcast Join | Shuffle Join |
|------|----------------|--------------|
| 适用 | 一张表足够小 | 两张都是大表 |
| 是否 shuffle 大表 | 否 | 是（两张都 shuffle） |
| 代价 | 小表占各节点内存 | 网络+磁盘 IO 大 |

## 8. Partition 的两个含义 —— 极易混，重点讲

"分区"这个词在大数据里有**两个完全不同的含义**，面试和排错都极易混淆，必须掰开：

### 含义 A：表分区（存储层概念，Hive Partition）

**一句话定义**：按某个列（如 `date`、`country`）把表数据在存储上切成一个个子目录，物理上分开存放。

**解决什么问题**：查询时只读需要的分区，跳过其余数据——叫**分区裁剪（Partition Pruning）**。

**例子**：Hive 表 `orders` 按 `date/country` 分区，S3 上目录长这样：
```
s3://.../orders/date=2026-07-20/country=US/part-xxx.parquet
s3://.../orders/date=2026-07-20/country=ID/part-xxx.parquet
```
查 `WHERE date='2026-07-20' AND country='US'` 时，引擎只扫那一个目录，其余全跳过。这就是为什么你项目里强调"分区键（date/country）必须放 SELECT 字段列表最后"，且 `save ... partitionBy` 顺序要和 DDL 一致——它决定数据落到哪个物理目录。

### 含义 B：Spark 分区（计算层概念，并行度）

**一句话定义**：Spark 把一个 RDD/DataFrame 的数据切成 N 份，每份叫一个 partition，一个 partition 对应一个 task，由一个 CPU core 处理。它是**并行度**的单位。

**解决什么问题**：决定这份数据能被拆成多少个 task 并行跑。分区太少 → 并行度不够、单 task 太大易 OOM；分区太多 → 调度开销大、小文件多。

**例子**：`spark.sql.shuffle.partitions=200` 表示 shuffle 之后数据切成 200 个分区，即最多 200 个 task 并行做下游计算。你项目里把它调到 100 是为了"降低 shuffle 文件数、防 S3 限流"。

### 对比（这张表建议背下来）

| 维度 | 表分区（Hive Partition） | Spark 分区（Partition） |
|------|-------------------------|------------------------|
| 属于 | 存储层 | 计算层 |
| 是什么 | 数据在磁盘/S3 上的物理子目录 | 内存中数据的并行切片 |
| 目的 | 分区裁剪，少读数据 | 控制并行度 |
| 单位 | 一个分区=一个目录 | 一个分区=一个 task |
| 怎么设 | 建表 `PARTITIONED BY` | `repartition` / `shuffle.partitions` |
| 关键词 | Partition Pruning | 并行度 / task |

一句话点破：**Hive 分区是"数据存在哪个文件夹"，Spark 分区是"这份数据拆成几个 task 并行算"**。两者没有必然对应关系。

## 9. Lazy Evaluation / Transformation vs Action —— 懒执行

**一句话定义**：Spark 的算子分两类——Transformation（转换，如 `select/filter/join/groupBy`）只是"记账"、不真正执行；Action（行动，如 `save/count/collect/print`）才真正触发计算。不到 action，什么都不算。

**解决什么问题**：懒执行让引擎能拿到整条 lineage（血缘），做全局优化（谓词下推、算子合并、列裁剪）后再一次性执行，比一步步立即算高效得多。

**关键陷阱（你项目 CLAUDE.md 反复强调）**：每个 action 都会**从头**沿 lineage 重算上游所有 transformation。如果一个脚本里有 N 个 action 共享同一个上游 lazy view，那个上游（含所有 JOIN/shuffle）会被**重算 N 次**。

**例子**：
```sql
select ...大量JOIN... to base;   -- transformation，此刻不执行
print agg1_from_base;            -- action ①，触发 base 全量重算
print agg2_from_base;            -- action ②，base 又从头算一遍
-- 13 个 print → base 的 join 跑 13 次，shuffle 放大 13×
```
解法：把重复用到的 lazy view **物化**到临时表（打断 lineage），或把多个 action 合并成一个 `UNION ALL` 单 print。这正是你项目"monthly features IO-bound"那条记忆的核心。

| 概念 | 例子 | 是否触发执行 |
|------|------|-------------|
| Transformation | `select` `filter` `join` `groupBy` `to view` | 否（只记血缘） |
| Action | `save` `print` `count` `collect` `show` | 是（触发计算） |

## 10. 数据倾斜（Data Skew）—— 某个 key 数据超多拖死任务

**一句话定义**：数据按 key 分区后分布极不均匀，某几个 key 的数据量远超其他，导致处理这些 key 的 task 慢得离谱，拖垮整个作业。

**解决什么问题**：并行计算的总耗时取决于**最慢的那个 task**（木桶效应）。99 个 task 1 分钟跑完，1 个倾斜 task 跑 1 小时，整个 job 就是 1 小时。

**为什么产生**：shuffle 时相同 key 进同一分区。如果某个 key（如 `user_id=NULL`、某爆款商品、某大 V）占了数据的一大半，它全挤进一个 task。

**例子**：
```sql
SELECT seller_id, COUNT(*) FROM orders GROUP BY seller_id
-- 某超级卖家占了 40% 订单 → 它那个 task 数据量是别人的几百倍
```
典型信号：Spark UI 里某个 task 的 shuffle read/耗时远超其他，或 stage 卡在 99% 不动。**常见解法**：

- **加盐（salting）**：给热点 key 拼随机后缀打散成多个 key，聚合后再合并。
- **过滤/单独处理**热点 key（如 NULL 单独拎出）。
- **map 端预聚合**减少进 reduce 的量。
- 开启 **AQE（Adaptive Query Execution）** 自动切分倾斜分区。

## 11. Spill（溢写）—— 内存放不下写磁盘

**一句话定义**：计算（如排序、聚合、shuffle）时，中间数据超过分配的内存，Spark 把一部分数据写到本地磁盘临时腾出内存，叫溢写。

**解决什么问题**：内存有限，数据可能远超内存。Spill 是"宁可慢也别 OOM"的兜底——保证任务能跑完，代价是磁盘 IO 让它变慢。

**例子**：一个 task 要对 2GB 数据排序，但只分到 1GB 执行内存 → 排一部分写盘、再排一部分、最后归并。你在日志/Spark UI 里看到 `Spill (Memory)` / `Spill (Disk)` 有值，就说明发生了溢写。**大量 spill 是性能红灯**，尤其存算分离下本地盘还小（你那条"SEA 节点本地盘仅 ~5.8GB"的记忆就是这个坑）——盘写爆了任务直接失败。

**Spill 和数据倾斜常一起出现**：倾斜 task 数据量巨大 → 内存装不下 → 疯狂 spill → 更慢甚至撑爆本地盘。优化优先级：**先消 spill（调内存/减少单分区数据量），而不是无脑加 CPU**。

## 12. 幂等（Idempotent）—— 重跑不出错

**一句话定义**：一个操作执行一次和执行多次，结果完全一样。重复跑不会产生副作用（不会重复累加、不会写脏）。

**解决什么问题**：分布式任务经常失败重试、人工重跑、调度补数。如果不幂等，重跑一次数据就翻倍/错乱。幂等让"失败了重跑一遍"成为安全操作，这是数据管道可靠性的基石。

**怎么做到**：

- **覆盖写而非追加**：`INSERT OVERWRITE`（按分区覆盖）而不是 `INSERT INTO`（追加）。重跑同一天，直接覆盖那天分区，结果不变。
- **按主键 upsert** 而不是 insert。
- **确定性逻辑**：同样输入永远同样输出（少用 `now()`、随机数、非确定 UDF）。

**例子**：
```sql
-- 幂等：重跑 2026-07-20 直接覆盖该分区，跑几次结果都一样
INSERT OVERWRITE TABLE t PARTITION(date='2026-07-20') SELECT ...
-- 非幂等：重跑就多插一遍，数据翻倍
INSERT INTO TABLE t SELECT ...
```
面试点睛：**幂等是可重跑（re-runnable）的前提，可重跑是 backfill 的前提**。三者一条链。

## 13. Backfill（回补） / CDC（变更数据捕获）

### Backfill（回补 / 补数）

**一句话定义**：对历史某段时间的数据重新计算/补算，通常因为逻辑改了、数据错了、或新增了一张表需要填历史。

**解决什么问题**：数据管道上线时只算"从今天起"，但下游需要历史；或发现过去某段算错了要修正。Backfill 就是"按历史每一天重跑一遍任务"。

**例子**：你把某指标公式修了 bug，需要把过去 90 天全部重算——用 Airflow 把 DAG 按 `2026-04-22 ~ 2026-07-20` 每个分区重跑一遍。**能顺利 backfill 的前提就是任务幂等**（覆盖写），否则补数会把数据搞乱。

### CDC（Change Data Capture，变更数据捕获）

**一句话定义**：捕获源数据库（OLTP）里的增删改（INSERT/UPDATE/DELETE），实时/准实时同步到下游（数仓、Kafka、ES）。

**解决什么问题**：数仓要拿到业务库最新数据。全量拉太重、太慢；CDC 只抓"变化的部分"，增量同步，低延迟、低负载。

**怎么实现**：读数据库的事务日志（如 MySQL binlog、Postgres WAL），把每一条变更事件流出来。典型工具 Debezium、Flink CDC、Canal。

**例子**：MySQL `orders` 表有人下单（INSERT）→ binlog 记录 → Debezium 捕获 → 推到 Kafka → 下游 Spark/Flink 消费更新数仓。**CDC 常作为流处理管道的 Source**（呼应第 5 条），是实时数仓的入口。

## 14. Schema / Schema-on-read vs Schema-on-write

**Schema（模式）**：数据的结构定义——有哪些字段、每个字段什么类型。

**核心区别在于"什么时候校验 schema"**：

- **Schema-on-write（写时模式）**：写入前就必须符合预定义结构，不符合就拒绝。传统数据库/数仓走这条。**先建表定义列，才能写数据。**
  - 优点：数据规整、查询快、类型有保证。
  - 缺点：不灵活，源结构一变就要改表。
- **Schema-on-read（读时模式）**：写入时不校验，什么都能存（原始 JSON/日志）；**读的时候才套一个 schema 去解析**。数据湖走这条。
  - 优点：灵活，先存下来再说，适合半结构化/schema 多变的数据。
  - 缺点：读时才发现数据脏/字段缺、查询可能更慢。

**例子**：

| 维度 | Schema-on-write | Schema-on-read |
|------|-----------------|----------------|
| 校验时机 | 写入时 | 读取时 |
| 代表 | MySQL、Hive 严格表、StarRocks | S3 上原始 JSON、数据湖 |
| 灵活性 | 低（先建表） | 高（先存后解析） |
| 典型场景 | 结构化数仓 | 日志/埋点/半结构化 |

你项目 CLAUDE.md 里那个坑——"JSON schema 中 `array<string>` 遇到纯字符串值时 Spark 会按字符拆分"——就是 schema-on-read 的典型问题：读时套 schema 解析，源数据格式不统一就出幺蛾子。

## 15. ETL vs ELT —— 现代数据栈为什么转向 ELT

**一句话定义**：都是"抽取(Extract)-转换(Transform)-加载(Load)"，区别在 **Transform 和 Load 的先后顺序**。

- **ETL**：抽取 → **先在中间层转换清洗** → 再加载进数仓。转换在数仓之外做。
- **ELT**：抽取 → **先原样加载进数仓/数据湖** → 再用数仓自身算力转换。转换在数仓内部做。

**为什么现代转向 ELT**：

1. **存储便宜了**（S3 白菜价）：先把原始数据全存下来无所谓，不必在入库前就砍掉。
2. **数仓算力强了**（Trino/StarRocks/Spark MPP）：转换直接用数仓自身的分布式算力，不需要单独的转换服务器。
3. **更灵活**：原始数据都在，需求变了直接重新 transform，不用重新抽取。
4. **保留原始数据**：ETL 转换后原始数据常丢失，ELT 保留原始层（ODS），可追溯、可重算。

**例子**：

| 维度 | ETL | ELT |
|------|-----|-----|
| 转换位置 | 数仓外的中间层 | 数仓/湖内部 |
| 转换时机 | 加载前 | 加载后 |
| 原始数据 | 常丢失 | 保留 |
| 前提 | 存储贵、数仓算力弱的年代 | 存储便宜、MPP 数仓 |
| 典型 | 老式 Informatica | S3 + Spark/Trino 现代数据栈 |

你的管道 `load hive`（从 S3 读原始）→ Spark 转换 → `save` 回 Hive，本质就是 ELT：原始数据先落 S3，再用 Spark 在数仓内部转换。

## 16. 数据湖 / 数据仓库 / 湖仓一体（Lakehouse）

**数据仓库（Data Warehouse）**：结构化、schema-on-write、为分析优化过的规整数据。数据进来前先建模清洗。适合 BI 报表、固定分析。缺点：贵、不灵活、存不下半/非结构化数据。

**数据湖（Data Lake）**：一个啥都能装的大存储（S3 上放 Parquet/JSON/图片/日志），schema-on-read，先存后治理。优点：便宜、灵活、能存原始/半结构化数据。缺点：容易变"数据沼泽"——没治理、没事务、数据质量差、查询慢。

**湖仓一体（Lakehouse）**：想同时要"数据湖的便宜灵活"+"数据仓库的可靠好查"。在数据湖的开放存储（S3 上的 Parquet）之上，加一层**表格式（Table Format）**——Iceberg / Delta Lake / Hudi——给数据湖补上：ACID 事务、schema 演进、时间旅行、行级更新、分区管理。既能像数仓一样可靠查询，又保留湖的低成本与灵活。

**例子**：

| 维度 | 数据仓库 | 数据湖 | 湖仓一体 |
|------|---------|--------|---------|
| 存储 | 专有格式 | S3 原始文件 | S3 + 开放表格式 |
| Schema | 写时 | 读时 | 灵活 + 有约束 |
| 事务/ACID | 有 | 无 | 有（表格式提供） |
| 数据类型 | 结构化 | 全部 | 全部 |
| 代表 | Teradata、传统数仓 | S3 + Hive 裸表 | Iceberg / Delta / Hudi |

一句话：**数据湖 = 便宜能装但乱；数据仓库 = 规整可靠但贵死板；湖仓一体 = 在湖上加事务和管理，鱼和熊掌兼得**。你项目现在 Hive 表 + S3 是偏"湖+数仓"混合形态，Lakehouse 是这条路的进化方向。

## 面试高频问题 + 答题要点

### Q1. 讲讲 OLTP 和 OLAP 的区别？

**要点**：本质是"业务在跑" vs "看业务跑得怎么样"。OLTP 一次动几行、要事务和低延迟、行存、高并发（MySQL 下单扣库存）；OLAP 一次扫百万行做聚合、要吞吐、列存、延迟不敏感（Trino 算月度 GMV）。**升华**：正因为要求相反，才要把业务库数据 ETL 到分析系统，两边各司其职，这就是数据工程存在的理由。

### Q2. 为什么列存适合分析、行存适合交易？

**要点**：分析查询"少列多行聚合"，列存只读需要的列、同列数据压缩率高、还能向量化(SIMD)批处理，IO 和 CPU 都省。交易查询"按主键读整行/频繁更新"，行存一行连续，一次读到全部字段、改起来也方便。**一句话**：OLAP 要几列 → 列存；OLTP 要整行 → 行存。

### Q3. Shuffle 为什么慢？怎么优化？

**要点**：慢在三点——(1) shuffle 前数据要按目标分区**落盘**；(2) 再**跨节点走网络**拉取；(3) 产生 `map分区数×reduce分区数` 个文件，存算分离写 S3 还会限流。它还是 stage 的分界，下游必须等上游全部完成。**优化**：能广播就 broadcast join、减少 shuffle 分区数、map 端预聚合、开 AQE、处理数据倾斜。

### Q4. Hive 的分区和 Spark 的分区是一回事吗？

**要点**：完全两码事。Hive 分区是**存储层**概念——按 date/country 把数据存成不同物理目录，目的是查询时分区裁剪、少读数据。Spark 分区是**计算层**概念——一份数据切成 N 片并行处理，一片一个 task，控制并行度。前者管"数据存哪个文件夹"，后者管"这份数据拆几个 task 算"，两者没有必然对应。

### Q5. 什么是懒执行？为什么会有"一个脚本跑很多遍上游"的坑？

**要点**：Spark 的 transformation（select/join/filter）只记血缘不执行，只有 action（save/count/print）才触发计算。而**每个 action 都从头沿 lineage 重算上游**。所以一个脚本里 13 个 print 共享同一个含大 JOIN 的上游 view，这个 JOIN 会被算 13 遍，shuffle 量放大 13 倍，可能把 S3 打限流、job abort。**解法**：把复用的 view 物化到临时表打断 lineage，或多个 action 合并成一个 UNION ALL。

### Q6. 数据倾斜怎么发现、怎么解决？

**要点**：**发现**——Spark UI 里某个 task 的 shuffle read/耗时远超其他，或 stage 卡在 99% 半天不动。**成因**——shuffle 时某个热点 key（NULL、爆款、大卖家）的数据全挤进一个 task，木桶效应拖垮全局。**解决**——热点 key 加盐打散再聚合合并、NULL/热点单独处理、map 端预聚合、开启 AQE 自动切分倾斜分区。

### Q7. 什么是幂等？为什么数据管道特别强调它？

**要点**：一个操作跑一次和跑多次结果一样。数据任务经常失败重试、人工重跑、补数，不幂等重跑就数据翻倍/错乱。实现靠**按分区覆盖写（INSERT OVERWRITE）** 而非追加、按主键 upsert、逻辑确定性（少用 now()/随机）。**升华**：幂等是可重跑的前提，可重跑是 backfill 的前提，这是管道可靠性的地基。

### Q8. 现代数据栈为什么从 ETL 转向 ELT？

**要点**：因为两个前提变了——存储变便宜了（S3），数仓算力变强了（Spark/Trino/StarRocks MPP）。所以不必在入库前就用单独服务器转换清洗（ETL），而是**先把原始数据原样加载进湖/仓（ELT），再用数仓自身算力转换**。好处：保留原始层可追溯可重算、需求变了直接重跑 transform、更灵活。

### Q9. 存算分离解决了什么问题？代价是什么？

**要点**：传统存算一体（HDFS+本地计算）里存储和计算绑死，但两者增长节奏不同——数据一直涨、计算只在高峰忙，绑一起就得都按峰值买，且扩容要搬数据。存算分离把存储（S3）和计算（Spark 按需拉起）拆开，各自弹性、共享一份数据、计算用完即走。**代价**：计算要走网络读远端存储，比本地盘慢，还带来 shuffle 写 S3 限流、本地盘小易 spill 失败等新问题。

### Q10. 数据湖、数据仓库、湖仓一体的区别？

**要点**：数据仓库结构化、schema-on-write、可靠好查但贵且死板；数据湖 S3 上啥都能装、schema-on-read、便宜灵活但容易变"数据沼泽"（无事务、无治理、质量差）。湖仓一体是在数据湖的开放存储之上加一层表格式（Iceberg/Delta/Hudi），补上 ACID 事务、schema 演进、时间旅行、行级更新——既保留湖的低成本灵活，又获得数仓的可靠性。

### Q11.（附加）Broadcast Join 和 Shuffle Join 怎么选？

**要点**：两张都是大表 → 只能 Shuffle(Sort-Merge) Join，两边都按 key shuffle，贵。一张表足够小（几十 MB）→ Broadcast Join，把小表整个复制到每个节点，大表不用 shuffle，本地直接匹配，快得多。代价是小表占各节点内存，所以有阈值（`autoBroadcastJoinThreshold`），太大反而 OOM。本质是"用空间换 shuffle"。

### Q12.（附加）Spill 和数据倾斜有什么关系？

**要点**：常常连锁出现。倾斜 task 分到的数据量巨大 → 执行内存装不下 → 疯狂 spill 到本地磁盘 → 更慢，甚至在本地盘小的节点上把盘写爆导致任务失败。所以排查慢 job 时看到大量 spill，往往背后是倾斜。优化优先级是**先消 spill / 治倾斜**（调内存、减少单分区数据量、打散热点），而不是无脑加 CPU——因为瓶颈是 IO 不是算力。
