# 数仓建模：维度建模与数仓分层

> 面向已经维护 ETL 多年、听过"dim 维表"但缺体系的工程师。目标是把散落的经验串成一套可以在面试里讲清楚的知识框架，并结合本项目（`analytic-framework-workflows`）里已经写进 `CLAUDE.md` 的真实工程规则来印证"为什么要这么建模"。

---

## 0. 一句话地图

数据从下往上层层加工：**原始数据（ODS）→ 清洗成明细（DWD）→ 按维度汇总（DWS）→ 面向应用出结果（ADS）**，旁边挂一个共享的 **DIM 维度层**。每一层内部再用**维度建模**（事实表 + 维度表 + 明确的粒度）来组织。全篇讲的就是这两件事：**横向分层** 和 **每层内的维度建模**。

---

## 1. 为什么要数据建模

### 概念
数据建模 = 在把数据落成表之前，先想清楚"这张表代表什么、一行是什么、字段属于谁"，用一套统一的结构约定去组织数据，而不是来一个需求就随手拼一张表。

### 不建模的痛（你多年 ETL 大概率都踩过）
- **口径混乱**：A 报表算"GMV"含退款，B 报表不含退款，老板看到两个数字对不上，撕逼半天发现是两个人各写各的 SQL。
- **重复计算**：十个看板各自从原始日志现算"当日下单用户数"，同一段重逻辑跑十遍，集群被拖垮，还算出十个略微不同的值。
- **难维护**：某个字段口径要改，结果它散落在 30 个 SQL 里，改漏一个就静默出错。改表结构没人知道下游谁在用，一改就炸。
- **无法复用**：新需求来了只能从最原始的数据从头拼，没有可复用的中间成果，人效极低。

### 建模解决什么
- **统一口径**：一个指标只在一个地方定义一次，全公司引用同一份，"GMV"就是那一列，不再各算各的。
- **复用**：把清洗、关联、汇总的中间成果沉淀成公共表，下游直接用，算一次给所有人用。
- **解耦 + 可维护**：分层 + 单一职责，改一层不影响另一层；表结构演进有迹可循。
- **可追溯**：字段从哪来、怎么算的，顺着分层血缘能查到源头。

> **本项目印证**：`CLAUDE.md` 里的 `ddl-mirror` 规则明确要求"任何对生产表 schema 的改动 MUST 在 `scripts/ddl/` 下落地对应 `.sql` 文件"，理由就是"防止表结构演进口口相传，保证运维/灾备/新人可追溯 schema 时间线"。这正是"建模 = 让结构可追溯"在真实工程里的落地：光改 mlsql 不补 DDL，就是典型的"不建模"退化。

## 2. 事实表（Fact）vs 维度表（Dim）

这是维度建模的两个基本粒子，也是面试必问。

### 概念
- **事实表（Fact）= 记录"发生了什么"**。一行 = 一个业务事件；数据量大、持续增长；主要装两类列：**度量值（measure，数值）** 和 **指向维表的外键（foreign key）**。
- **维度表（Dim）= 记录"是什么"**。描述性的、相对静态的实体：商品、用户、店铺、时间、地区；数据量小；主要装文字/属性字段，用来做过滤、分组、下钻。

一个通俗类比：事实表是"流水账的每一笔"，维表是"这笔账里出现的人和物的档案"。

### 电商例子
一张 **订单明细事实表 `dwd_order_item`**：

| order_id | user_key | product_key | store_key | date_key | 下单数量 | 成交金额 | 折扣金额 |
|---|---|---|---|---|---|---|---|
| 事件标识 | 外键→用户维 | 外键→商品维 | 外键→店铺维 | 外键→时间维 | measure | measure | measure |

配套的维表：
- **商品维 `dim_product`**：product_key、商品名、类目、品牌、上架日期……（"这个商品是什么"）
- **用户维 `dim_user`**：user_key、性别、注册渠道、会员等级、常住城市……
- **时间维 `dim_date`**：date_key、年、月、周、是否节假日、是否大促……
- **地区维 `dim_region`**：省、市、大区……

分析"华东地区 3C 类目大促期间的成交额"，就是拿事实表的 measure，按几张维表的属性去过滤和分组。

### 为什么要拆成两类
把"数值事件"和"描述属性"分开存，事件表只存瘦瘦的外键+数字（省空间、写得快），描述属性集中在维表里维护一次（改品牌名只改一行，事实表几亿行不用动）。这就是维度建模的地基。

> **本项目印证**：项目里大量 `dim_*` 表（如 `load_dim_live_product_table_from_pq_v2.mlsql`）和以 relation/attribution 为事件的宽事实表，就是这套 fact/dim 分工的实例。`CLAUDE.md` 反复强调"共享 dim 表职责单一"，正是把维表当"档案"来守护。

## 3. 粒度（Granularity）——描述任何一张表之前的第一件事

### 概念
**粒度 = 事实表里"一行代表什么"**。是一笔订单？一个订单行（一笔订单里的一个商品）？还是"一天一个店铺的汇总"？这必须在建表前第一句话就定死。

### 为什么描述一张表必须先讲粒度
粒度不明确，后面所有讨论都是错的：
- **决定能不能 join / 会不会翻倍**：你以为一行是"一个订单"，实际是"一个订单行"，一 join 金额就重复累加、算出天文数字。
- **决定度量怎么聚合**：粒度是"一天一店"，那"当日 GMV"直接就在行里；粒度是"订单行"，就得 SUM 上来。
- **决定唯一键**：粒度就是主键的定义。"一天一个店铺"→ 主键 = (date, store)。
- **粒度越细越灵活但越大**：明细粒度能向上汇总成任何口径（DWD 存最细粒度就是这个道理）；预汇总粒度查得快但丢了下钻能力。

一条实用纪律：**先能用一句话说清"这张表一行 = ____"，再谈字段。** 说不清粒度就先别写 SQL。

### 电商例子
- `dwd_order_item`：粒度 = **一个订单行**（一笔订单买了 3 种商品 = 3 行）。
- `dws_store_1d`：粒度 = **一天一个店铺**（每店每天一行汇总）。
- `dws_user_trade_1d`：粒度 = **一天一个用户**。

> **本项目印证**：`CLAUDE.md` 的 `evidence-before-claim` 规则把"描述某表的行粒度/唯一性前，grep 该表的产出节点看 GROUP BY / DISTINCT / SORT BY+FIRST 去重逻辑"列为硬性纪律，还专门记了踩坑："把 `tiktok_shop_snapshot_popup_info_v1` 当多行风险但实际上游已 1:1"——本质就是**没先确认粒度就下结论**。粒度不是学院派概念，是这个项目里用 grep 逼着你先搞清的东西。

## 4. 星型模型 vs 雪花模型

### 概念
- **星型模型（Star Schema）**：中间一张事实表，周围一圈维表，事实表直接连每张维表。维表**不再往下拆**，允许冗余（比如 `dim_product` 里直接把"类目名、品牌名、一级类目名"都平铺进去）。画出来像颗星。
- **雪花模型（Snowflake Schema）**：把维表按范式**规范化拆分**。比如商品维再拆出"类目维"，类目维再拆"一级类目维"，一层层引用。画出来像雪花。

### 对比
| | 星型 | 雪花 |
|---|---|---|
| 维表 | 冗余、扁平、不再拆 | 规范化、层层拆分 |
| 存储 | 略费（有冗余） | 省（无冗余） |
| JOIN 数量 | 少（事实表直连维表） | 多（要一层层 join 回去） |
| 查询 | 快、SQL 简单 | 慢、SQL 复杂 |
| 维护更新 | 改属性要更新冗余 | 改一处即可 |

### 为什么大数据里星型更常用
- **存储便宜、算力贵**：省那点空间没意义，多一次 shuffle join 的代价才是真痛。星型用冗余换 JOIN 减少，正合大数据的成本结构。
- **列存 + 压缩**：Parquet/ORC 对重复值压缩得极好，冗余维属性的存储代价被摊薄。
- **SQL 简单**：分析师少写几层 join，出错概率低、可读性高。

一句话：**雪花省的是磁盘，星型省的是 JOIN；大数据时代 JOIN 更贵，所以星型胜出。**

## 5. 维度建模四步法（Kimball）

Kimball 的经典四步，是"从需求到建表"的标准动作，面试能背下来 + 举个例子就够加分。

1. **选择业务过程（Business Process）**：锁定要分析哪个业务动作。电商如"下单"、"支付"、"退款"、"加购"。一个业务过程对应一张（或一组）事实表。
2. **声明粒度（Declare the Grain）**：这张事实表一行代表什么。见第 3 节——**这一步定错，后面全错**。例：粒度 = "一个支付订单行"。
3. **确定维度（Identify Dimensions）**：这个粒度下，我们想从哪些角度分析？→ 用户、商品、店铺、时间、地区、支付方式……每个角度一张维表。
4. **确定事实（Identify Facts）**：这个粒度下有哪些可度量的数值？→ 支付金额、优惠金额、支付件数……即度量列。

顺序不能乱：**先业务过程 → 再粒度 → 再维度 → 再事实**。很多翻车都是跳过第 2 步直接堆字段。

> **本项目印证**：项目 `add-mlsql-node` skill / `openspec` 流程强制"新增节点/新建表先落 spec + DDL + 依赖"，本质就是逼你走完"先想清楚业务过程和粒度、再动手写 SQL"这套四步法，而不是拍脑袋加表。

## 6. 度量（Measure）与可加性

度量的**可加性（additivity）**决定了它能不能被直接 SUM，这是个容易被忽略但面试偶尔考的点。

### 三类度量
- **可加（Fully Additive）**：沿**所有**维度都能相加。典型：**金额、数量**。成交金额可以按用户加、按商品加、按天加、按地区加，怎么加都对。
- **半可加（Semi-Additive）**：沿**部分**维度能加，沿时间维不能加。典型：**余额、库存快照**。10 个仓库的库存可以横向相加（= 总库存），但"1 号库存 + 2 号库存 + 3 号库存"把三天的库存加起来就毫无意义。半可加度量对时间通常要用"取最新"或"取平均"而非求和。
- **不可加（Non-Additive）**：**任何维度都不能直接相加**。典型：**比率、百分比、平均值**。三个店铺的转化率不能相加，也不能简单平均——必须回到"分子之和 / 分母之和"重新算。

### 为什么重要（也是实战最大坑）
**比率类度量绝不能在下游被 SUM 或 AVG。** 正确做法是：事实/汇总表里存**可加的分子和分母**（如"成交订单数"和"访问数"），把"转化率"留到最上层展示时再 `SUM(分子)/SUM(分母)` 算。存了比率再往上加 = 错误结果。

### 电商例子
- 可加：`成交金额`、`下单件数` → DWS 层随便 SUM。
- 半可加：`账户余额`、`当日库存` → 跨天不能 SUM，要取期末或均值。
- 不可加：`转化率 = 支付数/访问数`、`客单价` → 存分子分母，别存比率。

> **本项目印证**：`CLAUDE.md` 把"把 `attribution_quality = (sum_attributed)/real_total` 当成 video 覆盖率"列为踩过的坑——一个**比率型字段**被误当成可直接理解/聚合的量。这就是不可加度量的语义陷阱：ratio 必须回到分子分母看，不能望文生义、更不能顺手加。

## 7. 数仓分层：ODS / DWD / DWS / ADS（+ DIM）

### 概念：从下往上层层加工

```
        ADS   应用/结果层   ← 直接给报表、接口、看板的最终结果
         ↑
        DWS   轻度汇总层     ← 按维度做主题汇总（一天一店、一天一用户）
         ↑
        DWD   明细清洗层     ← 清洗后的最细粒度事实明细（一行一事件）
         ↑
        ODS   原始贴源层     ← 原样同步业务库/日志，几乎不加工
        
        DIM   维度层        ← 横向共享的维表（商品/用户/时间/地区），供各层 join
```

### 每层职责
- **ODS（Operational Data Store，贴源层）**：把业务库、埋点日志**原样**同步进来，保持和源系统一致，几乎不做转换。作用是"落地 + 隔离源系统"，下游不用直连生产库。例：`ods_order`、`ods_user_log`。
- **DWD（Data Warehouse Detail，明细层）**：对 ODS 做**清洗、去重、格式统一、脱敏、维度退化**，产出**最细粒度的事实明细**。这是维度建模真正开始的地方，星型模型的事实表就住这里。例：`dwd_order_item`（一行一订单行，脏数据已洗）。
- **DWS（Data Warehouse Summary，汇总层）**：以 DWD 为基础，**按主题、按维度做轻度汇总**，沉淀公共指标。例：`dws_store_1d`（一天一店 GMV/订单数）、`dws_user_trade_1d`。下游多个报表复用这一层，避免重复算。
- **ADS（Application Data Store，应用层）**：面向**具体应用/报表/接口**的最终结果，往往是 DWS 再拼装、过滤、排序后的成品。例：`ads_store_dashboard`、`ads_sales_top100`。
- **DIM（维度层）**：横向的共享维表，不属于纵向加工链，被 DWD/DWS 各层 join 使用。例：`dim_product`、`dim_date`。

### 为什么要分层
- **复用**：DWS 的公共汇总算一次，几十个 ADS 报表共用，不重复计算。
- **解耦**：源系统变了只影响 ODS；口径调整集中在 DWD/DWS；上层报表相对稳定。改一层不牵连全局。
- **口径统一**：指标在 DWD/DWS 定义一次，全公司引用同一份，从根上消灭"两个 GMV 对不上"。
- **可追溯**：出了问题顺着 ADS→DWS→DWD→ODS 一层层往下查血缘，定位快。
- **空间换清晰**：多存几层中间表，换来的是可维护性和协作效率，值。

> **本项目印证**：项目目录本身就是分层思想的体现——`step_1_pg_entity_dim_2_hive`（贴源+维度落地）→ `step_4_compute_features`（明细/特征计算）→ `step_5_generate_es_index`（应用层出 ES 索引），数据从下往上层层加工，最后 ADS 等价物是给线上查询用的 ES/StarRocks 索引。

## 8. 宽表（Wide Table）——威力大，滥用更狠

### 概念
**宽表 = 把多张相关表提前 join 打平成一张字段很多的大表**，用**空间冗余**换**查询时不用 join**。常见于 DWS/ADS 层，尤其是给 OLAP/看板/线上接口直接读的场景。

### 什么时候该建
- 查询高频、且几乎总是要 join 那几张表 → 预先打平，线上零 join、响应快。
- 下游是列存 OLAP（ClickHouse/StarRocks/Doris）或 ES 索引，本就适合"一行读全"的大宽表。
- 语义**同域**：这些字段本来就服务同一个分析主题（如"店铺当日经营大宽表"里的各项经营指标）。

### 什么时候是滥用（面试和实战都爱考的判断力）
**核心红线：不要为了"少 join 一次"就把跨语义字段塞进单一职责的维表。** 这会造成**语义耦合**，是维护灾难：
- 两个本无关的语义被硬绑在一张表，改 A 逻辑时容易误伤 B 字段。
- 表的职责变得模糊，没人说得清"这张表到底是什么"，回到了第 1 节"不建模"的痛。
- 收益极不对称：**省下的 join 次数**远小于**引入的语义耦合的长期维护成本**。

正确姿势：真要跨语义合并，应该**新建一张语义明确的 wide 表**（并且明说"它不再是 dim，而是 wide"），而**不是污染原有的单一职责 dim 表**。

> **本项目印证（重点案例）**：`CLAUDE.md` 有一条专门的规则 `no-abstraction-impulse`，几乎就是为这一节写的——
>
> > **FORBIDDEN 抽象冲动 — 不要为了减少 join / 减少代码而把跨语义字段塞同一张表。**
> > - 共享 dim 表（如 ratio dim / config dim）职责单一，**不要**为了"少 join 一次"加跨语义字段（如 seller profile / identity / 业务标签）
> > - 收益评估："减少的 join 次数" vs "引入的语义耦合"，通常**耦合代价远大于性能收益**
> > - 真要跨语义合表，应该是新建一张明确语义的 wide 表（并明确"它不再是 dim 而是 wide"），不是污染原 dim
>
> 它记录的真实踩坑是：曾想把 `shop_creator_user_id`（**卖家身份 / seller identity**）塞进 `tiktok_seller_daily_channel_ratio_in_30d_v1`（**渠道比率维表 / channel ratio dim**），把两个无关语义硬绑。后果是"后续维护语义混乱，改 ratio 算法时容易误改 identity 字段"。
>
> 应用纪律也很具体：**"加字段到表 X" / "把 Y 合并进 X 减少 join" 这类提案出现前，先自问『这字段属于表 X 的核心职责吗』；跨域则否决，建议另建表或新建明确语义的 wide 表。**
>
> 这就是"宽表威力大、滥用更狠"在真实工程里被写进规则去防的原因：**"少 join 一次"是最常见、也最有迷惑性的错误抽象动机。**

## 9. 缓慢变化维（SCD, Slowly Changing Dimension）

### 概念
维度的属性**会随时间变化**：用户地址搬了、商品换了类目、店铺改了名。**缓慢变化维**就是处理"维表属性变更时，历史怎么办"的一套策略。

### 两种最常考的 Type
- **SCD Type 1（覆盖）**：直接用新值覆盖旧值，**不留历史**。简单、省空间，但丢失了"变化前是什么"。适合：不关心历史、只要最新值的属性（如修正一个拼错的名字）。
- **SCD Type 2（加新行留历史）**：属性变了就**插入一条新行**，给每行加"生效时间 / 失效时间 / 是否当前"标记，**完整保留历史轨迹**。适合：需要"按当时状态"回溯分析的场景（如用户当时的会员等级）。代价是维表变大、查询要按时间点选对应版本。

（还有 Type 3 用额外列存上一版值等，面试点到 Type 1/2 即可。）

### 电商例子
用户从"北京"搬到"上海"：
- Type 1：`dim_user` 直接把城市改成"上海"，之前所有订单分析都变成"上海用户"了。
- Type 2：`dim_user` 里这个用户变成两行——北京（2020-2023 有效）、上海（2023-至今），历史订单 join 到当时有效的那行，"当年他是北京用户"这个事实被保住。

## 10. 拉链表（Zipper Table）

### 概念
**拉链表** 是 SCD Type 2 在中国数仓里的经典落地形态，面试极高频。它用 **`start_date` / `end_date` 两个字段记录每条维度状态的"有效区间"**，把一个实体的历史变化"拉成一条链"存在一张表里，既保留全部历史、又不像每天全量快照那样爆炸式占空间。

### 长什么样
用户会员等级变化：

| user_id | 会员等级 | start_date | end_date |
|---|---|---|---|
| 1001 | 普通 | 2023-01-01 | 2023-06-30 |
| 1001 | 黄金 | 2023-07-01 | 2023-12-31 |
| 1001 | 铂金 | 2024-01-01 | 9999-12-31 |

- `end_date = 9999-12-31`（或 NULL）表示"当前有效"。
- 查"某历史日期的状态"：`WHERE start_date <= '2023-08-01' AND end_date >= '2023-08-01'`，秒定位当时是"黄金"。

### 为什么用它
- **省空间**：相比"每天存一份全量快照"，拉链表只在**变化时**才加行，没变就不动。
- **留全历史**：任意历史时点的状态都能还原。
- 更新逻辑：每天把当天有变化的记录，旧行 `end_date` 封上"昨天"，再插一条新行开区间——这就是"拉链"的动作。

## 11. 面试高频问题 + 答题要点

**1) 事实表和维度表的区别？**
- 事实表记"发生了什么"，一行一事件，量大且增长，装度量值 + 维表外键；维表记"是什么"，描述性、量小、相对静态，装属性字段。事实表是流水，维表是档案。分开存是为了事实表瘦、维表属性集中维护。

**2) 星型模型和雪花模型的区别？为什么大数据常用星型？**
- 星型：维表扁平冗余、不再拆，JOIN 少、查询快、略费空间；雪花：维表按范式拆分，省空间但 JOIN 多、查询慢。大数据里存储便宜、JOIN（shuffle）贵，且列存压缩摊薄冗余成本，所以**用冗余换 JOIN 减少**的星型胜出。

**3) 数仓为什么要分层？**
- 复用（公共汇总算一次给所有下游用）、解耦（源系统变只影响 ODS，改一层不牵连全局）、口径统一（指标定义一次全公司引用）、可追溯（顺血缘查问题）。代价是多存中间层，换来可维护性，值得。

**4) 什么是粒度？为什么重要？**
- 粒度 = 事实表一行代表什么。它决定唯一键、决定度量怎么聚合、决定 join 会不会翻倍。描述任何表都要先一句话说清"一行 = 什么"，说不清就别写 SQL。粒度定错后面全错。

**5) ODS/DWD/DWS/ADS 各是什么？**
- ODS 原样贴源、隔离源系统；DWD 清洗去重出最细粒度明细（星型事实表所在）；DWS 按维度轻度汇总沉淀公共指标；ADS 面向具体报表/接口的成品。数据从下往上层层加工，旁挂 DIM 共享维度层。

**6) 什么时候该建宽表？什么时候是滥用？**
- 该建：查询高频且总要 join 那几张同域表、下游是列存 OLAP/ES、字段服务同一分析主题 → 预打平换零 join。滥用：为"少 join 一次"把**跨语义字段塞进单一职责的维表**，造成语义耦合、改 A 误伤 B、表职责模糊。要合并应新建语义明确的 wide 表，不污染原 dim。（本项目 `no-abstraction-impulse` 规则正是防这个。）

**7) 缓慢变化维（SCD）怎么处理？**
- 维度属性会变，历史怎么留。Type 1 覆盖不留历史（简单、只要最新值）；Type 2 加新行 + 生效/失效标记留全历史（能按当时状态回溯，表变大）。选哪种看"要不要按历史状态分析"。

**8) 拉链表是什么？解决什么问题？**
- SCD Type 2 的经典落地：用 start_date/end_date 记录每个状态的有效区间，把历史变化"拉成一条链"。相比每天全量快照极省空间，又保留全部历史；查历史时点用区间条件定位。end_date=9999-12-31 表示当前有效。中国数仓高频考点。

**9) 度量的可加性是什么？（进阶加分）**
- 可加（金额/数量，任意维度都能 SUM）、半可加（余额/库存，跨时间不能加）、不可加（比率/均值，任何维度都不能直接加）。关键实战纪律：**比率不能存了再 SUM，要存可加的分子分母，到最上层再 SUM(分子)/SUM(分母)**。

**10) 维度建模四步法？（进阶加分）**
- Kimball：选业务过程 → 声明粒度 → 确定维度 → 确定事实。顺序不能乱，粒度这步定错全盘皆错。

## 13. 结合本项目的三条工程箴言（面试可当"实战经验"讲）

1. **单一职责维表不可污染**（`no-abstraction-impulse`）：真实项目里差点把卖家身份字段塞进渠道比率维表，规则直接 FORBIDDEN。"少 join 一次"是最有迷惑性的错误抽象动机——记住它，面试聊"宽表滥用"时这就是你的实战案例。
2. **描述表先确认粒度、字段先 grep 验证**（`evidence-before-claim`）：项目要求"描述表粒度前先 grep GROUP BY/去重逻辑"，把"凭名字猜语义"列为踩坑之首。粒度不是理论，是逼你先搞清的第一件事。
3. **schema 演进必须留痕**（`ddl-mirror`）：改表结构 MUST 同步落 DDL 脚本，"防止表结构口口相传，保证可追溯"——这就是"建模让结构可追溯"最朴素的落地。
