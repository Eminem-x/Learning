## 0. 一页纸速查

| 必答项 | 一句话 |
|---|---|
| **「你怎么保证不资损？」** | **事前**（幂等 + 状态机 + 限额 + 防超额退）→ **事中**（实时核对 + 渠道熔断）→ **事后**（三层对账 + 差错处理 + 资损应急）。**三层都要说，只说幂等是不及格的** |
| 幂等落在哪 | **数据库唯一索引**，键 = `(渠道, 渠道流水号)` 和 `(商户, 商户订单号)`。查询判断 = check-then-act，有 TOCTOU 窗口，**不是幂等** |
| 回调可信吗 | **永远不可信**。四层：验签 → 时间戳+nonce 防重放 → 幂等表唯一索引 → **金额和状态以主动查询渠道为准** |
| TCC 三大坑 | **空回滚、防悬挂、幂等**（见 §3.2，这是 TCC 必考点） |
| 为什么用本地消息表而不是事务消息 | **Kafka 没有 RocketMQ 的半消息 + 事务回查机制**，所以我用本地消息表；如果用 RocketMQ 我会选事务消息 |
| 对账三层 | ① 渠道对账（外部）② 系统间对账（支付单↔账务流水↔订单）③ **账实核对（余额表 = 流水累加）** |
| 差错四分类 | 渠道有我方无=**漏单→补单**；我方有渠道无=**挂单→冲正**；金额不符=**以渠道为准，挂差异账**；状态不符=**主动查渠道** |
| 金额怎么存 | `(amount_minor int64, currency char(3))`，**指数从 ISO 4217 查，不要硬编码 ×100**（JPY/KRW 指数 0，KWD/BHD 指数 3） |
| 收银台 vs 支付网关 | 收银台在**前半段**（方式展示/路由/营销/3DS 编排，KPI 是**成功率与转化漏斗**）；支付网关在**后半段**（渠道抽象/回调/退款）。**我做的是后半段，要主动划清边界** |
| 换渠道重试的坑 | **必须先关闭原渠道的订单（close order），否则用户可能两边都付** |
| 热点账户 | 平台收款账户是所有订单的公共写入点 → **账户分桶**（拆 N 个子账户轮询写，读时 SUM 汇总） |
| 三币种分离 | **定价币种**（用户看到的）/ **结算币种**（渠道打款的）/ **记账币种**（财务本位币），汇率在下单时锁定并存档 |

## 2. 【P0】资金安全防控九件套（这个岗的核心考点）

> JD 原文：*「具备良好的**资金安全保障意识**，对分布式系统的**资金安全防控有实践经验**，对**保障数据一致性有落地经验**」*——这是整份 JD 里最重的一句。

### 2.1 全景：事前 / 事中 / 事后

```
【事前 · 不让错误发生】
  ① 幂等（唯一索引）        ② 状态机单向流转
  ③ 限额与风控              ④ 防超额退款

【事中 · 错了立刻发现】
  ⑤ 实时核对（余额变动 = 流水金额）
  ⑥ 渠道熔断与降级

【事后 · 错了能查能补】
  ⑦ 三层对账 + 差错四分类
  ⑧ 资损分级与应急预案
  ⑨ 全链路可追溯（流水号 + 请求响应存档）
```

**面试口径**：被问「怎么保证不资损」时，**先给这个三层框架，再挑两三个展开**。只答"我做了幂等"是不及格的——因为幂等只解决重复，解决不了漏、错、乱序。

### 2.2 ① 幂等：落在物理约束上

```go
// ❌ check-then-act：两条相同回调并发进来，都查到"未处理"
if exists, _ := dao.Exists(ctx, tradeNo); exists { return nil }
dao.Insert(ctx, rec)

// ✅ 让唯一索引裁决
err := dao.Insert(ctx, rec)
if errors.Is(err, gorm.ErrDuplicatedKey) {   // PG: 23505 unique_violation
    return nil                                // 已处理，幂等返回
}
```

**三层幂等键，各管一段**：

| 层 | 键 | 防什么 |
|---|---|---|
| 请求级 | `request_id`（客户端生成） | 用户/前端重复提交 |
| 业务级 | `UNIQUE(merchant_id, out_trade_no)` | 同一笔业务订单重复下单 |
| 渠道级 | `UNIQUE(channel, channel_trade_no)` | **渠道重复回调、报文重放** |

> **讲的时候先讲物理约束，再讲应用逻辑**——上一场我把顺序讲反了（先说"查询判断"），面试官第一反应是"这人不懂 TOCTOU"，把加分项讲成了减分项。

### 2.3 ② 状态机：只能单向流转

```
CREATED → PAYING → PAID → (REFUNDING → REFUNDED)
                 ↘ FAILED / CLOSED
```

- **禁止回退**：已 PAID 的单绝不能被一条迟到的 FAILED 回调打回——**乱序回调是真实存在的**
- 实现靠 **CAS + 影响行数判断**：

```sql
UPDATE pay_order SET status='PAID', paid_at=now()
 WHERE id=? AND status IN ('CREATED','PAYING');   -- 影响行数=0 → 说明已是终态，直接幂等返回
```

### 2.4 ④ 防超额退款（高频追问）

**并发退款是资损重灾区**：两个退款请求同时进来，各自读到"已退 0 元"，都通过校验。

```sql
-- 方案一：靠数据库约束兜底（最稳）
ALTER TABLE pay_order ADD CONSTRAINT ck_refund CHECK (refunded_amount <= paid_amount);

-- 方案二：条件更新，让 DB 做原子校验
UPDATE pay_order
   SET refunded_amount = refunded_amount + :amt
 WHERE id = :id AND refunded_amount + :amt <= paid_amount;   -- 影响行数=0 即超额，拒绝
```
**不要用「先 SELECT 校验再 UPDATE」**——同一个 TOCTOU 问题。

### 2.5 ⑤ 实时核对：不等日终

关键动作完成后立即做一次轻量校验，发现即告警 + 止血：

```
支付成功记账后 → 校验：账户余额变动量 == 本次流水金额？
                    → 不等 → 立刻告警 + 冻结该账户后续出金
```
**这是「事中」这一层的全部意义**：日终对账发现问题时，钱可能已经被提走了。

### 2.6 ⑦ 三层对账（必答，上一场丢分处）

| 层 | 比什么 | 发现什么 |
|---|---|---|
| **① 渠道对账** | 渠道对账单 ↔ 本地支付流水，按 `(渠道, 渠道流水号)` 全量比对 | 漏单、挂单、金额不符 |
| **② 系统间对账** | 支付单 ↔ 账务流水 ↔ 业务订单 | 支付成功了但没记账 / 没发货 |
| **③ 账实核对** | **账户余额表 == 该账户所有流水的累加** | 余额被改坏、少记流水 |

**差错四分类与处理**：

```
① 渠道有、我方无（漏单）：钱真到了但系统没记 → 补单 + 告警
② 我方有、渠道无（挂单）：系统记了但渠道没有 → 主动查渠道确认 → 冲正
③ 金额不一致            ：【以渠道为准】，差额挂"待处理差异账"，人工介入
④ 状态不一致            ：调渠道查询接口二次确认，以查询结果为准
```
术语：实收 > 应收 = **长款**；实收 < 应收 = **短款**。
**核心原则：以渠道为准，差异必须落表可追溯，绝不静默修正。**

> ⚠️ 上一场我的对账只有「数据量 + 抽样」。**抽样发现不了系统性偏差**，在支付岗这个答案不能用。

### 2.7 ⑧ 资损分级与应急

```
发现 → 【止血】优先于定位：关渠道开关 / 降级 / 冻结出金 / 停止批处理
     → 定位与影响面评估（涉及多少笔、多少钱、哪些用户）
     → 补偿（补单 / 冲正 / 退款）
     → 复盘与防重犯（加校验、加监控、加对账维度）
```
**「止血优先于定位」这句话说出来，面试官会知道你真处理过线上问题。** 这里可以挂你的 oncall STAR 故事。

## 3. 【P0】数据一致性方案选型（JD 明确要求"有落地经验"）

### 3.1 五种方案对比

| 方案 | 一致性 | 适用 | 代价 |
|---|---|---|---|
| **2PC/XA** | 强一致 | 单一 DB 集群内的跨库 | **同步阻塞**、协调者单点、性能差，互联网支付基本不用 |
| **TCC** | 最终一致（准实时） | **资金核心**：冻结 → 扣减 → 解冻 | **业务侵入极大**，每个服务要写三个接口 |
| **Saga** | 最终一致 | 长流程、可补偿的业务（履约、开通） | **无隔离性**（中间态可见，会脏读），补偿逻辑难写 |
| **本地消息表** | 最终一致 | 通用，最常用 | 需要定时扫表 + 下游幂等；有延迟 |
| **事务消息**（RocketMQ） | 最终一致 | 同上，但由 MQ 托管 | **依赖 MQ 支持半消息 + 事务回查** |

### 3.2 TCC 的三大坑（必考，答出来直接加分）

```
Try(冻结资源) → Confirm(真正扣减) 或 Cancel(释放冻结)
```

| 坑 | 场景 | 解法 |
|---|---|---|
| **空回滚** | Try 因网络超时**根本没执行到**，但全局事务失败了，Cancel 照样发过来 | Cancel 要能识别「没有对应的 Try 记录」→ **直接返回成功，不做任何释放** |
| **防悬挂** | Cancel **先于** Try 到达（Try 是超时重发的），Cancel 走完之后 Try 才到 → 冻结的资源**永远没人释放** | Try 执行前先检查「是否已有该事务的 Cancel 记录」→ 有则**拒绝执行** |
| **幂等** | Confirm/Cancel 都可能被重试 | 每个动作记录事务日志，按 `xid` 幂等 |

> 这三个词（空回滚 / 防悬挂 / 幂等）**是 TCC 面试的标准三连**，能主动说出来说明你不是背概念。

### 3.3 我的实际选型怎么讲（把"我用了什么"讲成"我为什么选它"）

> 「我们用的是**本地消息表**：业务事务里先落一条任务记录，再投递消息；即使 MQ 那一跳完全失败，定时扫描器也会捞回来重投。**可靠性的真相源是 PostgreSQL 的任务表，Kafka 只是快通道。**
>
> **为什么不用事务消息**：因为我们的 MQ 是 Kafka——**Kafka 的"事务"是跨分区原子写，它没有 RocketMQ 那种半消息 + 本地事务回查的机制**，实现不了"本地事务与消息发送的原子性"。所以在 Kafka 生态下，本地消息表是正确选择；如果是 RocketMQ 我会直接用事务消息，省掉扫表。
>
> **为什么没上 TCC**：我们的资金动作（充值/扣费）在**同一个库的同一个本地事务**里就能完成余额和流水的原子更新，没有跨服务的资金冻结场景，上 TCC 是过度设计。**真到跨服务扣减（比如账务服务独立出去），我会用 TCC，并处理空回滚和悬挂。**」

**这一段是整个面试里最能体现"技术判断力"的地方**——它同时展示了：知道所有方案、知道各自的前提、知道自己为什么这么选、知道什么时候该换。

## 4. 【P0】收银台 vs 支付网关：必须搞清的认知差

**我做的是网关（后半段），JD 招的是收银台（前半段）。**

```
用户点"去支付"
   ↓
【收银台 Cashier】← JD 招这一层
   · 支付方式展示与排序（本地化：欧洲 SEPA/iDEAL、拉美 PIX/Boleto、印度 UPI、东南亚电子钱包、日本便利店）
   · 支付方式路由（成功率优先 / 成本优先 / 限额路由 / 灰度）
   · 优惠营销与金额试算（满减、分期免息）
   · 风控前置 + 3DS/SCA 验证编排
   · 下单幂等、防重复提单
   ↓
【支付网关】← 我做的这一层
   · 渠道抽象、下单 / 回调 / 退款、验签、幂等落库
   ↓
【渠道】支付宝 / 微信 / Stripe / Airwallex / UseePay
   ↓
【账务与清结算】记账、对账、结算、资金归集
```

**收银台的 KPI 是「支付成功率」和「转化漏斗」，不是"接通渠道"。** 要能聊：

- **漏斗埋点**：收银台曝光 → 选方式 → 提单 → 跳转渠道 → 回调 → 成功，**每一步的流失率**都是优化目标
- **成功率优化**：渠道路由与灰度、失败归因（风控拒绝 / 限额 / 余额不足 / 渠道抖动）、**失败自动切换渠道**
- ⚠️ **换渠道重试的坑（很爱考）**：切渠道前**必须先关闭原渠道的订单（close order / 撤单）**，否则用户可能在两个渠道都完成支付 → **重复付款资损**

**我的讲法（承认 + 划边界 + 说可迁移的部分）**：

> 「我做的是渠道抽象和资金链路这后半段。收银台前半段的支付方式路由、营销组合、3DS 编排我没有直接做过，但我清楚**它的 KPI 是成功率和转化漏斗**，和我做的'接通渠道'是两个目标。我能直接迁移过来的是**下半段的资金安全和一致性**，以及跨境多渠道的踩坑经验。」

## 5. 【P1】系统设计题：「设计一个国际收银台」

> 字节支付面**必有系统设计**。按这个五段式答，30 分钟能讲完。

### 第 1 段：先问清需求与量级（**不要上来就画图**）

```
日单量？峰值 QPS？多少国家/币种/渠道？
成功率目标？资损容忍度（= 0）？
同步返回还是异步回调为主？是否需要支持部分退款/分账？
```

### 第 2 段：核心链路

```
业务下单 → 创建支付单（幂等：merchant + out_trade_no 唯一索引）
        → 收银台渲染（按国家/金额/风控筛选可用支付方式，排序）
        → 用户选择 + 提单 → 路由到渠道 → 调渠道下单
        → 跳转/SDK 唤起 → 用户支付
        → 【异步回调】验签 → 防重放 → 幂等落库 → 主动查渠道确认金额状态
        → 记账（账务服务）→ 本地消息表 → 通知业务方
        → 日终对账兜底
```

### 第 3 段：关键设计点（面试官在等这几个）

| 点 | 做法 |
|---|---|
| **幂等** | 三层幂等键（§2.2） + 状态机 CAS |
| **回调不可信** | 四层防线：验签 → 时间戳/nonce → 唯一索引 → **金额状态以主动查询为准** |
| **一致性** | 支付成功 → 记账 → 通知业务，用**本地消息表**；账务若独立成服务则用 **TCC** |
| **高可用** | 渠道熔断降级、**多渠道互备**、收银台可降级成极简版（只留最高成功率的一个渠道） |
| **兜底** | 三层对账 + 差错四分类；**任何异步链路都必须有对账兜底**，不能只靠重试 |
| **可观测** | 全链路支付流水号贯穿；漏斗埋点；渠道成功率/耗时分渠道分国家看板 |

### 第 4 段：国际化（这是"Global Payment"的重点，也是你的差异化）

见 §7。

### 第 5 段：演进与取舍（**最后一定要讲这一段**）

> 「一期先做单渠道打通 + 幂等 + 对账，因为**没有对账的支付系统不能上线**；二期做多渠道路由和成功率优化；三期做账务独立和分账。
> 取舍上：**我不会一开始就上 TCC 和分库分表**——单量没到之前，一个库里的本地事务是最简单可靠的方案，过早分布式化会让资金一致性问题指数级变难。」

## 6. 【P0】简历会被逐字扣的三句

| 简历原句 | 会被追问 | 准备 |
|---|---|---|
| 「抽象渠道无关的支付/回调/退款接口，接入五个渠道」 | **五个渠道的差异是怎么被抽象掉的？** | 见下面的渠道差异表 |
| 「设计钱包系统，支持充值、对账、转账、提现」 | 对账（已备 §2.6）、**转账的双边一致性**、**提现的出金风控与失败回滚** | 转账：同一事务内写双边流水 + 双边余额，靠 `CHECK(balance >= 0)` 兜底；提现：**先冻结再出金，渠道失败后解冻**，绝不能"先减余额后调渠道且不可回滚" |
| 「累计订单 10w+」 | **10w 在字节量级下很小 → 会转问"扩 1000 倍怎么办"** | 见 §8 |

### 渠道能力差异表（准备这张表，被问到直接画）

| 维度 | 差异 | 抽象策略 |
|---|---|---|
| 交互形态 | 跳转 H5 / SDK 唤起 / 服务端直连（卡） | 统一返回 `PaymentAction{type, url/params}`，由前端按 type 渲染 |
| 回调语义 | 有的只回调一次、有的重复回调、有的**乱序** | 统一转成幂等 + 状态机；**乱序靠状态机禁止回退** |
| 退款 | 是否支持部分退、退款是否异步、退款单号规则 | 统一成异步模型（同步结果也走一次内部"回调"） |
| 关单 | 有的支持主动关单，有的不支持 | **不支持关单的渠道，禁止参与"失败切渠道"策略** ← 这个细节很加分 |
| 对账单 | 格式、时区、拉取方式（API / FTP / OSS）各不相同 | 适配器层统一成内部对账模型 |
| 签名 | RSA2 / HMAC / 平台证书 + AES-GCM 解密 | 每渠道一个 `Verifier` 实现 |
| **不可抽象的** | 分期、3DS 挑战、本地钱包的特有字段 | **诚实地特化**——「我的原则是**共性抽象、差异特化**，强行抽象会让每个渠道都难用」 |

## 7. 【P1】国际支付特有（你的差异化优势，别浪费）

### 7.1 三币种分离（必答）

```
定价币种 presentment  —— 用户在收银台看到的（比如 USD）
结算币种 settlement   —— 渠道实际打款给你的（比如 CNY）
记账币种 accounting   —— 财务本位币
```
**汇率必须在下单时锁定并存档**（存汇率值 + 汇率来源 + 时间戳），否则退款时用新汇率算会产生差额。
**除不尽的差额**：约定舍入方向 + 差额单独记「**汇兑损益**」科目——**绝不能让它凭空消失**。

### 7.2 金额精度（上一场我答错的地方）

| 币种 | ISO 4217 指数 | `×100` 会怎样 |
|---|:--:|---|
| USD / CNY / EUR | 2 | 正确 |
| **JPY / KRW** | **0** | **Stripe 对 JPY 传的就是整数日元，×100 多算 100 倍** |
| **KWD / BHD / TND** | **3** | 少算 10 倍 |

**存 `(amount_minor int64, currency char(3))`，指数从币种表查，不要硬编码。**

### 7.3 合规（能说出名词就够）

- **PCI DSS**：卡号不落地，走 **tokenization**；用渠道托管的收银页/iframe 可以把合规范围降到最低（SAQ-A）
- **3DS2 / SCA**：欧盟 PSD2 强制**强客户认证**（双因素），有低额/低风险豁免。**3DS 会降低转化率**，所以收银台要做"能豁免就豁免"的编排
- **AML / KYC / 制裁名单筛查**：出金和大额必过
- **Chargeback（拒付）**：持卡人向发卡行发起争议 → 商户举证（representment）。**拒付率过高会被卡组织罚款甚至封停**，所以风控要前置

### 7.4 本地支付方式（说得出来 = 做过国际支付）

欧洲 **SEPA / iDEAL(荷兰) / Sofort(德国) / Bancontact(比利时)**；巴西 **PIX / Boleto**；印度 **UPI**；东南亚 **GrabPay / GoPay / DANA / OVO**；日本**便利店支付 Konbini**。

> **核心洞察**：「**国际支付的难点不在技术，在于每个市场的支付习惯完全不同**——收银台必须按国家/地区动态决定展示哪些方式、什么顺序，这直接决定转化率。」

## 8. 【P2】扩到 1000 倍：分库分表与热点账户

### 8.1 分片键怎么选（支付单的经典难题）

支付单有两个高频查询维度：**按支付单号查**（回调、对账）和 **按用户查**（我的订单）。分片键只能选一个。

**解法：基因分片（gene sharding）** —— 生成支付单号时，**把用户 ID 的低几位"基因"嵌进单号里**，这样用单号也能算出分片，两个维度都能直接路由，不需要额外的映射表。

### 8.2 热点账户（这题答出来档次立刻不一样）

**问题**：平台侧收款账户是**所有订单的公共写入点**，高并发下这一行会被行锁串行化，成为绝对瓶颈。

**解法一：账户分桶**

```
把平台账户 A 拆成 A_0 ... A_63 共 64 个子账户
写入时：随机/轮询选一个子账户记账      → 锁竞争降低 64 倍
读余额：SELECT SUM(balance) FROM ... WHERE parent='A'
定期：把子账户余额归集回主账户
```

**解法二：异步记账** —— 交易链路只写流水（append-only，无锁竞争），余额由**下游异步汇总**；代价是余额有延迟，**只适用于不需要实时余额校验的账户**（平台账户可以，用户账户不行）。

**注意事项**：分桶后**跨桶的余额校验要用 SUM**，且要防止某个桶被扣成负数——`CHECK(balance >= 0)` 要放在桶级还是父级，取决于业务是否允许桶间借调。

## 附录：自我思考

### 一、这场和腾讯那场，准备策略完全不同

| | 腾讯 IEG 游戏后台 | 字节 Global Payment |
|---|---|---|
| 我的位置 | **跨界**，要证明能力可迁移 | **主场**，要证明深度够 |
| 门槛 | 「精通 Go」是一票否决 | 「至少一种语言」，**门槛在资金安全** |
| 最该补 | Go 底层 + 游戏概念 | **资金安全九件套 + 收银台认知** |
| 风险 | 答不出 GMP/GC 直接挂 | 对账只会 count+抽样、验签答不出 → **在支付岗是硬伤** |

**共用的部分**（先做，两场都吃）：分布式一致性选型、oncall STAR 故事、Go 基础。

**如果只能拿一个**：**字节这个更该拿**——匹配度高、语言门槛低、有回流优势，且**支付是能长期沉淀的方向**，游戏后台对我是从零开始。

### 二、我最大的认知盲点是「我以为我做的就是收银台」

拆完 JD 才意识到，**我做的统一支付网关是"渠道抽象层"，而收银台是它前面那一层**。这两层的目标函数完全不同：网关追求"接通且不出错"，收银台追求"成功率和转化率"。

这个区别如果面试时才发现，会答得很难看——因为面试官问「你怎么提升支付成功率」时，我会下意识answer成"我怎么保证回调不丢"，**答的是另一个问题**。

**教训**：拿到 JD 第一件事，不是找匹配点，是**找出"我以为我会但其实是另一回事"的地方**。

### 三、上一场丢的分，这次全是必答题

模拟面试里我在支付题拿了全场最高的 6/10，但**丢的三块（验签防重放、渠道对账、多币种精度）恰好是这个岗的核心**。当时那是"可以补的短板"，现在是"必须会的门槛"。

**这说明一件事：短板的严重程度是由岗位定义的，不是由知识本身定义的。** 我在准备的时候，应该先看岗位再排优先级——而不是按"我哪里最不会"排。
