# 过度设计的避免：从「不知道不知道」走出来

> 来源：个人思考 / 与 Claude 的对话整理
> 收录时间：2026-04-25 CST
>
> 背景：在讨论 Knuth「过早优化」之后的延伸——过早优化好理解（业务优先 + 基础性能直觉即可），但「过度设计」更难，因为它常常是一个**「不知道自己不知道」**的问题。

---

## 一、核心悖论

> **过度设计**的反面不是「简单」，而是「**恰到好处**」。
> 但要判断「恰到好处」，前提是你**见过足够多的好与坏**。

新人最容易掉进两个相反的坑：
- 写得太糙，欠下技术债
- 学了几个模式后到处套，过度设计

---

## 二、先把「过度设计」拆开看

| 类型 | 表现 | 常见高发区 |
|---|---|---|
| **过早抽象** | 一个函数只被调用一次，就提炼成接口 + 实现类 | 后端：DAO/Service/Manager 三层套娃 |
| **过早泛化** | 「以后可能要支持多数据源」→ 写一堆策略模式 | 数据：还没接第二个源，就抽象 Connector |
| **过早配置化** | 把本来写死就行的参数全塞进 config / 数据库 | 数据：阈值、字段映射全做成可配置 |
| **过早分层** | 没有复用需求就拆 module / 微服务 | 后端：单体没跑稳就拆服务 |
| **过早可扩展** | 为「未来可能的需求」预留接口、事件、钩子 | 全部 |

## 三、几条可操作的判断准则

### 1. YAGNI（You Aren't Gonna Need It）

> 「**只为现在已经存在的需求写代码**」

每当想写一段「以后可能用到」的代码，先问：
- 这个「以后」有具体的用户/工单/PRD 吗？
- 还是只是「我觉得可能」？

**90% 的「以后」永远不会到来**。即使到来，那时的需求形态也大概率和今天预想的不同——为想象中的需求写的抽象，反而会成为真实需求来临时的障碍。

#### YAGNI 怎么理解

**YAGNI — You Aren't Gonna Need It**

「你不会需要它的」——极限编程（XP）创始人 Ron Jeffries 提出的核心原则。

**一句话理解**

只在真正需要某个功能时才去实现它，不要因为「以后可能用得到」而提前造。

**完整版原话**

> "Always implement things when you actually need them, never when you just foresee that you need them."
> 「只在真正需要时实现，绝不在仅仅预感会需要时实现。」
>
> —— Ron Jeffries

**为什么是 "Aren't"（不是 "Won't"）**

英文原文用 "Aren't gonna need it"（不会需要它的），口气很笃定。

不是「也许不需要」，而是「**统计上你大概率根本用不到**」——这是 XP 实践者多年观察的结论：预测出来的需求，**80% 以上要么根本不来，要么来时变了样**。

所以 YAGNI 不是一句「保守的劝告」，而是一个**基于统计经验的强主张**：与其为想象中的 20% 提前付出 100% 的复杂度，不如等真实需求到来时再针对性地构建。

**YAGNI 反对的 ≠ 思考未来**

YAGNI 反对的是**为想象中的未来写代码**，而不是反对**思考未来**。

正确的姿势是：
- ✅ 设计时**考虑**未来可能的演化方向（保留扩展的可能性）
- ❌ 不要为了未来**预先实现**那些扩展（不要焊死任何路径）

换句话说：**让代码保持「容易改」，而不是「已经改好」**。前者是真正的灵活性，后者只是预测出来的复杂度负债。

### 2. Rule of Three（三次原则）

来自 Martin Fowler 的《重构》：

> 第一次写：直接写
> 第二次遇到类似的：忍住，复制粘贴
> 第三次再遇到：这时候才抽象

**两次相似不足以判断模式**。三次出现，才能看清楚「真正不变的部分」是什么。提前抽象往往把「偶然相似」当成「本质共性」，结果是抽象得很丑、还得反复改。

### 3. 后端 / 数据开发场景下的具体翻译

- **ETL 脚本**：先把流程跑通，常量写死。第二个类似任务出现时，再考虑抽公共函数；第三个再考虑做框架。
- **字段映射**：一开始硬编码在代码里，不要急着做配置表。配置表的成本是「运行时不可见 + 一份文档外置」。
- **调度依赖**：DAG 直接写死依赖关系，不要急着搞「自动发现」。
- **异常处理**：先 fail fast，把错误抛出来。先观察真实失败模式，再决定哪些要重试、哪些要降级。
- **抽象基类**：不要先写 `BaseProcessor`，先写三个具体的 Processor，看它们到底有多少共性。

### 4. 「删一行的成本」高于「加一行的成本」

人们倾向于「多写点保险」，但代码的真正成本不在写，而在：
- 别人读的时候要理解
- 改的时候要小心不要破坏既有抽象
- 测试要覆盖所有分支

**每一行代码都是负债**。当犹豫「要不要加这个抽象」时，默认答案应该是「不加」。

## 四、关于「不知道不知道」——怎么补这个洞

「没见过好设计的人，分不清什么是过度设计、什么是基本功」——这不是靠克制能解决的，而是靠**输入**。

### 1. 读高质量代码

不是泛泛地「多读源码」，而是读领域内的标杆：
- 后端：Spring Framework、Django、FastAPI 的核心模块
- 数据：Airflow、dbt、Spark 的源码（特别是它们的抽象层是怎么演化出来的）
- 中间件：Redis、Kafka 的客户端实现

**重点不是读「最终形态」，而是读 git history**：看一个抽象是怎么从最初的「写死」一步步演化来的。这能治好「一上来就抽象」的病。

### 2. 学经典模式，但要理解**它解决的是什么问题**

读《设计模式》《重构》《Clean Code》《DDIA》时，最重要的不是记住模式名字，而是理解：

> **不用这个模式会怎样？什么场景下问题严重到必须用？**

比如「策略模式」——只有当**确实有 3 个以上**的策略、且策略需要**运行时切换**时才有意义。如果只有两个、且永远不会变，`if/else` 才是正确答案。

### 3. 主动 code review

把自己的代码扔给更资深的人 review，**直接问**：
- 「这里我是不是过度设计了？」
- 「这个抽象有必要吗？」
- 「如果是你，会怎么写？」

很多「不知道不知道」要靠**外部反馈**才能照见。如果暂时没有这样的人：
- 把代码贴给 LLM，让它从「简化」「YAGNI」角度评审
- 看开源项目的 PR review 评论，特别是 maintainer 拒绝某个 PR 时的理由

### 4. 时间维度的反馈

最有效的老师是**自己 6 个月前的代码**。建立一个习惯：

> 每次回头改老代码时，记录下：
> - 当时哪些「为未来准备」的设计真的用上了？
> - 哪些反而成了改动的障碍？

几次循环之后，会培养出对「过度设计」非常准确的直觉——因为**亲眼见过**自己的预测错了多少次。

## 五、一个实用的心法：默认简单，证据驱动复杂化

| 场景 | 默认做法 | 升级触发条件 |
|---|---|---|
| 一段逻辑 | 写在调用处 | 第 3 次复用时抽函数 |
| 一个函数 | 直接实现 | 出现第 2 个不同实现时抽接口 |
| 一个常量 | 硬编码 | 业务方需要在不重启下修改时做配置 |
| 一份数据流 | 单进程脚本 | 数据量/SLA 触及瓶颈时上调度/分布式 |
| 一个服务 | 单体 | 团队规模 / 部署节奏出现冲突时拆分 |

**升级永远比降级容易**。从简单往复杂走，每一步都有真实证据；从复杂往简单走，要面对的是「不敢删」的心理成本和「可能漏掉某个用例」的风险。

---

## 六、一句话总结

> **过早优化的反面是测量；过度设计的反面是克制 + 输入。**
>
> 克制让你不乱加东西，输入让你知道什么时候该加。

## 附录：自我思考

### 1. 「过度设计」其实是一种焦虑

仔细看，过度设计的根源往往不是技术问题，而是**心理问题**：
- 怕被未来的自己骂「当初怎么不考虑扩展性」
- 怕被同事觉得「写得太糙」
- 怕领导问「这个不能改/不能加功能怎么办」

所以会预先把所有「万一」都焊死在代码里。但真实情况是：**焊死了「万一」，反而焊死了「真实情况发生时的灵活性」**。一个简单直白的实现，永远比一个复杂抽象的实现更容易被改造。

### 2. 「不知道不知道」的本质是经验缺失

Dunning-Kruger 效应在工程上的版本：
- 第一阶段：什么都不会，但敢写
- 第二阶段：学了一些模式，到处套（**过度设计高发**）
- 第三阶段：被自己写的抽象坑过几次，开始克制
- 第四阶段：知道什么时候该简单、什么时候该抽象

第二阶段的人最危险——因为他们**有信心**自己写得「优雅」，但缺乏判断「优雅是否必要」的经验。
要走出第二阶段，唯一的路径是**让自己写的代码经历足够多的真实修改**，亲眼看到自己当初的预测错在哪里。

### 3. 数据 / 后端工作的特殊性

数据开发尤其容易过度设计，因为：
- 数据需求变化快（业务方一句话能改字段定义）
- 「可配置化」诱惑大（看起来很美的「配置驱动」）
- 经常有「多数据源 / 多场景」的幻觉

但实际上，**数据开发的复杂度不在抽象，而在数据本身**：脏数据、口径变化、上游 schema 漂移……把精力花在写「优雅的 Pipeline 框架」上，不如花在「把这一条数据流的口径文档写清楚」上。

### 4. 与 Knuth 的呼应

Knuth 的「过早优化」和这里讨论的「过度设计」其实是**同一种工程病的两个症状**：

> **在缺乏真实信号之前，就为想象中的需求付出真实的复杂度成本。**

无论是性能优化还是架构设计，正确的姿势都是：
1. **先做最小可行的正确实现**
2. **在真实使用中收集信号**
3. **基于信号做有针对性的改造**

这是一种把「工程」从手艺变成科学的态度。
