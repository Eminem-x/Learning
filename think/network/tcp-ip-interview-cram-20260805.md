## 0. 30 秒电梯版

> TCP 面试就六条主线：
> 1. **建连**：三次握手——**为了双向确认「我能发、你能收」**，两次无法确认客户端的接收能力，也挡不住历史重复连接。
> 2. **断连**：四次挥手——因为 TCP 是**全双工**，两个方向要各关一次；`TIME_WAIT` 等 **2MSL** 是为了**可靠地关掉对端 + 让旧报文在网络中消散**。
> 3. **可靠**：序号 + 累计确认 + 超时重传（RTO）+ **快速重传（3 个重复 ACK）** + SACK。
> 4. **流控**：滑动窗口，接收方用 `rwnd` 告诉发送方「我还能收多少」——**这是接收方保护自己**。
> 5. **拥塞**：慢启动 → 拥塞避免 → 快重传/快恢复，`cwnd` 是**发送方保护网络**。**实际发送量 = min(cwnd, rwnd)**。
> 6. **它的代价**：有序交付带来**队头阻塞**，重传+拥塞退避带来**延迟不可控**——所以实时场景（游戏/音视频）宁可用 UDP 自己做可靠性。

## 1. 三次握手 ★★★★★

```
Client                          Server
  │  ── SYN, seq=x ──────────────►│   Server: SYN_RCVD（进半连接队列）
  │  ◄── SYN+ACK, seq=y,ack=x+1 ──│   Client: SYN_SENT → ESTABLISHED
  │  ── ACK, ack=y+1 ────────────►│   Server: ESTABLISHED（移入全连接队列）
```

### 为什么是三次，不是两次？（必答）

**两个理由，都要说**：

1. **双向确认收发能力**：一次握手只证明「客户端能发」；两次证明「服务端能收能发」；**第三次才证明「客户端能收」**。TCP 是全双工，两个方向的能力都必须确认。
2. **防止历史重复连接**（RFC 793 的原始动机，更硬核）：客户端一个早已超时的旧 SYN 在网络里绕了一圈才到达服务端，服务端傻等着建连。**有第三次握手，客户端发现这不是自己当前想建的连接，会回 RST 中止**——两次握手做不到。

### 为什么不是四次？

第二步的 `SYN` 和 `ACK` **可以合并成一个包**，所以四次可以压成三次。

### 服务端的两个队列（线上排障必考）

```
SYN 到达  → 【半连接队列 SYN queue】     长度 net.ipv4.tcp_max_syn_backlog
三次握手完成 → 【全连接队列 accept queue】 长度 min(backlog, net.core.somaxconn)
应用 accept() → 从全连接队列取走
```

- **全连接队列满了会怎样**：默认**直接丢弃**这个 ACK（`tcp_abort_on_overflow=0`，客户端会重传，表现为"连上了但很慢"）；设成 1 则回 RST（表现为连接被拒）
- **排查命令**：`ss -lnt` 看 `Send-Q`（全连接队列上限）和 `Recv-Q`（当前排队数），`netstat -s | grep -i listen` 看溢出计数

### SYN Flood 与 syncookies

攻击者只发 SYN 不回 ACK，把**半连接队列**打满 → 正常用户连不上。
**解法 `net.ipv4.tcp_syncookies=1`**：队列满时服务端**不再分配内存**，而是把连接信息编码进 SYN+ACK 的初始序号里，等客户端的 ACK 回来时再还原出连接——**用算力换内存，无状态抗洪**。

### 其他爱问的点

- **ISN 为什么随机**：防止旧连接的报文被误认成新连接的（也防序号预测攻击）
- **第三次握手能带数据吗**：能。**TCP Fast Open（TFO）** 更进一步，第一次握手就能带数据（靠 cookie）

## 2. 四次挥手与 TIME_WAIT ★★★★★

```
Client                              Server
  │ ── FIN ─────────────────────────►│  Client: FIN_WAIT_1
  │ ◄── ACK ─────────────────────────│  Server: CLOSE_WAIT   ← 服务端还能继续发数据
  │                                  │  Client: FIN_WAIT_2
  │ ◄── FIN ─────────────────────────│  Server: LAST_ACK
  │ ── ACK ─────────────────────────►│  Client: TIME_WAIT（等 2MSL）→ CLOSED
```

### 为什么是四次？

因为 TCP 是**全双工**：一方发 FIN 只表示"我没数据要发了"，但**对方可能还有数据没发完**。所以 `ACK` 和对方的 `FIN` 不能像握手那样合并——中间隔着服务端处理剩余数据的时间（这段就是 `CLOSE_WAIT`）。

> 如果服务端确实没数据了，内核也可能把 ACK 和 FIN 合并 → **变成三次挥手**。这个补充能加分。

### TIME_WAIT 为什么等 2MSL？（必答，两个理由）

**MSL = Maximum Segment Lifetime**，报文在网络中的最大存活时间（Linux 实现里 `TIME_WAIT` 固定 **60 秒**）。

1. **保证最后那个 ACK 能到达对端**：如果 ACK 丢了，对端会重发 FIN；主动关闭方必须还活着才能重发 ACK。**一来一回正好 2 个 MSL**。
2. **让本次连接的所有旧报文在网络中彻底消散**：否则同样的四元组被立刻复用时，旧连接的迟到报文会串到新连接里，造成**数据错乱**。

### 线上排障（高频实战题）

| 现象 | 说明 | 处理 |
|---|---|---|
| **大量 `TIME_WAIT`** | 出现在**主动关闭方**。通常是短连接太多（比如每次请求新建连接） | 治本：**改长连接 / 连接池**；治标：`net.ipv4.tcp_tw_reuse=1`（**仅对主动发起连接的客户端有效**）、调大端口范围 `ip_local_port_range` |
| **大量 `CLOSE_WAIT`** | 出现在**被动关闭方**，说明**你的程序收到 FIN 却没调用 `close()`** | **这是代码 bug**，不是内核参数问题——查连接没关、goroutine 泄漏、异常路径没 `defer conn.Close()` |
| 大量 `FIN_WAIT_2` | 己方已关，对端迟迟不发 FIN | `net.ipv4.tcp_fin_timeout` 兜底 |

> ⚠️ `tcp_tw_recycle` **在 Linux 4.12 之后已被移除**，且在 NAT 环境下会导致连接被莫名丢弃——**面试里说"我会开 tw_recycle"是减分项**。

## 3. 可靠传输 ★★★★

| 机制 | 做法 |
|---|---|
| **序号 + 累计确认** | ACK 号表示"这个号之前的我都收到了"。注意是**累计确认**，中间丢一个会导致后面的都无法被单独确认 |
| **超时重传 RTO** | RTO 由 **SRTT（平滑往返时间）+ 4×RTTVAR（波动）** 动态算出；连续超时则**指数退避**（1s→2s→4s…） |
| **快速重传** | 收到 **3 个重复 ACK** 就立刻重传，不等超时——因为重复 ACK 说明后面的包到了、中间那个丢了 |
| **SACK（选择性确认）** | 累计确认的缺陷是"丢一个要重传一片"。SACK 让接收方告知**具体收到了哪些区间**，发送方只补缺失的那段 |

🎮 **游戏后台视角**：RTO 的**指数退避**是 TCP 在实时场景最致命的地方——网络抖一下，重传间隔就翻倍，玩家体感是"卡住好几秒"。**这是游戏用 UDP/KCP 的核心原因**。

## 4. 流量控制 vs 拥塞控制 ★★★★★（最爱考的对比）

| | **流量控制** | **拥塞控制** |
|---|---|---|
| 保护谁 | **接收方**（别把我的缓冲区撑爆） | **网络**（别把链路打爆） |
| 靠什么 | `rwnd`：接收方在 ACK 里告知剩余窗口 | `cwnd`：发送方自己维护的估计值 |
| 谁维护 | 接收方通告 | 发送方计算 |

> **实际能发多少 = `min(cwnd, rwnd)`** ——这句话是这两个概念的交汇点，一定要说。

### 流量控制的两个衍生问题

- **零窗口 + 窗口探测**：接收方通告 `rwnd=0` 后，发送方停发；但"窗口恢复"的通知如果丢了就死锁 → 发送方启动**持续计时器**定期发**窗口探测包**
- **糊涂窗口综合症**：接收方每次只腾出几字节就通告，导致大量小包 → 接收方"攒够半个缓冲区或一个 MSS 再通告"，发送方用 **Nagle 算法**攒包

### 🎮 Nagle × 延迟 ACK 互锁（游戏/低延迟场景必考）

- **Nagle**：小包先攒着，**等上一个包的 ACK 回来**再发 → 减少小包数量
- **延迟 ACK**：接收方**不立刻回 ACK**，等 ~40ms 看能不能捎带数据一起回

两个凑一起 → **发送方等 ACK，接收方等数据，互锁出 40ms 级的固定延迟**。
**解法：`TCP_NODELAY`（关闭 Nagle）**。游戏、RPC、交易系统基本都要开。

```go
tcpConn.SetNoDelay(true)   // Go 里 net.TCPConn 默认就是 true（已关闭 Nagle）
```

## 5. 拥塞控制四阶段 ★★★★★

```
cwnd
 │        ┌──── 拥塞避免（线性 +1）
 │       /                  ╲  丢包
 │      /                    ╲
 │  慢启动（指数 ×2）         ╲__ 快恢复（cwnd 减半，继续线性增）
 │ /
 └──────────────────────────────────► 时间
```

| 阶段 | 行为 |
|---|---|
| **慢启动** | `cwnd` 从 1 开始，**每收到一个 ACK 就 +1 → 每 RTT 翻倍**（指数增长）。到达 `ssthresh` 后转入拥塞避免 |
| **拥塞避免** | **每 RTT 只 +1**（线性增长），谨慎试探 |
| **快速重传** | 收到 3 个重复 ACK → 立即重传丢失段 |
| **快恢复** | `ssthresh = cwnd/2`，`cwnd = ssthresh`，**直接进拥塞避免**（不回到 1）。因为还能收到重复 ACK，说明网络没瘫 |

**两种丢包信号，反应完全不同**：
- **超时**（严重）：`cwnd` 直接打回 1，**重新慢启动**
- **3 个重复 ACK**（轻微）：走快恢复，`cwnd` 只减半

### 算法演进（说得出名字就够）

| 算法 | 思路 |
|---|---|
| **Reno / NewReno** | 经典四阶段，**以丢包为拥塞信号** |
| **CUBIC**（Linux 默认） | 用三次函数增长，高带宽长距离链路上比 Reno 更快占满带宽 |
| **BBR**（Google） | **不以丢包为信号**，而是主动测量**瓶颈带宽和最小 RTT**，直接按 `BDP` 发送。在**有随机丢包的链路（跨国、弱网）上远优于 CUBIC** |

💰🎮 **加分句**：「跨国链路上丢包不一定代表拥塞，CUBIC 会误判并降速，所以**跨境/弱网场景我会考虑 BBR**。」——这句同时对上"国际支付"和"全球游戏"两个场景。

## 6. TCP vs UDP ★★★★★

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（握手/挥手） | 无连接，一发就走 |
| 可靠性 | 确认+重传+去重+排序 | 不保证到达、不保证顺序、不去重 |
| 头部 | 20 字节起（最大 60） | **8 字节** |
| 传输单位 | **字节流**（无消息边界 → 粘包） | **数据报**（有边界，一次一个包） |
| 拥塞控制 | 有 | 无（要自己做） |
| 广播/组播 | 不支持 | 支持 |

### 🎮 为什么游戏用 UDP？（三个理由）

1. **队头阻塞**：TCP 保证有序交付，**前面一个包丢了，后面已经到达的包也不能交给应用**。游戏里"上一帧的位置"丢了根本不重要，我只要最新的
2. **重传的指数退避**：抖一下就退避成秒级，实时性直接崩
3. **拥塞控制不可控**：TCP 的降速策略是为吞吐设计的，不是为延迟设计的

**KCP** = 在 UDP 之上做的**可靠但不保序、重传更激进**的协议：**牺牲 10%~20% 带宽，换 30%~40% 的延迟降低**。核心是快速重传阈值更低、RTO 不做指数退避、支持选择性重传。

### 🎮 粘包拆包（长连接网关必考）

**根因**：TCP 是**字节流，没有消息边界**（叠加 Nagle 攒包、接收缓冲区批量读取）。**UDP 不会粘包**，因为它是数据报。

**三种解法**：
1. **长度前缀帧**（最常用）：`4 字节 body 长度 + body`
2. **分隔符**：如 `\r\n`（HTTP 用这个），缺点是 body 里出现分隔符要转义
3. **定长消息**：简单但浪费

## 7. 队头阻塞的四层辨析 ★★★★（gRPC/HTTP 面试的核心）

| 层 | 有没有队头阻塞 |
|---|---|
| **HTTP/1.1** | ✅ **应用层有**：一条连接同时只能处理一个请求，前一个不返回后面排队（pipelining 也没解决响应必须按序） |
| **HTTP/2** | ✅ **应用层解决了**：多路复用，一条 TCP 跑多个 stream，互不阻塞…… |
| **TCP 层** | ❌ **但 TCP 层的队头阻塞仍在**：一个 TCP 包丢了，**所有 stream 的数据都得等它重传**。并发流越多，一次丢包影响面越大 |
| **HTTP/3 (QUIC)** | ✅ **彻底解决**：QUIC 基于 **UDP**，在用户态自己实现可靠性，**每个 stream 独立重传**，互不影响 |

> **这套辨析说完，等于同时答了 HTTP/1.1、HTTP/2、HTTP/3 和 gRPC 的底层。** 是性价比最高的一段。

QUIC 的另外两个卖点：**0-RTT/1-RTT 建连**（合并了 TCP 握手和 TLS 握手）、**连接迁移**（用 Connection ID 而非四元组，手机从 WiFi 切 4G 连接不断）。

## 8. 长连接与心跳 ★★★★

### 🎮 TCP 有 keepalive，为什么还要应用层心跳？

| | TCP keepalive | 应用层心跳 |
|---|---|---|
| 默认间隔 | **7200 秒（2 小时）** | 自己定，通常 15~60s |
| 探测什么 | **只探测 TCP 连接是否还在** | **能探测应用是否还活着**（进程假死、GC 卡死、业务线程池满，TCP 层看起来完全正常） |
| 中间设备 | NAT/LB 的会话表通常几分钟就超时，2 小时才探测**早就断了** | 心跳同时起到**保活 NAT 映射**的作用 |

**结论：TCP keepalive 基本没用，长连接必须做应用层心跳。**

### 半开连接（half-open）

一方（比如客户端断电）没发 FIN 就消失了，另一方毫不知情，还以为连接正常——**只有真正发数据时才会发现**。这就是必须心跳的另一个理由。

## 9. IP 层与 MTU ★★★

```
MTU  = 1500（以太网标准）
MSS  = MTU − IP 头(20) − TCP 头(20) = 1460
```

- **分片**：IP 包超过 MTU 会被分片；**任何一个分片丢了，整个 IP 包都要重传** → 效率极差
- **PMTU 发现**：发送方置 `DF`（不分片）位，中间路由器过不去就回 ICMP「需要分片」并告知 MTU → 发送方调小。**如果防火墙把 ICMP 全禁了，PMTU 发现失效 → 出现"小包能过、大包卡死"的经典故障（PMTU 黑洞）**
- **TCP 天然避免分片**：靠握手时协商 MSS，主动把段切到 MTU 以内。**UDP 没这个机制，所以 UDP 应用要自己控制包大小**（🎮 游戏通常控制在 ~1200 字节以内，给隧道/VPN 留余量）

## 10. 💰 HTTPS / TLS（支付岗必考）★★★★

### TLS 1.2 握手（简化）

```
Client → ClientHello（支持的密码套件、随机数）
Server → ServerHello（选定套件、随机数）+ 证书链 + ServerKeyExchange
Client → 验证证书链 → 密钥交换（ECDHE）→ ChangeCipherSpec → Finished
Server → ChangeCipherSpec → Finished
之后用【对称密钥】加密通信
```

**四个必答点**：

1. **为什么要非对称 + 对称混合**：非对称（RSA/ECDHE）慢但能安全协商密钥，对称（AES）快但要先有共享密钥 → **用非对称协商出对称密钥，之后全用对称**
2. **证书链验证什么**：签名有效（用上级公钥验）、域名匹配、未过期、未吊销（CRL/OCSP）、根证书在本地信任库里
3. **前向安全（PFS）**：用 **ECDHE** 而不是 RSA 密钥传输——即使服务器私钥将来泄露，**也解不开之前抓到的流量**。金融场景必须开
4. **TLS 1.3 的改进**：握手从 **2-RTT 压到 1-RTT**，支持 **0-RTT** 恢复（代价是 0-RTT 数据**有重放风险**，所以**只能用于幂等请求**——💰 **支付请求绝对不能走 0-RTT**）

### 💰 中间人攻击怎么防

靠**证书信任链**。所以移动端支付 App 常做 **证书固定（Certificate Pinning）**——只信任写死的那张证书/公钥，防止用户设备被装了恶意根证书。

## 11. 💰 网络超时的语义：这是支付最重要的网络问题 ★★★★★

> **调渠道支付接口超时了——这笔支付到底成没成？**

**答案：不知道。超时的语义是「未知」，不是「失败」。** 可能是：
- 请求没到渠道（真失败）
- 请求到了、渠道处理成功了，但**响应在回来的路上丢了**（实际成功）

**所以支付系统的铁律**：

```
① 超时【绝对不能】直接标记为失败 —— 会导致用户已扣款、系统显示失败 → 资损/客诉
② 必须置为"处理中"，然后【主动查询渠道】确认最终状态（查询接口 + 定时补偿）
③ 重试必须带【相同的幂等键】，让渠道自己去重
④ 最终兜底是【对账】
```

**这段和 §2 的 TCP 知识是连着的**：网络超时之所以不可判定，本质是 **TCP 只能保证"字节送达"，不能保证"对端业务处理完成"**——这是**两军问题**（Two Generals' Problem），理论上无法通过通信解决，只能靠幂等 + 查询 + 对账在业务层绕过去。

> 这一段答出来，等于同时展示了网络底子和资金安全意识。**这是这两个知识点最值钱的交汇处。**

## 12. IO 模型与 epoll ★★★★（Go 后端绕不开）

| 模型 | 特点 |
|---|---|
| 阻塞 IO | 一个连接一个线程，连接多了扛不住 |
| 非阻塞 IO + 轮询 | 空转烧 CPU |
| **IO 多路复用** | 一个线程管多个 fd：`select` / `poll` / **`epoll`** |
| 信号驱动 / 异步 IO | Linux 上 AIO 支持不好，`io_uring` 是新方向 |

### select / poll / epoll 对比（必答）

| | select | poll | **epoll** |
|---|---|---|---|
| fd 上限 | 1024（`FD_SETSIZE`） | 无硬限制 | 无硬限制 |
| 每次调用 | **全量拷贝 fd 集合到内核** | 同左 | **只需一次 `epoll_ctl` 注册**，之后不拷贝 |
| 找就绪 fd | **O(n) 遍历** | O(n) | **O(1)**：内核用**红黑树管理 fd + 就绪链表**，直接返回就绪的 |

**LT（水平触发）vs ET（边缘触发）**：
- **LT**：只要还有数据没读完，`epoll_wait` 就会一直通知（默认，好写不易漏）
- **ET**：只在状态**变化**时通知一次 → **必须一次把数据读干净（循环读到 `EAGAIN`）**，否则数据就"卡"在那儿了。少一次系统调用，但难写

**Go 的位置**：`netpoller` 底层就是 epoll（Linux）/ kqueue（macOS），**Go 帮你把"异步 epoll"包装成了"同步的 goroutine 代码"**——所以 Go 里能放心写 `goroutine-per-connection`。

## 13. 线上排障命令速查

```bash
ss -s                       # 各状态连接数总览（比 netstat 快得多）
ss -lnt                     # 监听端口 + 全连接队列（Send-Q=上限, Recv-Q=当前排队）
ss -nt state time-wait | wc -l     # 数 TIME_WAIT
netstat -s | grep -iE 'listen|retrans|overflow'   # 队列溢出、重传统计
tcpdump -i any -nn 'port 8080' -w a.pcap          # 抓包，拖回本地用 Wireshark 看
mtr -rwbzc 100 <host>       # ping + traceroute 合体，定位丢包在第几跳
curl -w '@fmt' -o /dev/null -s <url>              # 分段耗时：DNS/连接/TLS/首字节
```

**一条经典排障链**：接口慢 → `curl -w` 看是 **DNS 慢 / 建连慢 / TLS 慢 / 服务端处理慢**（首字节时间）→ 若是建连慢，`ss -lnt` 看全连接队列有没有溢出 → 若是网络抖，`mtr` 看哪一跳丢包 → 必要时 `tcpdump` 抓包看有没有大量重传。

## 附录：自我思考

### 一、网络知识在面试里的真正考法，是「解释你系统里的现象」

复习时容易掉进"背协议细节"的坑——但面试官问三次握手，很少是想听 RFC 复述，他想听的是**你能不能用它解释线上现象**：

- 「连接偶发超时」→ 全连接队列溢出（`ss -lnt` 的 `Recv-Q`）
- 「接口固定慢 40ms」→ Nagle × 延迟 ACK 互锁
- 「小包正常、大包卡死」→ PMTU 黑洞
- 「服务重启后端口占满」→ `TIME_WAIT` 堆积
- 「连接数只涨不跌」→ `CLOSE_WAIT`，代码没关连接

**所以背的时候要正着背、反着用**：每学一个机制，问自己"它坏了会表现成什么现象"。

### 二、这一篇和两场面试的接口

- 🎮 **腾讯游戏后台**：§6（TCP vs UDP / KCP）、§7（队头阻塞）、§8（心跳与半开连接）、§9（UDP 要自己控包大小）、§12（epoll 与 Go netpoller）——**这几节直接就是那个岗的技术底座**
- 💰 **字节支付**：§10（TLS / 前向安全 / 0-RTT 不能用于支付）、**§11（超时语义 = 未知）**——尤其 §11，是**网络知识和资金安全的交汇点**，答出来比单独答任何一个都值钱

### 三、两军问题这个类比要记住

「TCP 只保证字节送达，不保证对端业务处理完成」——这句话把网络课本知识和支付系统设计连成了一条线。**面试里能把两个领域缝起来的答案，永远比孤立的知识点得分高**，因为它证明的是理解而不是记忆。
