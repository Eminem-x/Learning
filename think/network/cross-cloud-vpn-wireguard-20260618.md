# 跨云 VPN 内网互通:WireGuard 自建方案全解

> 来源:个人思考(结合公司实际 WireGuard 多云组网拓扑梳理)
> 收录时间:2026-06-18 17:09 CST

---

## 一、要解决的问题

不同云厂商(AWS、腾讯云、火山引擎)的 VPC 各自独立、互不相通,办公室网络又是另一张网。
目标:把它们拼成**一张逻辑内网**,让 AWS 上的机器能用内网 IP 直接访问腾讯、火山、办公室的机器。

由于不同厂商之间**没有共享的私有骨干网**,云原生的对等连接(VPC Peering / CEN / CCN)只能在**同一个厂商内部**使用,跨厂商用不了。因此跨云互通只能:

> **借公网当骨干 + 用 WireGuard 做加密封装和路由**,把各家 VPC 拼成一张逻辑内网。

### 三个观察点

1. **`volc-cngz.conf` 未在 `wg show` 中**:这台机本身就是火山节点,该 conf 可能是自身身份文件/模板;若它本应是独立 spoke,则当前是 down 的(待确认)。

3. **办公室 endpoint 是私网 IP**(`10.104.108.2`):办公室是**主动拨入** hub,自身可不需要公网 IP,但 hub 必须有公网 IP。

## 三、核心原理:公网底层,逻辑内网

WireGuard 是一张**叠加网络(overlay)**:真正的数据包在公网上跑,但被加密封装后,两端 VPC 看起来就像在同一个局域网里。"内网互通"是逻辑假象,不是物理专线。

```
你以为的(overlay,逻辑):
  10.101.x (AWS)  ──内网直连──  10.108.x (腾讯)

实际发生的(underlay,物理):
  35.91.27.188  ──公网 UDP 加密包──  43.153.106.192
  (AWS 公网IP)                      (腾讯公网IP)
```

`wg show` 里的 `endpoint` 是公网 IP——这就是"流量确实走公网"的证据。
**安全性来自加密**(公网上传的也是密文),而不是物理隔离。

## 四、关键概念辨析

### 1. 路由 vs 传输 vs NAT(三层不要混)

- **路由(routing)= 决定往哪个方向走**(控制层,查路由表选下一跳)。
- **传输(forwarding)= 真正把比特发出去**(数据层,由底层网络搬运)。
- **NAT = 额外改写地址**(只在地址不可用时才需要)。

> 路由本身不搬运数据,它只负责指路;真正搬运的是底层网络。NAT 只是地址不能用时的补救。

### 2. NAT / SNAT / DNAT

```
        NAT(网络地址转换 = 改写 IP 包头里的地址)
        ├── SNAT  改写「源地址」     → 管出向
        └── DNAT  改写「目的地址」   → 管入向
```

| | 改写谁 | 用途 | 例子 |
|---|--------|------|------|
| **SNAT** | 源 IP | 出向:私网机器访问公网 | `10.0.0.5` 出去 → 源改成公网 `1.2.3.4` |
| **DNAT** | 目的 IP | 入向:公网请求转发给内部服务 | 访问 `1.2.3.4:80` → 目的改成 `10.0.0.5:80` |
| **MASQUERADE** | 源 IP(动态) | SNAT 特例,出口公网 IP 不固定时用 | WireGuard hub 转发常用 |
| **PAT/NAPT** | 源 IP + 端口 | 多对一,共享一个公网 IP | 家用路由器、云 NAT 网关 |

> 一次完整连接经常 SNAT + DNAT 都用到。绑了公网 IP 的实例 = 入向 DNAT + 出向 SNAT 成对出现(即"1:1 静态 NAT")。

### 3. 两种 NAT 别混(公网 IP 还走不走 NAT?)

| | NAT 网关(SNAT) | 公网 IP 的 1:1 NAT |
|---|------------------|---------------------|
| 关系 | 多对一(一堆私网机器共享出口) | 一对一(一个私网 IP ↔ 一个公网 IP) |
| 谁需要 | **没有**公网 IP 的实例 | **有**公网 IP/EIP 的实例 |
| 源 IP 对外表现 | NAT 网关的 IP | 实例自己的公网 IP |
| 入向能用吗 | 不能(只能出) | 能(出入都行) |
| 你看得到吗 | 看得到这个网关组件 | 透明,系统里 `ip addr` 看不到 |

> **有公网 IP 还走不走 NAT?** 不走 NAT *网关*(直接用自己的公网 IP 出去,绕开网关);但云底层对公网 IP 本身做的是透明的 **1:1 静态 NAT**(尤其 AWS,实例网卡里其实只有私网 IP,公网 IP 是边缘网关映射的)。

## 五、什么时候走 NAT,什么时候只要路由

| 场景 | 是否走 NAT | 怎么传输 |
|------|-----------|----------|
| **同 VPC 内** | ❌ 不转换 | 私网 IP 直接路由,纯二/三层转发 |
| **同云跨 VPC**(对等/CEN) | ❌ 纯路由 | 网段不重叠就直接路由私网 IP,源/目的 IP 不变 |
| **跨云**(本场景) | ✅ hub 上 MASQUERADE | WireGuard 加密封装 + 公网搬运 + hub 中转 |
| **访问公网** | ✅ 必须转换 | 有公网 IP 用自身(1:1 NAT);没有则借 NAT 网关(多对一 SNAT) |

**NAT 只在三种情况才必须出现:**
1. 访问**公网**(私网 IP 不可路由);
2. 两个 VPC 网段**重叠**(没法用路由区分);
3. 某些设计(如 WireGuard hub)为简化回程路由**主动**加 MASQUERADE。

### "同云跨 VPC 只要路由"是怎么传的?

VPC 是云厂商用 SDN 在物理网络上**虚拟**出来的。做对等连接,实际只是在路由表加一条 `去 10.108.0.0/16 → 走对等连接`,然后:

```
实例A (10.101.0.5)
   │ ① 查路由:目的 10.108.x → 下一跳是对等连接
   ▼
物理主机虚拟交换机
   │ ② 原始包(源/目的 IP 不变!)用 VXLAN 封装,塞进云骨干
   ▼
云厂商私有骨干网(物理光纤,不走公网)
   ▼
对端虚拟交换机解封装 → 还原原始包
   ▼
实例B (10.108.0.8) ← 收到的源 IP 还是 10.101.0.5,全程没变
```

要点:**源/目的 IP 全程不变(=只要路由不用 NAT);底层有 VXLAN 封装但对你透明;走私有骨干不走公网,所以不产生公网流量费、不需公网 IP、延迟低。**

## 六、跨云组网的部署形态

### 每个 VPC 一台 WireGuard 网关(不是每台机器都装)

```
AWS-VPC (10.101.0.0/16)
┌─────────────────────────┐
│  app机器 10.101.0.50     │  ← 不装WG
│  db机器  10.101.0.60     │  ← 不装WG
│       │                  │
│       ▼ VPC路由表:       │
│  「去10.108.x → 下一跳   │
│    是WG网关机器」        │
│  ┌──────────────────┐   │
│  │ WG网关(装wg) ─────┼───┼──→ WireGuard隧道(公网) ──→ hub
│  └──────────────────┘   │
└─────────────────────────┘
```

- 一个 VPC **只需 1 台**(高可用 2 台)WireGuard 网关;
- 其余机器靠 **VPC 路由表**把目标网段指向网关,自身无感知。

### 别混淆两个"对等连接 / peer"

| 名词 | 含义 | 用在哪 |
|------|------|--------|
| **WireGuard 的 `[Peer]`** | 隧道配置里"对端节点",两端互填公钥 + endpoint | 跨云用这个 |
| **云的 VPC 对等连接(Peering)** | 云厂商托管功能,同厂商两 VPC 一键路由打通 | **仅同一个云内**可用 |

### hub-spoke vs full mesh

- 本公司是 **hub-spoke**:每个 spoke 只跟 hub 配 peer,spoke 之间互访经 hub 中转(配合 `ip_forward` + MASQUERADE)。
- **full mesh**:每两个 VPC 都互配 peer,N 个站点要 N×(N-1)/2 条隧道,管理成本高。hub-spoke 用中转换来了简洁。

## 七、跨境链路:广州 ↔ 海外(最难的一段)

**WireGuard 配置本身,广州到海外和海外到海外完全一样。** 难点不在配置,在**"中国↔海外这段公网链路的质量"**。

### 三座大山

1. **高延迟**:中美 RTT 常 150~250ms。
2. **丢包 / 抖动**:跨境出口拥塞,高峰丢包严重。
3. **UDP 被限速/干扰**:WireGuard 跑在 UDP 上,跨境 UDP 比 TCP 更容易被 QoS 甚至阻断。

### 三种搭建路径(便宜不稳 → 贵但稳)

**方案 A:公网直连(公司现状)**
```
火山广州 ──公网UDP──→ AWS美国 / 腾讯硅谷
```
配置最简单,但跨境段看运气。缓解:选**优质国际线路**节点(CN2 GIA / 三网精品)。

**方案 B:香港/新加坡中转(性价比)**
```
火山广州 ──优质线路(短)──→ 香港中转 ──干净国际网──→ AWS美国
```
把敏感的跨境段缩到最短,香港→美国是干净国际网。中转节点再跑一层 WireGuard 转发。

**方案 C:合规跨境专线 / 云全球加速(生产级推荐)**
```
火山广州 ──IPLC/IEPL专线 或 云私有骨干──→ 海外
```
- **跨境专线(IPLC/IEPL)**:运营商点对点物理专线,跨境段不走公网,稳定低延迟,但贵。
- **云全球加速**:阿里 GA、腾讯 GAAP、AWS Global Accelerator,用云私有骨干承载跨境段。
- WireGuard 可叠加在专线之上(专线保质量,WireGuard 保加密)。

### 公网直连的保命 tips

- **端口**:避开易被针对的端口;
- **keepalive**:`persistent-keepalive 25` 对穿 NAT、保活关键,保留;
- **MTU**:务必调好(WireGuard MTU 建议 1380~1420),否则大包被丢表现为"能连不能传";
- **监控**:盯跨境段丢包率和 `latest handshake`,频繁超时即这段在抖。

### ⚠️ 合规提醒

企业跨境数据传输,正规路子是**持证的跨境专线(IPLC/IEPL)或云厂商合规跨境产品**(方案 C)。纯公网 + 自建隧道虽技术可通,但跨境大流量在合规与稳定性上都有风险;若承载生产业务,建议推动走方案 C。

## 八、一图流总结

```
同 VPC          →  私网直连,不转换
同云跨 VPC      →  纯路由 + 云私有骨干 + VXLAN(云帮你做,透明)
跨云(本场景)  →  WireGuard 加密封装 + 公网搬运 + hub 中转 + MASQUERADE
访问公网        →  有公网IP用自身(1:1 NAT)/ 没有则借 NAT 网关(多对一 SNAT)
跨境(广州↔海外)→  公网直连 / 香港中转 / 跨境专线·全球加速
```

> 公网当"管道",WireGuard 当"加密内网",云厂商按管道里的流量收费。
> 路由负责指路,封装负责搬运,NAT 只在地址不可用时才出场。

## 附录:自我思考

1. **概念分层是理解网络的钥匙。** 这次最大的认知收获是把"路由 / 传输 / NAT"三件事彻底分开——很多困惑(比如"跨 VPC 只要路由那到底怎么传")都源于把"指路"和"搬运"当成一回事。一旦分层,NAT 就从"神秘必需品"变成"地址不可用时的补救",出现时机一下就清晰了。

2. **同名陷阱要警惕。** "对等连接"在 WireGuard(`[Peer]`)和云厂商(VPC Peering)里是两个完全不同的东西;"NAT"在"NAT 网关"和"公网 IP 1:1 映射"里也指不同机制。技术沟通中,先对齐名词指代,能省掉大量来回。

3. **抽象层的代价。** WireGuard 把跨云做成"逻辑内网"很优雅,但它掩盖了底层是公网这一事实——于是流量费、跨境抖动、UDP 限速这些"漏出来的真相"反而容易被忽略。抽象让人省心,也让人对真实成本和风险失去敏感。看到 AWS 那条 4.26 TiB,应该条件反射地去想"这是跨境公网出口,钱和稳定性都在这"。

4. **待办与演进方向。**
   - 确认 `volc-cngz` interface 状态(是自身身份文件还是 down 的 spoke);
   - 核实 AWS 4.26 TiB 入向流量的来源与计费方向是否符合预期;
   - 评估跨境链路从「方案 A 公网直连」向「方案 B 香港中转 / 方案 C 跨境专线」演进的必要性与成本,尤其在流量增长和合规要求下。
