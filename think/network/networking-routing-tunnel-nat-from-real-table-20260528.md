## 0. 这篇要解决的问题

一个看似简单的疑问:**"我连着 VPN 时,访问 `8.8.8.8` 的包,到底怎么走出去、又怎么回来?"**
顺着这个问题,把**子网 / 路由 / 最长前缀匹配 / 隧道封装 / NAT** 一次性串通。全程用一张**自己机器的真实路由表**当教材,不背概念。

## 1. 案例素材:真实的 `netstat -rn`

```
Destination        Gateway            Flags     Netif
0/1                10.0.10.1          UGScg     utun4
default            192.168.31.1       UGScg     en0
10.0.10/23         10.0.10.4          UGSc      utun4
10.0.10.1          10.0.10.4          UHr       utun4
118.145.207.26/32  192.168.31.1       UGSc      en0
128.0/1            10.0.10.1          UGSc      utun4
192.168.31         link#17            UCS       en0
192.168.31.117/32  link#17            UCS       en0
...(127/169.254/224/255 等系统保留,略)
```

**先认清每个角色:**

| 地址 / 名字 | 是谁 | 层 |
|------|------|----|
| `192.168.31.117` | 我 Mac 的真实 IP | 🟥 真实网络 |
| `192.168.31.1` | 真实网关(小米路由器) | 🟥 真实网络 |
| `118.145.207.26` | VPN 服务器的真实公网 IP | 🟥 真实网络 |
| `10.0.10.4` | 我在隧道里的 IP(我的"门牌") | 🟦 隧道内部(虚拟) |
| `10.0.10.1` | VPN 服务器在隧道里的 IP(隧道网关) | 🟦 隧道内部(虚拟) |
| `10.0.10.0/23` | 隧道地址池(给所有 VPN 客户端发地址) | 🟦 隧道内部 |
| `utun4` | 虚拟接口 = 通往 OpenVPN 程序的"管道" | 🌉 两层之间的桥 |

> 读表小抄:**Gateway 是 IP** → 经下一跳路由器(Flags 带 `G`);**Gateway 是 `link#N`** → 直连,不经路由器(`#N` 是接口内部编号,这里 `#17`=en0)。
> 确认本机 IP **别靠猜路由表**,用 `ipconfig getifaddr en0`。

## 2. 子网 / CIDR:地址的"归属判定"

- 一个 IPv4 = 32 位。`/n` 表示**前 n 位是网段(锁定)**,后 `32-n` 位是主机(可变)。
- **地址数 = 2^(32-n)**;主机位 = 32-n。
- **街区速算法**:看 `/n` 落在哪段,该段街区大小 = `256 - 掩码该段值`。
  - `/24` → 255.255.255.**0** → 第4段每 256 一组
  - `/23` → 255.255.**254**.0 → 第3段每 **2** 一组(如 `10.0.10.0/23` = 第3段 {10,11})
  - `/22` → 255.255.**252**.0 → 第3段每 **4** 一组

**判断两个网段冲不冲突的唯一可靠方法:把两个区间都算出来,看有没有重叠**(别比掩码、别比"固定位"):
```
10.0.10.0/23 → 10.0.10.0 ~ 10.0.11.255  (第3段 10、11)
10.0.0.0/24  → 10.0.0.0  ~ 10.0.0.255   (第3段 0)
第3段 {10,11} ∩ {0} = ∅ → 不冲突
```

**实战避坑**:家庭 LAN 故意用冷门网段(如 `10.83.7.0/24`),避免和咖啡馆/公司/酒店的 `192.168.1.0/24`、`10.0.0.0/24` 撞,VPN 回家就永远不会路由冲突。

## 3. 路由表 + 最长前缀匹配:包"往哪走"的判定

**核心 4 句:**
1. 每台联网设备都有一张路由表。
2. 一条路由 = "目标网段 → 下一跳 / 从哪个接口出"。
3. 包来了,拿目的 IP 比对所有匹配的路由,**选前缀最长(最具体)的那条**——这就是**最长前缀匹配**。
4. `default`(`0.0.0.0/0`)是兜底:匹配一切但前缀最短,只有没别的匹配时才轮到它。

**直觉(寄信)**:`/0`="所有信默认丢邮局A";`/1`="城西的丢邮局B";`/24`="某小区送驿站C";`/32`="给张三本人直接送到家"。给张三的信 4 条都匹配 → **永远按最具体的"直接送张三家"**。

**用真实表验证(同一规则,三种结果):**

| 访问目标 | 哪些路由匹配 | 谁前缀最长 → 实际走哪 |
|---------|------------|----------------------|
| `8.8.8.8`(公网) | `default`(/0)、`0/1`(/1) | **/1 赢 → utun4 隧道** |
| `118.145.207.26`(VPN服务器) | `0/1`(/1)、`.26/32`(/32) | **/32 赢 → 真网关(绕开隧道,防环路)** |
| `192.168.31.50`(本地) | `0/1`(/1)、`192.168.31/24`(/24) | **/24 赢 → 本地直连** |

### 为什么"没动设置"也全部流量走 VPN?

不是自己设的,是 **VPN 服务器在连接时"推(push)"路由给客户端**(服务器开了「重定向网关 / 全局模式」)。它塞进两条:
```
0/1     → 10.0.10.1 → utun4   # 覆盖首字节 0~127
128.0/1 → 10.0.10.1 → utun4   # 覆盖首字节 128~255
```
- `0~127` + `128~255` = **整个 IPv4**(`128.0/1` 是 128~255,不是只有128!)。
- 这两条 `/1` 比原来的 `default`(`/0`)更具体 → **最长前缀匹配让它们永远赢过 default** → 所有去公网的流量走隧道,而 `default` 原封不动留着(断开 VPN 即恢复)。

**结论:服务器负责"塞路由",最长前缀匹配负责"让塞进来的路由生效"。** 你的全部上网流量因此都经过了 VPN 出口。

## 4. 隧道 / 封装:包"怎么走出去"

关键认知:**`utun4` 不是真网卡,是通往 OpenVPN 程序的一根管道。** 路由表里 Netif=`utun4` 的行,意思都是"**把包交给 OpenVPN**"。

**封装 = 信封套信封:**
```
内层信(隧道里):  收件人 8.8.8.8        寄件人 10.0.10.4
        ↓ OpenVPN 把它整个加密,锁进一个外层信封
外层信(真网络):  收件人 118.145.207.26  寄件人 192.168.31.117
```
真实互联网(邮政系统)**只看得见外层信封**,只管把它送到 VPN 服务器 `118.145.207.26`(这条加密管道在点"连接"时就建好、一直开着)。服务器拆开外层,才看到里面"给 8.8.8.8 的信"。

> 易错点纠正:OpenVPN **不会去"请求 10.0.10.1"**。`10.0.10.1` 是隧道里的虚拟门牌、不在公网上、无法被请求。OpenVPN 真正寄去的是**真实地址 `118.145.207.26`**。路由里 Gateway=`10.0.10.1` 只是"隧道另一头"的虚拟标签,理解流程时可忽略,真正起作用的是 `Netif=utun4`(=交给 OpenVPN)。

### 隧道地址的意义(为什么要 10.0.10.4 / 10.0.10.1)

VPN 连上 = 临时"搬进"虚拟小区 `10.0.10.0/23`,得有门牌才能收发信:
- **`10.0.10.4` = 你的门牌(回信地址)**:回来的包目的地址就是它,你 Mac 凭它认领"这是给我的"。
- **`10.0.10.1` = 小区门卫 / 隧道网关**:你在隧道里发包的下一跳;`ping 10.0.10.1` 通 = 隧道通。
- **`10.0.10.0/23` = 门牌池**:服务器(`.1`)给每个客户端发地址(你 `.4`,下一个 `.5`……)。这正是 OPNsense 配置里"隧道网络"那一栏。

## 5. NAT:服务器"记账 + 改地址",让回信找回你

**NAT = 网关转发时把"源地址"换成自己的,记一笔账;回包时按账本换回去。**

**为什么必须换**:私有地址(`10.x`/`192.168.x`)不全球唯一、公网不可路由。`8.8.8.8` 收到"源=10.0.10.4"根本不知道回哪去 → 必须换成真实公网 IP。

**怎么认领回来(账本 + 端口 = PAT):**
```
内网侧(隧道里)          公网侧(服务器对外)         目标
10.0.10.4:51000   ↔   118.145.207.26:40001   →   8.8.8.8
10.0.10.5:49200   ↔   118.145.207.26:40002   →   1.1.1.1
                          ↑同一个公网IP,靠端口40001/40002区分是谁的
```
IP 像楼号、端口像房间号:对外只有一个楼号,靠不同房间号区分每条连接。回信到 `:40001`,服务器查账 → 换回 `10.0.10.4` → 发回隧道。

> 最日常的 NAT:你家手机/电脑/电视共享一条宽带一个公网 IP,就是**家路由器(`192.168.31.1`)在做 NAT**。

## 6. 完整来回(把全部知识串成一条线)🔁

**去程:**
```
① 浏览器:  src=10.0.10.4:51000  dst=8.8.8.8     —— 进 utun4(子网/路由/最长匹配决定走隧道)
② OpenVPN: 加密+套外层信封,寄 118.145.207.26  —— 走真网卡 en0(封装)
③ 服务器:  拆信解密 → NAT 改 src=118.145.207.26:40001,记账 → 发给 8.8.8.8
```
**回程(原路反着来):**
```
④ 8.8.8.8: 回信到 118.145.207.26:40001
⑤ 服务器:  查账 40001→10.0.10.4 → 改回 dst=10.0.10.4 → 加密套信封 → 经隧道发回
⑥ 我 Mac:  utun4 收到,目的=10.0.10.4(我的门牌)→ 交给浏览器 ✅
```
③⑤的"改地址+记账/查账"=NAT;②⑤的"加密套信封"=隧道封装;走哪条路=路由+最长前缀匹配;地址归属=子网。**四块知识在这一个来回里全用上了。**

## 7. 最初问题的最终解答:为什么在公司开不了 VPN

整条学习线的起点是一个困惑:**"公司连内网 WiFi 能直接访问内网,回家用 OpenVPN 访问内网,为什么在公司开不了 OpenVPN?"** 现在用全部知识把它拆透。其中最核心、也最值得记的机制是 **NAT 回流(hairpin)被禁**。

### 先补一个概念:DNAT(前面只学了 SNAT)

NAT 有两个方向:

| | 改谁 | 用在哪 | 见过的例子 |
|---|------|--------|-----------|
| **SNAT**(源NAT) | 改**源**地址 | 出站 | `10.0.10.4 → 公网IP`(第5节) |
| **DNAT**(目的NAT) | 改**目的**地址 | 入站/端口转发 | WireGuard 菜谱里的"端口转发 `UDP 51820 → 内网服务器`" |

DNAT = "发到 `公网IP:端口` 的包,目的地址被改写成某台内网服务器"。它是外部流量能进到内网服务器的关键。

### 对照组:在家连,为什么正常 ✅

```
客户端 ──"连 118.145.207.26:VPN端口"──► 公网
                                          │
                                公司防火墙(公网IP 118.x)
                                   │ DNAT:目的改成内网VPN服务器
                                   ▼
                              VPN服务器(内网 10.0.0.5)
回复原路返回,路径对称,握手完成 ✅
```

### 在公司连:发夹弯(hairpin)问题 💥

VPN 配置文件里**写死了连公网 IP `118.145.207.26`**。但你人已在内网,客户端仍去找那个公网 IP:

```
客户端(内网 10.0.5.50)
   包: src=10.0.5.50  dst=118.145.207.26
        │ 118.x 是公网 → 按默认路由送到内网网关/防火墙
        ▼
   防火墙: "目标是我自己的公网IP?" → 得把包【掉头绕回内网】送给VPN服务器
        ↑ "出去又拐回同一个网络"的 U 形掉头 = NAT 回流 / hairpin / 发夹弯
```

**为什么会失败,两个层次:**

**① 很多防火墙默认不开 hairpin** → 见到"目标是自己公网IP又要拐回内网",直接丢弃或不处理 → 客户端超时。

**② 就算 DNAT 了,不做 SNAT 会"回复地址不匹配":**
```
DNAT后,VPN服务器收到:  src=10.0.5.50  dst=10.0.0.5
VPN服务器回复:          src=10.0.0.5   dst=10.0.5.50   ← 直接用内网IP回你
客户端: "我明明发给 118.145.207.26,凭啥 10.0.0.5 回我?" → 拒收 → 握手失败 ❌
```
这正是第5节学的**"回信地址必须匹配你发出去的目标"**(连接跟踪/账本)。要修好,防火墙必须额外 SNAT(让服务器把回复先发回防火墙、再由防火墙换回公网IP答复你)——这一整套"掉头+双向改地址"就是 hairpin NAT 功能,而它常被关掉。

### 完整答案:多因叠加

hairpin 只是其一。合起来才是全貌:

| 原因 | 机制 |
|------|------|
| **① NAT 回流被禁** | 内网访问自己公网IP的掉头请求,防火墙不处理 / 回复地址不匹配 |
| **② 路由冲突** | VPN 推送网段与脚下内网网段重叠 → 最长前缀匹配下本地路由被覆盖(见第3节) |
| **③ 防火墙封端口 / 只在WAN口监听** | 内网出站到 VPN 端口被挡,或 VPN 只在公网口提供服务 |
| **④ 可信网络检测** | 客户端探测到"已在内网" → 主动拒绝建隧道 |

**最根本一点**:VPN 的使命是"把外部设备拉进内网"。你人已在内网(公司 WiFi 能直连),"从外面进来"的入口机制(公网IP→防火墙→DNAT)对内网设备本就没有干净路径——所以这些限制一部分是技术上的自然结果,一部分是有意设计。

### 这个问题串起了整条线 🧩

公网/私有 → 路由(默认路由把公网IP包送去防火墙)+ 最长前缀匹配 → DNAT/SNAT → 连接跟踪(回复匹配)→ 封装(握手要先建加密管道)。**第一天只能记住"连不上";现在能把每个原因的数据包路径画出来。**

## 附录:自我思考

**1. "用真实数据反推"是这次学得透的根本原因。**
没有从教材定义入手,而是盯着自己 Mac 的 `netstat -rn`,一行一行追问"这是什么、为什么、怎么走"。每个抽象概念(最长匹配、封装、NAT)都落在一个看得见的真实地址上,于是记得牢、推得动。这验证了路线图里的"三角循环":理论必须经过"在自己机器上看见"才算进脑子。

**2. 几个最容易绊倒人的点,都是"层"没分清。**
- 把 `10.0.10.1`(虚拟门牌)当成 OpenVPN 要"请求"的真实目标——混淆了🟦隧道内部与🟥真实网络两层。
- 以为路由表能告诉你"这是不是公司 VPN"——混淆了"机制(包往哪走)"与"身份(VPN 是谁的)"。
- 纠结 `0/1` 和 `128.0/1` 是不是全部——没把 `128.0/1` 看成"128~255 整个上半区"。
**凡是绕晕,先问:我现在说的是哪一层?** 分层一清,迷雾就散。

**3. 路由表暴露了一个值得记住的事实:你的网络行为可被 VPN 服务器单方面改写。**
"没动设置却全局走 VPN",本质是服务器 push 了 `/1` 路由 + 最长前缀匹配生效。这意味着连上任何 VPN,你的全部流量(含私人浏览)理论上都经过对方出口。技术中性,但要心里有数。

**4. 一个闭环、一个待闭环。**
最初问"VPN 在公司为何连不上",其中"路由冲突(本地网段与 VPN 目标重叠)"已用最长前缀匹配讲透并闭环;而另一个原因"NAT 回流(hairpin)被禁",现在有了 NAT 基础,是下一步可以自己拿下的目标。学习本就是这样:一个问题牵出一串,逐个收口。
