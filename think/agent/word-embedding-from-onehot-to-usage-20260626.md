# 从 one-hot 到调用 embedding 模型:一条理解链

> 来源:个人思考(对话整理)
> 收录时间:2026-06-26 02:12 CST

---

本文把「embedding 到底是什么、怎么训练、平时调用时发生了什么」串成一条完整的理解链。它不重复训练时的数学走查(那部分见同目录《词向量是怎么训练出来的》),而是顺着一连串「为什么」把概念之间的关系打通:

> **one-hot → ID/token → 查表 → 训练得到 embedding → 使用时只跑前向 → 为什么 one-hot 不会撑爆内存 → token 数量为何固定**

---

## 一、起点:one-hot 是什么

机器学习模型只能处理数字,不能直接吃「猫」「狗」这种符号。最朴素的做法是 **one-hot**:向量长度 = 类别总数,只有一个位置是 1,其余全是 0,那个 1 的位置代表是哪个类别。

| 词 | one-hot 向量 |
|----|-------------|
| 猫 | `[1, 0, 0, 0]` |
| 狗 | `[0, 1, 0, 0]` |
| 鱼 | `[0, 0, 1, 0]` |

为什么不直接编号成 `猫=1, 狗=2`?因为那会引入**假的大小关系**(模型会以为「鱼 > 猫」)。one-hot 让每个类别**彼此正交、地位平等**。

**但 one-hot 的致命缺陷**:任意两个词的距离都相等——「猫」和「狗」并不比「猫」和「桌子」更近。**它完全不带语义**,只回答「是不是同一个」。

---

## 二、ID 只是 one-hot 的「门牌号」

实际代码里,我们不存 one-hot 向量,而是给每个词一个整数 ID:

```python
word_to_ix = {"hello": 0, "world": 1}
```

关键认识:

> **整数 ID = one-hot 向量里那个「1」所在的位置。**

`ID=2` 等价于 one-hot `[0, 0, 1]`,它们是同一信息的两种写法。ID 中的 `0、1、2` 是「第几号」,**不是数值**,彼此平等无大小关系。

---

## 三、embedding = 一张可训练的查找表

`nn.Embedding(vocab_size, dim)` 本质就是一张 `词表数 × 维度` 的矩阵:

```
        dim0   dim1   ...  dim_d
猫    [  ?,     ?,    ...,   ?  ]   ← 第 0 行
狗    [  ?,     ?,    ...,   ?  ]   ← 第 1 行
```

用 ID 查表 = 取出对应那一行。数学上等价于「one-hot 向量 × 矩阵」,但实现上直接按行号取,**那个巨型 one-hot 向量从不真的造出来**(这点在第六节展开)。

刚初始化时,表里的数字是**随机的、没有意义**。语义要靠训练得到。

---

## 四、关键洞察:embedding 是训练的「副产品」

这是最容易忽略、却最重要的一点。

训练时,模型表面在学的任务是**预测词**(n-gram 预测下一个词 / CBOW 预测中间词)。embedding 表只是为了把这个预测任务做好,而**被顺带调整出来的中间参数**。

一次训练迭代 = **前向 + 反向 + 更新**:

| 步骤 | 方向 | 干什么 |
|------|------|--------|
| 前向传播 | 输入 → 输出 | 算出预测结果 + 损失(错多少) |
| 反向传播 | 输出 → 输入 | 算出每个参数的梯度(该往哪调) |
| 更新参数 | — | 按梯度调整参数(embedding 表也在内) |

> 用考试打比方:前向 = 做题,算损失 = 对答案,反向 = 复盘错在哪,更新 = 订正。

你没有直接告诉模型「猫应该是什么向量」,你只是逼它做填空题。为了把填空做对,它**不得不**把意思相近、上下文相似的词调到相近的向量——**语义就这样涌现出来**。这就是为什么「相近的词向量也相近」。

校准一句常见误解:

> 不是「训练 embedding」,而是「训练一个预测模型,**顺便**得到 embedding」。

另外:玩具语料(一首诗)学出的向量其实没用,真实模型在**几十亿词**的语料上训练,质量取决于数据量。

---

## 五、平时调用 embedding 模型 = 只跑前向

你平时调的 embedding 模型,就是**别人已经训练好的模型**,你只是用它做查询(推理),**不再训练,参数一个都不变**。

| 阶段 | 谁做 | 发生什么 |
|------|------|---------|
| 训练 | 模型作者(一次性) | 海量语料上前向+反向+更新无数次 |
| 使用 | 你(每次调用) | 文本进 → **只跑前向** → 向量出 |

但现代 embedding 模型比玩具版强在三点:

1. **不是死查表,而是带上下文计算**。同一个词在不同句子里向量可能不同——「苹果很好吃」vs「苹果发布新手机」。底层是 Transformer,向量是**算出来的**,不是简单取行。
2. **输入是 token 不是词**。文本先被切成子词片段(见第七节)。
3. **整句 → 一个向量**。把所有 token 信息融合(池化)成一个向量代表整段意思。

完整流程:

```
你的文本 → 切 token → 查每个 token 初始向量(查表)
        → 过 N 层网络计算(带上下文) → 池化合并 → 返回向量
        └──────────── 全程只有前向,无反向、无更新 ────────────┘
```

用词校准:对现代模型是「**算**出一个结果」而非「**取**一个结果」。查表只是前向的第一步,真正的语义来自后面整个网络。

---

## 六、为什么 one-hot 不会撑爆内存

一个自然的担心:全世界那么多词,用 one-hot 岂不是需要天文数字的内存?

**直觉没错**——假设词汇 1000 万,one-hot 全集 = 1000万 × 1000万 ≈ 400 TB,根本跑不动。

**但现实里这不会发生**,原因有二:

**① one-hot「乘矩阵」只是数学说法,从不真的执行。** 既然结果就是「取第 N 行」,何必造一个超长向量再做矩阵乘?直接用整数索引取行即可。那个庞大的 one-hot 向量**在内存里从未真正存在过**,只是帮助理解原理的。

**② 真正存储的只有 embedding 表,小得多:**

| | one-hot 全集(虚构) | embedding 表(真实) |
|--|--------------------|--------------------|
| 形状 | 1000万 × 1000万 | 1000万 × 768 |
| 大小 | ~400 TB | ~30 GB |

embedding 的核心价值之一:**用「稠密低维」替代「稀疏超高维」**。

---

## 七、token 让词表大小「固定」下来

第六节解决了「单个向量超长」,但「词汇无穷多」由另一招解决:**子词分词(subword tokenization)**。

分词器在训练时就定死了一个**固定大小的 token 词表**(如 5 万、10 万),里面装的不是整词,而是**词的碎片**(整词、词根词缀、单字母、甚至单字节)。任何生词都能**拆成已知碎片**拼出来:

```
Schwarzenegger → "Schwar" + "zen" + "egger"
最坏情况 → 拆到字节级别
```

终极兜底:byte-level 分词器词表包含全部 256 个字节,所以**任何输入(中文、emoji、乱码)都不会产生「未知 token」**,大不了拆到字节。

这解决了早期 word2vec 按整词时的 **OOV(未登录词)** 痛点——那时遇到生词只能给个 `<UNK>`,信息全丢。

代价:生词被拆得很碎时,token 数变多(更占长度、更费钱),语义靠模型重新拼,可能不如常见整词精准。但「无法表示」的硬伤被彻底解决。

---

## 八、三个概念的关系

| 概念 | 是什么 | 起什么作用 |
|------|--------|-----------|
| token | 文本切出来的碎片单位 | 让词表大小**固定**(几万) |
| ID / one-hot | token 的编号(门牌号) | 概念上是 one-hot,实际只用整数 |
| embedding 表 | 词表数 × 维度 的稠密表 | 真正存储的东西,按 ID 查行 |

校准:不是「one-hot 变成了 token」。而是两招合一——

- **token 让词表数量固定**(表的行数封顶)
- **索引查表让 one-hot 不必真的造出来**(不存巨型稀疏向量)

于是从理论上的几百 TB,压到普通机器装得下的几百 MB。

---

## 九、一句话总览

> 给定语料 → 子词分词把词表固定住 → 一张随机的「ID→向量」稠密查找表 → 用「预测词」任务驱动前向/反向/更新反复训练 → 表里的向量从随机变得有语义 → 这张训练好的表(连同网络)就是 embedding 模型。**平时调用就是:文本进,只跑一次前向,向量出。**

## 附录:自我思考

**1. 「副产品」视角是这条链里最反直觉、也最关键的一环。** 很容易以为「embedding 是被直接训练的目标」,但实际上它是为了完成「预测词」这个代理任务而被顺带优化出来的。一旦接受这个视角,很多事就顺了:为什么相近词向量相近(因为它们在预测任务里可互换)、为什么需要海量语料(代理任务要见够多上下文)、为什么单个维度不可解释(没人规定某维代表什么,它只是优化的中间状态)。

**2. 「概念解释」和「工程实现」要分开看。** one-hot × 矩阵是概念解释,索引查表是工程实现;两者数学等价,但内存代价天差地别。这种「数学上成立 ≠ 实现上照做」的模式在深度学习里反复出现(如 softmax 的数值稳定化、log_softmax 合并计算)。理解原理时用前者,谈性能时用后者。

**3. 我担心的「内存爆炸」其实命中了 NLP 史上的真实转折点。** 从 one-hot 到稠密 embedding、从整词到子词,都是为了同一组约束:有限内存 + 无穷词汇 + 要带语义。技术演进往往不是「想出更聪明的东西」,而是「在硬约束下被逼出来的折衷」。带着「它在解决什么约束」去读论文,比死记结构更有效。

**4. 还没打通的点**:现代模型「带上下文计算」具体怎么实现(注意力机制如何让同一个词在不同句子里得到不同向量)、池化(pooling)把多个 token 向量合并成一个时具体用什么策略(平均?取 [CLS]?),这两块是从「静态查表」到「真正的句向量模型」的关键跳跃,值得下一步专门走一遍。
