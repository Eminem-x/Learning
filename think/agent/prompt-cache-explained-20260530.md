# Prompt Cache(提示词缓存)是什么 —— 结合我自己的 Claude Code 用量

> 来源：个人思考(与 Claude 的对话整理)
> 收录时间：2026-05-30 15:55 CST

---

## 一句话结论

AI agent 每轮回答都要把**整段对话历史**重新发给模型重算一遍;**prompt cache 把"已经算过的历史前缀"的中间结果存起来**,下一轮开头一致时直接复用,跳过重算。

在我自己的 9284 次 Claude Code 调用里,这个机制省下了约 **$17,776(81.7%)** 的费用。

---

## 一、为什么会有"一模一样"的输入可以缓存

最大的误区:以为缓存的是"问题 → 答案",要两个人问一样的问题才命中。**不是的。**

大模型本身**没有记忆**。它不记得上一轮说过什么。所以每次回答,程序都要把**到目前为止的整段对话**重新打包发过去。看这个增长过程:

```
第 1 轮发送:
  [系统提示] + [工具定义] + 我问:"agent 的 cache 是什么"

第 2 轮发送:
  [系统提示] + [工具定义] + 我问:"agent 的 cache 是什么"
  + 模型答:"..." + 我追问:"怎么会有一样的问题"
       └────────── 这一整段,和第 1 轮逐字一模一样 ──────────┘
```

每一轮的**开头**都和上一轮重合,只是末尾追加了新内容。把对话想成往文档末尾不断追加:

```
第1轮:  ████
第2轮:  ████░░        (████ 没变,只多了 ░░)
第3轮:  ████░░▒▒      (████░░ 没变,只多了 ▒▒)
```

所谓"一模一样",指的是**同一场对话的历史,在每一轮里被原样重发**——缓存吃的就是这个重复,而不是"两次提问内容相同"。

### 关键限制:只能复用"前缀(prefix)",且逐字节一致

缓存只能复用**从头开始连续相同**的部分。一旦某个字节变了,从那里往后都得重算。两个实践推论:

1. **不变的东西放最前面**(系统提示、工具定义)——它们几乎永不变,所以永远命中,省得最多。
2. **改了系统提示里一个字**,后面整段缓存全作废,因为"前缀不再一致"。

## 二、Prefill 是什么 —— 理解它才知道缓存省了哪一步

大模型生成文字分**两个阶段**,机制完全不同:

### 阶段 1:Prefill(预填充)—— 一次性读完输入

把整段对话发过去后,模型要先**把所有输入 token 读一遍、理解一遍**:

- **并行**处理全部输入 token(比如 5000 个一起算)。
- 每层、每个 token 算出一对向量,叫 **key / value(KV)**,这是"模型对输入的理解",会暂存供后面用。
- 算完顺带吐出**第一个**输出 token。

特点:**计算密集**,海量矩阵乘法,和输入长度成正比。输入越长越慢。

### 阶段 2:Decode(解码 / 生成)—— 逐字往外蹦

- 每生成 1 个新 token,只针对**这 1 个** token 做一次前向计算(前面的 KV 已经在 prefill 算好存着,直接用)。
- 串行,一个接一个,直到结束。特点:**内存带宽密集**,和输出长度成正比。

### 两阶段对比

| | Prefill | Decode |
|---|---|---|
| 处理对象 | 输入的**全部** token | 每次 **1 个**新 token |
| 并行性 | 全部并行,一次搞定 | 串行,逐个 |
| 瓶颈 | 算力(矩阵乘法) | 内存带宽 |
| 和长度关系 | 输入越长越慢 | 与输出长度成正比 |

### 缓存省的就是 Prefill

每追问一句,开头那一大段历史本来都要**重新 prefill**(重新读、重新算 KV)。

> **Prompt cache 做的事:把上一轮 prefill 算好的 KV 存下来。下一轮发现前缀一致,就跳过这段 prefill,直接拿存好的 KV 用,只对末尾新增那句做 prefill。**

类比:你每次回答前都要先把前面几百页笔记重读一遍。缓存 = 脑子里**还记着**刚读过的内容,从上次停的地方接着写,不用重头翻。

## 三、Prefill 为什么是花钱的大头

反直觉的点:**不是因为单个输入 token 贵——恰恰相反。** Opus 单价:

| | 单价(美元/百万 token) |
|---|---|
| 输入(prefill 处理的) | $15 |
| 输出(decode 生成的) | **$75** ← 贵 5 倍 |

论单价,生成一个字比读一个字贵 5 倍。prefill 成为大头,靠的是另外两件事:

1. **量巨大**:agent 干活时,上下文(系统提示 + 工具定义 + 历史 + 代码)动辄几万 token,而回答可能就几百字。输入量常是输出的几十上百倍。
2. **每轮重付**:没有缓存的话,这一大坨输入**每追问一轮就重新 prefill、重新计费一次**。

单价低 × 量大 × 每轮重复 = 总账上 prefill 成了真正的吞金兽。

### 用我自己的真实账单拆解(最有说服力)

**实际**(有缓存)花的 $3,986,构成:

| 项目 | 金额 | 占比 |
|---|---|---|
| 缓存读取(命中的 prefill) | $1,997 | 50% |
| 缓存写入(新内容的 prefill) | $1,059 | 27% |
| 输出(decode 生成) | $924 | 23% |
| 全新输入 | $6 | 0.2% |

→ 输入 / prefill 侧合计 **77%**,输出仅 23%。

**假如没有缓存**的 $21,745,构成:

| 项目 | 金额 | 占比 |
|---|---|---|
| 输入 / prefill(全价重付) | **$20,821** | **96%** |
| 输出 | $924 | 4% |

→ 没缓存时,prefill 直接吞掉账单的 **96%**,输出几乎可忽略。

> 结论:**prefill 贵,不贵在单价(它最便宜),而贵在"量大 + 每轮重复支付"。** 正因为它是账单主体,缓存才值钱——把"每轮全价重付的 prefill"压成"一次写入 + 多次 1/10 价读取"。这也是我的账省下 81.7% 的来源:省的几乎全是 prefill。

## 四、这部分缓存物理上存在哪

**存在模型提供方(Anthropic)的服务器上,不在我的电脑里。**

1. **主要在 GPU 显存(HBM)里**:缓存的内容就是 KV 张量(每层每 token 的 key/value),推理在 GPU 上跑,KV 自然先待在高速显存里,方便下轮快速取用。
2. **请求间隙可能被卸载(offload)**到更便宜的地方:CPU 内存(RAM)或本地高速 SSD/NVMe,命中时再加载回 GPU。
   *(注:这是业界推理系统的通行做法;Anthropic 未公开其 prompt cache 的具体存储层细节,这一条是机制上的合理推断,非官方确认。)*
3. **我本地存的只是对话的原始文本**,跟这个"算好的 KV 缓存"是两码事。

### 为什么有 5 分钟 TTL

这些 KV 占的是**昂贵的显存/内存**,服务器要同时扛海量用户,不可能无限期帮你留着。**5 分钟内没人来复用就清掉腾地方。** TTL 本质是"存储成本"和"复用收益"的折中。

### TTL 的两个关键机制(最容易想错的地方)

把对话想成 `A → AB → ABC → ABCD` 不断 append,很多人以为"一段时间后只剩 ABC、ABCD,前面的 A、AB 先单独过期了"。**这是错的**,原因有二:

**机制 1:命中会"续命",TTL 是"距上次使用 5 分钟",不是"距创建 5 分钟"。** 每次缓存被读到,它的 5 分钟倒计时就重置一次:

```
T=0:00  发 A      → 写入 A,    倒计时 5:00
T=0:30  发 AB     → 读到 A(A 续命,重置 5:00),prefill B,写入 AB
T=1:10  发 ABC    → 读到 AB(A、B 续命),prefill C,写入 ABC
T=2:00  发 ABCD   → 读到 ABC(A、B、C 全续命),prefill D,写入 ABCD
```

只要你一轮接一轮地聊(间隔 < 5 分钟),每轮都"读到"整条前缀,A、B、C 的倒计时被反复重置——**整条永远是热的,谁都不过期**。

**机制 2:过期是"整条一起凉",不是"老的先掉"。** 后面的缓存物理上**包含**前面的:ABCD 的 KV 里本就含着 A、B、C 那部分。所以不可能"ABCD 在、A 没了"。真正触发过期的是**你停下来**:

```
T=2:00  发 ABCD,倒计时 5:00
T=2:00~7:00  去吃饭,没动
T=7:00  整条 A、B、C、D 一起过期(不是只掉 A、AB)
T=8:00  回来发 ABCDE → 找不到可用前缀 → ABCD 从头完整 prefill(贵)→ 重新写入
```

| 直觉设想 | 实际 |
|---|---|
| 一段时间后"只剩 ABC、ABCD" | ❌ 要么整条都在,要么整条都没 |
| A、AB 会先单独过期 | ❌ A、B 是 ABCD 的一部分,ABCD 在它们就在 |
| 过期靠"距创建时间" | ❌ 靠"距上次被读到的时间";一聊就续命 |

一句话:**缓存不是"队列里旧元素先出队",而是"整条前缀的保温杯"——每说一句就续一次热水(+5 分钟),超过 5 分钟没碰,整杯一起凉。**

## 五、缓存按"内容"命中,不按"会话"

缓存的钥匙是**那段文本长什么样(token 串)本身**,不是"哪一次会话"。推论:

- 任何请求,只要开头和缓存里某段**逐字节相同**,就命中——哪怕来自另一个会话。
- 所以 **系统提示 + 工具定义** 这一大坨,在你所有对话里都一样、又都在最前面,常常**跨会话命中**:开一个全新对话,开头那截可能直接是热的。

> 更精确的说法:缓存的是**"一段前缀内容"**;一次具体的"用户提问 + 模型回答"的累积上下文,只是这段前缀最常见的形态。公共的开头部分还能在不同对话间共享。

## 六、缓存的是"输入处理",不是"输出结果"

一个常见误解:在会话 A 问"你好",再到会话 B 也问"你好",回答会一样吗?**不一定,而且通常不会完全一样。**

- 缓存存的是 **prefill 的产物(输入 KV)**——"模型读懂了输入"这一步。
- **回答是在 decode 阶段现场逐字生成的,这一步从不进缓存。**

```
会话 A:  [系统提示+工具] 你好  →(prefill)→(decode 采样)→ "你好!有什么可以帮你的?"
会话 B:  [系统提示+工具] 你好  →(命中缓存,跳过 prefill)→(decode 重新采样)→ "你好,很高兴见到你 😊"
                                      ↑ 省了这步              ↑ 这步重来,结果可能不同
```

decode 生成每个 token 时带**随机采样**(temperature > 0):算出下一字的概率分布后"掷骰子"挑一个,同样输入两次结果可能不同。即便 temperature=0(贪心),也只是**倾向于**一样,仍不保证逐字相同(浮点、批处理、模型版本都会带来差异)。

| | 存什么 | 命中后 |
|---|---|---|
| **Prompt cache(就是它)** | 输入的 prefill(KV) | 更快更便宜,但**回答重新生成** |
| **响应缓存(它不是)** | 问题 → 答案的映射 | 直接吐出**一模一样**的旧答案 |

> 会话 B 问"你好"会**更快、更省钱**,但回答**未必和 A 相同**。这也闭环回最初的疑问:prompt cache 从不要求"问题答案重复",它只缓存输入处理过程,没替模型"作答"。

## 七、结合我自己的真实用量算一笔账

数据来源:本机 `~/.claude/projects/**/*.jsonl`(Claude Code 把每次调用的 token 用量记在这里),共 **125 个会话日志、9284 次 API 调用**,绝大多数是 Opus(4.7/4.8)。

### 用量

| 指标 | 数值 |
|---|---|
| 缓存**读取**的 token(命中) | **1,351,147,012(约 13.5 亿)** |
| 缓存**写入**的 token | 57,879,448 |
| 全新输入 token(未命中) | 407,823 |
| 输出 token | 12,369,408 |

**关键比例:输入侧 token 里约 96% 来自缓存命中。** 读取:写入 ≈ **23:1** —— 写一次,反复命中 23 次,把缓存的便宜占到了极致。

### 费用对比(按 Anthropic 官方按量单价)

| | 金额 |
|---|---|
| 实际产生的费用 | **$3,990** |
| 假如完全没有缓存 | **$21,767** |
| **缓存省下** | **$17,776(省 81.7%)** |

### 算法说明(以 13.5 亿缓存读取 token 为例,Opus 单价)

- **没缓存**:全按普通输入 token → `$15 / 百万` → 约 **$20,000**
- **有缓存**:命中只收 1/10 → `$1.5 / 百万` → 约 **$2,000**

光这一项就差一个数量级。代价是缓存**写入**加价 25%(`$18.75/百万`),但写入量小,完全被读取省下的覆盖。这就是缓存的经济学:**写一次,命中越多越赚。**

### 三个前提(避免误读)

1. **若用订阅套餐(Max/Pro),$3,990 是"名义价"**,并非真按此掏钱;但"省下 $17,776"的**相对节省真实存在**,也是订阅额度能撑这么多调用的原因。若是 API 按量付费,则是真金白银。
2. **单价按 <200K 上下文档位算**;实际用的是 Opus 1M 上下文版,超 200K 部分单价约翻倍,所以绝对金额可能被**低估**。
3. **百分比(81.7%)很稳**,分子分母同单价,可放心引用。

## 八、给学 agent 的人的提炼

把缓存当成 agent 工程的**一等公民**,而不是省钱的副产品:

- **结构顺序决定命中率**:把最稳定的内容(系统提示、工具定义、长背景)放最前,易变内容放最后。前缀越稳,命中越多。
- **别在中途改前缀**:动态注入时间戳、随机内容到提示开头,会让后面全部缓存失效。
- **时间窗口很重要**:多 agent 编排、轮询、定时任务,要么压在 5 分钟 TTL 内保持缓存热,要么干脆拉长间隔认了一次重算——卡在正好 5 分钟是最差的。
- **读写比是健康度指标**:`cache_read / cache_write` 越高,说明你的提示结构越"可复用"。我的是 23:1,属于很高。
- **优化要瞄准 prefill**:总账大头是输入侧(我的实测 77%~96%),所以"压缩/复用上下文"比"让回答短一点"省钱得多。回答虽单价高,但量小。
- **缓存 ≠ 确定性**:命中缓存只省 prefill,回答仍现场采样生成。别指望"同样的输入拿到同样的输出";要可复现得另调 temperature、seed 等,与缓存无关。

## 附录:自我思考

1. **"模型无记忆"是理解一切的起点。** 之前我一直下意识以为对话是"连续"的,模型记得我说过什么。其实每轮都是把全部历史重新喂一遍的"无状态请求"。一旦接受这点,缓存、TTL、上下文窗口、token 计费全都顺理成章了——它们都是为"无状态 + 重发历史"这个事实打的补丁。

2. **缓存便宜的本质是"用存储换算力"。** Prefill 是算力开销(贵、并行、随长度涨),缓存把它转化成一次写入 + 多次廉价读取。这和我熟悉的计算机系统里"空间换时间"是同一套思想,只是搬到了 LLM 推理层。

3. **最该内化的工程直觉:前缀稳定性 = 钱。** 以前写提示词只关心"内容对不对",现在还得关心"结构稳不稳、顺序合不合理"。一个把时间戳放在系统提示开头的小疏忽,可能让命中率从 96% 掉到 0,费用翻 5 倍而我毫无察觉。

4. **用真实数据验证概念,胜过看十遍文档。** 这次没有用任何编造的例子,而是直接扒自己的 9284 次调用——13.5 亿缓存读取、省下 $17,776,这些数字比任何比喻都让我记住"缓存到底意味着什么"。后面学 agent,这个习惯要保持:**凡能用自己的数据验证的,就别只读理论。**

5. **我一开始把缓存类比成"队列/LRU 里旧元素先淘汰",错得很自然。** 真相是"整条前缀的保温杯 + 命中续命"。错因在于我把 A、AB、ABC 当成了平级独立项,忽略了"后者物理上包含前者"。提醒自己:**类比要先确认底层数据结构,别用熟悉的模型硬套。**

6. **"输入缓存"和"输出缓存"是两回事,混淆会闹笑话。** 我差点以为两次问"你好"会拿到一样的回答。分清后才真正理解:prompt cache 省的是"读题"(prefill),从不替模型"作答"(decode)。**省钱 ≠ 确定性**——这是 agent 工程里很容易踩的认知坑。
